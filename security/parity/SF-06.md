# SF-06 Block integrity (version 4) and hashed blocks (version 3)

Row: SF-06 in [plan/security.md](../../plan/security.md). Story: E3-S4.
Date: 2026-10-25 (Sprint 2). Status: verified (read side; the block writers exist and are tested, whole-file saves come with E3-S7).

## What was proven

Every version 4 payload block is checked with its own HMAC and block index before its data is used; a flipped, cut, swapped, repeated, dropped or appended block is refused as damaged (`Corrupt`, never `WrongKey`, FMT-05.8). Version 3 hashed blocks are checked the same way after the start bytes (FMT-07). No partial data is returned.

## Side by side with the reference command line tool (installed 2.7.11)

| Case | Larsal | Reference message (paraphrased) |
|---|---|---|
| 4.1: byte flipped in the first block's HMAC, early block data, late block data; 4.0: early block data | `Corrupt` | invalid inner header id size (its block layer fails, the next layer reports it) |
| 4.1: file cut 10 bytes into the block stream | `Corrupt` | invalid inner header id size |
| 3.1: byte flipped at payload offset 40 or 200 | `Corrupt` | no root group |
| 3.1: file cut at 1,000 bytes | `Corrupt` | no root group |

Known difference, not a weakness of Larsal: the reference can open a version 4 file whose final (empty) block was removed when every upper layer stops reading before it (FMT-06 Edge cases, reproduced in Sprint 2). Larsal always requires the final block and gives `Corrupt`.
