# SF-07 Fresh random values on every save

Row: SF-07 in [plan/security.md](../../plan/security.md). Story: E3-S7. Spec: CRY-03.
Date: 2026-10-25 (Sprint 3). Status: verified.

## Tests (all pass)

`tests/write_version.rs`: `cry_03_t10_at_b03_ten_thousand_saves` (AT-B03: 10,000 saves, 40,000 distinct values: no master seed, IV, salt or stream key repeats, within a kind or across kinds), `cry_03_t1_seed_and_iv`, `cry_03_t2_chacha20_nonce`, `cry_03_t3_salt`, `cry_03_t5_salt_length`, `cry_03_t6_field_stream_key`, `cry_03_t7_challenge`, `cry_03_t8_padding_item`, `cry_03_t9_padding_length_draw`, `cry_03_t11_one_random_source`. Unit tests in `src/lib.rs`: `cry_03_t12_source_failure`, `cry_03_t13_order_third_draw_fails`, `cry_03_t21_key_change_check` (App goes further: a save whose new transformed key equals the old one fails, `Io(Other)`, LD-92).

## Independent check

App's `resave` example saved `testdata/default-time.appvault` 60 times. A separate Python program (hashlib and libgcrypt, no App code) checked each file's header HMAC and every block HMAC, decrypted it and read the values:

| Value | Length | Distinct of 60 |
|---|---|---|
| master seed | 32 | 60 |
| payload IV | 16 | 60 |
| KDF seed | 32 | 60 |
| inner stream key (stream id 3) | 64 | 60 |
| padding item value (CRY-03.7) | 74 to 509 bytes, rule 64 to 511 | 60 |

No value appeared under two kinds.

The hardware key is asked again with the new salt: App's copy of the reference's hardware-key test vault opened in the reference only with the answer to the copy's own salt; the old answer gave the HMAC mismatch.
