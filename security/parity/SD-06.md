# SD-06 Unknown data kept on save

Row: SD-06 in [plan/security.md](../../plan/security.md). Story: E3-S7. Spec: FMT-10.20, FMT-10.27, FMT-11.45.
Date: 2026-10-25 (Sprint 3). Status: verified.

The reference does not keep unknown document parts (FMT-10.20), so this row is a Larsal extra. Observed again in Sprint 3: the reference's own save (`mkdir`) of Larsal's copy below removed all 14 unknown elements. Larsal deliberately drops unknown outer header fields (FMT-02.21, LD-21), as the reference does.

## Open, save, open again (independent check)

A demo vault was built from `testdata/rich-v4.larsalvault` with 14 unknown elements in 13 places: the document root, Meta, MemoryProtection, CustomIcons, the vault custom data, Root, a group, a group's Times, an entry (one element with nested children, one marked `Protected="True"`), an entry's AutoType, an Association, a history item, and DeletedObjects. It was sealed with its own key by a Python program (no Larsal code).

- Larsal opened it and saved a copy, then opened the copy and saved a second copy (the `resave` example).
- In both copies (decrypted by the Python program) every unknown element sits under the same parent with the same name, attributes and text. Larsal re-indents an element that holds only child elements (LD-81, FMT-10.27). The second save wrote the unknown parts byte for byte as the first. The protected one kept its raw text and took no keystream (FMT-09.14).
- The reference opened the built vault and both copies; its exports of all three equal its export of the original vault.
