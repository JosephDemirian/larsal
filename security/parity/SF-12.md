# SF-12 Public header data free of secrets; no public id added

Row: SF-12 in [plan/security.md](../../plan/security.md). Story: E3-S7. Spec: FMT-02.29, FMT-03.22, FMT-03.23.
Date: 2026-10-25 (Sprint 3). Status: verified for larsal-format. The quick unlock side of APP-04.8 (never use the public id) is checked again in E5.

## Code review

`header::write_header` writes fields 2 (cipher), 3 (compression), 4 (master seed), 7 (IV), 11 (KDF settings with the fresh salt), 12 only when the vault holds public custom data, and 0. Public custom data comes only from the header that was read (`open` fills `Vault::public_custom_data`, `save` writes it back through `header::map_entries`); no code in larsal-format or larsal-model adds an item, so Larsal never adds the reference's public id. Every field is public by design; no key, password or protected value is in the header.

## Tests and observations

- `tests/write_file.rs`: `d50_fmt_03_23` (three public entries kept with their types, written sorted), `d52_fmt_03_8`, `d54_fmt_03_23`, `d58_fmt_03_23`, `c09_fmt_02_6_fmt_02_29`, `c51_fmt_02_29` pass.
- Header read, with an independent Python reader, of the 20 files Larsal wrote for the cipher and KDF matrix, the empty-password case and the hardware-key case: fields 2, 3, 4, 7, 11, 0, and nothing else.
- A demo vault given three public entries (a name, a number, bytes) and resaved by Larsal: field 12 holds the same three entries with the same types and values, sorted by name as FMT-03.22 says (rebuilt sorted map equal byte for byte), and no other entry. The reference opened Larsal's copy and its export equals the original's.
