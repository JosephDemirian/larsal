## 2. The module (`app_crypto::base64`)

- `Form::Padded`: the standard alphabet with `=`. Written with the `=`. Read: the length must be a multiple of 4 and the padding exactly right; the unused low bits of the last character are ignored, which RFC 4648 section 3.5 allows. Key files need this (FMT-18.12). It calls `Base64::decode_in_place` on a wiping copy of the text: that call checks the alphabet, the length and the padding, but does not encode the last block again.
- `Form::PaddingOptional`: the standard alphabet. Written as `Padded`. Read with full, partial or no padding, but never more `=` than the encoding writes; the unused bits must be zero. It strips the trailing `=` (`unpadded`), then calls `Base64Unpadded::decode`.
- `Form::Url`: the URL-safe alphabet (RFC 4648 section 5). Written without padding. Read as `PaddingOptional` reads (`Base64UrlUnpadded`).
- The functions: `encode` (String), `encode_secret` (SecretString), `decode` (Vec) and `decode_secret` (SecretBytes, exact length). The secret versions write only into buffers that are wiped, and run under `secret::scrubbed`, the stack wipe of every crypto call in app-crypto (Checker 2, section 17). Every read returns `Result<_, app_crypto::Error>`.
- No input causes a panic: app-crypto denies `unwrap_used`, `expect_used`, `panic`, `indexing_slicing` and `arithmetic_side_effects`, and clippy passes with `-D warnings`.

## 11. For Checker 2 (base64.rs as crypto code)

- **base64ct calls**: `Base64::encode`, `Base64UrlUnpadded::encode`, `Base64::encoded_len`, `Base64UrlUnpadded::encoded_len`, `Base64::decode_in_place`, `Base64Unpadded::decode` and `Base64UrlUnpadded::decode`. base64ct has no lookup tables and no branches on the data (its README: constant-time "best effort").
- **Where App's own code branches on the text**, and why that is safe:
  - `unpadded` counts the trailing `=` (`take_while` from the end). For a valid text that count follows from the length, which is public. It reads no other character.
  - `match form` and the length checks (`body.len() % 4`, `get(..n)`, `get_mut(..text.len())`): public values.
  - `.ok()`, `ok_or` and `?` branch on whether the text is valid. The caller learns that from the result anyway.
  - `encode` and `encode_secret` call `String::from_utf8` on base64ct's output. Its ASCII fast path branches on the high bit only, which is 0 for every base64 character, so its path does not depend on which characters the text holds.
  - The module's doc comment says the same: timing depends on the length, the run of trailing `=` and validity, never on which characters the text holds.
- **Wiping**: `decode_secret` decodes into a `SecretBytes` of the text's length (in `Padded`, the text is first copied into it), then copies the `n` bytes into a `SecretBytes` of exact length; both are wiped on drop, also on the error path. `encode_secret` writes into one `Vec` of the exact length, which `String::from_utf8` moves without a copy into a `SecretString` (wiped on drop, spare capacity included); the error branch, which cannot happen, wipes the bytes through `SecretBytes`. Since section 17 both run under `secret::scrubbed`, which zeroes the stack where base64ct keeps its last group (Checker 2 issue 1). `decode` and `encode` are for bytes that are not secret (encrypted import parts, icons, host keys, tests). The callers that hold secrets use the `_secret` forms: the passkey key and the credential id (bitwarden.rs) and the key file (keyfile.rs).
- **No panic**: the crate's lints deny unwrap, expect, panic, indexing and arithmetic side effects; clippy passes; the property test `r5_any_text_gives_bytes_or_an_error` gives any byte string of up to 64 bytes to every form.
- **Error path**: `Error::Base64` is a unit variant; its message is fixed and names nothing of the text.
- **The copy**: `vendor/crates-io/base64ct-1.8.3` is byte-for-byte its `.crate` (section 4).
