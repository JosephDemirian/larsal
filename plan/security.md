# Security

## Goal

1. Match every security feature of the reference app. The parity matrix below lists them. Every row ends with proof.
2. Go further where it is cheap and safe (see Extra hardening).
3. Prove it with attacks and checks: [attacks-and-checks.md](attacks-and-checks.md).

## What we protect

- Vault contents: passwords, usernames, notes, attachments, one-time password secrets, passkeys, SSH keys.
- The master password, key files and hardware-key responses.
- Keys in memory while a vault is open.
- Values the user copies.

## Who attacks, and what we promise

| Attacker | What they have | Our promise |
|---|---|---|
| Thief of the vault file | The file and unlimited time | Without the key nothing is readable. Guessing is slow because of the Argon2 cost. |
| Tamperer | Write access to the file (cloud folder, USB stick) | Any change is found before data is used. We never show half-checked data. |
| Hostile file | A crafted vault, key file or import file | No crash, no hang, no memory blow-up, no code execution. |
| Other apps on the Mac, normal user rights | Clipboard, screen capture, keystroke taps, debugger attach | Copies are concealed and cleared. The window can be hidden from capture. Master password typing uses secure input. Debugger attach is denied. |
| Hostile website | Messages through the browser extension | No fill without association, user consent and a matching site. |
| Supply chain | A bad dependency or build | Few, pinned, audited crates. Signed, reproducible builds. |
| Malware with admin rights | Full control of the Mac | Out of scope, as for every password manager. We still keep secrets in memory as briefly as possible. |

## Safe defaults

Values match the reference app unless ours is stricter. Spec cards APP-01 and CRY-02 confirm each one.

| Setting | Default |
|---|---|
| New vault cipher | AES-256 (ChaCha20 and Twofish-256 offered, as in the reference; spec/decisions.md LD-20) |
| New vault key derivation | Argon2id, 64 MiB memory, cost tuned to 1 second on this Mac |
| Lock after idle | On, 5 minutes |
| Lock on screen lock, sleep, user switch | On |
| Clear clipboard | After 10 seconds |
| Concealed clipboard | On |
| Hide window from screen capture | On |
| Passwords masked in lists and details | On |
| Network features (breach check, website icons, update check) | Off until the user turns each one on |
| Save | After every change, atomic |
| Backup before save | On |
| Remember key file paths | Off (the reference: on; spec/decisions.md LD-51) |
| Automatic lock with unsaved changes | Writes an encrypted recovery copy, then locks; never waits for an answer (LD-50) |

## Extra hardening (beyond the reference app)

- Every secret is wiped from memory when no longer needed, not only key material.
- Every parser has hard size limits, and runs under fuzzing in every sprint.
- No XML DTD or entities, ever.
- Constant-time compares for every MAC and key check.
- KDF settings below a safe minimum are refused unless the user confirms them, with the cost shown.
- The screen layer holds no secret except a value the user is viewing.
- No web engine in the app. The screen reaches the core only through the functions `larsal-ffi` exports (`API.md`).
- Reproducible builds and a published software bill of materials.
