## 1. Native messaging in Chrome-family browsers and Firefox

- On macOS Chrome reads a host manifest from `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/` for one user, or from `/Library/Google/Chrome/NativeMessagingHosts/` for every user. Chromium has its own folder, `~/Library/Application Support/Chromium/NativeMessagingHosts/`. The manifest `name` may use only lowercase letters, digits, underscores and dots. `path` must be absolute on macOS, `type` can only be `stdio`, and `allowed_origins` takes no wildcards. Source: [Chrome, Native messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).
- Size limits: a message from the host to the browser is at most 1 MB, and a message to the host at most 64 MiB. Source: same page.
- `connectNative` keeps one host process running until the port closes. `sendNativeMessage` starts a new process for each message. The host's first argument is the caller's origin, `chrome-extension://<id>/`. The extension needs the `nativeMessaging` permission. Source: same page.
- Chrome stops an MV3 service worker after 30 seconds without events, or when one request runs longer than 5 minutes. Since Chrome 105 an open `connectNative` port keeps the worker alive. When the host crashes, the port closes and the worker ends after its timers; the docs say to connect again in `onDisconnect`. Source: [Chrome, The extension service worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).
- Firefox on macOS reads host manifests from `~/Library/Application Support/Mozilla/NativeMessagingHosts/<name>.json` (or `/Library/Application Support/Mozilla/...`). They list add-on ids in `allowed_extensions`, and the add-on needs an explicit gecko id. Source: [MDN, Native manifests](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Native_manifests).
- On macOS Bitwarden's desktop app writes its host manifest into these folders under `~/Library/Application Support`: Google/Chrome (and Beta, Dev, Canary), Chromium, Microsoft Edge (and Beta, Dev, Canary), Vivaldi, BraveSoftware/Brave-Browser (and Beta, Nightly), net.imput.helium, Mozilla and Zen. It has no Opera or Arc entry. Its `path` names a separate small relay program, `desktop_proxy`, next to the app. Its `allowed_origins` lists four fixed store ids (Chrome, Chrome beta, Edge, Opera), and Firefox gets one add-on id. Source: [bitwarden/clients, native-messaging.main.ts](https://github.com/bitwarden/clients/blob/main/apps/desktop/src/main/native-messaging.main.ts).
- Arc: no official page was found. A community report on the large commercial password manager's own forum names `~/Library/Application Support/Arc/User Data/NativeMessagingHosts/` (the link is left out: its domain holds a name the guard bans). Opera on macOS: forum reports conflict; some developers got a host working only from Chrome's user folder, with Opera's extension id in `allowed_origins`. Source: [Opera forums, post 15735](https://forums.opera.com/post/15735). INT-01's check V-INT01-1 stays open.

## 2. Manifest V3 rules that shape the code

- MV3 forbids remotely hosted code: anything run that is not in the extension's own files. JSON and CSS data are not code. Sources: [Chrome, Deal with remote hosted code violations](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code).
- The default `extension_pages` CSP is `script-src 'self'; object-src 'self';`. The loosest allowed value is `script-src 'self' 'wasm-unsafe-eval'; object-src 'self';`, so bundled WebAssembly needs `'wasm-unsafe-eval'`. Source: [Chrome, Manifest content_security_policy](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy).
- Content scripts run in an isolated world: they share the page's DOM but not its JavaScript. A script in the MAIN world runs under the page's CSP. Chrome supports `world: "MAIN"` in the manifest since 111; Firefox and Safari support it unevenly. Content scripts cannot use static ES-module imports in Chromium or Firefox; the ways around it are an ordered list of classic files, a bundler, or a dynamic import of a `web_accessible_resources` file, which makes the extension detectable. Sources: [Chrome, Content scripts](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts); [Mozilla bug 1536094](https://bugzilla.mozilla.org/show_bug.cgi?id=1536094); [chromium-extensions thread](https://groups.google.com/a/chromium.org/g/chromium-extensions/c/aukfgctFl1k); [Apple developer forums 728849](https://developer.apple.com/forums/thread/728849).
- `web_accessible_resources` exposes nothing by default, because sites could fingerprint installed extensions or exploit their bugs. With `use_dynamic_url` the files are served under an id that changes at each browser restart or extension reload. Source: [Chrome, Manifest web_accessible_resources](https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources).
- Chrome's security advice: treat a message from a content script as made by an attacker; treat data sent to a content script as readable by the page; keep secrets and privileged work in the service worker; avoid `innerHTML` and `document.write`; check the sender in `runtime.onMessage`; ask for the fewest permissions. Source: [Chrome, Stay secure](https://developer.chrome.com/docs/extensions/develop/security-privacy/stay-secure).
- The browser fills `runtime.MessageSender`: `url` (the frame's own URL when the script runs in an iframe), `origin` (can differ from `url`, or be opaque for sandboxed frames), `frameId` (0 is the top frame) and `documentId`. Source: [MDN, runtime.MessageSender](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/API/runtime/MessageSender). Chromium's threat model says that even a compromised renderer must not be able to spoof `MessageSender.url`, `MessageSender.origin` or `MessageSender.id`, and names `ContentScriptTracker` as the check on IPCs from a renderer process that claims to act for an extension's content scripts. That source covers Chromium only; Firefox and Safari are not checked here. Source: [Chromium, Threat Model And Defenses Against Compromised Renderers, "Messaging"](https://chromium.googlesource.com/chromium/src/+/main/docs/security/compromised-renderers.md).
- `activeTab` gives access to the current tab only when the user invokes the extension (an action click, a context menu item, a keyboard command or an omnibox suggestion). It shows no install warning, and access ends when the user leaves the site. Source: [Chrome, The activeTab permission](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab).
- Chrome 148 exposes every extension API under `browser` as well as `chrome`, and `runtime.onMessage` listeners may return a Promise. For older Chrome the docs give a one-line guard that sets `browser` to `chrome`, or `minimum_chrome_version: 148`. Mozilla's webextension-polyfill (MPL-2.0) does nothing in Firefox, Safari and Chrome 148+, and its repository was archived on 2026-07-30. Sources: [Chrome, The browser namespace](https://developer.chrome.com/docs/extensions/develop/concepts/browser-namespace); [mozilla/webextension-polyfill](https://github.com/mozilla/webextension-polyfill).
- For one MV3 manifest across browsers, MDN advises listing both `background.scripts` and `background.service_worker`. Chrome uses the service worker and has ignored `scripts` since 121. Firefox has no extension service worker (bug 1573659) and runs `scripts` as an event page. Safari uses `scripts` unless `preferred_environment` says `service_worker`. Source: [MDN, manifest.json background](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/background).

## 3. Safari web extensions

- A Safari web extension has three sandboxed parts: the macOS app that contains it, its JavaScript, and a native app extension. Only the background script and extension pages can send native messages; content scripts cannot. Safari ignores the application id the script names and delivers every message to the containing app's own app extension, whose `beginRequest(with:)` reads `SFExtensionMessageKey`; from Safari 17, `SFExtensionProfileKey` names the Safari profile. The containing app can push messages to the JavaScript with `SFSafariApplication.dispatchMessage`, received on a `connectNative` port. The app and its app extension share data only through an app group. Source: [Apple, Messaging between the app and JavaScript in a Safari web extension](https://developer.apple.com/documentation/safariservices/messaging-between-the-app-and-javascript-in-a-safari-web-extension).
- Larsal groups on macOS: a group of the form `<team id>.<group name>` needs no registration. Group members can talk over Mach IPC, XPC, POSIX semaphores, shared memory and UNIX domain sockets; the socket "needs to be in your app group container", within `SOCK_MAXADDRLEN`, and this works "between a sandboxed app and a nonsandboxed app". On macOS 15 the system skips the container prompt only for Mac App Store apps, for group ids that begin with the Team ID, and for groups a provisioning profile authorizes. Larsal extensions must be sandboxed. Sources: [Apple, Larsal Groups entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.application-groups); [Apple forums 756701](https://developer.apple.com/forums/thread/756701); [Apple forums 788364](https://developer.apple.com/forums/thread/788364); [Apple forums 718589](https://developer.apple.com/forums/thread/718589).
- Bitwarden's Safari handler (`SafariWebExtensionHandler.swift`) does not contact the desktop app. It runs `LAContext` itself and reads a keychain item the desktop app wrote, with no app group and no XPC. Browser biometric unlock needs the desktop app running and signed in, works in Chromium browsers, Firefox 87+ and Safari 14+, and has an optional "Require verification for browser integration" step. Sources: [SafariWebExtensionHandler.swift](https://github.com/bitwarden/clients/blob/main/apps/browser/src/safari/safari/SafariWebExtensionHandler.swift); [Bitwarden, Unlock with biometrics](https://bitwarden.com/help/biometrics/).
- Distribution: a signed app through the App Store, or a Developer ID-signed and notarized app outside it; both need the Apple Developer Program (README D7: $99 a year). For tests, Safari's Developer setting "Allow unsigned extensions" resets when Safari quits. "Add Temporary Extension" loads a folder for 24 hours, but messaging with the app needs an Xcode project, and Xcode embeds the extension into the app at build time. Safari 26 added a web-based packager for the App Store only; developers report it as unreliable. Sources: [Apple, Distributing your Safari web extension](https://developer.apple.com/documentation/safariservices/distributing-your-safari-web-extension); [Apple, Running your Safari web extension](https://developer.apple.com/documentation/safariservices/running-your-safari-web-extension); [Apple forums 845035](https://developer.apple.com/forums/thread/845035).

## 4. Firefox

- Firefox MV3 runs non-persistent event pages (Firefox 106+). Since Firefox 127 host permissions are shown and granted at install, and the user can take them back at any time. Since 2025-11-03 a new Firefox extension must declare `browser_specific_settings.gecko.data_collection_permissions`; the example uses `"required": ["none"]`. Sources: [Extension Workshop, MV3 migration guide](https://extensionworkshop.com/documentation/develop/manifest-v3-migration-guide/); [Mozilla Add-ons blog, 2025-10-23](https://blog.mozilla.org/addons/2025/10/23/data-collection-consent-changes-for-new-firefox-extensions/).
- Release Firefox installs only extensions signed by Mozilla. Listed and self-distributed extensions are both uploaded to Mozilla's add-on site (AMO) for signing. Signing takes up to 24 hours, and a manual review can come at any time. AMO wants the source code and reproducible build steps when an extension uses minifiers, bundlers, template engines or other machine-made code; the reviewer rebuilds and compares. Obfuscated code is not allowed. Mozilla names no fee; the account is a Mozilla account. Sources: [Signing and distribution overview](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/); [Source code submission](https://extensionworkshop.com/documentation/publish/source-code-submission/); [Developer accounts](https://extensionworkshop.com/documentation/publish/developer-accounts/).

## 5. Stores, fees and extension ids

- Chrome Web Store: a one-time registration fee; the register page names no amount, which is shown at registration, and the developer agreement leaves it to Google. Review usually takes a few days and can take weeks; it takes longer for new developers, new extensions and broad host permissions such as `<all_urls>`. Minified code is allowed, obfuscated code is not. Sources: [Register your developer account](https://developer.chrome.com/docs/webstore/register); [Developer agreement](https://developer.chrome.com/docs/webstore/program-policies/terms); [Review process](https://developer.chrome.com/docs/webstore/review-process).
- The manifest `key` keeps an unpacked extension's id fixed during development, which native messaging's `allowed_origins` needs. Source: [Chrome, Manifest key](https://developer.chrome.com/docs/extensions/reference/manifest/key).
- Microsoft Edge Add-ons: "There is no registration fee"; it needs a Partner Center account owned by a Microsoft account. Source: [Microsoft, Register as a Microsoft Edge extension developer](https://learn.microsoft.com/en-us/microsoft-edge/extensions/publish/create-dev-account).
- Vivaldi installs extensions from the Chrome Web Store. Source: [Vivaldi blog](https://vivaldi.com/blog/chrome-web-store-extensions-in-vivaldi-browser/).

## 6. How proven extensions are built

- Bitwarden's MV3 manifest: host permissions `https://*/*` and `http://*/*`; content scripts at `document_start`, the autofill script in all frames; its in-page menus (`overlay/menu-list.html` and others) and a passkey page script are `web_accessible_resources` with `use_dynamic_url: true`; CSP `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'`; `nativeMessaging` is optional on Chrome and Firefox but required on Safari. It builds per browser with webpack. Sources: [manifest.v3.json](https://github.com/bitwarden/clients/blob/main/apps/browser/src/manifest.v3.json); [package.json](https://github.com/bitwarden/clients/blob/main/apps/browser/package.json).
- Bitwarden compiles its Rust SDK to WebAssembly for its web clients, and UniFFI covers Swift and Kotlin. Proton Pass's extension uses webpack, TypeScript and React, with 25 runtime and 37 development packages; its shared Rust library reaches the web through wasm-pack and wasm-bindgen and mobile through UniFFI. Sources: [bitwarden/sdk-internal](https://github.com/bitwarden/sdk-internal); [Bitwarden contributing docs, SDK on the web](https://contributing.bitwarden.com/architecture/sdk/web/); [Proton Pass extension package.json](https://github.com/ProtonMail/WebClients/blob/main/applications/pass-extension/package.json); [protonpass/proton-pass-common](https://github.com/protonpass/proton-pass-common); [Proton, Rust in the authenticator](https://proton.me/blog/authenticator-rust).
- Bitwarden's native messaging channel is built in the extension from standard primitives, not a NaCl box: an RSA-2048 key pair made by the extension and an AES-256-CBC-HMAC session key (INT-01, D-INT01-2, from Bitwarden's `nativeMessaging.background.ts`).
- WebAssembly is turned off in Safari's Lockdown Mode and in Edge's Enhanced Security mode. For Edge, Proton writes: "As Proton Pass depends on WASM, the extension and web app won't automatically work in this mode." For Safari it writes only that "WASM is also disabled in Lockdown Mode in Safari" and that the user adds an exception for Proton's site; whether Lockdown turns WebAssembly off in extension pages too is not checked (section 18). Bitwarden writes that its web clients "require the use of WebAssembly" and that Lockdown Mode "actively disables WASM support in Safari"; it names no JavaScript fallback. A WebKit bug reports that since iOS 17.4 an added exception no longer helps. Sources: [Proton Pass troubleshooting](https://proton.me/support/pass-troubleshooting); [Bitwarden, WASM not supported](https://bitwarden.com/help/wasm-not-supported/); [WebKit bug 273824](https://bugs.webkit.org/show_bug.cgi?id=273824).

## 7. Autofill attacks and their defences

- Princeton CITP (2017): third-party scripts on 1,110 of the top 1 million sites injected invisible login forms, and browser login managers filled them. The defence it names: "require user interaction before autofilling login forms". Source: [No boundaries for user identities](https://blog.citp.princeton.edu/2017/12/27/no-boundaries-for-user-identities-web-trackers-exploit-browser-login-managers/).
- Oesch and Ruoti (USENIX Security 2020), section 7.1: managers should require user interaction before autofill by default, and the paper suggests "removing the option to disable user interaction". "Autofilling into iframes, same- or cross-origin, is also dangerous as it allows clickjacking attacks to circumvent user interaction requirements." It recommends no fill in iframes, or moving the interaction out of the page into the browser's own UI. Source: [USENIX page](https://www.usenix.org/conference/usenixsecurity20/presentation/oesch) ([PDF](https://arxiv.org/pdf/1908.03296), pages 11 to 14).
- Marek Toth, "DOM-based Extension Clickjacking" (DEF CON 33, 2025-08-09, updated 2026-01-14): a page makes a manager's in-page UI invisible but still clickable in three ways: opacity on the extension's root or its open-shadow children; opacity 0 on `html` or `body`; or an overlay with `pointer-events: none`, including Popover API top-layer elements. Credentials leaked in 10 of 11 managers and one-time codes in 9 of 11; passkeys leak through "signed assertion hijacking" when the site lacks session-bound challenges. Every tested manager fills all subdomains, so an XSS on any subdomain is enough. Proposed defences: MutationObserver style checks, a closed shadow root, `html` and `body` opacity checks, the Popover API, the extension's UI last in the DOM, closing the menu when another top-layer element exists, and `elementsFromPoint` (which does not see `pointer-events: none` popovers). The author: "Doesn't exist simple protection"; the safest choice is a new popup window. Listed as fixed: Bitwarden 2025.8.2, Proton Pass 1.31.6, iCloud Passwords 3.1.30, Dashlane, Enpass, Keeper, NordPass, RoboForm, LogMeOnce and the reference's own browser add-on; two large commercial managers were still listed as open on 2026-01-14. Sources: [marektoth.com](https://marektoth.com/blog/dom-based-extension-clickjacking/); [The Hacker News](https://thehackernews.com/2025/08/dom-based-extension-clickjacking.html).
- Bitwarden turns fill on page load off by default ("compromised or untrusted websites could take advantage of this"). It quietly skips page-load fill in an iframe whose src does not match the item's URI, warns on a manual fill into such an iframe, and warns before filling an http site when the item expects https. Its keyboard fill is Cmd+Shift+L. Source: [Bitwarden, Auto-fill logins](https://bitwarden.com/help/auto-fill-browser/).

## 8. Crypto in the extension

- WebCrypto has X25519 in Chrome 133, Firefox 130 and WebKit (on by default since December 2024), and Ed25519 in every engine. It has no XSalsa20-Poly1305, which INT-01's `crypto_box` channel uses. A non-extractable WebCrypto private key cannot be exported; its public half always can. Sources: [Igalia, X25519 in WebKit](https://blogs.igalia.com/jfernandez/?p=1913); [Mozilla bug 1904836](https://bugzilla.mozilla.org/show_bug.cgi?id=1904836); [MDN, SubtleCrypto.generateKey](https://developer.mozilla.org/en-US/docs/Web/API/SubtleCrypto/generateKey).
- TweetNaCl-js (public domain or Unlicense) was audited by Cure53 in January and February 2017, which found no security problems; one bug was fixed after the audit. Sources: [Cure53 audit](https://tweetnacl.js.org/audits/cure53.pdf); [dchest/tweetnacl-js](https://github.com/dchest/tweetnacl-js).
- `crypto_box` has no stable release on the newer RustCrypto generation: the newest is 0.10.0-pre.0 (2025-10-05), and the newest stable is 0.9.1 (2023-08-17). Source: [crates.io, crypto_box versions](https://crates.io/crates/crypto_box/versions). Larsal pins `crypto_box = "=0.9.1"` with the note "older generation, duplicates crypto crates; … Re-pin when 0.10 is out" (`Cargo.toml` line 57), and LD-203 asks E7-S1 to re-pin it onto E9-S2's `curve25519-dalek` generation.
- `aes-gcm` 0.11.1 is already in Larsal's tree (through `ssh-cipher`, `Cargo.lock`), and E16-S2 makes it a direct larsal-crypto dependency and vendors `hpke` with `x25519-dalek` ([plan/architecture.md](../../plan/architecture.md), "Approved crates to add"). `hkdf` 0.13.0 is a direct larsal-crypto dependency today (`crates/larsal-crypto/Cargo.toml`).

- Google Chrome, Firefox, Brave and Safari are installed on this Mac; Edge is not. The project's mockup tools already drive the installed Chrome headless and offscreen (`design/option-a/tools/export-reference.mjs`), and `scripts/` already uses Python 3 (`scripts/make-option-a-assets.py`, `scripts/check-names.sh`). Source: `ls /Applications` and the files named.
- Web Authentication Level 3 became a W3C Recommendation on 2026-08-25. It holds the `prf` extension (section 10.1.4), test vectors (section 16, with CTAP2 hmac-secret in 16.17.1) and WebDriver commands for virtual authenticators used in tests. Sources: [W3C, webauthn-3](https://www.w3.org/TR/webauthn-3/); [Chrome, Emulate authenticators](https://developer.chrome.com/docs/identity/webauthn-tab).

## 10. The web vault: the served-code risk

- Whoever serves a web page's code can serve one targeted user other code. The ETH Zurich paper sets aside this "trivial attack" of a malicious client, and says it is "especially true for signed software releases (e.g., desktop and mobile clients, browser extensions)", where "a signed malicious client would constitute proof of vendor misconduct"; its proof-of-concept tests ran against Bitwarden's web client. Source: [Scarlata, Torrisi, Backendal, Paterson, USENIX Security 2026 prepub](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf), section 2 and footnote 3.
- The large commercial password manager's white paper, Appendix A.1: its web client "is fetched from our servers as a set of JavaScript files"; its integrity "depends on the integrity of the TLS connection" and "on the security of the host from which it's delivered", and it "introduces a number of significant risks". User advice: "Use (code signed) native clients as much as possible". A.1.1: JavaScript "offers us very limited ability to clear data from memory", and WebCrypto's limits forced PBKDF2 "instead of a memory-hard KDF such as Argon2". A.10.3: web browsers do not "reliably allow protecting an encryption key with hardware", so the device key is stored "lightly obfuscated". Source: [security design white paper](https://agilebits.github.io/security-design/leopard.html#sec:cryptoHTTPS).
- Ptacek (2011): "Secure delivery of Javascript to browsers is a chicken-egg problem"; "There is no reliable way for any piece of Javascript code to verify its execution environment"; with garbage collection, secrets linger in memory. Source: [copy of "Javascript Cryptography Considered Harmful"](https://gist.github.com/atoponce/e90089cb5a13ef38a7a07f8e64370dab).
- Bitwarden's white paper: web client integrity "depend[s] on the integrity of the HTTPS TLS connection"; it sends CSP, HSTS and X-Frame-Options SAMEORIGIN; the account key stays in memory while unlocked, and locked clients purge keys "as aggressively as possible". SRI is not mentioned. Source: [Bitwarden Security Whitepaper](https://bitwarden.com/help/bitwarden-security-white-paper/).
- Attempts to check served code: WAIT (2021) proposes an extension, a server header and public logs so the browser can block undisclosed changes ([arXiv 2104.06136](https://arxiv.org/abs/2104.06136)). Meta's Code Verify (2022) is an extension that compares WhatsApp Web's JavaScript with a hash Cloudflare publishes; it protects only where it is installed ([Meta engineering](https://engineering.fb.com/2022/03/10/security/code-verify/); [Cloudflare blog](https://blog.cloudflare.com/cloudflare-verifies-code-whatsapp-web-serves-users/); [Code Verify on AMO](https://addons.mozilla.org/firefox/addon/code-verify/)). WEBCAT (Freedom of the Press Foundation, 2025-03-19, a developer preview) uses developer-signed manifests of asset hashes, Sigstore or Sigsum logs, enrolment with a cooldown, and a Firefox extension that fails closed ([SecureDrop news](https://securedrop.org/news/introducing-webcat-web-based-code-assurance-and-transparency/)); a later list post says major parts of that design are deprecated ([sigsum-general](https://lists.sigsum.org/mailman3/hyperkitty/list/sigsum-general@lists.sigsum.org/thread/U6T465DCAW4F665EEYMMNWI2AXQIM7TC/), not confirmed in the repository). ## 11. The web vault: Rust in WebAssembly

- `wasm32-unknown-unknown` has full `core` and `alloc`. Its default features are multivalue, mutable-globals, reference-types, sign-ext, nontrapping-fptoint and bulk-memory (the last two from Rust 1.87); simd128 is off by default. The target imports no host functions for std. On it `std::fs` always returns errors and `std::thread::spawn` panics. Source: [rustc, wasm32-unknown-unknown](https://doc.rust-lang.org/rustc/platform-support/wasm32-unknown-unknown.html).
- `SystemTime::now()` and `Instant::now()` panic on this target; Rust maintainers called this "an intended implementation detail" (2018, 2019). Source: [rust-lang/rust #48564](https://github.com/rust-lang/rust/issues/48564). larsal-format calls `SystemTime::now()` in open (`open_time`, `crates/larsal-format/src/lib.rs` line 113) and in save (line 220, through `now()` at line 137); larsal-crypto's `kdf.rs` uses `Instant::now` for the KDF calibration (line 94) and already takes a caller's `Clock = fn() -> Duration` for its benchmark (lines 85 to 95). Whether rustc 1.99.1 still panics is not checked here.
- getrandom docs: `wasm32-unknown-unknown` is "not automatically supported"; browser support comes from the `wasm_js` feature through wasm-bindgen; the `custom` backend needs one user-defined function named `__getrandom_v03_custom`; `extern_impl` needs a nightly-only feature. Source: [docs.rs getrandom 0.4.3](https://docs.rs/getrandom/0.4.3/getrandom/). Larsal's copy of getrandom 0.4.3 keeps only `src/backends/getentropy.rs`; its `backends.rs` still names `mod custom` under `cfg(getrandom_backend = "custom")`, and any other target fails with "target is not supported" (`vendor/crates-io/getrandom-0.4.3/src/backends.rs` lines 10 to 37 and 186). Its `wasm_js` feature pulls in wasm-bindgen and js-sys (its `Cargo.toml`).
- curve25519-dalek 5.0.0's build script picks the 32-bit backend when the pointer width is 32, as on wasm32; `cfg curve25519_dalek_bits = "64"` overrides it; upstream notes "TODO(Wasm32): Needs tests + benchmarks" (`vendor/crates-io/curve25519-dalek-5.0.0/build.rs` lines 36 to 42 and 135 to 160). E0-S7 step 4b cut Larsal's copy of the u32 backend ([plan/architecture.md](../../plan/architecture.md), Approved crates, Ed25519 row).
- The `cpubits` macro treats wasm32 as 64-bit, so p256, polyval and aes pick their kept 64-bit or portable code there (`vendor/crates-io/cpubits-0.1.1/src/lib.rs` lines 146 to 151, 258 to 260, 433 to 435; `p256-0.14.0/src/arithmetic/field.rs` lines 7 to 16).
- sha2 0.11.1 uses its wasm SIMD module only under `target_feature = "simd128"`, and those files are cut from Larsal's copy; a default wasm32 build uses the portable code, and a `+simd128` build would not compile (`vendor/crates-io/sha2-0.11.1/src/sha256.rs` line 41, `sha512.rs` line 38).
- The `unsafe_code` lint flags `#[no_mangle]` and `#[export_name]` as well as `unsafe` blocks, so hand-written wasm exports do not compile in a crate under `#![forbid(unsafe_code)]` (Rust rule 2). Source: [rustc lints, unsafe_code](https://doc.rust-lang.org/rustc/lints/listing/allowed-by-default.html).
- Dependencies of Larsal's crates: larsal-format depends on larsal-platform only under `cfg(target_os = "macos")` (memory page locks); larsal-crypto and larsal-model need no OS crate; larsal-core depends on larsal-platform (libc only) and uses `std::fs` in `storage.rs` (`crates/larsal-format/Cargo.toml`, `crates/larsal-core/Cargo.toml`). The only installed rustup target is `aarch64-apple-darwin`, and the toolchain is rustc 1.99.1 (`rustup target list --installed`, `rustc --version`).

## 12. The web vault: memory, Argon2 and threads

- wasm32 memory tops out at 4 GiB. Chrome allows 4 GB with an opt-in and 2 GB by default; WebKit then allowed up to 2 GB; Firefox 89 planned 4 GB on x64 and arm64. Sources: [V8, Up to 4GB of memory in WebAssembly](https://v8.dev/blog/4gb-wasm-memory); [WebKit bug 229353](https://bugs.webkit.org/show_bug.cgi?id=229353); [Mozilla dev-platform](https://groups.google.com/a/mozilla.org/g/dev-platform/c/90hVJF-X9c4).
- `WebAssembly.Memory` grows in 64 KiB pages and cannot shrink; each grow detaches the old ArrayBuffer. Source: [MDN, Memory.grow](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/Memory/grow).
- argon2-browser (2020, Intel i7, Argon2d, 1 MiB, 100 iterations, one lane): Chrome wasm 225 ms, Firefox 195 ms, Safari 174 ms, wasm with SIMD 119 to 135 ms, native -O3 42 ms, native SSE 15 ms; its parallelism option "won't be computed in parallel" in the browser. Source: [antelle/argon2-browser](https://github.com/antelle/argon2-browser).
- WebAssembly threads need SharedArrayBuffer, which browsers allow only on cross-origin-isolated pages (COOP same-origin and COEP require-corp). Source: [web.dev, COOP and COEP](https://web.dev/articles/coop-coep).
- Bitwarden's Argon2id defaults are 32 MiB, 6 iterations and 4 threads; above 64 MiB a warning shows in iOS autofill. Source: [Bitwarden, KDF algorithms](https://bitwarden.com/help/kdf-algorithms/).
- Larsal: argon2 0.6.0 is pinned without default features, so its `parallel` feature (rayon) is off and Larsal computes the lanes one after another on the Mac too; argon2's SIMD path is x86-only, so Apple silicon already runs the portable code (`Cargo.toml` line 44; `vendor/crates-io/argon2-0.6.0/Cargo.toml`; `argon2-0.6.0/src/lib.rs` lines 193 to 271). A new vault defaults to Argon2id with 64 MiB, parallelism min(4, CPUs) and iterations tuned to 1,000 ms, and Larsal asks before opening above 1 GiB or 128 lanes ([CRY-02](../crypto/CRY-02-key-derivation.md) CRY-02.23; `crates/larsal-format/src/limits.rs` lines 85, 86, 236, 237).
- `crypto.getRandomValues` throws QuotaExceededError above 65,536 bytes per call; it is "suitable for cryptographic purposes" and works in workers. Source: [MDN, Crypto.getRandomValues](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues).

## 13. The web vault: headers, sessions, clipboard and the back-forward cache

- `'wasm-unsafe-eval'` in `script-src` allows only WebAssembly compiling and instantiating; without it a page with a CSP cannot run WebAssembly; `'unsafe-eval'` would also allow `eval()`. WebKit implemented it in 2022, and a 2025 regression in Safari web extensions was fixed. Sources: [MDN, script-src](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/script-src); [WebKit bug 235408](https://bugs.webkit.org/show_bug.cgi?id=235408); [WebKit bug 290153](https://bugs.webkit.org/show_bug.cgi?id=290153).
- `fetch()` takes an `integrity` option checked like a script tag's (sha256, sha384, sha512). `WebAssembly.instantiateStreaming` rejects a response not served as `application/wasm`. Sources: [MDN, RequestInit](https://developer.mozilla.org/en-US/docs/Web/API/RequestInit); [MDN, instantiateStreaming](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/instantiateStreaming_static).
- The `Integrity-Policy` header (`blocked-destinations=(script)`) makes SRI required on every script in Chrome 138+; it replaces the never-shipped `require-sri-for`. Safari 26 has the header; `blocked-destinations` for script is listed for Chrome and Edge 138 only. Sources: [web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/reporting-integrity-violations.json); [centralcsp, Integrity-Policy explained](https://next.centralcsp.com/en/blog/integrity-policy-explained) (secondary).
- Safari 18.0 (2024-09-16) "Added support for subresource integrity in imported module scripts" and "Added support for the WebAuthn PRF extension". Source: [Safari 18 release notes](https://developer.apple.com/tutorials/data/documentation/safari-release-notes/safari-18-release-notes.md).
- Trusted Types reached Baseline in February 2026 (Chrome and Edge 83, Safari 26, Firefox 148); enforcing needs `require-trusted-types-for 'script'`. Sources: [MDN, trusted-types](https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Content-Security-Policy/trusted-types); [dev.to, Trusted Types is Baseline](https://dev.to/grimicorn/trusted-types-is-baseline-dom-xss-is-now-a-type-error-1k1h) (secondary).
- OWASP: "Common idle timeouts ranges are 2-5 minutes for high-value applications"; an absolute timeout of 4 to 8 hours suits all-day office use; localStorage and sessionStorage "are accessible to any JavaScript executing in the origin". Source: [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html). Larsal's Mac idle lock default is 300 seconds ([APP-02](../app/APP-02-lock.md) line 30).
- Bitwarden's web vault timeouts are "Time passed", "On browser refresh" and "Custom"; a refresh locks and closing the tab logs out; it has no system-based or Never options, while its extension does. Source: [Bitwarden, Vault timeout](https://bitwarden.com/help/vault-timeout/).
- Clipboard: in Firefox and Safari "Writing requires transient activation", and they do not support the `clipboard-read` and `clipboard-write` permissions; Chromium writes with either the permission or transient activation. So a timed clear after a copy cannot be relied on in Safari or Firefox. Source: [MDN, Clipboard API](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API).
- The back-forward cache keeps "a snapshot of the entire page in memory, including the JavaScript heap"; `pagehide` and `pageshow` carry `persisted`; pages with sensitive data must clear or update state on restore; `Cache-Control: no-store` has kept pages out of it, but Chrome is changing that. Source: [web.dev, bfcache](https://web.dev/articles/bfcache).
- Option A's locked CSS loads its fonts only from local copies in `design/option-a/vendor/fonts` (`design/option-a/app.css` lines 3 to 7), so a web page can use the locked look with no outside font.

## 16. Design picks

Each pick says what, why, and its sources. The lead takes them, or not, in LD rows (rule 9). B1 to B12 are the extension, B13 to B29 the web vault, B30 the licences.

### The extension

**B1 One code base in plain JavaScript, with no build step that changes code.** `extension/` holds ES2022 modules for the background and the extension pages, plain HTML and CSS, and a short ordered list of classic files for the content scripts. No TypeScript compiler, no bundler, no minifier, no package from a package registry, no UI framework. The code calls `browser.*` with the one-line guard `globalThis.browser ??= chrome` and no polyfill.
- Why: LD-272 (6) and LD-221 (no outside code). The smart parts (matching, site access, the generator, codes, passkeys) already live in Rust in Larsal (INT-01 to INT-04), so the extension is a thin screen plus a relay. Bitwarden and Proton Pass need webpack, TypeScript and dozens of packages because their logic runs in the extension (section 6). With nothing minified or bundled, AMO needs no source upload and every reviewer reads the shipped files (section 4).
- Sources: sections 2, 4, 6.

**B2 One manifest source, one small script per browser, few permissions.** `extension/manifest.json.in` plus `extension/build.py` (Python 3 standard library, as `scripts/` already uses) writes each browser's `manifest.json` and package folder: both `background.scripts` and `background.service_worker`; for Firefox a gecko id and `data_collection_permissions` `none`; for development builds the `key` member, so the id stays fixed for `allowed_origins`. Permissions: `nativeMessaging` (Safari requires it), `storage`, `activeTab`, `scripting`, and `http://*/*` and `https://*/*` host permissions (needed by the locked in-page frames; this means a longer Chrome review). The CSP stays the default `script-src 'self'; object-src 'self'`: no WebAssembly in the extension (B3). Each browser's minimum version is the lowest release that has every API the code uses (WebCrypto X25519, section 8), set by INT-11.
- Why: MDN's one-manifest advice; Chrome's `key` keeps the id; fewest permissions (Chrome's advice), except what the frames need. The one-line `browser` guard replaces `minimum_chrome_version: 148`, so Opera, Brave and Vivaldi releases that trail Chromium keep working.
- Sources: sections 2, 4, 5.

**B3 The channel uses the browser's own WebCrypto, not a crypto copy and not WebAssembly.** The extension's half of INT-01's channel uses only WebCrypto: X25519 for the session exchange and the identification key, HKDF-SHA256 for the keys, AES-256-GCM for every message, `crypto.getRandomValues` for nonces. These are the primitives of the HPKE suite Larsal already takes for sharing (P8: X25519, HKDF-SHA256, AES-256-GCM). The identification private key and the session keys are non-extractable `CryptoKey` objects; the identification key is kept in the extension's IndexedDB. A Spec agent writes the exact key schedule (two keys, one per direction, from HKDF over the X25519 secret with both session public keys in its input; 12-byte nonces; the proof of INT-01.28 as an AES-GCM seal under a key from the identification key's X25519 secret) into INT-01 with known-answer vectors that the Rust side and WebCrypto must both give. Larsal's side uses `x25519-dalek`, `hkdf` and `aes-gcm` in larsal-crypto, which E16-S2 brings anyway; `crypto_box` leaves the plan.
- Why: (1) `crypto_box` has no stable release on Larsal's crypto generation, and 0.9.1 duplicates crypto crates (section 8), so E7-S1's re-pin (LD-203) cannot be done with a stable release. (2) WebCrypto is the browser's own implementation, so Larsal ships no JavaScript crypto (rule 3, LD-272 (6)); the vault crypto still exists only once, in Rust. (3) It works where WebAssembly is off: Edge's Enhanced Security mode stops such extensions (Proton, section 6); Safari's Lockdown Mode turns WebAssembly off in pages, and for extension pages it is unchecked (section 18). The users who turn those modes on are the ones Larsal is for. (4) A non-extractable identification key cannot be read by a script, which narrows INT-01's note that malware reading extension storage takes the key (a process that reads the browser's profile files is still out of scope). (5) Bitwarden's channel is also built from standard primitives in the extension, not from a NaCl box (section 6). (6) Larsal's Rust side needs no crate beyond E16-S2's.
- Rejected: a copy of TweetNaCl-js cut to `box` (audited, public domain; keeps INT-01 unchanged, but Larsal would ship a second crypto implementation in JavaScript and need a ruling that extends rule 3); Larsal's larsal-crypto compiled to WebAssembly for the extension (`'wasm-unsafe-eval'`, a wasm build before E7 can start, AMO's rebuild review, and no extension in Lockdown Mode).
- Cost: INT-01's channel rules change before E7-S1 builds them (INT-01.20, INT-01.21, INT-01.23, INT-01.26, INT-01.28, D-INT01-2 and their test cases). The frame, the relay, the identity rules, the request table and the errors stay. If the lead takes B3, these rows are no longer true and the lead updates them: LD-189 ("Channel: NaCl box through crypto_box (re-pinned at E7-S1)"), LD-203's re-pin, [plan/architecture.md](../../plan/architecture.md) line 81 (larsal-crypto `boxes.rs`, XSalsa20-Poly1305; the new file is `bridge.rs`) and line 255 (approved crates, "Browser bridge boxes (E7) | `crypto_box`"), the `crypto_box = "=0.9.1"` pin at `Cargo.toml` line 57, and E7-S1's "Re-pin `crypto_box` first" in plan/epics.md.
- Sources: sections 6, 8; [INT-01](../integrations/INT-01-browser-bridge.md); [sync-server.md](sync-server.md) P8.

**B4 The host program stays a separate relay, written in Rust.** `larsal-bridge` is its own small binary crate in Larsal's bundle, as INT-01 says and as Bitwarden ships `desktop_proxy`. It holds no key, parses no box and links no vault code. The extension keeps one `connectNative` port per session, which keeps Chrome's worker alive; on `onDisconnect` it connects again and says hello again.
- Why: INT-01.4 and INT-01.5; Chrome's lifecycle page (section 1).

**B5 Browsers and folders.** Now: Chrome, Edge, Brave, Vivaldi and Firefox (INT-01.8, D-INT01-6), Opera after V-INT01-1. "The other Chromium browsers" of LD-272: add Chromium (`Chromium/NativeMessagingHosts/`) and Arc (`Arc/User Data/NativeMessagingHosts/`) after a Verify check with a test HOME. The settings page's Browsers group gets Edge, Chromium and Arc rows, drawn in `design/option-a/proposals.html` (LD-268) for the owner's one-pass review (AT-K05), which never blocks the build.
- Why: Bitwarden's folder list (section 1); the Arc and Opera folders are unproven, so a check comes first.

**B6 Extension ids.** One Chrome Web Store listing serves Chrome, Brave, Vivaldi, Arc and Opera (through Chrome-store installs); Edge Add-ons gives a second id; Firefox gets one gecko id. `allowed_origins` lists only those, plus one debug id from the `key` member (INT-01.9).
- Why: Bitwarden lists fixed store ids (section 1); Vivaldi installs from the Chrome Web Store (section 5).

**B7 Safari: a Safari web extension target inside Larsal.app, relaying to Larsal's app-group socket.** `macos/Larsal.xcodeproj` gets a Safari web extension target whose resources are the same `extension/` files with the Safari manifest. Its sandboxed app extension (`SafariWebExtensionHandler.swift`) holds only the app-group entitlement `<team id>.app.larsal.browser` and relays each message, unchanged, to `bridge.sock` in that group's container (INT-01.13, D-INT01-7). Larsal stays non-sandboxed, gets the same group entitlement, and checks the peer's code signature (INT-01.7). A group id that starts with the Team ID avoids the macOS 15 prompt. Sessions are found by `sid` (INT-01.14). The Safari extension ships and updates inside Larsal.app, so its version always matches Larsal's. Notices stay off on this route for now (INT-01.14): the popup asks `status` when it opens.
- Why: Apple documents the socket-in-the-group-container route between a sandboxed and a non-sandboxed program (section 3); one protocol for every browser (D-INT01-7).
- Not taken: Bitwarden's Safari handler, which reads a vault key from a keychain item (section 3): Larsal never puts a key where the browser side can read it.
- Sources: section 3.

**B8 The extension never unlocks anything itself.** `unlock` makes Larsal show its own unlock panel with Touch ID (APP-06), as the locked frame says ("Unlock it in Larsal").

**B9 Fill only on a user action.** A fill happens only after a pick in Larsal's in-page menu, Fill in the popup, or the keyboard command. "Fill when a page loads" (R02-4) stays off by default; when the user turns it on, it fills only the top frame, only on https, only when exactly one entry matches, and never into an iframe. A fill into an iframe always needs an explicit pick plus INT-02.19's prompt. The background takes `url`, `origin` and `frameId` only from `runtime.MessageSender`, never from text a content script sends, and INT-04's passkey origin comes from there too. A password reaches a content script only at the moment of fill, and no code uses `innerHTML`.
- Why: Princeton CITP, Oesch and Ruoti, Bitwarden's defaults (section 7); Chrome's advice and MessageSender (section 2).

**B10 The in-page frames resist the 2025 clickjacking attacks.** Each of the 7 in-page frames is a page of the extension's own origin (`web_accessible_resources` with `use_dynamic_url`) in an iframe inside a closed shadow root, placed in the top layer with the Popover API and kept last in the DOM. Before a click in it counts, the content script checks the computed opacity and visibility of `html`, `body`, the host and its ancestors, watches their `style` and `class` with a MutationObserver, checks that no other top-layer element is open, and checks `elementsFromPoint` at the click point. On any doubt it closes the menu and points the user to the toolbar popup, which the page cannot cover. A new attack row, AT-F09 "Invisible extension UI" (Toth's three methods), goes into plan/attacks-and-checks.md.
- Why: Toth found 10 of 11 managers open and lists these defences; no single one is enough ("Doesn't exist simple protection"), so all are used, with the popup as the safe way out (section 7).

**B11 Tests on this Mac with no window (rule 10).** Pure modules (message framing, state, field detection rules) run under macOS's `jsc` with injected bytes. Code that needs WebCrypto or a page runs in the installed Chrome, headless (`--headless=new`), with a throwaway profile and a test HOME, driven by `extension/test/driver.py` (Python standard library) over `--remote-debugging-pipe`, which loads the unpacked extension with `Extensions.loadUnpacked` under `--enable-unsafe-extension-debugging`. Only if that fails does the team ask the owner for Chrome for Testing (rule 7). Test pages never use an IP host: the names `site-a.test`, `site-b.test` and `sub.site-a.test` point to 127.0.0.1 through `--host-resolver-rules`, and a test certificate made for the run is trusted only by the throwaway profile through `--ignore-certificate-errors-spki-list`, because WebAuthn and INT-04.10 refuse IP hosts and INT-02.19 takes an IP host as one site (section 14). E7-S7b checks that these flags work, and that Chrome with a throwaway profile finds a host manifest in the folder Larsal writes under the test HOME. WebKit's rendering of the same pages is checked in an offscreen `WKWebView` in LarsalTests (the Safari engine, no window). The Rust side uses INT-01's test client; the Safari relay is tested by calling the handler with a test request and a test socket folder. Runs in real Safari, and Firefox runs that need a window, wait for the owner's go.
- Why: the mockup tools already drive this Chrome headless (section 9); no download and no new tool.

**B12 Store steps and costs are the owner's (LD-272 (4)).** Chrome Web Store: a one-time fee, its amount shown at registration. Edge Add-ons: free, with a Microsoft account. AMO: a Mozilla account, no fee named, signing needed even for self-distribution. - Sources: sections 3, 4, 5.

### The web vault

**B13 Shape: four static files served by larsal-server.** `web/index.html`, `web/app.js` (one ES module with no imports, so one SRI value covers it), `web/app.css` (Option A's locked CSS and its local fonts) and `vault.wasm` (built from `larsal-web` by the release build). No service worker. JS, HTML and CSS need no build tool.
- Why: LD-272 (6); Vaultwarden serves its web vault the same way (section 10); the locked CSS needs no outside font (section 13).

**B14 The vault code exists once: Rust compiled to WebAssembly.** A new crate `larsal-web` (GPL-3.0-or-later) is the only crate built for `wasm32-unknown-unknown`. It does for the browser what larsal-ffi does for Swift: it holds the signed-in account and the open vaults in wasm memory and exports about 15 functions that take and return byte buffers. It links larsal-crypto, larsal-model, larsal-format and larsal-proto (records only) for the first release, and larsal-core later for edits. It never links larsal-platform, larsal-sync or larsal-ffi: JavaScript makes every request with `fetch`, and Rust only turns bytes into bytes, so Rust rule 12 holds. larsal-server serves `vault.wasm` as a file and never links larsal-web; the P16 "server blind" check also names larsal-web.
- Why: Bitwarden and Proton ship their Rust core to the web as WebAssembly (sections 6, 10); LD-272 (6) asks for one crypto; Argon2 at Larsal's settings needs native-like code (section 12).

**B15 Exports without wasm-bindgen.** The exports and two imports (random, time) are hand-written in one file, `larsal-web/src/abi.rs`, with about 100 lines of JS glue in `app.js`. The `unsafe_code` lint flags `no_mangle`, so larsal-web gets the same kind of Rust rule 2 exception as larsal-platform: `unsafe` only in `abi.rs`, a `// SAFETY:` note on each block, two Checkers.
- Why: no crate and no build tool is added (LD-221, LD-272 (6)). Fallback: wasm-bindgen (Bitwarden, Proton) as an LD-221 copy with a written reason, if the surface grows past what a Checker can read line by line.

**B16 Random numbers and other build switches on wasm.** Restore getrandom 0.4.3's upstream `src/backends/custom.rs` into Larsal's copy byte for byte (LD-221 (3), (7)), and set `getrandom_backend = "custom"` for the wasm target only. larsal-web defines `__getrandom_v03_custom`, which calls the imported `crypto.getRandomValues` in chunks of at most 65,536 bytes and fails closed. That function returns getrandom's error type, so larsal-crypto re-exports the type and its constructor (as `larsal_crypto::random::BackendError`), and larsal-web never depends on getrandom: rule 3 ("Only larsal-crypto imports them") holds, and `larsal-crypto::random` stays the only door. `wasm_js` is not used (it pulls in wasm-bindgen and js-sys). Set `curve25519_dalek_bits = "64"` for the wasm target (the u32 backend is cut), and run the RFC 8032 vectors under wasm, since upstream marks wasm32 as untested. Never build with `+simd128` (sha2's wasm SIMD files are cut).
- Sources: section 11.

**B17 A clock seam in larsal-format.** Open and save take the time from the caller, with the `Clock = fn() -> Duration` pattern `kdf.rs` already has; larsal-web passes `Date.now()` through its time import. The KDF benchmark (`Instant`) stays off the web path: the web creates no vault and changes no KDF setting.
- Why: `SystemTime::now()` panics on this target (section 11).

**B18 Argon2 in the browser keeps the Mac's settings.** Larsal's argon2 is single-threaded already, so the web loses only the wasm-versus-native factor (about 4 to 5 times in older measurements); no threads, no SharedArrayBuffer, no COOP and COEP for threads. A 64 MiB demo vault is measured in JavaScriptCore, Chrome and Firefox before any limit is fixed. A vault whose Argon2 memory is above the measured web ceiling is refused with a plain message, and the tab never crashes. When WebAssembly is off (Lockdown Mode, Edge's Enhanced Security), the page shows a plain message. No JavaScript crypto fallback.
- Sources: section 12; section 6 for Lockdown Mode.

**B19 Secrets stay in Rust, in wasm memory (rule 4).** The vault key, the account secret and the decrypted vault live only in wasm memory. JavaScript gets only list text (titles, user names) and the one value the user asks for with Show or Copy. On lock, larsal-web drops the session (its types wipe), then JavaScript fills the whole `memory.buffer` with zeros and drops the instance; the next unlock makes a new one, which also gives back Argon2 memory that wasm cannot shrink. Any wasm trap (panic = abort) counts as a lock. The docs say plainly that the page's own JavaScript can read wasm memory: this gives wiping, not isolation from served code.
- Sources: sections 10, 12.

**B20 Lock and session.** The page locks on idle (APP-02's 300 seconds), on reload or tab close (Bitwarden's web behaviour), on `pagehide` (the back-forward cache keeps the heap) and on a trap; there is no "never" option. The 32-byte P5 session token lives only in the module's memory, never in localStorage or sessionStorage, and travels in the same header the Macs use. The server keeps its idle expiry and an absolute expiry of at most 8 hours (the lead picks within OWASP's 4 to 8). After a reload the user signs in again with the passkey.
- Sources: section 13; [sync-server.md](sync-server.md) P5.

**B21 Strict headers on every web response.** CSP `default-src 'none'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self'; font-src 'self'; img-src 'self'; connect-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'; require-trusted-types-for 'script'; trusted-types 'none'`. The DOM is built with `createElement` and `textContent`, never `innerHTML`. Also: `Integrity-Policy: blocked-destinations=(script)`; an SRI value on the script tag; `fetch("vault.wasm", {integrity})` served as `application/wasm`; HSTS; `X-Content-Type-Options: nosniff`; `Referrer-Policy: no-referrer`; COOP `same-origin`; CORP `same-origin`; a Permissions-Policy that denies everything except `publickey-credentials-get`, `publickey-credentials-create` and `clipboard-write`; `Cache-Control: no-store` on `index.html`.
- Sources: section 13.

**B22 The served-code risk, smallest steps first.** (1) The sign-in page says it plainly: the web vault trusts the server that serves it; Larsal's Mac app and its extension do not. (2) The web files are reproducible, and a release manifest (path to SHA-256) is signed with Larsal's release key (Ed25519 through larsal-crypto); larsal-server refuses at start to serve a web folder that does not match it. (3) Later: Larsal's extension checks the served files against the signed manifest, as Code Verify, WAIT and WEBCAT do. (4) Later: the same web vault pages packaged inside the extension, where only packaged code runs (MV3), which makes them a store-signed client. Isolated Web Apps and WAICT wait until browsers ship them. The lead writes the known limit like LD-266 (4).
- Why: the ETH paper and both white papers treat served code as the web's weak point (section 10).

**B23 Sign-in is a WebAuthn passkey.** ES256 (P-256), attestation `none`, user verification required: the P5 pattern where no Secure Enclave exists. The server stores the COSE public key and sends its one-time nonce as the WebAuthn challenge. It checks `type`, the challenge, the origin, `rpIdHash`, the UP and UV flags, and the P-256 signature over `authenticatorData || SHA-256(clientDataJSON)` with larsal-crypto's P-256 verify (E16-S2). A small CBOR and COSE reader in larsal-proto has a fuzz target and passes the WebAuthn Level 3 vectors. Not taken: a non-extractable WebCrypto key in IndexedDB as the device key, because any served script can use it, it sits on disk, and it has no user verification.
- Sources: sections 9, 14; [sync-server.md](sync-server.md) P5.

**B24 Adding a browser is adding a device.** A signed-in Mac approves it with the SYN-05 code compare and seals the account secret to the page's one-time HPKE key (made in wasm); or the user types the Recovery Kit. Then the page registers its passkey as a device: the approving Mac signs the browser's passkey public key with the identity key, as SYN-06.11 step 5 signs a new device (`sync-device-v1`, CRY-04), and in the kit path larsal-web signs it after the account unlock. The server refuses a browser device without that signature (AT-L12). The device list shows it as a browser. To keep the account secret between visits, PRF is used where the browser has it: the account secret is wrapped with AES-256-GCM under HKDF of the PRF output, and that blob is stored on the server per passkey, as Bitwarden does; the server cannot open it. Without PRF the browser keeps nothing, and each visit needs a Mac's approval or the kit. The account password is typed at every visit, so P6 is unchanged.
- Sources: section 14; [sync-server.md](sync-server.md) P6.

**B25 Clipboard.** Copy only inside the user's click. Try to clear after APP-03's time; where the browser refuses, say plainly that the clipboard could not be cleared. Never read the clipboard.
- Source: section 13.

**B26 Scope in two steps.** First release: sign in, unlock, browse, search, Show, Copy and one-time codes, with larsal-crypto, larsal-model, larsal-format and larsal-proto only. Second: edit and save with PUT If-Match and the MOD-11 merge on 412, with larsal-core compiled to wasm, after its size is measured (zxcvbn, regex, png). New vaults, KDF changes, imports, exports and attachment saves stay on the Mac.

**B27 Tests on this Mac (rule 10).** The engine's tests stay native (it is the same code). One wasm check runs under macOS's `jsc`: larsal-crypto's known-answer vectors, and a demo vault opened under wasm gives the same entries as natively; only that harness injects randomness. Page tests run in headless Chrome with a throwaway profile and a WebAuthn virtual authenticator over the same driver as B11; WebKit is checked in an offscreen `WKWebView`. Safari page runs wait for the owner's go.

**B28 Server work stays on the LD-263 (13) stack.** larsal-server gets: a static route for the web folder with B21's headers and B22's manifest check; WebAuthn register and assert routes; storage for the PRF-wrapped blob; a fuzz target for each new parser. Browsers cannot pin P17's self-signed certificate, so a hosted web vault needs a certificate browsers trust and a domain, which also fixes the passkeys' RP ID: owner steps (rule 7). Tests on this Mac use E7-S7b's test names and its certificate, trusted only by the throwaway profile (B11).

**B29 Order.** The web vault epic (E20) starts after E16-S7b and E17-S1 (LD-272 (2): after E16 and the account part of E17); adding a browser also waits for the code compare (E17-S2) and devices (E17-S3). Its `.cargo/config.toml` lines, the getrandom file and the release-build step wait for the E0-S7 follow-up, which owns vendor/, the Cargo files and scripts/ now. The extension (E7) runs beside the sync epics within the 4-agent limit (LD-272 (5)); its channel waits for E16-S2's crates (B3).
