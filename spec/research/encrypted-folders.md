## Scope and primary evidence

The owner wants portable, independently encrypted files and names in an existing storage folder, first through Larsal's own window. A cloud directory is hostile filesystem input, not a Larsal service. No account, upload protocol, mount or new crypto construction is proposed. The cards are [FIL-04](../files/FIL-04-folder-format.md), [FIL-05](../files/FIL-05-folder-screens.md), [FIL-06](../files/FIL-06-folder-limits-and-conflicts.md). Existing FIL-01–03 supply the local-output threat analysis; their single-file format does not become a folder format.

## Comparison and proposed profile

The smallest established interoperable choice is **classic8-gcm-local-1**: classic format8, `SIV_GCM`, local password masterkey file, creation JWT `HS256`, read `HS256/HS384/HS512`, shortening threshold220 on creation. This retains LD-337(4)'s format family. F15 supplies a comparable own-window workflow. F16/F17 confirm the common independent-file pattern but differ on wire format and leakage. No whole-vault container, new cryptographic manifest, custom final tag or service is added to classic files.

Format8 also permits `SIV_CTRMAC` and remotely retrieved keys. Those are explicit unsupported profiles, not successful interoperability; pre8 migration, symlink following, remote key retrieval and universal-format writes are not quietly inferred. Required successful foreign-vault/app checks stay OPEN. F03 explicitly records NFC password normalization from format6. Carrying that unchanged rule into classic8 is an inference from its published history, not an undocumented application guess. Unicode table coverage, exact secure transport/wiping and successful composed/decomposed/non-ASCII peer tests remain OPEN; no trial of multiple normalizations or silent credential substitution.

F03's classic history distinguishes format7's node/shortening layout from earlier layouts, while format8 separates authenticated configuration from password key retrieval without changing the directory-object layout. Older version numbers are not assumed readable because an application supports8. This proposal neither silently migrates earlier vaults nor labels their refusal a successful required foreign-vault test. F33's current passthrough sample specifically requires macOS26; FSKit's initial15.4 availability does not imply that newer sample protocols work on15.4. S5 must verify availability of each API it selects and keep the macOS14 own-window path.

**UVF is published working material**, not absent and not equivalent to classic8. F09–14 define spec1, JWE, seed-based derivation and a content format with mandatory trailing partial/empty EOF treatment. It addresses whole-chunk truncation structurally, but still does not give name-to-content binding or file freshness. Seed pins protect only metadata already observed by a client; existing data, old headers and old directories retain key-rotation limitations. A UVF password profile is application-specific. Claiming that every UVF peer opens Larsal's choice would require exact recipient/profile/tool evidence. Recommendation: study it, do not silently migrate or advertise it as supported. Every required future interoperability success remains OPEN, never replaced by refusal.

The historical F06 review found a release-signing-key exposure and an adapter default issue. F07 gives later context, including key revocation. It does not establish current format8/GCM or UVF safety, nor Rust crate safety. F05 and F08 are more current, distinct security lessons: authentic object reassignment and untrusted key-location metadata. No comprehensive current audit of the chosen complete profile was located and read; none is asserted.

## Integrity scope and selected first-party Open

Classic content uses the F02 header/chunk arrangement normatively. Full-chunk truncation can leave a valid shorter file; there is no authenticated total length or final marker to validate. Swapping authentic whole objects or replaying old versions can also authenticate. New-header/full-file rewrites on Larsal edits reduce old/new chunk splicing; they do not repair authentic whole-object substitution, legacy writers retaining headers, or unseen rollback. This is why local pins are change warnings, not a universal freshness proof.

To retain the original no-plaintext-on-corruption obligation, use E22's candidate: capture ciphertext only, seal exclusive custody, validate all available authenticated structure to a wiping discard buffer, then replay the same sealed descriptor to the explicitly authorized output. Reopening the cloud path or hashing after output is insufficient. This catches invalid tags/structure before release, but cannot detect cryptographically valid classic truncation/replay. All custody, output-ownership and revocation mechanisms need implementing proof; 0700/chmod alone does not stop arbitrary same-user memory/fd access. No product or crypto run occurred here.

Lead selects controllable first-party Open: Larsal owns every live document view/provider/handle and creates no readable disk copy. Rust retains bounded content and exact arbitrary-file byte access; text/image/PDF cases must have meaningful presentation, not a hex-only substitute. Save Out is explicit persistent readable export. Finder/arbitrary-app access remains separate S5 with signing. The submitted external Open Copy/Finish route and external-custody exception are withdrawn. F36’s inability to recall another app remains a reason not to select that route for S4; it is not a conflict inherent in original own-window acceptance. FIL-05 names callback-provider, text, Image I/O and PDF candidates (F43–49), with no-disk/index/cache, buffer/callback lifetime and API/secret review still required in S4. No candidate is claimed proven; APP-10’s actual OS capture limits remain.

Original S3 is precisely “one changed byte gives the generic error and no plaintext”. Keep it unchanged and OPEN. Whole-object/chunk truncation, replay and substitution belong to separate original S6 handling/disclosure. Enumerate unauthenticated directory-ID link text, shortened-name mapping/representation, storage metadata and unsigned/re-encoded config representation separately from signed/authenticated values. An exact one-byte counterexample would need its specific object/mutation and narrow ruling; these different attacks do not establish one. No broad-corruption acceptance replacement is proposed.

## Observer leakage and concurrent storage

An observer sees recognizable encrypted configuration/objects, public profile/KDF parameters, ciphertext lengths, counts, per-ciphertext-directory membership/fan-out, node representations, name lengths and name equality over time, creation/modification/access times supplied by storage, changed objects, traffic/ordering and historical versions. Flattening conceals direct plaintext parent mapping at rest but does not erase folder shape: clear directory IDs in classic links, correlations and access history can reveal relationships. Do not call it “no metadata”. Neither file extensions nor backups hide encryption's use. Exact plaintext file size is derivable from the chosen chunk layout. Local own-window labels, external apps, cache, snapshots and backups are additional observers. The user-selected folder name and source plaintext remain outside encryption.

No shared password gives author attribution or protects against another holder forging data. Password rewrap is not data-key rotation or retroactive revocation, F42. Anyone holding the portable wrapped keys can try passwords offline. Generated ten-word credentials reduce that risk; they do not exclude endpoint malware or future cryptanalysis. No absolute quantum, anonymous, recovery or secure-erasure promise.

APP-05's coordinated I/O and local advisory locks are reused as platform patterns, not remote exclusion. Before publishing edits, preserve the base and newly created ciphertext durably in local private recovery, recheck the observed target identity/digest and commit with platform-safe ownership. If it changed, preserve both and stop replacing. If two offline Macs each committed, later exposure of both branches or provider conflict versions produces FIL-06's deterministic conflict set. A storage provider can suppress one branch indefinitely. No protocol without a cooperating compare-and-swap/version service can promise otherwise. Recovery retention consumes disk; reaching its bound stops mutations before data is lost. No automatic ciphertext recovery deletion or recovery upload. Recovery retains original encrypted names plus parent IDs; derive clear names only during an authorized Rust session. No decrypted name/content in raw recovery objects, journal bodies/filenames or logs after lock/restart; unique demo-name-marker absence and successful name/version recovery after unlock are required contrasts.
