## 1. Scope and evidence

E22 encrypts one ordinary file, including an image, locally. [FIL-01](../files/FIL-01-format-and-keys.md), [FIL-02](../files/FIL-02-screens-and-flows.md), [FIL-03](../files/FIL-03-limits-and-errors.md) specify it. No reference source, application or command line tool was accessed. The Lead research is input, not approval. Findings below were rechecked using public primary documentation on 2026-11-05. Facts, design inferences and Lead rulings are distinguished.

E23 may reuse the threat analysis, secret-boundary review, safe destination rules and resource accounting. It must independently research encrypted names, directory shape, per-file random access, concurrent edits, cloud conflict handling, the folder format and File Provider. E22 neither creates folder-vault cards FIL-04 to FIL-06 nor substitutes one large age file for that capability. E23's Mac speed measurements remain in E23-S1; none are claimed here.

These recommendations are design inferences, not security rankings. Neither signatures nor a strong primitive removes weak passwords, malware, public-key verification, output ownership or backups. E22 creates a portable local file and contains no network, upload or Larsal-server storage path. LD-340's no-password-verifier obligation applies to every Larsal service and remains unchanged; the owner-chosen USB, cloud and email destinations expressly authorized by E22 do not create a Larsal service. Anyone obtaining a portable passphrase-encrypted file can test guesses offline, so a weak chosen phrase remains unsafe. No third-party-storage no-guess promise is made. Any later Larsal service that stores or transports these files requires a reviewed design satisfying LD-340 before that feature is built.

## 4. Reviewed profile and library route (LD-366)

**P1: Larsal age-classic-1** means binary age v1 write, binary and strict armor read, one scrypt recipient OR 1–1024 native X25519 recipients. No SSH, tagged, native hybrid, plugin, detached-header or automatic identity-discovery path. Unknown recipient stanzas can be skipped inside the bounded public-key header; a supported matching identity is still required. Unsupported-only files get FIL-03's generic decrypt failure. The required external interoperability peer is the separately approved age 1.3.2 tool, in the exact classical profile and both directions. Rust age 0.12.1 documentation was studied as a library alternative; no Rust peer binary, library harness or package closure is requested or approved by this proposal. A Rust peer run may be added only with a separately itemized reviewed dependency/tool request. The compatibility claim is this classical profile, not all age tools/features. External encrypted native identity files are accepted through the same bounded decrypt/validation path, with a separate credential prompt; no recursive encrypted-identity nesting. The inner content is a bounded native identity list, not another executable format.

**Route selection:** follow the existing larsal-format pattern: larsal-files arranges the public wire format and operation state; larsal-crypto imports the approved primitive/encoding crates and owns all secrets and cryptographic operations. Reuse existing random, HKDF, HMAC, X25519, base64 and wiping types. Add RustCrypto scrypt and ChaCha20Poly1305 plus bech32 for native keys, rather than the complete Rust age library. This is our own format arrangement from S01, not a new cryptographic construction or source translation. A full format/recipient review and published vectors are mandatory. S11's full library is the alternative considered first: lower parser effort, but beta status, broad dependencies, internal RNG/secret ownership and unproved native PQ capability require exceptions or a patch. The selected route preserves the current single RNG/import boundary without such exceptions. The specification route is recorded by LD-366; original dependencies, sensitive reviews and AT-J03/download gates still govern implementation and adding crates.

All wire syntax and equations are exactly S01, referenced normatively rather than copied here: version/header grammar, canonical base64, header MAC, native recipient wrapping, payload key derivation, STREAM counter/final bit, identity Bech32, strict armor. File key is fresh 16 bytes; payload nonce fresh 16 bytes. Payload plaintext chunks are 65,536 bytes, tag 16 bytes. Recipient bodies are 32 bytes. Password profile uses scrypt r8/p1/dkLen32. FIL-01 adds operational constraints; it does not change these equations or strengthen the 128-bit file key by calling the payload key 256 bits.

Native PQ is published (S01/S03); ML-KEM is standardized (S07); the hybrid HPKE binding remains a draft (S08). This proposal offers classical public keys with a clear quantum warning. A native hybrid implementation is **OPEN**, with no guessed Rust identity API, tagged-key equivalence, home-made KEM/combiner or claim of whole-file 256-bit quantum strength. E22-S1 asks whether a mode is published, not that PQ implementation has passed. If Lead requires PQ at first release, its exact implementation/dependency route and implementing-story acceptance must be added before building, without dropping password, classical recipients or armor/foreign-file flows.

## 5. Validation/output-failure boundary (R2, LD-367)

S10 and S04 show why successful chunks are not whole-file validation. A damaged late chunk, lost final marker or trailing data may fail after earlier plaintext exists. Whole-file RAM buffering conflicts with bounded memory. Plaintext staging conflicts with no plaintext temporary file. Reopening the original path for a second pass has a substitution race. A hash recomputed while already writing cannot retract earlier bytes.

**Candidate, not preapproved proof:** capture only ciphertext into a fresh owner-only operation directory, close every writable handle, retain one read handle, unlink the snapshot name, fully validate header and payload to EOF into a wiping discard buffer, then rewind that same descriptor and decrypt again to the user's final destination. No plaintext is staged. No writer is ever given the descriptor, no original-path reopen, no cloud location for scratch; ciphertext capture, read errors and input-change checks precede output creation. Platforms unable to establish exclusive snapshot custody must fail before output. A same-user process with arbitrary memory/fd control or admin malware remains outside this candidate's assurance; 0700 alone is not a same-UID security boundary.

A sealed captured ciphertext that fails syntax, credential, header, payload, final-marker or EOF validation yields MSG-FILE-DECRYPT before any final output is created or any plaintext is emitted. The ciphertext-only capture and discard pass are the proposed way to satisfy the original E22-S3 corruption check with bounded memory and no plaintext temporary file; their custody, replay and filesystem behavior still require the implementing stories' sensitive review and tests. A later read/write/sync failure or process/power failure after that successful validation is a separate output-I/O fault. It can leave bytes at the explicitly authorized final path; it is not evidence that initially malformed ciphertext passed validation. Report the actual failure and cleanup/uncertain result without a success claim. E22-S4's original "cancel leaves no partial output" remains unchanged: a handled cancellation with a surviving incomplete output fails that check, even when the warning is correct. A crash is not a handled cancellation. Neither this boundary nor the candidate constitutes runtime proof.

No overwrite in this first proposal: choose a new filename. Destination is exclusively created 0600 in an already opened parent directory whose identity is bound to user selection; use descriptor-relative operations/no-follow and verify regular type, uid, single link and dev/inode. Retain the descriptor and bind cleanup to the exact inode, never unlink a substituted pathname. Existing files, symlinks, hard links and source aliases fail with no change. No ordinary replacing rename. These are policy proposals motivated by S19 and existing APP-05; exact macOS primitives need two sensitive Checkers in S3. An error cleaning up is itself reported, never hidden as “nothing saved”.

## 6. Resource derivation and future benchmark scope

Let P be plaintext length, C=65,536, n=max(1,ceil(P/C)), H be bounded binary header length. Binary output B=H+16+P+16n. Empty input still has one authenticated final chunk. For P=4,000,000,000, n=61,036 and tag overhead=976,576 bytes. For P=4 GiB, n=65,536 and tag overhead=1,048,576. Counts and ceilings are checked before arithmetic/allocation; no u64 wrap or chunk-counter wrap. Practical accepted size is limited by filesystem free space, signed 64-bit offsets and FIL-03, not a small RAM-sized file cap.

S17 and S14 give a dominant scrypt V allocation of 128*r*N bytes; with r8 this is 1024*2^logN. Proposed write logN18 costs 256 MiB dominant storage; read ceiling20 costs 1 GiB, plus B/T and stack/process overhead. It is a cost bound, **not measured peak RSS or latency**. Reject >20 or malformed decimal before any KDF. One active file operation, one KDF at a time. Proposed non-KDF working-buffer budget: 8 MiB independent of P (header2 MiB, bounded stanza/key metadata, two chunk buffers, armor/copy buffers); exact allocations must be measured in S3. Do not lower logN automatically to fit memory or claim immediate cancellation inside a synchronous scrypt call.

Snapshot scratch needs the input ciphertext size B (armored input may be larger A); final output adds P. The candidate requires input read A, snapshot write A, full validation read A and final-decrypt read A plus output write P; armor decode is streamed each pass. Disk traffic and two decrypt passes are acknowledged, never marketed as a one-pass benchmark. Unknown-size input is counted incrementally and fails closed at signed-offset/free-space boundaries. Available-space preflight is advisory; every later I/O error remains checked.

S1 requires study of published limits/reviews/vectors; it does not require unapproved runtime measurements. **No benchmark was run or added as an S1 gate.** S3 must record release build/target/OS/CPU/storage, time and peak RSS for demo sizes 0,1,65535,65536,65537, 16 MiB, 1 GiB and 4 GB, both modes, disk-to-disk plus separate KDF; record capture/validate/save stages separately and cold/warm runs. S4's original 4 GB round trip and cancel-leaves-no-partial-output check remain OPEN. The required external interoperability peer is the separately approved age 1.3.2 tool, in the exact classical profile and both directions. Rust age 0.12.1 documentation was studied as a library alternative; no Rust peer binary, library harness or package closure is requested or approved by this proposal. A Rust peer run may be added only with a separately itemized reviewed dependency/tool request. E23's measured speed target is separate. Raw I/O or an existing vault primitive baseline would not prove future file-format performance.
