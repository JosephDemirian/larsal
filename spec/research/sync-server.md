## 1. How other products sync

### Bitwarden

- The sync endpoint is `GET /sync`. It takes no cursor or time. It returns the user's full data on every call (profile, folders, collections, items, policies, sends): a full copy, not "changes since". Source: [bitwarden/server: SyncController.cs (GitHub)](https://github.com/bitwarden/server/blob/main/src/Api/Vault/Controllers/SyncController.cs).
- Clients ask `GET /accounts/revision-date` to decide if a full sync is needed. The server must change that date whenever items change. A bug on the EntityFramework databases left it unchanged, so Android never saw new items (fixed in pull request #2634). Source: [bitwarden/server issue #2615: account revision date not bumped with EntityFramework DBs](https://github.com/bitwarden/server/issues/2615).
- Pull request #994, "Validate cipher updates with revision date", made the API refuse an item update whose last known revision date did not match, because "Syncs between clients which are out-of-date can cause data loss by updating records with stale data." It was merged on 2020-11-23 and reverted the same day. Source: [bitwarden/server PR #994](https://github.com/bitwarden/server/pull/994).
- Today a save from an old copy is refused with "The cipher you are updating is out of date. Please save your work, sync your vault, and try again." There is no merge. Source: ['cipher out of date' error (Bitwarden Community)](https://community.bitwarden.com/t/cipher-out-of-date-error-bitwarden-password-manager/86851).
- Bitwarden lite (one container) can use SQLite, MSSQL, PostgreSQL or MySQL/MariaDB; standard installs need MSSQL. `BW_DB_PROVIDER=sqlite` makes `vault.db`. It is "intended for personal use and home-labs" and needs 200 MB of RAM and 1 GB of disk. Source: [Lite Deployment (Bitwarden Help)](https://bitwarden.com/en-gb/help/install-and-deploy-lite.md).

### Vaultwarden

- Vaultwarden is "An alternative server implementation of the Bitwarden Client API, written in Rust", "based upon the Rocket web framework", under AGPL-3.0, and "not associated with Bitwarden". A reverse proxy is advised, because the web vault needs HTTPS. Source: [dani-garcia/vaultwarden README (GitHub)](https://github.com/dani-garcia/vaultwarden).
- It builds with the Cargo features `sqlite`, `mysql` and `postgresql`; `cargo build --features sqlite --release` gives one binary. Source: [Vaultwarden wiki: Building binary](https://github.com/dani-garcia/vaultwarden/wiki/Building-binary).
- Nearly all state is in `db.sqlite3`. Attachments are separate files, and `rsa_key*` files sign the login tokens. Backups use the SQLite `.backup` command (the Online Backup API) or `VACUUM INTO`; a built-in `vaultwarden backup` exists since 1.32.1. Source: [Vaultwarden wiki: Backing up your vault](https://github.com/dani-garcia/vaultwarden/wiki/Backing-up-your-vault).
- Live changes go over a WebSocket at `/notifications/hub`, on by default since 1.29.0. Phone clients use push through credentials from Bitwarden's cloud. Source: [Vaultwarden wiki: Enabling WebSocket notifications](https://github.com/dani-garcia/vaultwarden/wiki/Enabling-WebSocket-notifications).
- CVE-2024-39925: in Vaultwarden 1.30.3, a member who left an organization kept the organization key. Source: [CVE-2024-39925 record](https://cveawg.mitre.org/api/cve/CVE-2024-39925).

### Standard Notes

- The server is "a dumb data-store". Each item has a random key and XChaCha20-Poly1305 content, with the item id and version bound as authenticated data. Item keys are encrypted under the root key. Source: [Standard Notes encryption whitepaper](https://standardnotes.com/help/security/encryption).
- Argon2id (64 MiB, 5 iterations, 512-bit output) runs on the client, and the result is split. The first half (the master key) is "never revealed to the server". The second half (the server password) is sent at registration and at every sign-in. Our reading: the server so receives a value made from the password, which it could test guesses against at Argon2 cost. Source: [Standard Notes encryption whitepaper](https://standardnotes.com/help/security/encryption).
- Sync sends the `sync_token` of the last call and pages with `cursor_token`. Conflicts come back as `sync_conflict` or `uuid_conflict`, each with the unsaved and the server item. In the official server, `sync_token` is the time of the last sync. (Secondary source: the author of a Rust server for this protocol, Rocket plus SQLite.) Source: [Standard Notes Sync Protocol, and SFRS, a Rust implementation (typeblog)](https://en.typeblog.net/56eb/standard-notes-sync-protocol-and-sfrs-a-rust-implementation).
- "Our server cannot read your note contents", so the app resolves a conflict itself, mostly by making a copy of the note. Source: [How do I clear duplicates? (Standard Notes Help)](https://standardnotes.com/help/33/how-do-i-clear-duplicates).
- The self-hosted server is Docker only, on Linux: an API gateway, a syncing server and worker, auth and its worker, a database and a Redis cache; about 570 MB of RAM in use. Source: [Getting started with self-hosting (Standard Notes Help)](https://standardnotes.com/help/self-hosting/getting-started).

### Enpass

- Enpass uses "a client-side merge sync algorithm". A device downloads the changed encrypted vault, opens it, merges, and uploads only if it has its own changes. Conflicts are resolved on the device, and the cloud is "a dumb drive". Back ends include OneDrive, Google Drive, Dropbox, iCloud, Nextcloud, WebDAV, network folders and Wi-Fi sync. Source: [Enpass Security Whitepaper v1.4](https://dl.enpass.io/docs/whitepaper/enpass-security-whitepaper.pdf), pages 6 and 7.
- The Wi-Fi sync server is "a small WebDAV file server" with a self-signed certificate and a random access password per vault. Both devices show a time-based code; if the codes differ, the user stops (a possible man in the middle). Source: the same whitepaper, printed page 33.
- A vault is a plain metadata file for sync plus an encrypted database. Attachments over 1 KB are separate encrypted files, so large files do not grow the main database. Source: the same whitepaper, page 3.

## 2. Conditional writes and file servers

- RFC 9110 section 13.1.1: If-Match is used "to prevent accidental overwrites when multiple user agents might be acting in parallel" (the lost update problem). The server must use the strong ETag compare and may answer 412 when the condition fails. Source: [RFC 9110: HTTP Semantics](https://www.rfc-editor.org/rfc/rfc9110.html).
- RFC 6585: 428 Precondition Required means "the origin server requires the request to be conditional"; 429 Too Many Requests is for rate limits. Source: [RFC 6585: Additional HTTP Status Codes](https://www.rfc-editor.org/rfc/rfc6585.html).
- RFC 4918 (WebDAV) section 7.2: clients avoid overwriting others' changes "using entity tags in If-Match headers with any requests that would modify resources". Locks are the other way. Source: [RFC 4918: HTTP Extensions for WebDAV](https://www.rfc-editor.org/rfc/rfc4918.html).
- Not every WebDAV server honours If-Match: Go's `x/net/webdav` PUT ignores If-Match and If-Unmodified-Since, so a stale PUT got 201, not 412. The issue is still open. Source: [golang/go #44492](https://github.com/golang/go/issues/44492).
- The Nextcloud desktop client added If-Match with the base ETag on single-file uploads on 2026-07-17, so a conflicting write gets 412 "instead of clobbering". Chunked uploads are not covered yet. Source: [nextcloud/desktop PR #10394](https://github.com/nextcloud/desktop/pull/10394).
- SUNDR (fork consistency): a dishonest server can make one user miss another's change, but "either user will detect the attack upon seeing a subsequent operation by the other", so the server must keep the two views forked; "Once two honest users sign incompatible histories, they cannot see each others' subsequent operations without detecting the problem." Source: [Li, Krohn, Mazières, Shasha: Secure Untrusted Data Repository (SUNDR), OSDI 2004 (paper PDF)](https://www.usenix.org/legacy/event/osdi04/tech/full_papers/li_j/li_j.pdf), section 2.

## 3. Cloud folders on macOS

- TN3150: a dataless file holds only metadata, and the system fetches its contents when it is read. That can hang an app, give ETIMEDOUT or get it killed by the watchdog. Apps should check `SF_DATALESS` in `st_flags`, or turn fetching off per thread with `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, …, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)` and handle EDEADLK, and read contents off the main thread. Source: [TN3150: Getting ready for dataless files (Apple)](https://developer.apple.com/tutorials/data/documentation/technotes/tn3150-getting-ready-for-data-less-files.md).
- File Provider: opening a dataless file makes the system fetch it. The system may make a file dataless again to free disk space, but "won't convert a materialized item into a dataless item if the item has pending changes". Source: [Synchronizing the File Provider Extension (Apple)](https://developer.apple.com/tutorials/data/documentation/fileprovider/synchronizing-the-file-provider-extension.md).
- NSFileCoordinator "coordinates the reading and writing of files and directories among multiple processes". Use one per file operation and per thread. Source: [NSFileCoordinator (Apple Developer Documentation)](https://developer.apple.com/tutorials/data/documentation/foundation/nsfilecoordinator.md).
- File presenters "are not notified about changes made directly using low-level read and write calls to the file. Only changes that go through a file coordinator result in notifications." Source: [NSFilePresenter (Apple Developer Documentation)](https://developer.apple.com/documentation/foundation/nsfilepresenter).
- Blocking file calls on iCloud Drive, other file providers, USB disks or SMB take an "indeterminate" time. Apple advises no file I/O on the main thread, and `coordinate(with:queue:byAccessor:)` on a background queue. Source: [Improving performance and stability when accessing the file system (Apple)](https://developer.apple.com/tutorials/data/documentation/foundation/improving-performance-and-stability-when-accessing-the-file-system.md).
- NSFileVersion: when two computers save a cloud file at once, one version becomes current and the others are marked as conflicts, to be resolved "as soon as possible". The API has `unresolvedConflictVersionsOfItem(at:)`, `isResolved`, `removeOtherVersionsOfItem(at:)` and `localizedNameOfSavingComputer`. Source: [NSFileVersion (Apple Developer Documentation)](https://developer.apple.com/tutorials/data/documentation/foundation/nsfileversion.md).
- `startDownloadingUbiquitousItem(at:)` starts the download of a cloud item that is not on the Mac; its state is in `NSMetadataUbiquitousItemDownloadingStatusKey`. Source: [startDownloadingUbiquitousItem(at:) (Apple)](https://developer.apple.com/tutorials/data/documentation/foundation/filemanager/startdownloadingubiquitousitem(at:).md).
- Dropbox makes a "conflicted copy" when edits cannot be joined: two people at once, offline edits, or an automatic save on another computer. The copy's name gets the editor's name, "conflicted copy" and the date. Source: [Conflicted copies (Dropbox Help)](https://help.dropbox.com/organize/conflicted-copy).
- Dropbox on File Provider lives in `~/Library/CloudStorage`. Files not marked "available offline" may become online-only when disk space is low. Source: [Expected changes with Dropbox on File Provider (Dropbox Help)](https://help.dropbox.com/installs/macos-support-for-expected-changes).
- OneDrive can make a copy of a file with the computer's name added to the file name. Source: [Duplicate files in OneDrive (Microsoft Support)](https://support.microsoft.com/en-us/onedrive/duplicate-files-in-onedrive).
- (Secondary, vendor page.) On a macOS WebDAV mount, `flock` succeeds but locks only on this Mac, and the WebDAV client caches folder listings for a few seconds. Source: [Telnyx CloudFS: serve (vendor documentation)](https://developers.telnyx.com/docs/edge-compute/cloudfs/serve).

## 4. Signing in without giving the server a password

- RFC 2945, SRP (September 2000, Standards Track): a stolen password database still forces "an expensive dictionary search". Source: [RFC 2945](https://www.rfc-editor.org/rfc/rfc2945.html).
- RFC 5054 (SRP for TLS, Informational) section 3.3: an attacker who gets a verifier can "attempt a dictionary attack to recover that user's password". Source: [RFC 5054](https://www.rfc-editor.org/rfc/rfc5054.html).
- The large commercial password manager uses SRP, but derives the SRP secret from the account password plus a device-held Secret Key. It says the verifier "can be used in password cracking attempts", and that the second secret "makes it impossible to launch such a cracking attack without also having the user's Secret Key". Source: [its security white paper, Appendix B: Secure Remote Password](https://agilebits.github.io/security-design/srp.html).
- In that design the Secret Key is a 128-bit random value made and kept on the user's devices, and printed on an Emergency Kit. "On its own, a PAKE would still leave something crackable on the server." Sources: [chapter 4: A modern approach to authentication](https://agilebits.github.io/security-design/modernauth.html); [Account password and Secret Key](https://agilebits.github.io/security-design/apsk.html).
- In that design the account unlock key is PBKDF2-HMAC-SHA256 (650,000 iterations) over the password, XORed with HKDF over the Secret Key. Source: [A deeper look at keys](https://agilebits.github.io/security-design/deepKeys.html).
- Proton signs in with SRP inside certificate-checked TLS; an active attacker gets one password guess per sign-in attempt. Source: [Encrypted email authentication (Proton blog)](https://proton.me/blog/encrypted-email-authentication).
- RFC 9807, OPAQUE (July 2025, Informational, IRTF CFRG): the server never learns the password, even at registration. But section 10.11: "a corrupted server can run an exhaustive offline dictionary attack to validate guesses for the client's password; this is inevitable in any (single-server) aPAKE protocol". Source: [RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html).
- opaque-ke 4.0.1 implements RFC 9807. "This library was audited by NCC Group in June of 2021", at an early version; no audit of 4.x is stated. Source: [opaque-ke README (docs.rs)](https://docs.rs/crate/opaque-ke/latest/source/README.md). Its 4.x line depends on digest 0.10, hkdf 0.12, hmac 0.12, curve25519-dalek 4 and argon2 0.5: the older RustCrypto generation. Source: [opaque-ke 4.1.0-pre.2 Cargo.toml (docs.rs)](https://docs.rs/crate/opaque-ke/4.1.0-pre.2/source/Cargo.toml.orig). The NCC review was two consultants over 15 days in June 2021. Source: [Public Report: WhatsApp opaque-ke Cryptographic Implementation Review (NCC Group)](https://www.nccgroup.com/research-blog/public-report-whatsapp-opaque-ke-cryptographic-implementation-review/).
- The `srp` crate 0.6.0: "This crate has never received an independent third party audit for security and correctness. USE AT YOUR OWN RISK!" It uses num-bigint and digest 0.10. Source: [srp 0.6.0 documentation (docs.rs)](https://docs.rs/srp/latest/srp/).
- Web Authentication Level 3 (W3C Recommendation, 25 August 2026): the private key is "expected to never be exposed to any other party", the server stores only the public key, and sign-in is a signed challenge. Source: [Web Authentication Level 3 (W3C)](https://www.w3.org/TR/webauthn-3/).
- The Secure Enclave works only with NIST P-256 keys and cannot import keys. It needs a Mac with Touch Bar and Touch ID, or an Apple silicon Mac. Keys are made with `kSecAttrTokenIDSecureEnclave`, `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` and the `privateKeyUsage` flag. Source: [Protecting keys with the Secure Enclave (Apple)](https://developer.apple.com/tutorials/data/documentation/security/protecting-keys-with-the-secure-enclave.md).
- `security-framework` 3.7.0 (already approved for Larsal) has `Token::SecureEnclave` in its key options, "Only compatible with KeyType::ec()". Source: [security_framework::key::Token (docs.rs)](https://docs.rs/security-framework/3.7.0/security_framework/key/enum.Token.html). Its normal dependencies are bitflags 2.11, core-foundation 0.10, core-foundation-sys 0.8.6, libc and security-framework-sys 2.17 (log is optional). Source: [security-framework 3.7.0 dependencies (crates.io)](https://crates.io/api/v1/crates/security-framework/3.7.0/dependencies).
- TN3137: macOS has a file-based keychain (the login keychain) and the data protection keychain. "macOS builds the list of data protection keychain access groups available to your program from its code signing entitlements"; "These entitlements must be authorized by a provisioning profile", which needs an app-like bundle. "Protecting a key with the Secure Enclave" is one of the features that require the data protection keychain. Source: [TN3137: On Mac keychain APIs and implementations (Apple)](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains).

## 5. How other products share

### Bitwarden

- The organization key comes from a secure random generator and is never stored plain on the server. It is wrapped with RSA-OAEP to each member's public key; to add a member, a confirming member's client fetches the newcomer's public key from the server and wraps the same key to it. Source: [Bitwarden Security Whitepaper](https://bitwarden.com/help/bitwarden-security-white-paper/).
- Sign-in sends a hash made from the master password, which the server hashes again (PBKDF2-SHA256, 600,000 iterations). Source: the same whitepaper.
- Joining is invite, accept, confirm. At confirm the admin checks that the member's fingerprint phrase matches. Email invitations expire after five days. A "Never prompt to verify fingerprint phrases" option exists. Source: [Manage users (Bitwarden Help)](https://bitwarden.com/help/managing-users/). The phrase is five words from the EFF long word list, compared over a second channel. Source: [Fingerprint phrase (Bitwarden Help)](https://bitwarden.com/help/fingerprint-phrase/).
- Roles: Owner ("Only a current owner can invite new owners"; a second owner is advised), Admin, User; custom roles only for Enterprise. Source: [Member roles (Bitwarden Help)](https://bitwarden.com/help/user-types-access-control/). Collection levels include View, View with hidden passwords, Edit and Manage; hidden fields "limit but don't prevent access". Source: [Collection permissions (Bitwarden Help)](https://bitwarden.com/help/collection-permissions/).
- Families organizations "allow six users". Source: [About organizations (Bitwarden Help)](https://bitwarden.com/help/about-organizations/).
- Issue 10 (Low): every member holds the same organization key, so collections are not a crypto boundary. Accepted as "an intentional design choice". Source: [Bitwarden Cryptography Report](https://bitwarden.com/assets/Kki4W785JIPOdFj6EeWB5/dbf51066c1041aa90dc503ca0c911194/2025_Bitwarden_Cryptography_Report.pdf).
- A removed member loses access, but offline devices keep a read-only cached copy for a short time. If misuse is expected, the docs advise changing the credentials the member could see. Source: [Revoke and remove members (Bitwarden Help)](https://bitwarden.com/en-gb/help/remove-users/). Revoking is a temporary removal that can be undone without rejoining. Source: [Revoke access (Bitwarden Help)](https://bitwarden.com/help/revoke-users/).
- Account recovery: at enrolment the user's key is encrypted to the organization's public key; an admin's client unwraps it and wraps it again for a new password. Source: [Bitwarden Security Whitepaper](https://bitwarden.com/help/bitwarden-security-white-paper/).
- Log in with device: the new device sends a public key made for that one request; the approving device encrypts the user key to it after the approver checks a request-specific fingerprint phrase. Requests expire after 15 minutes. Source: [Log in with device (Bitwarden Help)](https://bitwarden.com/help/log-in-with-device/).

### The large commercial password manager

- Each vault "has its own key". To share, the sharer's client encrypts a copy of the vault key to the recipient's public key; the server "never has a copy of the decrypted vault key". The design "does not attempt to verify the identity of an individual". Source: [How vaults are shared](https://agilebits.github.io/security-design/sharedVaults.html).
- Appendix C: a hostile server could give out "dishonest public keys" and get vault keys "with little ability for users to detect or prevent this". It calls key checks "a weak point in public-key cryptography" with "no good solutions to it in general". Source: [Appendix C, Verifying public keys](https://agilebits.github.io/security-design/mitm.html).
- "The server will reject any attempt from a read-only user of a vault to upload data to that vault"; Write is "enforced by the server, not the client". Reveal, export and print are enforced only by the client. Source: [Access control enforcement](https://agilebits.github.io/security-design/access-control.html).
- On removal, a "well behaved client" is told to forget keys and data, but the vendor "can't make Tom forget information that he's already had". Source: [Revoking access](https://agilebits.github.io/security-design/revoke-access.html).
- Recovery: a copy of every vault key is encrypted to the recovery group's public key ("implicit sharing"); in the family plan this is the Organizer role. "Recovery mechanisms are inherently weak points." Source: [Restoring a user's access](https://agilebits.github.io/security-design/restore.html).

### Proton Pass and Apple

- Proton Pass makes a 32-byte random vault key, encrypted and signed with the owner's user key. To invite, the admin's client encrypts the vault key to the recipient's address key; the recipient checks the signature, then encrypts the key again to its own user key. Proton warns about "the distribution of fake public keys". Source: [Proton Pass security model (Proton Blog)](https://proton.me/blog/proton-pass-security-model).
- Apple shared password groups: the owner "is the only person who can add or remove other members"; a removed person "may still have access to the accounts and passwords you shared while they were in the group". Source: [Manage shared passwords and passkeys (Apple)](https://support.apple.com/guide/personal-safety/ips3ce9f6e15/web).
- Apple Family Sharing: one organizer plus up to five other members, six in all. Source: [How Family Sharing works (Apple Support)](https://support.apple.com/en-ae/105062). Proton Pass Family is for up to 6 people. Source: [spec/research/business-model.md](business-model.md), 4.5.

## 6. What a hostile server can do

All from [Zero Knowledge (About) Encryption: A Comparative Security Analysis of Three Cloud-based Password Managers (Scarlata, Torrisi, Backendal, Paterson; USENIX Security 2026 prepub)](https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf), unless another source is named. The study assumes a fully hostile server and finds 12 attacks on Bitwarden, 7 on LastPass and 6 on Dashlane.

- **BW01, automatic enrolment:** when a user accepts an invite, the server swaps the organization public key for its own and turns on recovery enrolment. The client then sends the user key encrypted to the attacker. It works even with "an honest invitation from a trusted enterprise or family member", and can spread "in a worm-like fashion".
- **BW02, key rotation:** the new user key is wrapped to an organization key that came from an unauthenticated sync, so the server can supply its own.
- **BW04 to BW07, item-level encryption:** fields encrypted one by one with unauthenticated metadata; for example a server moves a password into the URL field.
- **BW08, organization injection:** nothing binds a vault to its organizations, and "anyone can encrypt a chosen symmetric key under the public key of any user". "The client will silently accept the new organisation at the next sync." **BW09, organization overwrite:** right after a user makes an organization, the server swaps its key; this is "entirely undetectable".
- **LP07 and DL02, sharing key overwrite:** the server sends a recipient public key it controls; recipient keys "are not authenticated in any way" and "no key transparency is implemented". LP01: admin keys for password reset are fetched without a check.
- **The fixes (section 5.1):**
  - Public key authentication: keep known public keys after an (optional) out-of-band check, or use a CA "not under the control of the same entity that controls the password manager's server". This fixes the sharing attacks BW09, LP07 and DL02. With it, "assuming that a correctly signed list of admins is published", BW01, BW03 and LP01 are fixed too.
  - Ciphertext authentication: "By signing plaintexts before encryption, clients can verify that the user themself is the sender" (signcryption). This fixes BW02, BW08 and BW03.
  - Both together are needed for keys sent by other users, such as invites: BW01, BW09 and LP01.
- **Rollback:** "complete roll-back of vaults cannot be ruled out without outsourcing versioning information to a trusted third party or local cryptographic state" (section 6).
- **Vendor answers:** key rotation now has fingerprint checks, and "Transparent signing of organization and emergency access keys is under active development". Organization key injection (Issue 5) is "Accepted, and under active development". Source: [Bitwarden Cryptography Report](https://bitwarden.com/assets/Kki4W785JIPOdFj6EeWB5/dbf51066c1041aa90dc503ca0c911194/2025_Bitwarden_Cryptography_Report.pdf).

## 7. Building blocks for sharing keys and the code two people compare

### Wrapping a key to a person

- RFC 9180, HPKE: modes base, psk, auth and auth_psk. "In the Base mode, there is no authentication of the remote party at all." Auth mode is "vulnerable to key-compromise impersonation"; the RFC suggests signing the (enc, ct) pair with the sender's key. `info` can "fold in identity information" and should carry identities to avoid misbinding. Suite ids: DHKEM(X25519, HKDF-SHA256) 0x0020, HKDF-SHA256 0x0001, AES-256-GCM 0x0002, ChaCha20Poly1305 0x0003. Single-shot Seal and Open. Source: [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html).
- RFC 9180 Appendix A has no vector for X25519 with AES-256-GCM: A.1 is X25519 with AES-128-GCM, A.2 is X25519 with ChaCha20Poly1305, A.3 to A.7 use other suites. Source: [RFC 9180, Appendix A](https://www.rfc-editor.org/rfc/rfc9180.html). The JSON file the RFC names as [TestVectors] has base-mode (mode 0) records for kem_id 32, kdf_id 1, aead_id 2, our suite. ## 10. Design picks

Each pick says what, why, and its sources. The lead took P1 to P24 in LD-263 (rule 9), with P2 in LD-265, the key change of P3 in LD-264, and the order, version and limit rulings in LD-266; LD-267 gives "same vault" one meaning (P2, P3), adds the cloud-folder rollback guard (P18 (6)) and fixes the server's old versions and size cap (P15). P20 to P24 carry the numbers LD-263 gives them; the test pick is P25.

**P1 The server stores locked vault files, not items.** Each vault is one opaque encrypted file with a version number. Larsal downloads it, merges with MOD-11, and uploads with If-Match.
- Why: the vault format does not change; the merge exists and passed 1,000 random cases (E4-S12); the server sees only ids, sizes, times and IPs, never item counts, types or item times; the item-level attack class BW04 to BW07 cannot happen; it is the client-merge model Enpass runs with a dumb drive (section 1). Per-item storage (Bitwarden, Standard Notes) needs a new format and still refuses stale saves or makes duplicates (section 1).
- Ceiling: every save uploads the whole file. Uploads are debounced. Split attachments out (the Enpass pattern) only if measured sizes call for it.

**P2 Deleted entries stay deleted (LD-265, LD-267 (2)).** Every same-vault merge (change on disk, conflict copy, server sync) runs the deletion pass of FMT-15.11 over the whole vault. Share imports and the import wizard still never apply deletions.
- One meaning of "same vault" for every same-vault rule: the deletion pass, the metadata and the key (LD-267 (2), an addendum to LD-264 and LD-265). A copy is the same vault when it has the same root group id and opens with this vault's key, or with credentials the user gave for that copy (MOD-11.29). The key, or the user's own credentials, is the proof; the id alone is not.
- Except a copy under a key this Mac retired (its own credential change, or a key it replaced in an earlier merge): it gets the content merge only, never its key and never its deletions, and Larsal says the copy uses a replaced password. Each Mac keeps, in local state never synced (as P4), a salted SHA-256 of each transformed key it retired. Every save writes a fresh KDF seed (FMT-04.17), so a copy saved again under the retired password has another transformed key; each record therefore also keeps the KDF settings and seed its key was made with, and Larsal runs the credentials given for a copy through them to compare. Otherwise LD-264's newer key stands (P3).
- Why: only a key holder can make a copy that opens with the vault's key, so its deletions are the user's own. Without the pass, every stale Mac brings deleted entries back through the cloud folder or the server (section 9, Larsal today; [business-model.md](business-model.md) section 6.2). This blocks E15 and the E16 client. It goes further than the reference app, so it needs a parity note.
- Why the exception: a password change often follows a leak, so a copy under the replaced password must not bring that password back or delete entries. The honest case still converges, because each Mac keeps its own deleted-objects list: a deletion B made under the old key reaches every copy after B's next sync (LD-267 (2); only local state stops a rollback, section 6).
- The texts that said the opposite change with it (E15-S1): FMT-15.10, MOD-11.15, the MOD-11 notes "No lost data" and SI-09, and FMT-15's security notes. SD-03 and AT-I05 now read: "a merge keeps every entry of both sides, except an entry that the same vault's deleted-objects list removed after its last change (FMT-15.11, LD-265)". E15-S1 writes the one meaning above into MOD-11's Notation, and E16-S1's MOD-11.19 edit uses it, so MOD-11 holds one definition.

**P3 The sync protocol is plain HTTPS with conditional writes.**
- `GET /v1/vaults` lists `{id, version, size}` (the cheap poll, like Bitwarden's revision date). `GET /v1/vaults/{id}` returns the bytes with an ETag, and 304 to If-None-Match. `PUT /v1/vaults/{id}` needs If-Match, or `If-None-Match: *` to create a new vault (RFC 9110): neither gives 428, a stale ETag gives 412, an over-cap body gives 413, a role without write gives 403, no session gives 401, too many calls give 429 (RFC 9110, RFC 6585).
- Client loop: download, open, merge the local copy into the server copy (the server copy is the target, as in APP-05.27 Merge), safe-save locally, then PUT with If-Match. On 412: retry at most 3 times with jitter, then show an error.
- A key change (a new master password or key file), by LD-264, which changes LD-60 for sync. In server sync and in a cloud-folder merge the other side is the same vault (P2, LD-267 (2)) when it has the same root group id and opens with this vault's key or with credentials the user gave for that copy. The result takes the newer of the two keys (the vault's own key-change time), as the merge after a change on disk already does; a copy under a key this Mac retired never gives its key or its deletions (P2). A share import and the import wizard never take a key. When the server copy does not open with this Mac's key, Larsal asks for the credentials that copy opens with (MOD-11.29, APP-05.29), never "the new" ones, and uploads nothing until it opens. The key-file part of P7 stays in the key.
- The case that needs this wording: Mac A changes the password while Mac B uploads an edit under the old one. The server copy then opens only with the old password, so A asks for it, merges, and the result keeps both edits and A's newer key. The old password is a key A retired, so A takes the content only, none of B's deletions, and says the copy uses a replaced password. B then asks for the new password; its merge runs the deletion pass with B's own deleted-objects list, so a deletion B made under the old key is deleted everywhere after B's next sync (LD-267 (2)).
- E16-S1 edits MOD-11.19 limit 2, the AT-A09 note and T55 (a new case (d)) to say this, with the meaning of "same vault" that E15-S1 writes (P2); E15-S2 builds it in larsal-core's merge. E16-S7b (server) and E15-S4 (cloud folder) check the case above, and a third case: a planted copy under A's old password with a key-change time in the future neither brings the old key back nor deletes anything on A (LD-267 (2)).
- Why: without it, a password change on one Mac is undone by the next upload from another, and the old password opens the vault again (LD-264). A server without the key cannot make a copy that opens, so taking the newer key gives it no new power.
- When: on unlock, after a save (debounced), every 60 seconds while unlocked, and on Sync now (Bitwarden's rhythm, [business-model.md](business-model.md) 3.4). No push channel now: push to Macs needs APNs and the paid Apple account.

**P4 Rollback guard on each Mac.** Per server vault, Larsal keeps in local state (never synced): the highest version seen, the SHA-256 of the last synced bytes, the key epoch and, for shared vaults, the highest member-list sequence number and its hash. It refuses anything older and warns.
- Why: only local state or a trusted third party stops a full rollback (section 6).
- Known limit (LD-266 (4), narrowed by LD-290 (3)): a client refuses a member-list fork it sees (P9) and an upload made on another branch (SHR-02.12); a server that also keeps the vault apart is found only by the list-code compare (SHR-02.13; SUNDR, section 2). See section 12.
- Upload signatures (P11) need the identity key, which comes with the account (P6, E17-S1). So PUT signing of personal vaults starts in E17-S1; before that, the E16 client relies on this version and hash guard alone.

**P5 Sign-in uses device keys and a signed challenge. No password goes to the server, in any form.**
- Each Mac has a P-256 sign-in key in the Secure Enclave (the only curve it supports), made through the approved `security-framework`, this device only. Macs without a Secure Enclave use a software P-256 key in the data protection keychain, this device only.
- Before W-02: the data protection keychain and the Secure Enclave need keychain access groups from code-signing entitlements authorized by a provisioning profile (TN3137, section 4), so unsigned test binaries cannot use them. Until W-02 gives the entitlement: cargo tests use a software key behind a test seam (in memory, never written); the app keeps a software key in the login keychain (the file-based keychain). The this-device-only checks stay open until W-02.
- Sign-in: the server sends a one-time nonce; the Mac signs a fixed label, the server origin, the nonce and the device id; the server checks it with the stored public key. The session token is 32 random bytes; the server stores only its SHA-256 and enforces idle and absolute expiry (OWASP). No refresh tokens: signing again is cheap.
- Why: SRP and OPAQUE both leave a record that a corrupted server can attack offline (RFC 5054 section 3.3, RFC 9807 section 10.11). The large commercial password manager closes that hole only by adding a 128-bit Secret Key. Larsal's vaults never depend on the server, so sign-in needs no password at all; device keys are the WebAuthn pattern (section 4). The `srp` crate is unaudited, and opaque-ke uses the older crypto generation.

**P6 Account keys: two secrets, the account password stays on the Mac.**
- Sign-up makes, on the Mac: a random 256-bit account secret; an Ed25519 identity key (signs); an X25519 key (receives wrapped keys), signed by the identity key.
- The private keys are wrapped with AES-256-GCM under a key made from the account password (Argon2id, on the Mac only) combined with the account secret through HKDF. The wrapped blob is stored on the server. Without the 256-bit secret, nobody can test password guesses against it.
- The Recovery Kit is the account secret, printed or saved once. From it, HKDF also makes an Ed25519 recovery sign-in key; the server stores only its public key.
- A new Mac gets the account in one of two ways: (1) an existing Mac approves it after both screens show the same code (P10), then seals the account secret to the new Mac (HPKE) and signs its device key; or (2) the Recovery Kit plus the account password. Either way the account password is typed on the new Mac.
- No email in this first build: an account is a random id plus public keys (Threema's pattern, section 7). Invites work by invite code (P10). Email comes with billing (E17, later), with the NIST and OWASP code rules of section 8.
- Why: this is the two-secret design of the large commercial password manager (section 4) without its SRP, since sign-in needs no password (P5). No email means less personal data on the server and no address enumeration; email is never a sign-in factor anyway (NIST, section 8).

**P7 A personal vault on the server gets a second secret.** When a vault is added to the server, Larsal adds a random 32-byte key-file part (FMT-04.3) to its key, through the existing credential change. The master password stays. The part is wrapped (HPKE) to the owner's own X25519 key and stored on the server beside the vault, so every Mac of the account gets it; it is also kept on the Mac in the device store of P5 (the Keychain, this device only, once W-02 is answered). The vault still opens elsewhere with the password plus the key file, which Larsal can export.
- A vault that already has a key file keeps it: FMT-04.5 has one key-file slot, so Larsal adds no second part. Larsal wraps that file's F (the output of FMT-18) to the account key in the same way, and the server copy is again not guessable from the master password.
- Why: nothing on the server may be guessable from a master password (business-model.md 3, "What this means for Larsal"). It is the second-secret idea with no format change.

**P8 One random key per shared vault, wrapped with HPKE and signed.**
- A shared vault is an ordinary Larsal vault keyed only by one random 32-byte key-file part (FMT-04.3, FMT-04.5). A family gets one default shared vault; a team can have many.
- The key is wrapped to each member with HPKE base mode, suite DHKEM(X25519, HKDF-SHA256) 0x0020, HKDF-SHA256 0x0001, AES-256-GCM 0x0002. `info` = a version label, group id, vault id, key epoch and recipient member id. The admin signs (suite, enc, ct, info) with the Ed25519 identity key.
- Why: one key per vault is a real crypto boundary (Bitwarden's accepted Issue 10 is the opposite); HPKE binds context through `info`, has test vectors, and the `hpke` crate is on Larsal's crypto generation; RFC 9180 and the ETH paper both advise signing the wrap (sections 6 and 7). The signed wrap is the paper's ciphertext authentication, which fixes BW02 and BW08 (section 6). Not `crypto_box`: no stable release on Larsal's generation, not vendored, and sealed boxes cannot bind context.
- Not now: post-quantum suites (X-Wing). The suite id in the wrap record lets it change later.

**P9 A signed, hash-chained member list per group.** Each entry holds a sequence number, the previous entry's hash, the action (add, remove, role change), the member's identity and X25519 keys, the role and the signer. The creator signs the first entry. A client accepts an entry only if its signer was an owner or admin in the state before it, and keeps the last sequence number and hash it saw (P4), so it refuses a rollback or a fork it sees. The server stores the list, checks the same rules, and takes its role table from it; it cannot write a valid entry.
- Why: it is the paper's "correctly signed list of admins", which, with authenticated public keys (P10), fixes BW01, BW03 and LP01 (ETH paper section 5.1; section 6 here). The other attacks are covered by the other picks: BW09, LP07 and DL02 by the code compare and pinned keys (P10); BW02 and BW08 by the signed wraps (P8). P8, P9 and P10 together cover all six.

**P10 Invites and the code two people compare.**
- An invite is a one-time invite code (128 random bits, in a link), valid 5 days (Bitwarden's email invites, section 5), sent by the inviter through any channel. It carries no key.
- Then both Macs run commit-then-reveal: the invitee's Mac first sends a hash commitment over its identity keys and a random nonce; the inviter's Mac sends its keys and nonce; the invitee reveals. Both screens then show the same 6-digit code, made with SHA-256 over both identity keys, the group id and both nonces. The two people compare it (in person or on a call). An attacker gets one guess, 1 in 10^6 (the ZRTP pattern, section 7).
- Only after "Codes match" does the admin sign the add entry and wrap the key. Both sides pin each other's identity key. A changed pinned key shows a loud warning and needs a new compare.
- The same compare approves a new Mac of one's own account (P6), as Bitwarden's login with device does with a phrase (section 5).
- Why: the compare and the pinned keys are the paper's public key authentication (an out-of-band check, then stored keys), which fixes BW09, LP07 and DL02 (ETH paper section 5.1; section 6 here). A short code is enough only with the commitment; a 60-digit number (Signal, WhatsApp) needs no protocol state but is long. Users seldom compare long numbers (the commercial manager's Appendix C, section 5).

**P11 Roles.**
- Family (AGPL core): Organizer (up to 2, so a lost account cannot freeze the list) and Member; at most 6 people (Apple, Bitwarden and Proton all use 6); everyone can edit.
- Team (the paid folder): Owner, Admin, Member, Read-only, plus per vault Can view, Can edit, Can manage. No "hidden password" levels: Bitwarden itself says they limit but do not prevent access.
- Reading is enforced by crypto (holding the vault key). Writing is enforced twice: the server refuses uploads (403), and every client checks that each uploaded version is signed (Ed25519, over vault id, version and SHA-256 of the bytes) by a member whose role allows editing. The screen says plainly that a read-only member can copy anything they can see.

**P12 Removing a member.** An admin signs a remove entry, which starts a new key epoch. The admin's Mac makes a new vault key, saves the shared vault with it through the existing credential change, wraps it to the remaining members and uploads with If-Match. Larsal shows "Passwords <name> could see": every entry in the vault at removal (with history, attachments and the recycle bin), each with a tick the user sets once it is changed. Entries deleted for good after the person joined show as one line with their count and dates (for example, "3 items deleted for good since <name> joined; Larsal can no longer name them"), because the deleted-objects list keeps only an id and a deletion time (FMT-15.1). Larsal says the truth: the removed person keeps every copy they had, and only a new password at the website protects. The server also deletes their wrapped keys and open invites, and answers them 403 on the group's routes (SHR-04.5), as a second line only.
- Why: MLS's new epoch on removal (section 7); Bitwarden, the commercial manager and Apple all say a removed person keeps what they saw (section 5); Vaultwarden's CVE-2024-39925 is what happens without a new key.

**P13 No admin reset and no key escrow in the first build.** BW01, BW02, BW03 and LP01 all come from escrow plus unchecked keys (section 6). A person recovers with their Recovery Kit or their other Mac. A lost account loses no shared data: the others still hold the vault key and invite the new account again. Local vaults still open with their master password.

**P14 The server stack: hyper on tokio, rustls with ring, SQLite.** One binary `larsal-server`: hyper 1 (http1, server), hyper-util (tokio, server, http1), http-body-util (body size limits), tokio (rt, net, time, sync), tokio-rustls (no default features; ring, so no aws-lc), rustls's server side (already in the tree) and rusqlite (bundled SQLite). JSON uses Larsal's own `json.rs`. It listens on 127.0.0.1 by default.
- No axum: about a dozen routes fit in one match, and axum adds tower, matchit, mime, sync_wrapper and serde (section 9). Not hand-written HTTP over `std` and `httparse`: Larsal would own HTTP framing on a server that will one day face the internet, and rule 9 says to use the proven standard. hyper is what Rocket (Vaultwarden) and axum (Atuin) are built on.
- tokio's current-thread runtime (`rt`) with `spawn_blocking` for SQLite and file work; SQLite has one writer anyway.

**P15 Server storage.** SQLite in WAL mode with `synchronous=FULL` holds accounts, devices, sessions, vault rows (id, version, size, blob hash, uploader signature), member lists and invites. Vault bytes are content-addressed files: written to a temp file, flushed with `F_FULLFSYNC`, renamed (Larsal's safe-save pattern); the vault row then moves with a compare-and-swap `UPDATE … WHERE version = ?`. An orphan sweep runs at start. 5 old versions are kept for restore only; the merge needs no base. The size cap is Larsal's vault limit, FMT-01.31's 1,140,850,688 bytes (LD-263 (13), LD-267 (7)). Backup is the SQLite online backup plus the blob folder (Vaultwarden practice).
- Why files: Larsal's vault limit is above SQLite's BLOB default, and files are faster for large data (section 9).

**P16 The server provably cannot open a vault.** A check fails when `larsal-server`'s `cargo tree` holds `larsal-format`, `larsal-core`, `larsal-platform`, `larsal-ffi` or `larsal-sync`. larsal-format is the only code that reads a vault file. Sync is an additive `sync` cargo feature next to `net`, so the no-network build (SN-05) remains.

**P17 TLS for the demo on this Mac.** At first start the server makes a self-signed certificate (rcgen, already in the tree for tests) and prints its SHA-256 fingerprint. When the user adds the server, Larsal shows the fingerprint, the user compares it, and Larsal pins it (the Enpass Wi-Fi sync code is the precedent, section 1). That needs a pinned-certificate path in `net.rs` next to macOS trust, reviewed under SN-03. A hosted server later uses a CA certificate and plain macOS trust.

**P18 Cloud folders (E15).**
1. Swift wraps the unlock read, the reload read and the pre-save checksum in a coordinated read, and the save's temp-file rename in a coordinated write (`.forReplacing`), on a background queue, with the Rust I/O inside the accessor. kqueue and the 30-second check stay (LD-216).
2. Before a read, Larsal tests `SF_DATALESS` (`stat` `st_flags`, through libc, already in the tree). If set, the vault shows "Still downloading" and Larsal calls `startDownloadingUbiquitousItem`, or lets the coordinated read fetch it off the main thread. The 30-second check may turn fetching off on its thread and treat EDEADLK as "no change".
3. Conflict copies: for iCloud, `NSFileVersion.unresolvedConflictVersionsOfItem`, a MOD-11 merge of each, then `isResolved` and `removeOtherVersionsOfItem`. For other clouds: sibling files in the vault's folder with the same extension whose name starts with the vault's base name, that open with the current key and have the same root group id (P2, LD-265); Larsal merges them, then moves each copy to the Trash after the user says OK. A sibling that does not open with the current key is listed as needing its own password; once the user gives the credentials it opens with (MOD-11.29) and its root group id matches, it merges, and the result keeps the key P3 picks (LD-264); a copy under a key this Mac retired gets the content merge only (P2, LD-267 (2)). The finder never lists Larsal's own files: the backup path that APP-05.20 makes for this vault (default `{FILE_NAME}.old.larsalvault`, on by default) and Larsal's temp files (APP-05.11). Without this rule the backup, a same-vault copy that opens with the current key, would be merged and offered for the Trash, and the user would lose the safety copy. Names alone are not trusted: Dropbox and OneDrive name copies differently, and Google Drive's pattern is not confirmed (section 3).
4. APP-05.10 says plainly that `flock` covers one Mac only; across Macs the cloud's conflict copy is the signal.
5. A Finder-mounted WebDAV share is a network folder (the 30-second check covers it). No direct WebDAV client now. If one comes later, it reuses the E16 client and first probes with a wrong ETag, expecting 412, because some servers ignore If-Match (section 2).
6. Rollback guard for cloud-folder vaults (LD-267 (3)). For each vault in a cloud or network folder, Larsal keeps in local state never synced (as P4) the newest change time it has seen in that vault and the SHA-256 of the last bytes it read or wrote. A disk version that is older is never reloaded silently: Larsal merges it as a same-vault copy (P2), so nothing newer and no deletion is lost, and warns that the file went back in time. E15-S1 writes this into APP-05.26; E15-S4 builds and checks it.
   - Why: by APP-05.26 a vault with no unsaved changes reloads a changed file silently. An older copy put back by a cloud service, a hostile folder or a stale Mac that chose Overwrite (APP-05.28) would then drop newer entries and raised KDF settings, and the next save spreads that to every Mac. A rollback with no conflict copy never reaches the finder of item 3. Only local state stops a full rollback (ETH paper section 6, quoted in section 6 here; [business-model.md](business-model.md) section 3, "Guard against rollback").

**P19 Licences and folders.** `larsal-proto` and `larsal-sync` are part of the Mac app: GPL-3.0-or-later. `larsal-server` is AGPL-3.0 and links `larsal-proto` (the GNU FAQ allows linking GPLv3 and AGPLv3 code, section 9). The team features live in one folder only, `crates/larsal-server-teams/`, under Larsal's own paid team license, linked into `larsal-server` only through the cargo feature `teams` (Bitwarden's `bitwarden_license` folder and `OSS` build, section 9). The build without `teams` is the full AGPL server for families. The Mac app holds no paid code. E14-S2 writes the licence texts.
- The `teams` build links paid-licence code into an AGPL binary. That is lawful only for whoever holds the rights to all of it. So, as for Bitwarden, it rests on Larsal's contributor agreement (LD-262 (3)): every GPL and AGPL line in `larsal-server`'s tree must be covered by it. Outside crates stay permissive (the deny.toml allowlist), so they add no copyleft.

**P20 Two rule exceptions, recorded the LD-220 (2) way (LD-263 (18)).** (a) `larsal-server` holds the server's own network code; Rust rule 12 names only the client's `net.rs`. (b) Its TLS (tokio-rustls, rustls, ring, and rcgen for the TLS certificate and key only) imports crypto outside larsal-crypto and draws TLS randoms through ring (AGENTS.md rule 3, Rust rule 7). Session tokens, nonces and invite codes still come from `larsal-crypto::random`.
- Why: a TLS server needs its own listener and the TLS library's own randoms, as `net.rs` already does for the client (LD-220 (2)); nothing that Larsal's protocol makes depends on them.

**P21 New crates and their versions (LD-263 (19), LD-266 (5)).** Each crate of section 11 gets an AT-J03 review, a line in the approved table and Larsal's own copy in `vendor/` (LD-221). The plan fixes no version: the vendoring story takes the newest release that is at least 14 days old on its start day, and confirms the feature names on that version.
- Why: a release that has been public for two weeks has had time for a yank or an advisory (the Chromium rule, section 9); a version written into a plan ages before the story starts.

**P22 SQLite is built from its bundled source (LD-263 (19)).** `libsqlite3-sys` with `bundled`, not macOS's own SQLite.
- Why: every host builds the same SQLite, E19 needs it on Linux, and gate G1 reads only our tree. Source: [libsqlite3-sys Cargo.toml (docs.rs)](https://docs.rs/crate/libsqlite3-sys/latest/source/Cargo.toml.orig).

**P23 KDF cost of a shared vault (LD-263 (20)).** A shared vault keyed only by a random 256-bit part (P8) uses the lowest KDF cost Larsal allows (CRY-02, [FMT-03](../format/FMT-03-kdf-map.md)).
- Why: nobody can guess a random 256-bit key, so a high cost buys nothing, and MOD-11 never lowers KDF settings in a merge, so a high cost could never come down again.

**P24 Two sharing features (LD-263 (21), LD-262 (6)).** E11's shared groups (INT-08, `larsal-share`: one group of your own vault copied to a container file with a share password, no server) and E18's server sharing (`larsal-sync` `share.rs`) stay separate. Neither crate calls the other, and the screens use different words: "a group of your vault, shared as a file" and "a vault shared through your server". E16-S8 shows both side by side.
- Why: they protect different things in different ways (one shared password, against keys per person and a signed member list), so one name for both would mislead. Source: [spec/integrations/INT-08-shared-groups.md](../integrations/INT-08-shared-groups.md).

**P25 Tests on this Mac only (LD-262 (2)).** The server runs in-process on 127.0.0.1:0 with an rcgen certificate and a temp data folder; the client trusts it through `net.rs`'s test anchors. Must pass: two clients race PUTs and both changes survive; a PUT without If-Match gets 428; a rolled-back server version is refused; a crash between the blob write and the commit leaves a consistent store; a revoked device gets 401. A "hostile server" test mode replays BW01, BW02, BW08, BW09, LP07 and DL02 (swapped keys, an injected group, forced enrolment, rolled-back versions), and every one must be refused. Every request parser gets a fuzz target. Demo accounts and vaults only; nothing is hosted.
