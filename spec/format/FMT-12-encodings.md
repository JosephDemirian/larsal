# FMT-12 Encodings: times, booleans, ids, binary data

Status: reviewed
Epics: E3-S6 (the write rules here are also used by E3-S7, the version 3 text times by E3-S8)
Parity rows: SF-08, SD-06, SF-05

## What it does

Every value in the vault's XML document (FMT-10, FMT-11, FMT-13, FMT-14, FMT-15) is text inside an element. This card fixes how each kind of value is turned into that text and back:

- times: the version 4 binary form, the version 3 text form, which forms the reader accepts, the epoch, time zones, out-of-range values;
- booleans: plain, nullable (three states), and attribute booleans;
- integers;
- UUIDs;
- colors;
- base64 binary data;
- text: XML decoding on read, line endings, whitespace, characters XML forbids, escaping and stripping on write;
- the `Protected` attribute, which can sit on any value element.

Larsal's code for this lives in `larsal-format/document/encode.rs`. The rules are the reference's normal (non-strict) reading mode. Its strict mode is used only by its own tests and is not copied.

## Inputs and outputs

- Read: the decoded text of one element (after XML decoding, FMT-12.23), its attributes, and, for protected values, the protected-field stream (FMT-09). Out: a typed value, "invalid" (handled per type below), or a document rejection.
- Write: a typed value. Out: the element text, already escaped for XML.
- Types in `larsal-model`: time = signed 64-bit seconds since 0001-01-01T00:00:00 UTC (`times.rs`); UUID = 16 bytes (`uuid.rs`); boolean; three-state boolean; signed 32-bit integer; color = text; binary = bytes; text = string (protected text uses the secret string type).
- Limits: the text of one element is bounded by `limits.rs` before it is decoded, with the numbers of FMT-08.12 (see Security notes).

## Rules

FMT-12.1 Time model. A time is a signed 64-bit count of seconds since 0001-01-01T00:00:00 UTC. It uses the proleptic Gregorian calendar, every day is 86,400 seconds, and there are no leap seconds. Reference points: 0001-01-01T00:00:00Z = 0; 1970-01-01T00:00:00Z = 62135596800; 9999-12-31T23:59:59Z = 315537897599. Unix time t converts as seconds = t + 62135596800. Times are whole seconds; there is no fraction.

FMT-12.2 Time, binary form (written in version 4). Take the seconds count as 8 bytes, little-endian two's complement, and base64-encode them (FMT-12.21). The result is always 12 characters and ends with `=`. Larsal writes every time in this form, because Larsal writes only version 4 (FMT-16).

FMT-12.3 Time, text form (written by the reference in version 3). `YYYY-MM-DDTHH:MM:SSZ` in UTC: the year has 4 digits with leading zeros, there are no fractional seconds, and it ends with a capital `Z`. For years outside 1 to 9999 the reference writes empty text (observed: seconds 315537897600 and -1 both written as `<X/>`). For a time it read in the text form with an offset or with no zone, the reference's version 3 writer writes the time as read, in that offset or in local time, and adds `Z` when the text does not already end with `Z`: `2010-08-08T17:24:53+02:00` is written `2010-08-08T17:24:53+02:00Z`, and `2010-08-08T17:24:53` (no zone) is written `2010-08-08T17:24:53Z` (both observed; see Edge cases). Larsal reads this form (FMT-12.6). It writes it only if it ever writes version 3, which is not planned.

FMT-12.4 Time, which form on read. The reader does not look at the file version: version 3 and version 4 files may use either form for any time (observed both ways). The form is chosen by the text alone. If the whole text has the strict base64 shape, it is the binary form; otherwise it is the text form. Strict base64 shape: zero or more groups of 4 characters from `A–Z a–z 0–9 + /`, optionally followed by one final group of 3 such characters plus `=`, or 2 such characters plus `==`, with nothing else, not even whitespace. Empty text has this shape. Observed with the installed CLI: `Zd/www4AAAA=` followed by LF, by CR LF, or preceded by LF is not binary (it is an invalid text time, so the current time). The source's shape test is a regular expression whose end anchor, in the regex library the toolkit links, can also match just before one final LF, so a build of the source may read `Zd/www4AAAA=` + LF as binary (2010-08-08T17:24:53Z). The installed CLI links the same regex library, and its binary holds the same pattern and uses the same regular expression class; it does not use the toolkit's older whole-string match call, so that is ruled out as the reason. It still does not read `Zd/www4AAAA=` + LF as binary (also not `AAAA` + LF, and not in a version 3 file), and why is not known. Larsal keeps the strict rule above (no trailing whitespace). Check with Verify on a build of the source; if it differs, add the case to the AT-A11 watch list.

FMT-12.5 Time, binary form on read. Base64-decode the text (FMT-12.20). Keep the first 8 bytes and drop the rest. If there are fewer than 8, pad with 0x00 bytes at the end. Read the 8 bytes as a signed 64-bit little-endian seconds count. So empty text (or an empty element) is 0, which is 0001-01-01T00:00:00Z.

FMT-12.6 Time, text form on read: Larsal's grammar. Larsal reads a time text that does not have the base64 shape (FMT-12.4) with this grammar. The whole text must match, from its first character to its last; nothing is trimmed. Digits and letters are ASCII only.
1. Date: `YYYY-MM-DD`, with exactly 4 digits for the year (0001 to 9999), 2 for the month (01 to 12) and 2 for the day (a day that exists in that month and year, proleptic Gregorian calendar).
2. If the text is only the date, the time is 00:00:00 on that day, UTC (rule 7).
3. Otherwise the 11th character is the separator: `T`, `t` or one space (0x20). After it comes the time, `HH:MM` or `HH:MM:SS`, exactly 2 digits each: hour 00 to 23, minute 00 to 59, second 00 to 59. Missing seconds mean 00.
4. End of day: hour 24 is allowed only as `24:00` or `24:00:00` with no fraction, and means 00:00:00 of the next day. The reference also accepts some fractions there (`24:00:00.0`, `24:00.0`); Larsal does not (FMT-12.28 g and l).
5. Fraction (optional, only right after the seconds): `.` or `,` followed by one or more digits. It is dropped: the seconds are truncated, not rounded.
6. Zone (optional, last): `Z` or `z` means UTC. An offset is `+` or `-` followed by `HH:MM`, `HHMM` or `HH`, with hour 00 to 23 and minute 00 to 59; subtract it to get UTC (`2010-08-08T17:24:53+05:00` is 2010-08-08T12:24:53Z). An offset directly followed by `Z` or `z` (for example `2010-08-08T17:24:53+02:00Z`) is read as UTC and the offset is ignored. The reference reads it the same way when the time has whole seconds with no fraction or with a fraction of 4 or more digits. That covers every text of this shape the reference writes itself (FMT-12.3: always whole seconds, never a fraction). With no seconds (`17:24+02:00Z`, also `24:00+02:00Z`) or with a fraction of 1 to 3 digits (`17:24:53.5+02:00Z`), the reference finds the text invalid and Larsal does not (FMT-12.28 k).
7. No zone: the time is UTC, so the result does not depend on the machine (decided: spec/decisions.md, default rule; the reference uses the machine's local time zone, FMT-12.28 a).
8. Anything else is invalid (FMT-12.7). That includes leading or trailing whitespace, any character after the zone or after the time when there is no zone, a leading `+` on the year, second 60, an impossible date such as `2010-02-30`, and a base64-looking text whose length is not a multiple of 4 (for example `AAAAAAAAAAA`).
These shapes are the ISO 8601 extended forms plus the RFC 3339 options (lowercase `t` and `z`, a space as separator), with one omission: Larsal does not accept a decimal fraction of the hour or of the minute (`17.5`, `17:24.5`), although ISO 8601 allows both. No known writer produces them. The reference reads a minute fraction but not an hour fraction (FMT-12.28 g). Normal version 3 files hold only `YYYY-MM-DDTHH:MM:SSZ` (FMT-12.3). A result outside 0001-01-01T00:00:00Z to 9999-12-31T23:59:59Z (for example from `9999-12-31T24:00:00Z` or `0001-01-01T00:00:00+01:00`) is kept per FMT-12.8. FMT-12.28 lists every shape found so far that the reference reads differently.

FMT-12.7 Invalid time. A time text that has neither form becomes the current UTC time, without error, in the reference's normal mode. Larsal does the same, using the open time (FMT-10.10). No other component relies on an error here (source, re-read by Verify: the reader raises an error for an invalid time only in its strict mode, and only the reference's unit tests turn strict mode on; vault opening and XML import both use the normal mode).

FMT-12.8 Time range. Larsal keeps any 64-bit value read from the binary form and writes it back unchanged. Values outside 0 to 315537897599 (before 0001-01-01T00:00:00Z or after 9999-12-31T23:59:59Z) are kept but must not be turned into a calendar date without checked arithmetic. How the screen shows them is MOD-09. The reference, observed with the installed CLI: values in that range and somewhat beyond (-1, 315537897600, 66854713576923) round-trip unchanged in version 4. At the extremes its arithmetic wraps: 9223372036854775807 was written back as -1, and -9223372036854775808 as 0. The source is built on a newer toolkit that refuses such overflow instead of wrapping (check with Verify). Larsal's keep-unchanged rule is correct for every value the reference writes.

FMT-12.9 Time zones. Stored times are always UTC. Reading the binary form, or the text form with `Z`, never applies the local time zone. Converting to local time is a screen matter only.

FMT-12.10 Booleans in elements, on read. The text must equal `true` or `false`, compared without regard to case using Unicode case folding. Only one fold matters for these words: U+017F (long s) folds to `s`, so `falſe` is false (observed). Empty text, or an empty element, is false. Anything else rejects the document (the reference reports an invalid boolean value). That includes `1`, `0`, `yes`, and `true` with any whitespace around it. There is no trimming.

FMT-12.11 Booleans in elements, on write: `True` or `False`, capitalized.

FMT-12.12 Three-state booleans (group `EnableAutoType` and `EnableSearching`, FMT-11). On read, the text must equal `null`, `true` or `false`, compared without regard to case using the same Unicode case folding as FMT-12.10 (so `falſe` with U+017F is `false`, observed): `null` means inherit from the parent group, `true` means enabled, `false` means disabled. Anything else, including empty text and surrounding whitespace, rejects the document (the reference names the element in its error). On write: lowercase `null`, `true` or `false`.

FMT-12.13 Booleans in attributes (`Protected`, `ProtectInMemory`, `Compressed`). The attribute is true when its value equals `true` without regard to case, or is exactly `1`. Missing, or any other value (for example `yes`), is false, with no error (observed: `Protected="1"` decrypts, `Protected="yes"` leaves the base64 text as the plain value). On write, the attribute is written only when true, with the value `True`.
Attribute names are matched exactly, case-sensitively, on the full name as written, prefix included. This is unlike element names, which are matched on the local name (FMT-10.7). So `x:Protected="True"` (even with `x` declared), `protected="True"` and `PROTECTED="True"` are not the `Protected` attribute: the element is read as plain text, its text is taken literally, and it takes no keystream bytes (observed). The same exact matching applies to every attribute the reader looks at: `Protected`, `ProtectInMemory`, `Compressed`, `ID` and `Ref` (FMT-11, FMT-13). Such a differently named attribute on a known element is an unknown attribute and is not written back (FMT-10.20). A Builder who matched attribute names on the local name would decrypt these values and take keystream bytes, and every later protected value would decode differently from the reference (SF-08).

FMT-12.14 Integers on write: ASCII decimal, a leading `-` for negative values, no `+`, no leading zeros, and `0` for zero.

FMT-12.15 Integers on read. Trim leading and trailing whitespace: every character with the Unicode White_Space property, including TAB, LF, CR and U+00A0 (observed: U+00A0 around `5` reads as 5). Then accept an optional single sign followed by one or more ASCII digits `0–9`. The sign is `+`, `-`, or U+2212 MINUS SIGN, which means the same as `-` (observed: U+2212 `5` reads as -5). No other sign character is accepted: U+FF0D, U+FE63, U+2013, U+FF0B and U+207A reject the document (observed). Nothing may come between the sign and the digits. Leading zeros are allowed. The value must fit in a signed 32-bit integer (-2147483648 to 2147483647). Anything else rejects the document (the reference reports an invalid number value): empty text, `0x10`, `7.0`, `1e3`, `- 1`, two signs (`--1`, `+-5`, U+2212 U+2212 `5`), a sign after the digits, `2147483648`, `-2147483649`, non-ASCII digits, group separators. Larsal writes only the ASCII `-` (FMT-12.14). The U+2212 rule was observed with the installed CLI (toolkit major version 5); the source is built on toolkit major version 6, whose integer conversion may treat U+2212 differently: check with Verify on a build of the source.

FMT-12.16 UUIDs on write. Base64 (FMT-12.21) of the 16 UUID bytes in RFC 4122 order, the order of the canonical hex text. The result is always 24 characters ending in `==`. The null UUID (16 zero bytes) is written `AAAAAAAAAAAAAAAAAAAAAA==`.

FMT-12.17 UUIDs on read. Base64-decode the text (FMT-12.20).
- Zero bytes: the null UUID, no error.
- Any length other than 16: the null UUID, no error. The reference's strict mode would reject it; its normal mode does not.
- 16 zero bytes: the null UUID.
- Otherwise: those 16 bytes.
What a null UUID means depends on the element. A group or entry `UUID` gets a new random UUID (FMT-11). A reference (`RecycleBinUUID`, `LastSelectedGroup`, `CustomIconUUID` and the others) means none (FMT-10.16, FMT-11, FMT-14). Because decoding is lenient, whitespace and line breaks inside the text are fine, and missing padding is fine.

FMT-12.18 Colors. On read, the text is kept exactly as read: not checked, not trimmed, no case change (observed: `red` and `#ffef00` are kept as written). On write, the kept text is written exactly. Empty text gives `<X/>`. Larsal uses a color for display only when it matches `#` followed by exactly 6 hex digits, in either case. Colors Larsal creates are written `#rrggbb`: `#` followed by exactly 6 lowercase hex digits, two for red, two for green, two for blue. This is the form the reference's own color pickers write, and it is the one case for every color Larsal creates, inside the XML document and in public custom data (FMT-03.23). Larsal never changes the case of a color it only read. On read, both cases mean the same color.

FMT-12.19 Colors in the reference's strict mode (tests only) must be 7 characters: `#` followed by three 2-digit hex parts, each at most FF. Larsal does not reject on this. It is listed only so that a Builder knows that `#` plus 6 hex digits is the intended shape.

FMT-12.20 Base64 on read (lenient). This applies to every base64 value: UUIDs, binary-form times, attachments, icons, protected values and the header hash.
- Skip every character that is not in `A–Z a–z 0–9 + /`. That includes `=` wherever it is, whitespace, line breaks, `-` and `_`.
- Each kept character gives 6 bits, in order. Emit one byte each time 8 bits have collected.
- At the end, drop any leftover bits (fewer than 8), whatever their value.
- This never fails. Some results: `QUJD RA==` gives `41 42 43 44`; `QUJDR` gives `41 42 43`; `QUJDRA=AQ==` gives `41 42 43 44 00 10`; `-_` gives nothing.

FMT-12.21 Base64 on write: RFC 4648 section 4, standard alphabet, with `=` padding, no line breaks, no whitespace. Empty data gives empty text, so `<X/>`.

FMT-12.22 Protected values. Every value element listed in FMT-12.29, not only entry string values, may carry a true `Protected` attribute (FMT-12.13). No element outside that list is ever decrypted. The value types fall into two groups:
- Text group: plain text, booleans (FMT-12.10), three-state booleans (FMT-12.12), integers (FMT-12.15), times in either form (FMT-12.4 to FMT-12.6) and colors (FMT-12.18). For these the plaintext is the value's text, which is then parsed by the type. A protected time therefore holds the encrypted bytes of its text: for a binary-form time, the 12 ASCII characters of its base64 text, not the 8 raw bytes.
- Byte group: UUIDs (FMT-12.17), the header hash (FMT-10.21), custom icon data (FMT-14), `Meta/Binaries` pool items (FMT-13; XOR comes before gunzip) and inline entry attachment values (FMT-13). For these the plaintext bytes are the value.
If the attribute is true and the element text is not empty:
1. Base64-decode the text (FMT-12.20) to get the ciphertext.
2. XOR it with the next bytes of the protected-field stream (FMT-09). The stream is shared by the whole document and used strictly in document order.
3. Text group: decode the plaintext as UTF-8 exactly as FMT-09.15 step 3 says (its replacement rule for invalid sequences, and one leading `EF BB BF` dropped: decided: spec/decisions.md LD-25), then parse that text by the element's type. The reference decodes every protected text value with the same reader, in `Meta` as in entries (from the source). Byte group: the plaintext bytes are the value.
Empty text uses no stream bytes. A non-empty text that decodes to zero bytes (for example `====`, or only whitespace) uses no stream bytes either, and its value is empty: empty text for the text group, which is then parsed by the type (so a text value or color is empty, a boolean is false, a time is 0 = 0001-01-01T00:00:00Z, and an integer or three-state boolean rejects the document), and empty bytes for the byte group (so a UUID is null). Elements Larsal keeps as unknown are not value elements in this sense: they follow FMT-09.14 only (decided: spec/decisions.md LD-24). They are never decrypted, they take no stream bytes on read or on write, and their raw text is kept and written back unchanged, the same as the reference, which skips them (FMT-10.20). On write, Larsal puts `Protected="True"` only where FMT-09 and FMT-11 say (entry string values), never on metadata. A kept unknown element is written back with the attributes FMT-10.20 keeps (every attribute without a prefix), so an unprefixed `Protected` attribute on it stays, with its raw text, and still takes no stream bytes (FMT-09.14). Larsal writes inline attachments back as pool items (FMT-13.9), so it never writes a protected inline attachment value. Observed: the reference decrypts `Protected="True"` on `DatabaseName` and on a time element in `Meta`, in document order, in version 3 (Salsa20) and in version 4 (ChaCha20), and on every element of the FMT-12.29 sweep test in version 4.

FMT-12.23 Text on read (XML decoding). Standard XML 1.0, in this order:
1. End-of-line handling on the raw text: CR LF becomes LF, and a CR on its own becomes LF (observed: raw `a CR LF b CR c` reads as `a LF b LF c`).
2. Then decode the predefined entities `&lt; &gt; &amp; &quot; &apos;`, decimal and hex character references, and CDATA sections. A CR written as `&#13;` stays a CR (observed).
3. Comments and processing instructions inside a value element are dropped, and the text around them is joined (observed: `a<!-- c -->b<?pi x?>c` reads as `abc`).
4. A child element inside a value element rejects the document.
There is no trimming: leading, trailing and whitespace-only text is kept exactly (observed: `  N  ` stays). There is no Unicode normalization. Larsal's XML library must be set up so that step 1 happens and step 2 does not undo it.

FMT-12.24 Characters XML 1.0 forbids, on read. A document holding a character outside the XML 1.0 Char set is rejected, whether raw or as a character reference. That covers U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F, lone surrogates, U+FFFE and U+FFFF (observed: raw 0x01, `&#1;`, `&#xFFFE;` and `&#xD800;` are all rejected). Invalid UTF-8 up to the end of the root end tag rejects the document. Bytes after the root end tag are not read by Larsal, even when they are not valid UTF-8 (FMT-10.5; the reference sometimes rejects them, a known difference listed there). U+007F to U+009F are allowed on read. A custom data key read keeps none of the characters FMT-12.25 removes: the reader removes them, so a key reads as the next save writes it (FMT-14.10, INT-08.32).

FMT-12.25 Characters removed on write. Before writing any text value (all of `Meta`, group and entry texts, custom data, unprotected entry string values), remove every one of these: U+0000 to U+0008, U+000B, U+000C, U+000E to U+001F, U+007F to U+0084, U+0086 to U+009F, U+FFFE, U+FFFF, and any lone surrogate (a Rust `String` cannot hold one). Keep TAB, LF, CR, U+0085 and every other character, including characters above U+FFFF (observed: `x U+0080 y U+0085 z U+009F w U+007F v` is written as `x y U+0085 z w v`). The reference logs each removed code point. Larsal logs only the count. Base64 values are not affected, because they hold only alphabet characters.

FMT-12.26 Escaping on write. `&` becomes `&amp;`, `<` becomes `&lt;`, `>` becomes `&gt;`, `"` becomes `&quot;`. The apostrophe, TAB and LF are written raw. Every character other than CR is written as raw UTF-8, never as a character reference (observed: U+1F600 is written as `F0 9F 98 80`). Larsal writes CR as `&#13;`, so that a CR survives the next read. The reference writes CR raw, and its own next read turns it into LF (observed). Larsal's choice keeps user data, and the reference reads it back as CR (decided: spec/decisions.md, default rule).

FMT-12.27 Empty values on write. An empty text value is written `<X/>`. The reference writes `<X></X>` when a value becomes empty only because of FMT-12.25 (observed). Both read as empty text. Larsal always writes `<X/>`.

FMT-12.28 Time, text form: how the installed reference reads it, and Larsal's known differences. The reference hands the text to its toolkit's ISO date parser. Observed with the installed CLI (toolkit major version 5) on a machine at +02:00, each value placed in `DatabaseNameChanged` of a version 4 demo vault and read back with `export`:
- Read the same by both (results as in FMT-12.6): `Z` or `z`; lowercase `t`; a space as separator; no seconds; a fraction with `.` or `,`; offsets `±HH:MM`, `±HHMM` and `±HH`, including `+00:00`, `-00:00` and `+23:59`; `24:00` and `24:00:00`, with no fraction, as the end of the day (with a fraction see g and l); an offset followed by `Z` (the offset is ignored) after whole seconds with no fraction or with a fraction of 4 or more digits, for example `...53+02:00Z`, `...53-05:30z`, `...53.1234+02:00Z` and `2010-08-08T24:00:00+02:00Z` (other shapes see k). Each item holds on its own; some combinations differ (k, l).
- Invalid in both (the current time is used, FMT-12.7): leading whitespace; a `+` before a 4-digit year (`+2010-08-08...`; for a 3-digit year see j); a 5-digit year; year 0000; a 1-digit month or day (`2010-8-8`); a 1-digit hour or minute; an hour alone (`2010-08-08T17Z`); an hour fraction (`17.5Z`, `17,5Z`); `24:00:01`; `24:00:00.5`; hour 25; minute 60; second 60; an impossible date; a date followed by `Z`, by `T` alone or by one space alone; a date separator that is not punctuation (`2010+08+08`, `2010~08~08`, `2010 08 08`; see h); a separator other than `T`, `t` or space between date and time; an offset with hour 24, minute 60 or seconds (`+05:00:00`); trailing whitespace after an offset (`+02:00 `); a sign followed by other text (`-garbage`); a fraction whose first characters are not digits as i requires (`.5Zjunk`, `.5garbage`, `.12garbage`, `.5xyzZ`); a minute fraction mark with no digits or with a non-digit in its first 5 characters (`17:24.Z`, `17:24.5xZ`, `17:24.5` + space); `17:24:Z`, `17:24xZ` and `17:24 Z`; a `-` in place of a leading digit (`2010--8-08`, `17:24:-5Z`).
- Known differences (for the AT-A11 allow-list), where Larsal follows FMT-12.6 and the reference does this. Items b to d, g, i and j first remove a final `Z` or `z` from the text (UTC); if there is none, they look for the last `+` or `-` after the date and, if one is found, read the rest as the offset (e). What is left is the time part.
  a. No zone (`2010-08-08T17:24:53`, `2010-08-08`, `2010-08-08T17:24`): the reference uses the machine's local time zone (at +02:00, `2010-08-08T17:24:53` became 15:24:53Z). Larsal: UTC.
  b. Text after the seconds that does not start with `.` or `,`, when the text does not end in `Z` and holds no `+` or `-` after the date: the reference ignores that tail, including any `Z` in it, and uses local time. Examples: `2010-08-08T17:24:53` + space, `...53` + LF, `...53Z` + space, `...53Z` + LF, `...53garbage`, `...53UTC`, `...53Zgarbage`, all read as 15:24:53Z at +02:00. Larsal: invalid. (Text after `HH:MM` with no seconds is invalid in both, for example `17:24xZ`.)
  c. Text between the seconds and a final `Z` that does not start with `.` or `,`: `...53 Z` and `...53xyzZ` are read by the reference as 17:24:53Z, the extra text ignored. Larsal: invalid.
  d. Text between the seconds and an offset: `...53 +05:00` and `...53x+05:00` are read by the reference as 12:24:53Z. Larsal: invalid. (A tail that starts with `.` or `,` follows i here too: `...53.1234x+05:00` is 12:24:53Z, `...53.5x+05:00` is invalid.)
  e. Offsets of other shapes, read by the reference as: `+5` 12:24:53Z, `+050` 12:24:53Z, `+05:0` 12:24:53Z, `+05:3` 12:21:53Z, `+5:30` 11:54:53Z, `+-05:00` 22:24:53Z. Larsal: invalid.
  f. A 1-digit second: `2010-08-08T17:24:5Z` is read by the reference as 17:24:05Z. Larsal: invalid.
  g. A decimal fraction of the minute: `HH:MM`, then `.` or `,`, then digits, with no seconds. The reference looks at the next 5 characters of the time part after the mark (fewer if it ends sooner). They must all be ASCII digits (but see j), or the time is invalid. With v their value and n their count (1 to 5), the seconds are floor(v × 60 / 10^n). Anything after those 5 characters is ignored. Observed: `17:24.5Z` and `17:24,5Z` give 17:24:30Z; `17:24.25+05:00` gives 12:24:15Z; `17:24.123456Z`, `17:24.1234567Z`, `17:24.123456789Z` and `17:24.12345xZ` give 17:24:07Z (only `12345` used); `17:24.99999Z` gives 17:24:59Z; `24:00.0Z` gives 2010-08-09T00:00:00Z; `17:24.5` (no zone) gives local time, 15:24:30Z at +02:00. Invalid: `17:24.Z`, `17:24.5xZ`, `17:24.5` + space, `17:24.5 Z`, and a full-width full stop (U+FF0E) as the mark. Larsal: invalid (FMT-12.6).
  h. Date separators: in place of each `-` of the date (the 5th and the 8th character), the reference accepts any punctuation character, each position checked on its own. Observed accepted: `/`, `.`, `_`, `:`, `(` with `)`, `-` with `/`, U+2014, U+00B7 and U+FF0F, for example `2010/08/08T17:24:53Z` gives 17:24:53Z, and `2010/08/08` alone gives local midnight (2010-08-07T22:00:00Z at +02:00). Observed rejected: `+`, `~` and space. This matches the set of Unicode general category P (punctuation), while `+` and `~` are math symbols and space is a separator; that the set is exactly category P was inferred, then observed by Verify: all 38 punctuation characters tried, from every subcategory of P (connector, dash, open, close, initial quote, final quote, other; ASCII and beyond, for example U+203F, U+301C, U+300C, U+00AB, U+2019, U+3001, U+203B), were accepted, and all 22 other characters tried were rejected: math symbols (`<`, `=`, `>`, `|`, U+00D7, U+2212 besides `+` and `~`), currency signs (`$`, U+20AC), modifier symbols (`^`, the grave accent, U+00A8), other symbols (U+00A9, U+00B0), spaces (space, U+00A0, U+3000), a letter, TAB and U+0660. Larsal: invalid.
  i. A fraction of the second (after `HH:MM:SS`, a `.` or `,`). The reference looks only at the next 4 characters of the time part after the mark (fewer if it ends sooner). If there are none, the fraction is zero and the time is valid. If the first is not an ASCII digit, the time is invalid. Otherwise whitespace at the end of those characters is dropped, and what remains must be all ASCII digits, or the time is invalid. Anything after those 4 characters is ignored. The fraction itself is then dropped, as in FMT-12.6 rule 5. Observed, with no zone (local time, 15:24:53Z at +02:00): `...53.1234garbage`, `...53,1234garbage`, `...53.5` + space, `...53.1234` + space, `...53.5` + U+00A0, and `...53.` at the end. Observed, with a final `Z` (17:24:53Z): `...53.Z`, `...53.1234xyzZ`, `...53.12345Z`, `...53.123 Z`. Observed invalid: `...53.5garbage`, `...53.12garbage`, `...53.5xyzZ`, `...53.5Zjunk` (no final `Z`, so the `Z` is inside the 4 characters), `...53.12 3Z`, `...53. Z`, and `...53.` followed by U+0665 then `Z`. Larsal: valid only when FMT-12.6 accepts the whole text, so of the cases above only `...53.12345Z` is valid in Larsal (17:24:53Z, the same as the reference); all the others are invalid in Larsal. The general rule above was inferred from these cases, then tested by Verify with 21 more cases with a final `Z`, each predicted from the rule first; all 21 matched (observed with the installed CLI). Examples: `...53.1   xZ` valid (the `x` is the fifth character after the mark), `...53.1  xZ` invalid, `...53.1 2Z` invalid, `...53.12` + TAB + `Z` valid, `...53,12 3Z` invalid, `...53.9` + three U+2003 + `junkZ` valid, `...53.9` + U+2003 + `x` + U+2003 + `Z` invalid.
  j. A `+` in place of the first digit of a numeric field. The reference reads it as `0`. Observed, each with a final `Z`: `2010-+8-08T17:24:53Z` and `2010-08-+8T17:24:53Z` give 2010-08-08T17:24:53Z; `2010-08-08T+7:24:53Z` gives 07:24:53Z; `2010-08-08T17:+4:53Z` gives 17:04:53Z; `2010-08-08T17:24:+5Z` gives 17:24:05Z; `2010-08-08T17:24.+5Z` gives 17:24:03Z (as `.05`); `+201-08-08T17:24:53Z` gives 0201-08-08T17:24:53Z. A `-` in the same places is invalid. The date fields do not depend on the zone (`2010-+8-08T17:24:53` gives local time, 15:24:53Z at +02:00). In the time part without a final `Z`, the last `+` is taken as the start of an offset (e) instead: `2010-08-08T+7:24:53` is invalid, while `2010-08-08T+7:24:53+05:00` gives 02:24:53Z (observed). Larsal: invalid.
  k. An offset followed by a final `Z` or `z`, after a time with no seconds or with a fraction of 1 to 3 digits. The reference removes the final `Z` first, so the offset is not read as an offset: it is the tail of the time part (c after whole seconds, i after a fraction, the note under b after `HH:MM`). After `HH:MM` the tail starts with `+` or `-`, which is invalid there. After a fraction, the 4 characters i looks at hold the sign, so they are not all digits. Observed invalid (current time): `2010-08-08T17:24+02:00Z`, `...17:24+0200Z`, `...17:24-05Z`, `2010-08-08T24:00+02:00Z`, `...24:00-05:00Z`, `...53.5+02:00Z`, `...53,5+02:00Z`, `...53.12+02:00Z`, `...53.123+02:00Z`, `...53.5-05:30Z`. Larsal (FMT-12.6 rules 3 to 6): `17:24+02:00Z` is 17:24:00Z, `24:00+02:00Z` is 2010-08-09T00:00:00Z, and each fraction case is 17:24:53Z. Here Larsal reads a time where the reference does not. The reference never writes these shapes (FMT-12.3: whole seconds, no fraction), so every file it writes reads the same in both.
  l. End of day with a fraction. After `24:00:00`, the reference accepts a fraction whose value, rounded to whole milliseconds, is 0. Only the first 4 characters after the mark count (i). Observed, each 2010-08-09T00:00:00Z: `2010-08-08T24:00:00.0Z`, `...24:00:00,000Z`, `...24:00:00.00Z`, `...24:00:00.0000Z`, `...24:00:00.000000Z`, `...24:00:00.0004Z`, `...24:00:00.00049Z` (only `0004` counts), `...24:00:00.0z`, and `...24:00:00.0000+02:00Z` (the offset ignored, as in the first list). With an offset and no final `Z`, the offset applies: `...24:00:00.0+02:00` gives 2010-08-08T22:00:00Z, the same as `...24:00:00+02:00`. With no zone it is local time (a). Observed invalid in both: `...24:00:00.0005Z`, `...24:00:00.001Z`, `...24:00:00.5Z`, and `...24:00:00.0+02:00Z` (the 1-digit fraction case of k). The rounding rule was inferred from these cases; Verify then tried every 4-digit step (observed with the installed CLI): `.0000` to `.0004`, and also `,0004`, `.00045`, `.00049999`, `.0004` + space + `Z` and `.0004xZ`, gave 2010-08-09T00:00:00Z; `.0005`, `.0006`, `.0009`, `.001` and `.00099` were invalid. Larsal: every fraction after hour 24 is invalid (FMT-12.6 rule 4), so these give the open time. The minute-fraction form `24:00.0Z` is item g.
Larsal rejects b to j and l because no known writer produces them and, for b and for no-zone cases of g to i, the reference's own result depends on the machine. Larsal keeps rule 4 for l: an end-of-day time with a zero fraction is not a shape any known writer produces, and the open succeeds either way (only that one time value differs, FMT-12.7). Item k goes the other way: Larsal's reading is the plain ISO 8601 one, and the reference writes only whole seconds. The source is built on toolkit major version 6, whose ISO date parser may treat these corner shapes differently: check with Verify on a build of the source.

## Edge cases and errors

- Time text `20100808` has the base64 shape. It is read as binary: it decodes to `DB 4D 74 D3 CD 3C`, is padded to 8 bytes, and gives seconds 66854713576923. Larsal keeps it. The reference writes it back as `20100808AAA=` in version 4 and as empty text in version 3 (observed).
- Time text `2010-08-08T17:24:53+02:00` in a version 3 save: the reference writes `2010-08-08T17:24:53+02:00Z` (FMT-12.3). Its next read lets the final `Z` win and ignores the offset, giving 2010-08-08T17:24:53Z (63416885093): the time silently moves by the offset, here 2 hours (observed, in version 3 and in version 4 files). Larsal reads the original text as 2010-08-08T15:24:53Z and never writes text times. Larsal reads `2010-08-08T17:24:53+02:00Z` exactly as the reference does, as 17:24:53Z (FMT-12.6 rule 6), so both agree on files the reference already wrote this way.
- Time text without a zone in a version 3 save: the reference reads `2010-08-08T17:24:53` as local time and writes it back as `2010-08-08T17:24:53Z`, the local wall-clock time with `Z` added (observed). On the next read it is 17:24:53Z, so the time moves by the machine's offset. In a version 4 save the same input becomes 2010-08-08T15:24:53Z on a machine at +02:00. Larsal reads it as 2010-08-08T17:24:53Z in every case (FMT-12.6 rule 7). A known difference for AT-A11 (FMT-12.28 a).
- Time text with trailing whitespace, such as `2010-08-08T17:24:53Z` followed by LF: the reference drops the zone and the tail and reads local time; Larsal treats it as invalid and uses the open time (FMT-12.28 b). A binary-form time with trailing whitespace (`Zd/www4AAAA=` + LF) does not have the base64 shape, so both read it as an invalid text time and use the current time (FMT-12.4, observed with the installed CLI; a build of the source may read it as binary: check with Verify).
- Attribute with a prefix or another case, such as `<DatabaseName x:Protected="True">` or `<DatabaseName protected="True">`: not the protected attribute; the text is the plain value and takes no stream bytes (FMT-12.13, observed).
- Integer written with U+2212 MINUS SIGN, as a locale-aware writer might do: read as negative by both (FMT-12.15).
- Boolean with whitespace: `<Expires> True </Expires>` rejects the document. The reference is strict here and so is Larsal.
- Integer with whitespace: `<UsageCount> 7 </UsageCount>` is 7.
- UUID with the URL-safe alphabet (`-`, `_`): those characters are skipped, the length is wrong, so the UUID is null. A group then gets a new random UUID (FMT-11).
- A UUID with one wrong final character, such as `...VQ==` instead of `...VA==`, decodes to a different 16-byte value. That is not an error. It is simply another UUID.
- Protected value whose base64 text decodes to fewer bytes than the writer meant: the stream gets out of step for every later protected value. That cannot be detected here. FMT-09 owns stream errors.
- `Protected` on an element Larsal does not know: never decrypted, no stream bytes on read or on write, raw text kept and written back unchanged (FMT-09.14; decided: spec/decisions.md LD-24). The reference also takes no stream bytes for it (observed, FMT-10.20), so later protected values stay in step in both apps.
- Protected value whose non-empty text decodes to zero bytes, such as `<DatabaseName Protected="True">====</DatabaseName>`: no stream bytes, empty value (FMT-12.22).
- Error texts. The reference reports an invalid boolean value, an invalid number value, an invalid three-state value naming the element, or its XML parser's error. Larsal maps them all to `Corrupt` (APP-06) and never puts the value in the message.

## Security notes

- No panics on hostile values (AT-A08, AT-A10). Time conversion to calendar fields must use checked arithmetic for the whole 64-bit range. Base64 decoding is bounded by the text length. Integer parsing must not overflow. Boolean parsing never allocates beyond the text.
- XML attacks (AT-A07). Larsal's reader rejects DOCTYPE (FMT-10.9), caps the size of one text node and the total document size before decoding (`limits.rs`; the numbers are in FMT-08.12, the only limits table, decided: spec/decisions.md LD-22; this card sets none). Character references are bounded like text. Base64 attachment text (version 3 `Meta/Binaries` items and inline entry attachment values) is exempt from the single text node cap and bounded by the document limit instead (FMT-08.12, FMT-13).
- Protected values (SF-08). Ciphertext must be decrypted with the shared stream in document order. Getting the set of decoded elements wrong (FMT-10.11, FMT-12.22, FMT-12.29) puts every later password out of step. What must never happen: Larsal decrypting an element outside the FMT-12.29 list (a container, a `Ref` value, an unknown element), or skipping one on the list. Decrypted entry values go straight into the secret string type (Rust rule 3). They never go into errors or logs (AGENTS rule 4), and neither does any other decoded text.
- Stripping (FMT-12.25) changes user text silently. It is needed so that the reference and Larsal can read the file at all. Larsal logs only that characters were removed, never which or where.
- Text on screen (AT-E01). Every decoded text is untrusted. The screen sets it as text only.
- Header hash bytes (SF-05) use FMT-12.20 and FMT-12.21. The check itself is FMT-10.21.
- Known differences from the reference (for the AT-A11 allow-list): text times without a zone and the other text-time shapes in FMT-12.28 a to l (other tails after the seconds, offset shapes, a 1-digit second, minute fractions, punctuation date separators, fraction tails, a `+` in place of a leading digit, an offset before a final `Z` after no seconds or a short fraction, an end-of-day time with a zero fraction), CR on write (FMT-12.26), `<X/>` for stripped-to-empty (FMT-12.27), extreme time overflow (FMT-12.8). A text time the reader treats as invalid becomes the open time without error, so a fuzzer comparing Larsal and the reference must ignore time values for these shapes.

| FMT-12.24 forbidden | Raw 0x01; `&#1;`; `&#xFFFE;`; `&#xD800;`; byte `FF` (bad UTF-8) | Read | Document rejected, `Corrupt` |
| FMT-12.24 after the root end tag | Valid document with byte `FF` directly after the root end tag | Larsal reads | Opens; the trailing byte is not read (the reference rejects this one, FMT-10.5) |
| FMT-12.24 C1 allowed | `x&#x80;y` | Read | Accepted; value holds U+0080 |
| FMT-12.25 strip | Value bytes `78 C2 80 79 C2 85 7A C2 9F 77 7F 76` | Write | Text bytes `78 79 C2 85 7A 77 76` |
| FMT-12.25 keep set | U+0009 U+000A U+0020 U+D7FF U+E000 U+FFFD, and U+10437 | Write, read | Unchanged |
| FMT-12.25 strip all | U+0002 U+0019 U+FFFE U+FFFF | Write | Empty value |
| FMT-12.26 escapes | `a<b>&"c"'d` | Write | `a&lt;b&gt;&amp;&quot;c&quot;'d` |
| FMT-12.26 raw UTF-8 | `x😀y` | Write | Bytes `78 F0 9F 98 80 79` |
| FMT-12.26 CR | Value `l1` CR LF `l2` | Larsal writes, then the reference CLI reads | Larsal text is `l1&#13;` LF `l2`; the reference reads `l1` CR LF `l2` |
| FMT-12.27 empty | Empty name; name that is only U+0080 | Larsal writes | `<DatabaseName/>` both (the reference writes `<DatabaseName></DatabaseName>` for the second) |

## How this was learned

- Read in the reference source: the document reader's value readers (text with the `Protected` attribute, boolean, three-state, time, color, integer, UUID, base64, compressed base64), its base64 shape check, its clock helper, its byte-order helpers, the document writer's value writers (boolean, integer, time in both forms, UUID, base64, three-state), its text-stripping routine, and the color picker on the entry edit screen. Read the reference format tests, including its invalid-character round trip test, and its XML test document `NewDatabase`.
- Ran the installed reference CLI (version 2.7.11, built on toolkit major version 5; the source uses version 6) on demo data only, in `/tmp/spec-fmt10-12/`. A scratch script made version 3.1 and version 4.0 demo vaults (AES-KDF, password `demo`) holding each test value in `Meta` or in a group or entry. The CLI `export -f xml` command showed what was read and how it was written back: text times for version 3, binary times for version 4. Saves made with the CLI `mkdir` command were decrypted by the scratch script to confirm the in-vault bytes. Protected `Meta` values were made with the scratch script's own Salsa20 and ChaCha20, checked against the RFC 8439 and Salsa20 reference vectors, and then decrypted correctly by the CLI.
- Review round 1 additions, demo vaults only, machine time zone +02:00: about 70 more text-time shapes, each in `DatabaseNameChanged` of a version 4 demo vault, read back with `export` (FMT-12.28). Shapes with a +02:00 offset were checked again with +05:00 and -05:30 offsets, because at +02:00 an offset and local time give the same result. Version 3 demo vaults showed how the reference writes offset and no-zone times back (FMT-12.3). A version 4 demo vault with an all-zero inner stream key showed the zero-byte protected cases and the protected time ciphertext (FMT-12.22). Read in the source: which value readers decrypt through the text reader and which through the byte reader, and that a protected text decoding to zero bytes gives an empty value.
- Review round 2, demo vaults only: `<X Protected="True">QUJD</X>` in `Meta` before a protected `DatabaseName` (all-zero inner stream key). The CLI read the name from keystream byte 0, so the unknown element took no bytes (FMT-12.22 now points to FMT-09.14, which follows LD-24). Spot checks of `...53Z` + space, `...53 Z`, `17:24 Z`, `+02:00` + space, `17:24:5Z`, `+05:00Z`, `xyzZ` and `24:00:00` agreed with FMT-12.28.
- Review round 3, demo vaults only, in `/tmp/spec-fmt10-12/r3/` (version 4, inner stream key all zero): `x:Protected`, `protected` and `PROTECTED` on `DatabaseName` before a protected `DatabaseDescription` (FMT-12.13); 17 integer sign variants in `MaintenanceHistoryDays` (FMT-12.15); the three out-of-range text times (FMT-12.6); `Zd/www4AAAA=` with LF before or after it (FMT-12.4). Read in the source: the document reader looks attributes up by their full name as written, and reads integers with the toolkit's integer conversion; the base64 shape test is a regular expression with an end anchor.
- Review round 4, demo vaults only, in `/tmp/spec-fmt10-12/r4/`, machine at +02:00: about 60 more text-time shapes in `DatabaseNameChanged` of a version 4 demo vault, read back with `export`: minute fractions, punctuation date separators, fraction tails after the seconds, and a `+` or `-` in place of a leading digit (FMT-12.28 g to j); `falſe` and `nuLL` in a group's `EnableAutoType` (FMT-12.12); a version 3.1 demo vault with an all-zero protected-stream key holding `<DatabaseName Protected="True">uLPZ9gPA</DatabaseName>` (read as `Secret`, FMT-12.22); byte `FF` after the root end tag (FMT-12.24, FMT-10.5).
