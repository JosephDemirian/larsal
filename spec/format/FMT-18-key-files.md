# FMT-18 Key files: kinds, reading, creating

Status: reviewed
Epics: E3-S3
Parity rows: SF-10, SF-04, SR-07

## What it does

A key file is any file the user picks as a second secret next to (or instead of) the password. App turns the file's bytes into the 32-byte key file component `F`, which FMT-04 puts into the composite key (FMT-04.3).

The **content** decides how the bytes become `F`. The file name and extension never do. There are five kinds:

| Kind (name in this card) | What the file is | `F` | Old-format warning |
|---|---|---|---|
| XML 2.0 | An XML document with root `KeyFile`, version `2.0`, the key as hex digits and a 4-byte check value | The decoded bytes: first 32, padded with zero bytes when shorter | No |
| XML 1.0 | The same document with a version that starts with `1.0`, the key as base64 | Same as XML 2.0 | Yes |
| Raw 32 | Exactly 32 bytes, any content | The 32 bytes | Yes |
| Hex 64 | Exactly 64 bytes, all hex digits | The 32 decoded bytes | Yes |
| Hashed | Anything else, any size | SHA-256 of the whole file | No |

App also creates key files (FMT-18.20 to FMT-18.23). The reference creates two kinds: XML 2.0 with 32 random bytes, and a file of 128 random bytes (which reads back as Hashed).

Names: the usual extension of the XML 2.0 key file is `2E 6B 65 79 78`, stored encoded (name rule). The other kinds often use `.key`. App's own extension is `.appkey`. None of these change how a file is read.

## Inputs and outputs

Input: the bytes of the chosen file and its length in bytes. The reader may look at the content more than once (XML attempt, length checks, full hash), so App reads from a source it can rewind or re-open. The reference refuses a source it cannot rewind, such as a pipe, and gives no reason.

Output, one of:

- `F` (32 bytes, secret) plus the kind. The kind is needed only for the old-format warning (FMT-18.18).
- An error of kind `KeyFile` (FMT-18.19, FMT-04.21), with one reason: empty file; unsupported XML key file version (with the version text); XML 2.0 check value mismatch; unreadable XML key data; not a regular file; DTD not accepted (D-18-1); key file too large (D-18-3); or I/O, with the operating system's reason.

Limits: the reference has none. It hashes files of any size. App's limits are D-18-3 in Edge cases (decided: spec/decisions.md LD-22).

Notation: hex bytes are in file order. "Hex digit" means one of the bytes or characters `0`-`9`, `a`-`f`, `A`-`F` (`30`-`39`, `61`-`66`, `41`-`46`). `SHA256(x)` is FIPS 180-4. Base64 is the standard alphabet of RFC 4648 section 4.

## Rules

FMT-18.1 **Detection order.** App decides the kind in this order and stops at the first step that applies:
1. Length 0: error *key file empty* (FMT-18.2).
2. The XML attempt (FMT-18.6 to FMT-18.17). It ends in one of three ways. "Key": the kind is XML 1.0 or XML 2.0, done. "Fatal error": stop and report it; the other kinds are **not** tried. "Not an XML key file": go on to step 3.
3. Length exactly 32: Raw 32.
4. Length exactly 64 and every one of the 64 bytes is a hex digit: Hex 64.
5. Otherwise: Hashed.

Ties follow from this order. The XML attempt runs first for files of every length, so a file of any length, including 32 or 64 bytes, can end in a fatal XML error. Example: the 32-byte file `<KeyFile><Meta><Version>xx</Vers` is the fatal error *unsupported key file version* with text `xx`, not Raw 32 (FMT-18.6, FMT-18.9, FMT-18.10). No XML key file fits in 32 bytes, so a 32-byte file whose XML attempt does not end in a fatal error is Raw 32, even when it is text, hex digits or XML. A 64-byte file is Hex 64 only when all 64 bytes are hex digits; otherwise it is Hashed. An XML file that is "not an XML key file" falls into step 3, 4 or 5 by its length.

FMT-18.2 **Empty file.** A file of 0 bytes is the error *key file empty*. No kind, no `F`. The reference fails here with an empty reason text.

FMT-18.3 **Raw 32.** `F` is the 32 bytes exactly as stored.

FMT-18.4 **Hex 64.** `F` is the 64 hex digits decoded into 32 bytes, high nibble first, upper and lower case alike. Any other byte anywhere in the file (also a space, `0d` or `0a`) means the file is not Hex 64. So hex text that ends with a line end (65 or 66 bytes) is Hashed.

FMT-18.5 **Hashed.** `F = SHA256(all bytes of the file, in order)`, with nothing trimmed or added. There is no size limit in the reference; it reads the file in pieces of 16 KiB. App also hashes in pieces, so memory stays flat for any size (D-18-3).

FMT-18.6 **XML attempt: fatal error or silent fall-back.** A parse problem ends the walk of FMT-18.9. Parse problems are: not XML at all; not well-formed (for example mismatched tags, a child element inside `Version` or `Data`, an undeclared entity, a broken character or entity reference, the sequence `]]>` in text, an undeclared namespace prefix, an ordinary attribute repeated on one element (namespace declarations may repeat, see *Well-formedness checks* below), a character XML does not allow, a `<` that starts no valid markup); cut short by the end of the file; an XML declaration that breaks the declaration syntax, or a processing instruction named `xml` in the wrong place (FMT-18.7); a declared encoding name that is not a valid encoding name or is unknown (FMT-18.7); and a byte sequence that is invalid for the decoder in use (FMT-18.7). A declared encoding that differs from the one found from the first bytes is not a parse problem in itself: the reader switches decoders and parses on (FMT-18.7, *Switching the decoder*), and for most files the text it then meets gives one of the problems above. What happens then:
1. A fatal error raised earlier in the walk (FMT-18.10, FMT-18.12 to FMT-18.14) has already ended the attempt.
2. If the problem came while gathering a `Version` or `Data` text, the text gathered up to the problem (the completed text runs, FMT-18.9) is still checked by FMT-18.10 (for `Version`) or FMT-18.11 to FMT-18.15 (for `Data`), exactly as complete text would be (FMT-18.9). A fatal error from these checks wins: the attempt ends with that fatal error, not with a fall-back.
3. Otherwise the attempt ends as "not an XML key file", with no message, and the file is read by steps 3 to 5 of FMT-18.1.

So a damaged XML key file either gives a fatal error or quietly becomes a different key. In the second case the vault fails to open with the wrong-key result.

*Well-formedness checks.* App applies every well-formedness constraint of XML 1.0 (fifth edition) and of Namespaces in XML 1.0 (third edition) to the part of the file the walk parses (FMT-18.9). A breach is a parse problem. 2.7.11 does the same, with two exceptions, which App copies (both seen with 2.7.11):
1. **Namespace declarations may repeat.** One element may carry `xmlns`, or the same `xmlns:p`, more than once, with the same or a different value, also with other attributes between them. This is not a repeated attribute (seen on the root and on `Data`, FMT-18.6-l). Which value then binds the prefix never changes the result: elements are matched by local name (FMT-18.8), and `Hash` by its written name (FMT-18.13). A repeated ordinary attribute is still a parse problem (`a="1" a="1"`, or two `Hash`).
2. **An unpaired surrogate is an ordinary character.** A UTF-16 code unit from D800 to DFFF without its partner, a UTF-32 value from D800 to DFFF, and the two units that FMT-18.7 makes from a UTF-32 value above U+10FFFF, are allowed wherever a character is allowed: in text, attribute values, comments and processing instructions (seen, FMT-18.6-m). Such a character is kept in a `Version` text, so the text is not `2.0`, but a text that starts with `1.0` still counts as 1.0 (FMT-18.10). In a `Data` text it is a character above U+00FF, so the data is unreadable (FMT-18.11, FMT-18.6-o).

Seen with 2.7.11 to be parse problems, so the file falls back (FMT-18.6-k; the valid forms next to them read the key, FMT-18.6-n). Each is a breach of XML 1.0 or Namespaces 1.0, so a strict reader finds it too:
- `--` inside a comment, and a comment that ends with `--->`, before or inside the root;
- a name that breaks the name productions of XML 1.0 (NameStartChar, NameChar): `1x`, `a$b`, `-a`, `·a` (U+00B7 first), `a×b` (U+00D7), a combining mark (U+0300) first. `é` and `a·b` are valid names;
- whitespace between `<` or `</` and the name (`< Meta>`, `</ Version>`). Whitespace before the `>` of an end tag (`</Version >`) is allowed;
- an end tag whose written name differs from its start tag, even when both prefixes name the same namespace (`<x:KeyFile ...>` closed by `</y:KeyFile>`); this check also runs on the root's end tag, where the walk ends;
- attribute syntax: `<` or a bare `&` in a value, a value without quotes, a name without a value, no whitespace between two attributes, U+00A0 used as whitespace inside a tag;
- a repeated ordinary attribute, and two attributes with the same namespace name and local name through two prefixes;
- a prefix that is not declared, on an element or on an attribute; a name with two colons (`a:b:c`) or an empty prefix (`:a`);
- the reserved prefixes and namespace names: binding `xml` to any other namespace name; binding any other prefix to the `xml` namespace name `http://www.w3.org/XML/1998/namespace`; a default namespace equal to that name or to `http://www.w3.org/2000/xmlns/`; declaring the prefix `xmlns`; binding a prefix to `http://www.w3.org/2000/xmlns/`; undeclaring a prefix (`xmlns:x=""`); an element with the prefix `xmlns`. Allowed: `xmlns:xml` with its own namespace name, and `xml:` names (`xml:lang`, `<xml:a/>`) without any declaration;
- a processing instruction with no target, or with a colon in its target;
- character data before the root (`x<KeyFile>`), and `]]>` in text outside a CDATA section, also between elements;
- a character XML does not allow (byte `01`, U+FFFE) in a comment, a processing instruction, an attribute value, a CDATA section or text.

Any other place where 2.7.11 departs from strict XML 1.0 and Namespaces 1.0, not listed here, is a known difference for differential fuzzing (AT-A11): App stays strict there and gives the result of this card. No key file written by either app is affected; only crafted files can differ.

FMT-18.7 **Encoding and document start.** These rules describe the installed version 2.7.11 (seen for every form named; its XML reader is the one of the UI toolkit it bundles, version 5.15.18). The source build differs (end of this rule). App follows these rules exactly, with the eight decoders below and no others (D-18-4; decided: spec/decisions.md LD-32).

*Decoders.* The reader turns bytes into characters with one decoder at a time. These are the decoders App has (names after folding, see *Names* below; D-18-4):

| Decoder | Declared names that select it (App, D-18-4) | A mark at byte 0 of what it decodes |
|---|---|---|
| UTF-8 | `utf8` | `EF BB BF` is dropped |
| UTF-16 | `utf16` | `FF FE` (little-endian) or `FE FF` (big-endian) sets the byte order and is dropped. No mark: little-endian (2.7.11 uses the computer's byte order, little-endian on this Mac, seen; App: always little-endian) |
| UTF-16LE | `utf16le` | `FF FE` is dropped (seen) |
| UTF-16BE | `utf16be` | `FE FF` is dropped (seen) |
| UTF-32 | `utf32` | `FF FE 00 00` (little-endian) or `00 00 FE FF` (big-endian) sets the byte order and is dropped. No mark: little-endian, as for UTF-16 (seen) |
| UTF-32LE | `utf32le` | `FF FE 00 00` is dropped (seen) |
| UTF-32BE | `utf32be` | `00 00 FE FF` is dropped (seen) |
| ISO-8859-1 | `iso88591`, `latin1` | nothing is dropped: every byte is one character, U+0000 to U+00FF (seen) |

A dropped mark is not part of the text. Two mark cases were not seen; check with Verify. App drops the mark in both:
- Whether UTF-8 drops `EF BB BF` when it decodes again (the add rule of *Switching the decoder*). This matters only for files crafted so that parsing reaches the added text.
- Whether UTF-16 drops `FF FE` when it decodes again a block that starts with `FF FE 00 00`. This never changes the result: position `P` then lies inside the UTF-32 declaration, whose UTF-16 reading holds U+0000 characters, so it is always a parse problem.

Every other block that starts with a UTF-16 or UTF-32 mark already has UTF-16 or UTF-32 as its first decoder, so the generic decoder never decodes it again. UTF-16 and UTF-32 are different decoders from UTF-16LE, UTF-16BE, UTF-32LE and UTF-32BE, even where they decode the same bytes the same way.

*Text is counted in UTF-16 code units.* Every position in this card's decoded text (the position `P` below, and the text runs of FMT-18.9) counts UTF-16 code units: a character above U+FFFF counts as two. The UTF-16 and UTF-32 decoders never find an invalid byte sequence (seen, FMT-18.7-am):
- UTF-16: every 2 bytes give one code unit as they are. An unpaired surrogate is kept as one unit (an ordinary character, FMT-18.6). A last single byte at the end of the file gives nothing.
- UTF-32: every 4 bytes give a value `v`. When `v` is below 10000 (hex), it gives one unit `v`, so a value from D800 to DFFF is an unpaired surrogate. Otherwise, **including every value above 10FFFF**, it gives two units: first `((v >> 10) + D7C0) mod 10000`, then `(v mod 400) + DC00` (all hex). For a real character this is its UTF-16 pair. For a value above 10FFFF the first unit can be any character, and the second is always an unpaired low surrogate. Seen: the value `00A1C000` after `<Version>1.` gives the units `30` (`0`) and `DC00`, so the text starts with `1.0` and counts as version 1.0; the value `00A1C400` gives `31` (`1`) and the text `1.1` plus a surrogate is the fatal *unsupported key file version* (FMT-18.7-ao). One to three bytes left at the end of the file give nothing.

*Detection.* The first bytes decide the first decoder. The rows are checked from top to bottom:

| First bytes | First decoder |
|---|---|
| `FF FE 00 00` or `00 00 FE FF` | UTF-32 (the mark sets the byte order) |
| `3C 00 00 00` | UTF-32LE |
| `00 00 00 3C` | UTF-32BE |
| `FF FE` or `FE FF` | UTF-16 (the mark sets the byte order) |
| `3C 00` | UTF-16LE |
| `00 3C` | UTF-16BE |
| anything else, `EF BB BF` included | UTF-8 |

Without a mark, UTF-16 and UTF-32 are found only when the first character is `<`; a UTF-16LE document without a mark that starts with a space falls back (seen).

*Declaration syntax.* The XML declaration is optional. When it is there, it follows XML 1.0 section 2.8 in this strict form. Every breach is a parse problem, so the file falls back (FMT-18.6). All of the following were seen with 2.7.11 (test cases FMT-18.7-v to FMT-18.7-z):
- It is the very first thing in the text; only a byte order mark may come before it (see *Start of the document*). It starts with `<?xml` in lowercase. `<?XML` or `<?Xml` at the start is a parse problem.
- The first pseudo-attribute is `version`, with the value exactly `1.0`. A different value (`1.1`, `1.00`, `1.0 ` with a space) or a missing `version` is a parse problem. Many common XML readers accept version 1.1 or pseudo-attributes in any order; App must not.
- After `version` come any number of `encoding` pseudo-attributes, then any number of `standalone` pseudo-attributes. An `encoding` after a `standalone`, a second `version`, and any other name are parse problems. "Any other name" includes another case (`Encoding`), a prefix (`x:encoding`) and other names (`foo`). A repeated `encoding` or `standalone` is allowed. Every `encoding` value is checked and applied in the order written (*Switching the decoder* and *Names*, below), so the last one decides the decoder for the rest of the document.
- Each `standalone` value must be exactly `yes` or `no` (lowercase). `maybe` and `YES` are parse problems.
- Each value is in single or double quotes, and the closing quote matches the opening one. A value without quotes is a parse problem. At least one whitespace character (space, tab, `0d`, `0a`) must separate two pseudo-attributes. Whitespace is allowed around `=` and before `?>`.
- Each `encoding` value must first be a valid XML encoding name (XML 1.0 production EncName): one ASCII letter, then any number of ASCII letters, ASCII digits, `.`, `_` and `-`. Only a name that passes this check is compared with the known names (*Names*, below). So `_utf8`, `.utf8`, `-utf8`, `8utf`, `UTF+8`, `utf 8` and the empty name are parse problems, although they would fold to `utf8`. `u-t_f.8` passes and is UTF-8.
- A processing instruction whose target is `xml` in any case, anywhere other than that first declaration, is a parse problem. Examples: a second declaration right after the first, a declaration after a comment, and `<?xml version="1.0"?>`, `<?XML ...?>` or `<?xMl ...?>` inside the root. Bytes after the root's end tag are never parsed (FMT-18.9), so such a processing instruction there changes nothing. Targets that only start with the letters `xml`, such as `xml-stylesheet` (before the root) or `xmlfoo`, are ordinary processing instructions and are skipped.

*Switching the decoder.* A declared encoding never makes the reader start again. It switches the decoder and parses on from where it is. Exactly:
1. The first decoder (*Detection*) decodes the first block (bytes 0 to at most 8191, see *Invalid byte sequences*) and reads the whole declaration up to its `?>`. Let `P` be the position just after `?>`, counted in code units in this first text. A mark the first decoder dropped is not counted, so `P` is the length of the declaration in characters (a declaration is all ASCII).
2. Then each `encoding` value is handled in the order written. A name that fails the EncName check, or is unknown (*Names*), is a parse problem.
3. If the name selects the decoder in use, nothing happens.
4. Otherwise the named decoder becomes the decoder in use, and it decodes the current block again, from byte 0, dropping a mark as the *Decoders* table says:
   - Every decoder except UTF-8: the new text **replaces** the old text. Parsing goes on at position `P` of the new text, counted in code units. The units before `P` in the new text are never parsed, whatever they are. If `P` falls between the two units of one character, parsing starts at an unpaired low surrogate, which can never start valid markup, so it is a parse problem (seen, FMT-18.7-al).
   - UTF-8: the new text is **added after** the old text, which stays. Parsing goes on at position `P` of the old text. It reaches the added UTF-8 text only when the old text runs out, at the end of the block.
5. When every `encoding` value has been handled, and before parsing goes on, the block is checked once for invalid byte sequences (*Invalid byte sequences*). The check uses the decoding by the decoder then in use; without a switch, that is the first decoder. Errors that an earlier decoder found no longer count, even those of a decoder chosen by an earlier `encoding` value. Only UTF-8 can find one (*Invalid byte sequences*); seen for the first decoder in FMT-18.7-ak and for a UTF-8 decoder chosen by an earlier `encoding` value in FMT-18.7-ah. Later blocks are decoded by the decoder then in use.

The current block is the first block for every declaration shorter than 8192 bytes. A declaration whose `?>` lies in a later block is handled the same way with that block: the switch decodes again the block that holds `?>`, from that block's byte 0, and `P` counts from the start of that block's text. Seen with 2.7.11 (FMT-18.7-ak): a declaration with 8,200 spaces before `encoding="ISO-8859-1"` switches to ISO-8859-1 for the rest of the file; the same with `UTF-16LE` falls back; with no `encoding`, or with `UTF-8`, the long declaration is read normally. This model fits every result seen; only single-byte documents were run. Any other long declaration is a crafted file, and a difference there is a known AT-A11 difference (*Well-formedness checks*, FMT-18.6). The switch, the replace rule, the add rule for UTF-8 and the position `P` were all seen with 2.7.11 (test cases FMT-18.7-aa to FMT-18.7-aj). The add rule for UTF-8 is why a declared `UTF-8` behaves differently from every other name.

App copies this switch exactly (D-18-4; decided: spec/decisions.md LD-32).

*What the switch gives.* For files encoded the same way all through, the switch gives the results below. The rows marked "Hashed" in FMT-18.7-m and FMT-18.7-n are such results, not separate rules. Crafted files that change encoding at `P` can still be read as keys (FMT-18.7-aa to FMT-18.7-ad).
- The name is one of the names of the first decoder: nothing changes.
- A single-byte document (first decoder UTF-8) that declares ISO-8859-1: the declaration is ASCII, so position `P` is the same byte in both texts, and the whole document is read as ISO-8859-1 (FMT-18.7-e).
- A UTF-8 mark with any name other than UTF-8: the mark is now part of the new text. With ISO-8859-1 it is 3 characters, so `P` lands 3 characters before the end of the declaration, on its closing `"?>`. That is a parse problem whatever follows (FMT-18.7-m, FMT-18.7-ae). With a UTF-16 name, the new text at `P` is the bytes from `2 × P` on, read in pairs, which is a parse problem unless crafted (FMT-18.7-ac). With a UTF-32 name, the ASCII bytes form values above U+FFFF that count as two units each, so for an ordinary file `P` lands in garbage, a parse problem (see the single-byte case below).
- A UTF-16 or UTF-32 mark with the matching byte-order name (for example `FF FE` with `UTF-16LE`): the new decoder drops the mark and gives the same text. The document is read normally (FMT-18.7-af). With the generic name, the decoder does not change. With any other name except UTF-8, the new text is garbage at `P`, so it is a parse problem. With UTF-8, the bytes `FF` or `FE` are invalid UTF-8, so it is always a parse problem (FMT-18.7-ag).
- No mark, a UTF-16 or UTF-32 document, the matching byte-order name: nothing changes. The generic name: little-endian, so a little-endian document is read normally (FMT-18.7-d, FMT-18.7-ai), and a big-endian one gives garbage at `P`, a parse problem (FMT-18.7-n, FMT-18.7-ai).
- No mark, a UTF-16 or UTF-32 document that declares UTF-8: the old text stays, so the document is read normally if both of these hold. First, it ends inside the first block. Second, the whole block is valid UTF-8, which ASCII characters and `00` bytes are. A character above U+007F usually makes the block invalid UTF-8, so the file falls back. A document that goes past the first block falls back: after the old text, the reader meets the added UTF-8 text, and that text holds U+0000 characters (FMT-18.7-ag).
- A single-byte document that declares a UTF-16 name: the new text at `P` is the bytes from `2 × P` on, read in pairs. For an ordinary file that is garbage, so it falls back (FMT-18.7-m). A file whose UTF-16 text starts at byte `2 × P` (or that has only whitespace there) is read as a key (FMT-18.7-aa, FMT-18.7-ab). A single-byte document that declares a UTF-32 name: every 4 ASCII bytes form a value above U+10FFFF, which is not an error but counts as two units (*Text is counted in UTF-16 code units*). So `P` does not land at byte `4 × P`; for an ordinary file it lands in garbage and the file falls back (FMT-18.7-ae). A crafted file whose UTF-32 text starts exactly at unit `P` is read as a key (FMT-18.7-al).
- With several `encoding` values, each one switches in turn, so the last one decides the decoder for the rest of the document. A replace after an add removes the added text (FMT-18.7-z, FMT-18.7-ah).

*Names.* A name that passes the EncName check (*Declaration syntax*) is compared without regard to case, ignoring every character that is not an ASCII letter or digit. Seen: `utf8`, `UTF8`, `u-t_f.8`, `iso_8859-1`, `ISO8859-1`, `latin1` and `Latin-1` all work. A name that fails the EncName check is never compared; it is a parse problem. An unknown name is a parse problem.
- Seen working in 2.7.11: the Unicode names of the *Decoders* table; ISO-8859-1 and the aliases `latin1`, `CP819`, `IBM819`, `csISOLatin1` and `iso-ir-100`; and many legacy encodings: windows-1252, CP1252, windows-1250, ISO-8859-15, KOI8-R, Shift_JIS, EUC-JP, Big5, GB18030, IBM850, macintosh.
- Seen to fall back in 2.7.11: US-ASCII, ASCII, UCS-2, `l1`, x-mac-roman, System, Locale, x-unknown-enc. Also `ISO-10646-UCS-2` in a UTF-16LE document with its mark, and `ISO-10646-UCS-4` in a UTF-32LE document with its mark (FMT-18.7-aj).
- Enumerated by Verify in Sprint 2 against 1,177 candidate names that pass the EncName check (Python's codec names and aliases, the macOS iconv list and common legacy names), each declared in a plain ASCII XML 2.0 key file: 2.7.11 read the key for 126 distinct names after folding and fell back for every other candidate. Accepted: UTF-8; ISO-8859 parts 1 to 11 and 13 to 16 and 8-I, with the aliases latin1 to latin6, latin8 to latin10, iso-ir-100, 101, 109, 110, 126, 127, 138, 144, 148, 157, 199 and 226, the csISOLatin names, arabic, ASMO-708, cyrillic, ECMA-114, ECMA-118, greek, hebrew, iso-celtic and iso_8859-10_1992; windows-1250 to windows-1258 and CP1250 to CP1258; CP819, IBM819, CP850, IBM850, csPC850Multilingual, CP866, IBM866, csIBM866, CP874, IBM874; KOI8-R, csKOI8R, KOI8-U, KOI8-RU; macintosh, MacRoman, Apple-Roman; roman8, hp-roman8, csHPRoman8; TIS-620; TSCII; WINSAMI2 and WS2; the nine iscii names (bng, dev, gjr, knd, mlm, ori, pnj, tlg, tml); Big5, Big5-ETEN, Big5-HKSCS, CP950, GBK, CP936, MS936, windows-936, GB2312, GB18030, EUC-JP, Shift_JIS, SJIS, MS_Kanji, ISO-2022-JP, JIS7, EUC-KR, CP949. Fell back, among others: ASCII and US-ASCII, the ISO646 names, UCS-2. The Unicode names of the *Decoders* table are known too, but a single-byte file declaring them falls back (above), so this method does not list them. Names outside the candidate set were not tried. App knows only the names in the *Decoders* table; every other name is a parse problem, so the file falls back (D-18-4; decided: spec/decisions.md LD-32).

*Start of the document.* Anything before an XML declaration, even whitespace or a comment, is a parse problem. A document without an XML declaration is fine, and may start with whitespace (seen).

*Invalid byte sequences.* The reader takes in the input in blocks of 8192 bytes (offsets 0 to 8191, 8192 to 16383, and so on) and decodes each block with the decoder in use. Only UTF-8 has invalid sequences; ISO-8859-1, UTF-16 and UTF-32 never do (*Text is counted in UTF-16 code units*). A UTF-8 sequence split between two blocks is decoded across the boundary and is not an error (seen, FMT-18.7-an). For the first block that is the first decoder, and after a switch it is the new decoder (*Switching the decoder*; only the new decoding counts). An invalid sequence anywhere in a block is a parse problem as soon as the reader takes in that block, before any character of that block is used. The first block is taken in before the root element is read, and checked again after each switch. A later block is taken in only when the walk needs a byte from it. The walk never looks past the `>` that closes the tag where it ends (at the latest the root's end tag; or an end tag that ends the walk earlier, FMT-18.9). So a block that starts after that `>` is never decoded, also when the `>` is the last byte of the block before. Seen (FMT-18.7-an): the root's end tag ending at offset 8189, 8190 or 8191 and `FF` at offset 8192: the key is read; the same with `<Tail/>` ending at offset 8191. When the closing tag itself crosses into the next block, that block is taken in and checked: `</KeyF` at offsets 8186 to 8191 and `FF` later in the second block falls back. App must do the same: check each 8192-byte block as a whole before using any character from it. Seen with 2.7.11:
- A bad UTF-8 byte inside the `Data` text falls back, even where the data text before it would give a check value error.
- A fatal `Version` text at the start of the file and a bad byte later in the same block: falls back. With the bad byte in the second block: the fatal error.
- A bad byte right after the root's end tag: falls back when it is at offset 8191 or lower; ignored (the key is read) at offset 8192 or higher.
- Invalid UTF-8 seen to fall back: `FF`, the overlong form `C0 AF`, the surrogate form `ED A0 80`. A UTF-8 sequence cut off by the end of the file (for example `E2 82` as the last two bytes) is not an error.
- A document declared ISO-8859-1 has no invalid bytes: byte `E9` in its `Data` text is the character U+00E9, which makes the data unreadable (FMT-18.13).


*Source build (differs in installed version, check with Verify).* The source's build files need the UI toolkit at version 6.2.4 or later. That generation's XML reader knows only the Unicode encodings and ISO-8859-1, plus other encodings only when the toolkit is built with its optional Unicode conversion library. So a `KeyFile` document declared as windows-1252 is read as a key by 2.7.11 but most likely falls back in the source build. Seen only with 2.7.11: the detection table, the declaration syntax, the decoder switch (including the add rule for UTF-8 and the position `P`), the name comparison, the text runs kept or dropped on a parse problem (FMT-18.9) and the 8192-byte block. A newer toolkit may replace the old text for UTF-8 too. If so, a UTF-16 or UTF-32 document without a mark that declares UTF-8 falls back in the source build (FMT-18.7-ag). It may also treat unpaired surrogates, UTF-32 values above U+10FFFF and repeated namespace declarations differently (FMT-18.6, *Text is counted in UTF-16 code units*). None of this was run with a source build here.

FMT-18.8 **Root element.** The first element must have the local name `KeyFile`, in exactly that case. A declared namespace prefix (for example `<x:KeyFile xmlns:x="urn:d">`), a default namespace and any attributes on it are ignored. An undeclared prefix (`<x:KeyFile>` with no `xmlns:x`) is a parse problem, so the file falls back (FMT-18.6). If the first element has another name, or there is no first element (the file is not XML, or it breaks before its first element), the attempt ends as "not an XML key file". The names `Meta`, `Version`, `Key` and `Data` in FMT-18.9 are matched the same way: local name, exact case. The `Hash` attribute is not matched this way: it is matched by its full written name (FMT-18.13).

FMT-18.9 **The element walk.** After the root's start tag, the walk moves forward through the document one tag at a time and never goes back. Each move skips text, comments and processing instructions, and stops at the first of these:
- a start tag: the move *finds* that element, and the walk is now inside it;
- an end tag of any element: the move *meets an end tag*;
- the end of the input: this is a parse problem;
- a parse problem.

A move never skips over the content of an element the walk found: the next move looks inside that element.

*Gathering the text* of an element collects its character content, up to its end tag, into one text. It works in **text runs**. A run is the character data between two pieces of markup:
- Character references (`&#65;`, `&#x41;`) and the five predefined references `&lt;`, `&gt;`, `&amp;`, `&apos;` and `&quot;` are replaced by their character and belong to the run they stand in.
- A run ends at a tag, a comment, a processing instruction, a CDATA section or a reference to an undeclared entity. Each CDATA section is a run of its own (its content, FMT-18.11).
- Comments and processing instructions are skipped, and the runs on both sides are joined: `2<!--c-->.0` reads as `2.0`.
- A child start tag inside is a parse problem.

Without a parse problem, the text is all runs joined in order. On a parse problem, gathering stops, the parse problem stays set, and the gathered text is every run completed before the problem, joined in order. The current run (the one in which the problem was found) is added only for some problems:
- **Added** when the problem is at a `<` (the start of any markup, even broken markup or a child start tag), at a well-formed reference to an undeclared entity (`&bogus;`), or at a character XML does not allow (bytes `00`-`08`, `0B`, `0C`, `0E`-`1F`, or U+FFFE, U+FFFF; an unpaired surrogate is allowed, FMT-18.6). Examples: `3.0<b/>`, `3.0&bogus;` and `3.0` followed by byte `01` give `3.0`; `3.0 < 4` gives `3.0 ` (with the space); `9.9</Vers` at the end of the file gives `9.9`; `3.0&amp;&bogus;` gives `3.0&`; `3.0&#65;<b/>` and `3.0&#65;` followed by byte `01` give `3.0A`.
- **Dropped** when the problem is a broken character reference (bad syntax, a missing `;`, or a value that is not an allowed XML character: for example `&#0;`, `&#xD800;`, `&#x110000;`, `&#x;`, `&#65` followed by `<`); an `&` that does not start a well-formed reference (`&;`, `&` followed by `<`, `&abc` followed by `<`, `&amp` followed by a space); the sequence `]]>`; or the end of the input. Examples: `2.0&#0;` gives empty text; `3.0&amp;&#0;`, `3.0&lt;&#0;` and `3.0&#x41;&#0;` give empty text (the references are part of the dropped run); `3.0<!--c-->x&#0;` and `3.0<?p q?>x&#0;` give `3.0`; `3.0<![CDATA[x]]>&#0;` and `3.0<![CDATA[x]]>y&#0;` give `3.0x`; `2.0]]>` gives empty text; `3<!--c-->.0]]>` gives `3`. `]]` without a `>` after it is ordinary text: `3.0]]` reads as `3.0]]`.
- The end of the input drops the current run. So a file that ends inside `<Version>2.0` gives empty text. A file that ends inside the `Data` digits gives only the runs completed before (usually none, so empty data text; with a comment or processing instruction inside the digits, the digits before the last one). A file that ends inside a CDATA section drops that section: `3.0<![CDATA[4.0` at the end gives `3.0`, and `<![CDATA[3.0` at the end gives empty text.
- An invalid byte sequence is found for its whole 8192-byte block before any text of that block is used (FMT-18.7), so no text in that block is ever added.

*Which elements count.*
- **Looks inside.** A `Meta` or `Key` found at the top level opens a *look inside* that element. A look inside lasts until the walk meets an end tag, whichever element that end tag closes; then the walk is at the top level again, wherever it is in the document. A `Meta` or `Key` found during a look inside does not open a new look.
- **Version.** A `Version` found during a look inside a `Meta` counts, also when it sits in wrapper elements with other names inside that `Meta`, as long as no end tag was met in between. Its text is gathered, and FMT-18.10 is applied to the gathered text, even when gathering hit a parse problem.
- **Data.** A `Data` found during a look inside a `Key` counts, also through wrapper elements with other names, in the same way. Its `Hash` attribute is taken (FMT-18.13), its text is gathered, and FMT-18.11 to FMT-18.15 are applied to the gathered text, even when gathering hit a parse problem.
- **Everything else counts for nothing,** and the walk goes on inside it: at the top level, every element other than `Meta` and `Key` (a `Version` or `Data` found there too); during a look inside, every element the two rules above do not count (other names, a `Version` in a look inside a `Key`, a `Data` in a look inside a `Meta`, and a `Meta` or `Key`). So a wrapper element with another name at the top level is transparent.
- Gathering a `Version` or `Data` text takes in that element's own end tag. The walk does not meet that end tag: it goes on just after it, in the same look inside.

*What ends the walk.* The walk ends at the first of these:
- an end tag met at the top level, of any element. At the latest this is the root's end tag. It can come earlier: for example the end tag of an empty element with another name at the top level, or of a wrapper element;
- a parse problem anywhere, also one found while gathering a text (the gathered text is checked first, as above);
- a fatal error from FMT-18.10 or FMT-18.12 to FMT-18.15, which ends the whole attempt at once (FMT-18.6).

Then FMT-18.16 applies.

These rules, and the effects below that follow from them, are normative: App must give the same result for every input. The effects were each seen with the reference tool (test cases FMT-18.9-a to FMT-18.9-u and FMT-18.6-c to FMT-18.6-j). The first two apply to the usual order, with `Key` after `Meta`:
- An element with another name inside `Meta`, before or after `Version`, ends the walk before `Key` is reached. The file falls back (usually to Hashed).
- An empty element with another name inside `Key`, before `Data`, ends the walk. The file falls back.
- An empty element with another name at the top level, before `Meta`, ends the walk. The file falls back.
- An element with another name that wraps both `Meta` and `Key` is transparent: they are read normally.
- Elements with other names after `Key`, comments and processing instructions do not change the key. A later `Meta` or `Key` is still walked, unless an end tag ended the walk first, for example the end of an empty element with another name such as `<Tail/>` (FMT-18.9-s). A later `Meta` that is walked can make the file fatal with a bad `Version`, and its `Version` sets the warning kind (FMT-18.16). A later `Key` with `Data` that is walked is checked and replaces the data (FMT-18.15).
- A parse problem inside the `Version` or `Data` text does not always fall back: the gathered text (the completed runs) is checked first, and a fatal error from that check is reported (FMT-18.6). Which runs are kept decides the outcome: `<Version>2.0&#0;</Version>` is fatal with empty text, while `<Version>2.0&bogus;</Version>` reads `2.0`, passes, and then falls back.
- Bytes after the point where the walk ends are never parsed, even inside the root, so the root need not be closed (FMT-18.9-t). At the latest the walk ends at the root's end tag. Only the block encoding check of FMT-18.7 still applies to those bytes, when they lie in an 8192-byte block the reader has taken in.
- A `Data` inside an element with another name inside `Key` is read, because the walk goes on inside that element during the look inside `Key` (FMT-18.9-u).
- A `Key` placed inside `Meta`, after `Version` and an empty element with another name, is read: the walk does not check where `Key` sits.

FMT-18.10 **Version.** The text of `Version` is used exactly as read, not trimmed:
- If it starts with the three characters `1.0`, the version is 1.0. So `1.0`, `1.00` and `1.0.5` all count as 1.0.
- If it is exactly `2.0`, the version is 2.0.
- Anything else (for example ` 2.0` with a leading space, `2.0 ` with a trailing space, `2`, `3.0`, or empty text) is the fatal error *unsupported key file version*, reported with the text.

This check also runs on text gathered up to a parse problem (FMT-18.9), so `<Version>3.0<b/>` is fatal with text `3.0`, a file that ends inside `<Version>2.0` is fatal with empty text, and `<Version>2.0&#0;</Version>` and `<Version>2.0]]></Version>` are fatal with empty text.

The last `Version` read before a `Data` element applies to that `Data` element.

FMT-18.11 **Cleaning the data text.** Take the text of `Data` as gathered (FMT-18.9): after normal XML decoding (entity and character references, CDATA sections, line-end handling), with comments and processing instructions inside skipped and the pieces around them joined, and cut short at a parse problem. Remove every whitespace character: U+0009 to U+000D, U+0020, U+0085, U+00A0, U+1680, U+2000 to U+200A, U+2028, U+2029, U+202F, U+205F and U+3000. All other characters stay; for example U+200B (zero width space) and U+FEFF stay. After removal, any character above U+00FF counts as invalid for FMT-18.12 and FMT-18.13.

FMT-18.12 **Version 1.0 data.** The cleaned text must be strict base64: only `A`-`Z`, `a`-`z`, `0`-`9`, `+` and `/`, a length that is a multiple of 4, and `=` only as the final one or two characters (a last group of the form `xxx=` or `xx==`). Empty text counts as valid. The text is decoded. The decoding ignores the unused low bits of the last data character in a final `xxx=` group (its low 2 bits) or `xx==` group (its low 4 bits), even when they are not zero. So `QUJ=` decodes to `41 42` (the canonical form is `QUI=`) and `QR==` decodes to `41` (the canonical form is `QQ==`). App must not refuse such text. Many strict base64 decoders refuse non-zero unused bits by default (RFC 4648 section 3.5 allows that choice), so App's decoder must be set to accept them. The source and 2.7.11 both decode this way (source read: the strictness check is only a pattern on the alphabet, the length and where `=` may stand; 2.7.11 seen). Text that is not strict base64 (missing padding, the URL-safe alphabet, stray `=`, invalid characters) is the fatal error *key file data unreadable*. The `Hash` attribute is ignored for version 1.0.

FMT-18.13 **Version 2.0 data and check value.** Every cleaned character must be a hex digit. Any count is allowed, including zero and odd counts. Otherwise it is the fatal error *key file data unreadable*. Decoding: an odd count decodes as if a `0` stood in front, so `ABC` gives `0A BC`. The check value is the attribute of `Data` whose full written name is exactly `Hash`: no prefix and exact case. A missing attribute counts as empty text. Drop every character of it that is not a hex digit, put a `0` in front if the count is odd, and decode. The result must equal the first 4 bytes of `SHA256(decoded data)`, byte for byte. Upper and lower case both work. Otherwise it is the fatal error *key file check value mismatch*. No other attribute counts, for example `x:Hash` (even with `xmlns:x` declared) or `hash`. A `Data` that has only such an attribute counts as having no `Hash`, so it gives this fatal error. Two attributes named `Hash` on one `Data` are a parse problem (FMT-18.6), so the file falls back (FMT-18.13-n). The data text gathered up to a parse problem is checked the same way. Its last run is dropped when the file ends inside the digits, or when the digits are followed by a broken reference (such as `&#0;`) or by `]]>` (FMT-18.9). The result is usually empty data text, which has the check value `E3B0C442`. So it gives this fatal error unless `Hash` is `E3B0C442`; then the check passes and the parse problem makes the file fall back (FMT-18.6). When the digits are followed by `&bogus;` (a well-formed reference to an undeclared entity), the run is kept: with the right `Hash` the check passes and the file falls back.

FMT-18.14 **Data with no known version.** If no `Version` of 1.0 or 2.0 was read before a `Data` element, in walk order, that is the fatal error *key file data unreadable*. So `Key` before `Meta`, or a `Meta` without `Version`, is fatal.

FMT-18.15 **Several `Data` elements.** Each `Data` reached by the walk is checked in turn, and each can raise a fatal error. The decoded bytes of the last one are the result.

FMT-18.16 **End of the XML attempt.** When the walk ends:
- If no parse problem happened so far and the last decoded data is not empty: the result is "key". `F` is the first 32 bytes of the data; when the data is shorter than 32 bytes, the rest of `F` is zero bytes. The data was decoded by the version that applied to it (FMT-18.10). The kind, which only decides the old-format warning (FMT-18.18), is XML 1.0 or XML 2.0 following the **last** `Version` read anywhere in the walk before it ended, even one read after the data. Example: valid 2.0 data followed by `<Meta><Version>1.0</Version></Meta>` gives `F` = the 2.0 data and the old-format warning.
- Otherwise: "not an XML key file", even if a `Version` or a `Data` element was read. Example: valid 2.0 data with a matching check value but empty text falls back.

FMT-18.17 **DTD and entities.** App never processes a DTD or an entity declaration and never fetches anything a document names. When a document has a `DOCTYPE`, App skips it without processing it and then reads the root element's name. The skip is a scan in constant memory with no size limit; a `DOCTYPE` that App cannot skip as well-formed XML is a parse problem (FMT-18.6). Then:
- Root not `KeyFile`: "not an XML key file", exactly as FMT-18.8. The reference does the same: it stops at the root's name. So ordinary files with a `DOCTYPE`, such as SVG images and XHTML pages, are Hashed (or Raw 32 or Hex 64 by length) in both apps.
- Root `KeyFile`: the fatal error *DTD not accepted* (error kind `KeyFile`, FMT-18.19). App does not read the rest of the document and never falls back to the other kinds (D-18-1; decided: spec/decisions.md LD-30).

Reference behavior for a `KeyFile` document with a `DOCTYPE`: it reads an internal DTD subset and expands internal entities, so a key file can take its version or data from an entity. An external entity reference gives empty text, which then usually causes the error *unsupported key file version*.

FMT-18.18 **Old-format warning.** XML 1.0, Raw 32 and Hex 64 are old formats. When one is used, App shows a warning, not an error. The key works. The warning says the key file uses an old format that may stop being supported, and suggests creating a new key file. The reference shows it on unlock (command line tool and app; the app's dialog has a "don't show again" option) and when the key file is set in the key settings. XML 2.0 and Hashed never warn. The warning text is in APP-06.

FMT-18.19 **Errors.** Every key file error stops the unlock, or the key change, before any key derivation. None of them is the wrong-key result. Every one is the error kind `KeyFile` of `app-format/error.rs`, with one of the reasons below; the change to plan/architecture.md that adds this kind is listed in FMT-04.21. A key file that cannot be read is `KeyFile` with reason I/O, not the vault's `Io`, so the screen can say which file failed.

| Case | Reference reason text (paraphrased) | App error: kind `KeyFile`, reason | App message (proposal; APP-06 decides) |
|---|---|---|---|
| Empty file (FMT-18.2) | none; the reason is empty | key file empty | "This key file is empty." |
| Version not 1.0 or 2.0 (FMT-18.10) | says the key file version is not supported, then the version text | unsupported key file version (with the text) | "App does not support this key file version: <text>." |
| Check value mismatch (FMT-18.13) | says the checksum does not match and the key file may be damaged | key file check value mismatch | "This key file is damaged: its check value does not match." |
| Bad data or data before version (FMT-18.12 to FMT-18.14) | says the key file data is unexpected and the key file may be damaged | key file data unreadable | "This key file is damaged: its key data cannot be read." |
| Cannot open or read the file | the operating system's error text (for example, no such file) | I/O (with the system reason) | "App cannot read this key file: <reason>." |
| Not a regular file (pipe, socket, folder; Edge cases) | an empty reason | not a regular file | "Choose a regular file as the key file." |
| DTD in a `KeyFile` document (FMT-18.17) | no such error in the reference | DTD not accepted (decided: spec/decisions.md LD-30) | "App does not accept key files that declare a DTD." |
| Over a limit of D-18-3 | no such error in the reference | key file too large (decided: spec/decisions.md LD-22) | "This key file is too large to read." |

Around the reason, the reference's command line tool adds a prefix that names the key file path, on unlock and on create, and on create a second line saying the key file could not be loaded. Its app adds a short prefix saying the key file could not be opened.

FMT-18.20 **Creating: the XML 2.0 layout.** A created XML 2.0 key file is exactly these 12 lines. Each line ends with one `0a` byte, the last line too. No byte order mark, no `0d`. `H` is the check value: the first 4 bytes of `SHA256(data)` as 8 uppercase hex digits. `G1` to `G8` are the 32 data bytes as 64 uppercase hex digits, cut into groups of 8 digits (4 bytes) in order.

| Line | Leading spaces | Content after the spaces |
|---|---|---|
| 1 | 0 | `<?xml version="1.0" encoding="UTF-8"?>` |
| 2 | 0 | `<KeyFile>` |
| 3 | 4 | `<Meta>` |
| 4 | 8 | `<Version>2.0</Version>` |
| 5 | 4 | `</Meta>` |
| 6 | 4 | `<Key>` |
| 7 | 8 | `<Data Hash="H">` with `H` in place |
| 8 | 12 | `G1 G2 G3 G4`: four groups, one space between groups |
| 9 | 12 | `G5 G6 G7 G8` |
| 10 | 8 | `</Data>` |
| 11 | 4 | `</Key>` |
| 12 | 0 | `</KeyFile>` |

The file is always 278 bytes. A worked example is test case FMT-18.20-a.

FMT-18.21 **Creating: content and kind.** The 32 data bytes come only from App's OS random source (`app-crypto` random, AT-B04), fresh for every file. One exception: Save as key file of a linked vault (spec/sync/SYN-03-client-sync.md, SYN-03.12) writes the key-file part the vault already uses, not fresh bytes; FMT-18.20, FMT-18.22 and FMT-18.23 still apply (LD-273 (8)). App always creates XML 2.0 with 32 data bytes (random, except the one case above), in the exact layout of FMT-18.20, and offers the extension `.appkey`. The kind never depends on the file name (D-18-2; decided: spec/decisions.md LD-31). Reference behavior: it writes XML 2.0 when the chosen file name ends with `2E 6B 65 79 78` (stored encoded, name rule; case-sensitive; an uppercase extension does not count), and otherwise writes 128 random bytes as they are, which read back as Hashed.

FMT-18.22 **Creating: the file.** After writing, App sets the new file's permissions to owner read-only (`0400`), as the reference does. App never overwrites an existing file: creating a key file at the path of an existing file is refused (LD-99). Reference behavior: its command line create commands use an existing file at the given path as the key file instead of creating one, and its app relies on the system save dialog's replace prompt. If writing fails, App reports the system's reason and removes any partial file.

FMT-18.23 **Creating: read it back.** After creating a key file, App gets `F` by reading the new file with FMT-18.1, not from the bytes in memory, as the reference does. For a created XML 2.0 file this gives the kind XML 2.0 and `F` = the 32 data bytes.

FMT-18.24 **Choosing a key file (app layer, APP-06 and APP-07).** The vault file itself (same canonical path) cannot be its own key file: refused with an explanation. A file whose name ends with `.appvault`, or with the reference's vault extension `2E 6B 64 62 78` (stored encoded, name rule), gets a warning that it looks like a vault and that a key file must never change, with Continue and Cancel. The reference does both. Its unlock screen compares the vault extension case-sensitively; its key settings screen compares it case-insensitively. App compares case-insensitively in both places.

FMT-18.25 **Key files are only read.** App never writes to, moves or changes an existing key file. App keeps `F`, not the file, for later saves (FMT-04.17).

FMT-18.26 **Secrets.** `F`, the decoded XML data, the cleaned text and every buffer that held file content for the XML and Hex 64 checks are secret. They use App's secret types and are wiped after use. The file path is not secret, but it is not logged together with any key material. The hash state for Hashed is wiped after use.

## Edge cases and errors

- **Ordinary text files, pictures, documents.** Any file can be a key file. It is Hashed unless it is exactly 32 bytes (Raw 32) or 64 hex digits (Hex 64).
- **A text editor added a line end** to a Hex 64 file: it becomes Hashed, so the key changes. The vault then gives the wrong-key result. The reference behaves the same; no special handling.
- **A damaged XML key file** either falls back silently and then gives the wrong-key result, or gives a fatal error when the text read before the damage fails a check (FMT-18.6). A changed data digit in an XML 2.0 file is caught by the check value (FMT-18.13). A file cut short inside the `Data` digits, or a broken reference or `]]>` after the digits, gives a check value error (FMT-18.13).
- **Short or long XML data.** Shorter than 32 bytes: zero padded. Longer: cut to 32. Both silently (FMT-18.16).
- **Odd hex digit counts** in XML 2.0 data or the `Hash` attribute: decoded with a leading `0` (FMT-18.13).
- **Version text with spaces**, for example `<Version> 2.0 </Version>`: fatal error (FMT-18.10). The reference behaves the same.
- **A source that cannot be rewound** (pipe, socket): the reference refuses with an empty reason. App reads key files from regular files chosen by the user. Anything else is refused with a plain message.
- **Very large files.** Seen: a 1 GiB file of zero bytes is Hashed by the reference tool in about 0.6 seconds with about 25 MB of memory. Its `F` is `49bc20df15e412a64472421e13fe86ff1c5165e18b2afccf160d4dc19fe68a14`. App must stay this flat (AT-A12).
- **The app's "create key file" dialog** offers the XML 2.0 extension first. Whether the system save dialog on this Mac adds that extension when the user types a bare name (so that XML 2.0 is created) was not tested; check with Verify.
- **Installed version.** The key file reader's own steps are the same in the installed command line tool (2.7.11) and in the source. The only changes between them are a new way of matching base64 (same results for cleaned text) and code style. But the XML reader comes from the UI toolkit, and the two use different generations: 2.7.11 bundles toolkit version 5.15.18; the source build needs version 6.2.4 or later. The encoding set differs (FMT-18.7, differs in installed version, check with Verify). These were seen only with 2.7.11 (check with Verify for the source build): the declaration syntax and the decoder switch (FMT-18.7), the text runs kept or dropped on a parse problem (FMT-18.9), the 8192-byte block for encoding errors and when the next block is taken in (FMT-18.7), the code-unit counting and the UTF-16 and UTF-32 decoding (FMT-18.7), and the well-formedness checks with their two exceptions (FMT-18.6). Seen: every case in the test table that was run gave the predicted result with 2.7.11.
- **Decided D-18-1 (spec/decisions.md LD-30): a `KeyFile` document with a DTD.** A document whose root is `KeyFile` and that has a `DOCTYPE` is the fatal error *DTD not accepted* (FMT-18.17, FMT-18.19). This applies only when the root element is `KeyFile`. A document with any other root falls back as in the reference (FMT-18.17), so ordinary files with a `DOCTYPE` are never refused. App never processes a DTD, so it never computes a key that the reference would compute differently. The cost: App refuses **every** `KeyFile` document with a `DOCTYPE`, both the ones the reference reads as a key (it expands internal entities, FMT-18.17-a) and the ones it reads as Hashed, Raw 32 or Hex 64 (FMT-18.17-d). A vault made in the reference with such a file as its key cannot be opened in App. No reference tool writes such a file. History: falling back instead was not chosen.
- **Decided D-18-2 (spec/decisions.md LD-31): which kind App creates.** Always XML 2.0 with 32 random bytes, in the exact layout of FMT-18.20, with the extension `.appkey` (FMT-18.21). It has a check value, gives no old-format warning in either app, and both apps read it by content. History: copying the reference's choice by file name (otherwise 128 random bytes) was not chosen.
- **Decided D-18-3 (spec/decisions.md LD-22): limits.** The reference has no limits. App: (1) Hashed has no size limit and is hashed as a stream, for parity; (2) Raw 32 and Hex 64 need only the length and at most 64 bytes; (3) the XML attempt parses as a stream and never loads the whole file. Within a document whose root is `KeyFile`, any one `Version` text, `Data` text or `Hash` attribute longer than 1 MiB, or an element depth over 256 (the root is depth 1), is the fatal error *key file too large*. It must never fall back, so that App never computes a key the reference would compute differently. The limits apply only to what the walk of FMT-18.9 reaches before it ends, in walk order: the text gathered for a `Version` or `Data` that counts, the `Hash` attribute of a `Data` that counts, and the depth of each start tag the walk finds (counting or not, so wrapper elements count for depth, FMT-18.19-c). They never apply to a full parse of the file: the text of an element that counts for nothing (for example a `Data` at the top level, or a `Data` in a look inside a `Meta`) is skipped, not gathered, so it has no length limit; and bytes after the end of the walk are never parsed (FMT-18.9), so nesting or long text there is never counted (FMT-18.19-d). Documents whose root is not `KeyFile` stop at the root, so these limits never affect ordinary files. A skipped `DOCTYPE` has no size limit; it is scanned in constant memory (FMT-18.17). The lead revisits these numbers if a demo vault, or a vault a user reports, passes one.
- **Decided D-18-4 (spec/decisions.md LD-32): which encodings App reads.** Exactly the eight decoders of FMT-18.7 (*Decoders*): UTF-8, UTF-16, UTF-16LE, UTF-16BE, UTF-32, UTF-32LE, UTF-32BE and ISO-8859-1. They are found by *Detection* or selected by a declared name. App copies the decoder switch of FMT-18.7 exactly: the replace rule, the add rule for UTF-8, the position `P`, the marks each decoder drops, and the single check of the block by the last decoder. A declared name must first pass the EncName check of FMT-18.7 (*Declaration syntax*); a name that fails it is a parse problem. A name that passes is compared after folding case and dropping every character that is not an ASCII letter or digit. App knows `utf8`, `utf16`, `utf16le`, `utf16be`, `utf32`, `utf32le`, `utf32be`, `iso88591` and `latin1`. Every other declared name, US-ASCII included, is a parse problem, so the file falls back. What this gives:
  - Its name set matches the source build without the toolkit's optional Unicode conversion library (FMT-18.7, *Source build*; check with Verify), and its decoder switch copies 2.7.11 (the source build may differ, FMT-18.7 *Source build*).
  - It matches 2.7.11 for every document whose root is not `KeyFile` (both fall back).
  - Because the switch is copied exactly, App reads the crafted files that 2.7.11 reads as keys (FMT-18.7-aa to FMT-18.7-ad, FMT-18.7-ag, FMT-18.7-ah). A reader that instead treats any disagreement between the declared name and the mark or first bytes as a parse problem falls back on them, and differential fuzzing (AT-A11) finds that.
  - For every name tested, each name 2.7.11 refuses is refused by App too, US-ASCII included (FMT-18.7-f, FMT-18.7-l, FMT-18.7-w). That holds only because the EncName check comes first: without it, `_utf8`, `UTF+8` and `utf 8` would fold to `utf8` and App would read them as UTF-8, while 2.7.11 falls back.
  - Known difference from 2.7.11, decided here: a `KeyFile` document that declares a name 2.7.11 knows and App does not, that is the legacy encodings and the further ISO-8859-1 aliases `CP819`, `IBM819`, `csISOLatin1` and `iso-ir-100` (FMT-18.7-i, FMT-18.7-aj). For them 2.7.11 decodes and can read the key, while App falls back. App does not add those four aliases, so that its name set stays the source build's. No reference tool writes such a file.
  - Other possible differences, none seen, all in crafted files or on other computers: the two mark cases on a second decode that were not seen (FMT-18.7 *Decoders*; App drops the mark, check with Verify); declarations longer than the first block other than the single-byte ones of FMT-18.7-ak; departures from strict XML not listed in FMT-18.6; and, on a big-endian computer only, the byte order of UTF-16 and UTF-32 without a mark (FMT-18.7 *Decoders*; App always reads little-endian). The AT-A11 allow-list is in Security notes.
  - History: a fatal "unsupported key file text encoding" error for such documents, instead of the fall-back, was not chosen.

## Security notes

- What could go wrong: a reader that picks the kind by file name, trims a line end, or uses a different detection order gives a different `F`. The user is then locked out of vaults made by the reference (SF-10, SF-04). Matching the walk of FMT-18.9 exactly is what makes differential fuzzing (AT-A11) pass.
- A hostile key file must not crash App, hang it, or blow up memory (AT-A12, AT-A10): stream hashing, a streaming XML parse with the limits of D-18-3, no DTD and no entity expansion (AT-A07, D-18-1).
- Known differences for differential fuzzing (AT-A11): crafted key files where 2.7.11 departs from strict XML in ways not listed in FMT-18.6, long declarations other than those of FMT-18.7-ak, and the decided cases of D-18-1 and D-18-4 (LD-30, LD-32). The AT-A11 harness lists them as allowed. Every other difference is a bug.
- The silent fall-back (FMT-18.6) is parity behavior, not a weakness: a file that falls back gives a different key, and opening the vault then fails with the wrong-key result.
- Key file content and `F` never go into logs, error values, crash reports or the screen layer (rule 4 in AGENTS.md, SR-07, AT-C06), and are wiped after use (AT-C01).
- New key files: content only from the OS random source (AT-B04), new for every file (AT-B03), owner read-only (`0400`, compare AT-I06), never written over silently.
- A key file must never change after it is set. Warning about vault files (FMT-18.24) prevents the most common mistake: picking a file that changes on every save.
- Parity rows: SF-10 (every kind read, random creation with a check value), SF-04 (feeds the composite key), SR-07 (secret handling). Attacks: AT-A07, AT-A10, AT-A11, AT-A12, AT-B03, AT-B04, AT-C01, AT-C06.

## How this was learned

- Read in the reference source: the key file component (its load routine with the XML, raw, hex and hashed readers, and its creation routines), the helper routines that test for hex digits and base64 and that read files in pieces, the command line tool's unlock helper, its create and import commands and their key file loader, the unlock screen's key file chooser and old-format dialog, and the key settings screen's key file part. Also the reference's key tests, with their list of key file test files.
- Behavior of the reference's XML reader that the source does not show directly (where a move of the walk stops, which characters count as whitespace, encoding detection, entity handling, odd-length hex decoding) was confirmed by experiment, not assumed.
- Compared the source with the installed version's tag (2.7.11) for these parts: no change in the key file reader's own steps that alters results. The XML reader belongs to the UI toolkit, whose generation differs (2.7.11 bundles toolkit version 5.15.18, read from the app bundle; the source's build files require version 6.2.4 or later), so the encoding set differs (FMT-18.7).
- Review round 1: read again in the source that the reader checks the `Version` and `Data` text returned by the text read without first checking for a reader error (FMT-18.6, FMT-18.9). Then ran about 60 more demo key files with the reference command line tool 2.7.11 in `/tmp/spec-fmt04-fmt18/r3/`, in the same way: partial text on a parse problem (FMT-18.6-c to FMT-18.6-j), encodings, declarations and byte order marks (FMT-18.7-i to FMT-18.7-u), the 8192-byte block for invalid bytes (found by moving a bad byte across offsets 8191 and 8192), namespace prefixes, comments inside text, a later `Meta`, the warning kind (with the command line list command), BOM before hex, and an SVG file with a `DOCTYPE`. Every result is in the test table, marked "seen".
- Review round 2: read again in the source that the base64 check is only a pattern and that decoding uses the toolkit's lenient decoder (FMT-18.12). Then ran about 80 more demo key files with 2.7.11 in `/tmp/spec-fmt04-fmt18/r4/`, in the same way: broken references, predefined references, `]]>`, comments, processing instructions and CDATA sections around a parse problem inside `Version` and `Data` text (which runs are kept, FMT-18.9-m to FMT-18.9-r, FMT-18.13-l, FMT-18.13-m); the declaration's version, pseudo-attribute order, repeats, names, quotes and whitespace, the EncName check, and processing instructions named `xml` elsewhere (FMT-18.7-v to FMT-18.7-z); and base64 with non-zero unused bits (FMT-18.12-j). Every result is in the test table, marked "seen".
- Review round 3: ran 49 more demo key files with 2.7.11 in `/tmp/spec-fmt04-fmt18/r5/`, in the same way, then opened each vault with the reference tool itself, using a Raw 32 key file that holds the predicted `F`. The runs covered a declared encoding that differs from the first bytes or the mark (FMT-18.7-aa to FMT-18.7-ai). They showed the decoder switch, the position `P`, which decoders drop a mark, and the add rule for UTF-8. Two files did not match the model of a plain re-decode: the UTF-8 mark followed by ISO-8859-1 and then UTF-8, and UTF-16 documents without a mark that declare UTF-8. More files then confirmed the add rule. The runs also covered more ISO-8859-1 aliases (FMT-18.7-aj), the `Hash` attribute's exact name (FMT-18.13-n), the end of the walk after an empty element (FMT-18.9-s to FMT-18.9-u), and a `KeyFile` document with a `DOCTYPE` that the reference reads as Hashed (FMT-18.17-d). - Ran the reference command line tool 2.7.11 in `/tmp/spec-fmt04-fmt18/`. 77 demo key files were made with python3. For each one the tool tried to create a key-file-only demo vault.
