# FMT-10 Document: vault metadata

Status: reviewed
Epics: E3-S6 (the write rules here are also used by E3-S7, the version 3 header hash rule by E3-S8)
Parity rows: SF-05, SF-07, SF-08, SF-09, SF-13, SD-04, SD-05, SD-06

## What it does

Inside every vault file, after decryption, decompression and (in version 4) the inner header, the payload is one XML document (FMT-08, FMT-09). This card describes:

- the XML envelope: declaration, encoding, line breaks and indentation the reference writes, and what the reference accepts on read;
- the top structure: the root element, its two children `Meta` and `Root`, and what `Root` holds;
- every child of `Meta`: name, value type, default, the file versions it is written in, its position in the write order, and what happens when it is missing, invalid, repeated or unknown;
- the version 3 header hash that lives inside `Meta`.

Value encodings (times, booleans, numbers, UUIDs, colors, base64, text escaping and stripping) are in FMT-12. Groups and entries are in FMT-11. The attachment pool (`Binaries`) is in FMT-13. Custom icons (`CustomIcons`) and custom data (`CustomData`) are in FMT-14. `DeletedObjects` is in FMT-15. Other version 3 differences are in FMT-17. Which version App writes is in FMT-16.

Name rule. The root element name of the document contains a banned word. In this card it is written as `[ROOT]`. Its real name is the 11 ASCII bytes `4B 65 65 50 61 73 73 46 69 6C 65`, stored encoded (name rule). Wherever this card shows `<[ROOT]>`, the file holds those 11 bytes as the element name. The same applies to `[REFNAME]`, the reference's product name, bytes `4B 65 65 50 61 73 73 58 43` (9 bytes), and `[ORIGNAME]`, the original format author's product name found in old test vaults, bytes `4B 65 65 50 61 73 73` (7 bytes). All stored encoded (name rule).

## Inputs and outputs

Read:
- In: the XML document bytes (version 4: the bytes after the inner header, FMT-09; version 3: the bytes after the hashed block stream and optional gzip, FMT-07, FMT-08). For version 3 also the outer header bytes, from offset 0 through the last byte of the end-of-header field (FMT-02), for the header hash check. The protected-field stream (FMT-09), because any value element may carry `Protected="True"` (FMT-12.22; the full list of value elements is FMT-12.29).
- Out: the vault metadata in `app-model` (`vault.rs`): the fields in the FMT-10.10 table, the memory-protection flags, history limits, recycle bin settings, key change settings, group references, plus every unknown element kept for the next save (`unknown.rs`).
- Limits: document size, nesting depth, text node size and element counts are bounded by `app-format/limits.rs` before allocation, with the numbers of FMT-08.12 (see Security notes).

Write:
- In: the vault model. Out: UTF-8 XML bytes, version 4 forms only (App writes the version FMT-16 chooses: 4.0 or 4.1, or at least the version read while kept unknown parts remain, FMT-16.24). The reference also writes version 3.1 when the vault uses the version 3 key derivation and no version 4 feature; those forms are listed so App can read them. App writes 4.0 in that case (decided: spec/decisions.md LD-07; FMT-16).

## Rules

FMT-10.1 Declaration on write. The document starts with exactly these 56 bytes: `<?xml version="1.0" encoding="UTF-8" standalone="yes"?>` followed by one line feed (0x0A). No byte order mark. The rest of the document is UTF-8.

FMT-10.2 Layout on write. One element per line. Each line starts with one TAB (0x09) per nesting depth: `[ROOT]` at depth 0 (no TAB), `Meta` and `Root` at depth 1, children of `Meta` at depth 2, and so on. Lines end with LF (0x0A) only, never CR LF. An element whose only content is text is written on one line as `<Name>text</Name>`. An element with no content at all is written as `<Name/>` (no space before the slash). An element with child elements is written as its start tag on one line, then its children one depth deeper, then its end tag on its own line at the start tag's depth. After the closing `</[ROOT]>` there is exactly one LF and nothing else. Text values are written as they are (FMT-12.25 to FMT-12.27); a text value that contains LF therefore continues on the next line with no indentation. This layout is required for the whole document App writes, groups, entries and deleted objects included (FMT-11, FMT-13, FMT-14, FMT-15), not only for `Meta`; the save-to-save stability of kept unknown elements (FMT-10.27) depends on it.

FMT-10.3 Attributes on write are written as ` Name="value"` with double quotes, in the order the defining card gives (for example `<Binary ID="0" Compressed="True">` in FMT-13, `<Value Protected="True">` in FMT-09 and FMT-11).

FMT-10.4 Top structure on write. The root element `[ROOT]` holds exactly two children, in this order: `Meta`, then `Root`. `Root` holds exactly two children, in this order: the root group `Group` (FMT-11), then `DeletedObjects` (FMT-15; written as `<DeletedObjects/>` when the list is empty). Unknown elements kept by App are added as FMT-10.20 says.

FMT-10.5 Top structure on read. The first element of the document must be named `[ROOT]`; otherwise the document is rejected (the reference reports that there is no root group). Inside `[ROOT]`:
- `Meta`: zero or more. Each `Meta` is read in turn; a value read later replaces the same value read earlier. With no `Meta` at all, every metadata value keeps its default (FMT-10.10).
- `Root`: exactly one. No `Root` rejects the document (no root group). A second `Root` rejects the document.
- The order of `Meta` and `Root` does not matter. A `Meta` after `Root` is read normally.
- Any other child element is unknown (FMT-10.20).
- Text (white space or not), comments and processing instructions directly inside `[ROOT]`, between or around its children, are ignored and not kept.
- Stray content in the `Meta` containers. The same holds directly inside `Meta`, `MemoryProtection` and `Meta/Binaries` (FMT-13): text (white space or not), comments and processing instructions before, between or after their children are ignored, not kept and not an error. The reference skips every token that is not a start element in these places (from the source; observed: the text `junk &amp; text`, a comment and a processing instruction placed before, between and after the children of all three containers were ignored, and every value, flag and pool item was read correctly). Directly inside the containers of FMT-11, FMT-14 and FMT-15 the same rule is FMT-11.43. Text inside a value element is not stray: it is the value (FMT-12.23), and a child element there rejects the document.
- Content after the closing `</[ROOT]>` is not read. The reference opens a document that has extra elements, raw 0x01 bytes or text such as `garbage<` after its root end tag (observed). App does the same: it stops reading at `</[ROOT]>` and ignores what follows, whatever its bytes. This rule is about bytes inside the decompressed document only. Bytes after the gzip member are FMT-08.7 (`Corrupt`, decided: spec/decisions.md LD-02); bytes after the final block or after the logical end of the file are ignored (decided: spec/decisions.md LD-01; FMT-01, FMT-06, FMT-07).
- Invalid UTF-8 after `</[ROOT]>` is a known difference (AT-A11). The reference decodes the document in chunks, so badly encoded bytes close enough to the root end tag to fall in the same chunk reject the whole document (observed: byte `FF` directly after `</[ROOT]>` was rejected, reported as no root group), while the same byte further away is never decoded (observed: `FF` after 9,000 or 20,000 spaces opened). The chunk size was not measured for the vault document; for the same XML reader in key files FMT-18.7 (*Invalid byte sequences*) found blocks of 8192 bytes, which fits these observations. App ignores everything after `</[ROOT]>` in every case, because a rule that depends on distance cannot be matched exactly and the bytes carry no data. The source build may decode differently: check with Verify.

FMT-10.6 `Root` on read. Its `Group` child is the root group (FMT-11). No `Group` rejects the document (no root group). A second `Group` child of `Root` rejects the document. `DeletedObjects` is read per FMT-15. Any other child is unknown (FMT-10.20).

FMT-10.7 Element names are compared exactly and case-sensitively, on the local name. A namespace prefix or a default namespace declaration is ignored: `<x:Meta xmlns:x="urn:x">` on a declared prefix is read as `Meta` (observed). An undeclared prefix makes the document malformed, and it is rejected. A name in another case (for example `databasename`) is an unknown element. This local-name rule is for element names only. Attribute names are matched on the full name as written, prefix included, case-sensitively: `x:Protected` or `protected` is not the `Protected` attribute (FMT-12.13, observed).

FMT-10.8 XML input the reader accepts: encoding and declaration. The reference reads the start of the vault document with the same XML reader, and the same rules, as the start of a key file document. FMT-18.7 describes those rules in full (detection, declaration syntax, encoding names). Every case below that was tried on a vault document behaved as FMT-18.7 says. App reads only UTF-8 (decided: spec/decisions.md, default rule; no known writer produces other encodings inside a vault). So App applies FMT-18.7 with UTF-8 as its only decoder, in these steps:
1. Detection. The first bytes of the document are checked against these rows from top to bottom (the same rows as FMT-18.7 *Detection*); the first row that matches decides:

| First bytes | What FMT-18.7 detects | App |
|---|---|---|
| `FF FE 00 00` or `00 00 FE FF` | UTF-32 with a byte order mark | `Unsupported` |
| `3C 00 00 00` or `00 00 00 3C` | UTF-32 without a mark | `Unsupported` |
| `FF FE` or `FE FF` | UTF-16 with a byte order mark | `Unsupported` |
| `3C 00` or `00 3C` | UTF-16 without a mark | `Unsupported` |
| `EF BB BF` | UTF-8 with a byte order mark | UTF-8; these 3 bytes are dropped |
| anything else | UTF-8 | UTF-8 |

The reference decodes the four non-UTF-8 forms and opens such documents (observed: UTF-16LE, UTF-16BE, UTF-32LE and UTF-32BE, each with and without a mark and with no declaration). Every other start is read as UTF-8. So a document that starts with, for example, two `00` bytes and then UTF-8 text holds U+0000, which is `Corrupt` (FMT-12.24; the reference rejects it too, observed).
2. Start of the document. After a dropped `EF BB BF`, the declaration, when there is one, must be the very first thing. Anything before it, even white space or a comment, is `Corrupt` (observed: a space before `<?xml` was rejected). The declaration is optional; a document without one may start with white space (observed: a document starting with LF and no declaration opened).
3. Declaration syntax. The strict form of FMT-18.7 *Declaration syntax* applies: `<?xml` in lowercase; `version` first, then any number of `encoding`, then any number of `standalone` (value `yes` or `no`, lowercase); single or double quotes; no other pseudo-attribute names; no second `<?xml` processing instruction anywhere before the root end tag. Every breach is `Corrupt`, except the version values named in step 4 (observed: no `version`, `standalone` before `encoding`, `standalone="maybe"` and `<?XML` were all rejected; single quotes opened).
4. Version. The value must be exactly `1.0`. A value of `1.` followed by one or more ASCII digits that is not exactly `1.0` (the shape of XML 1.0 production VersionNum, for example `1.1` or `1.00`) is `Unsupported`: it names an XML version App does not read. Any other value (for example `2.0`, or `1.0 ` with a space) is `Corrupt`. The reference rejects all of them (observed: `1.1`, `1.00`, `2.0` and `1.0 `, each reported as no root group).
5. Encoding names. Each `encoding` value must first pass the EncName check of FMT-18.7: one ASCII letter, then any number of ASCII letters, ASCII digits, `.`, `_` and `-`. A name that fails is `Corrupt`. A name that passes is folded as FMT-18.7 *Names* says: ASCII letters are lowercased and every character that is not an ASCII letter or digit is removed. App accepts a name only when it folds to `utf8`; any other name is `Unsupported`. When `encoding` is repeated (the reference allows this, FMT-18.7), every value must pass. Results:
   - `UTF-8`, `utf-8`, `Utf-8`, `uTf-8`, `UTF8`, `UTF_8`, `utf.8`, `U.T.F.8` and `u-t_f.8` are UTF-8 in both apps (observed).
   - `_utf8`, `utf 8` and `UTF+8` fail the EncName check. Both apps reject them (observed), App as `Corrupt`.
   - `US-ASCII` and `ascii` fold to other names. Both apps reject them (observed: the reference does not know these names and reports no root group), App as `Unsupported`, although ASCII is a subset of UTF-8.
   - Names of other encodings the reference knows (`ISO-8859-1`, `latin1`, the UTF-16 and UTF-32 names, windows-1252 and others, FMT-18.7) are `Unsupported` in App. The reference decodes with them (observed: `ISO-8859-1` and `latin1` opened).
6. Known differences. The reference opens documents that App rejects as `Unsupported` in step 1 and with the non-UTF-8 names of step 5. These are deliberate differences and go on the AT-A11 known-differences list. In every other case of this rule both apps reject the same documents; only App's error kind is its own.
7. Source build (differs in installed version). The source needs the newer toolkit generation. Its XML reader knows fewer encodings and may compare names differently, for example without ignoring `.`, so `utf.8` and `U.T.F.8` might be rejected there (FMT-18.7, *Source build*). Check with Verify on a build of the source. If the source rejects a name that App accepts, App keeps its rule (App never misreads such a document; it only accepts a name the source does not), and the case goes on the AT-A11 watch list.

FMT-10.9 Document type declarations. The reference accepts a `<!DOCTYPE ...>`, expands internal entities declared in it, and silently replaces an external entity with empty text (observed with a local file entity). App rejects any document that contains a `<!DOCTYPE` as `Corrupt`, before reading further (security plan: no DTD, no entities, ever). A reference to an undefined entity (for example `&nbsp;`) is rejected by both.

FMT-10.10 `Meta` children: write order, types, defaults and versions. App writes the elements in exactly this order, except row 28, which is written directly after row 13 (decided: spec/decisions.md LD-62). "Default" is the value for a new vault and the value kept when the element is missing on read. "Open time" means the current UTC time, in whole seconds, taken when the read starts.

| # | Element | Type (FMT-12) | Default (new vault, and when missing on read) | Written in | If invalid on read |

Times are written in the binary form in version 4 and in the text form in version 3 (FMT-12.2, FMT-12.3). A null group reference is written as `AAAAAAAAAAAAAAAAAAAAAA==` (FMT-12.16). Empty text is written as `<Name/>`.

FMT-10.11 Known `Meta` children on read. The reader knows exactly the 28 names in the FMT-10.10 table and accepts them in any order, in every file version: a version 4 file may hold `HeaderHash` or `Binaries`, a version 3 file may hold `SettingsChanged`. The items of a `Binaries` element in a version 4 document join the attachment pool and can replace items from the inner header, per FMT-13.7. Every other child of `Meta` is unknown (FMT-10.20). App must treat exactly this set as known, so that every element whose protected value the reference decrypts is decrypted by App too, no other element takes keystream bytes (FMT-09.14), and the protected-field stream stays in step with the reference (FMT-12.22, FMT-09.13). FMT-12.29 lists every value element App decrypts, in `Meta` and in the rest of the document. Of the 28 names above, the containers `MemoryProtection`, `CustomIcons`, `Binaries` and `CustomData` are not value elements: a `Protected` attribute on them is ignored and takes no keystream bytes. Row 28, `MasterKeyChangeForceOnce`, is known to App but not to the reference, so it never takes keystream bytes either, even with `Protected="True"`; its text is read as written (MOD-13.13, FMT-09.14).

FMT-10.12 Values read are kept exactly. While the document is read, no "...Changed" time is updated: setting the name does not touch `DatabaseNameChanged`, and so on. The order of a value and its "...Changed" time in the file does not matter.

FMT-10.13 Repeated elements. When a simple `Meta` child appears more than once, the last one wins (observed with two `DatabaseName` elements: the second is kept). With two `Meta` elements, values from the second replace those from the first, and values only in the first stay. Repeated `MemoryProtection` containers merge flag by flag (FMT-10.17). Repeated `CustomIcons` and `CustomData` blocks add up instead of replacing (FMT-14.5, FMT-14.16), and the items of repeated `Binaries` all go into one pool (FMT-13.6, FMT-13.7).

FMT-10.14 Invalid values. Text values cannot be invalid. Times that cannot be read become the open time, without error (FMT-12.7). Integers and booleans that cannot be read reject the whole document (the reference reports an invalid number or an invalid boolean value). A UUID that cannot be read is null (FMT-12.17). A color is kept as read. These outcomes match the reference's normal reading mode. The reference also has a strict mode, used only by its own tests, that rejects more; App does not copy it.

FMT-10.15 History limits. `HistoryMaxItems` is the most history versions kept per entry. `HistoryMaxSize` is the most bytes of history kept per entry. Both are signed 32-bit integers, and -1 means no limit. On read, a value below -1 is ignored: the value read before it stays (the default if none was read before), the reference only logs a warning, and the next save writes that kept value (observed: `<HistoryMaxItems>5</HistoryMaxItems><HistoryMaxItems>-2</HistoryMaxItems>` is written back as 5). A value that is not an integer rejects the document (FMT-10.14). What the limits do is in MOD-03.

FMT-10.16 Group references. `RecycleBinUUID`, `EntryTemplatesGroup`, `LastSelectedGroup` and `LastTopVisibleGroup` each name a group by UUID. They are resolved after the whole document is read, against every group in the tree, wherever it is and whether it comes before or after `Meta`. A null UUID, an unreadable UUID, or a UUID that matches no group (including the UUID of an entry) gives "no reference". On write, the UUID of the referenced group is written, or the null UUID when there is none. So a dangling reference is written as the null UUID on the next save (observed). App does the same. The reference never sets `EntryTemplatesGroup`, `LastSelectedGroup` or `LastTopVisibleGroup` itself (no code sets them outside reading); it only carries them from read to write. App also only carries them. The root group itself is a valid target (observed: all four pointing at the root group are kept).

FMT-10.17 Memory protection flags. `MemoryProtection` holds five booleans, written in this order with these defaults:

| Element | Default |
|---|---|
| `ProtectTitle` | False |
| `ProtectUserName` | False |
| `ProtectPassword` | True |
| `ProtectURL` | False |
| `ProtectNotes` | False |

On read, a missing flag keeps the value read before it, or its default if none was read. Repeated `MemoryProtection` elements (in one `Meta` or in several) therefore merge flag by flag: each sets only the flags it holds, and the last value read for a flag wins (observed: a first container with Title True and Password False, then a second with only Notes True, gives Title True, UserName False, Password False, URL False, Notes True). An unknown child of `MemoryProtection` is unknown (FMT-10.20). An invalid boolean rejects the document. All five are always written. What the flags do on write (they force `Protected="True"` on the matching standard entry field) is in FMT-11 and MOD-12. On read, the flags never change a field's protection; that comes from the field's own attribute (FMT-09).

FMT-10.18 Recycle bin settings. `RecycleBinEnabled` (default True) says whether deleting moves items to the recycle bin. `RecycleBinUUID` names the recycle bin group (null until one is made). `RecycleBinChanged` is the time the recycle bin group was last set or cleared. The UUID is kept even when `RecycleBinEnabled` is False (observed). That is a file fact only: it holds for a read and write round trip. When the user turns the recycle bin off on the reference's vault settings screen, the reference clears `RecycleBinUUID` (so `RecycleBinChanged` moves). If the old bin is not empty it first asks whether to delete it: yes deletes the bin and everything in it; no keeps it as a normal group, renamed with ` (old)` added to its name and given the default group icon. An empty old bin stays as a normal group, unchanged (from the source). Behavior is in MOD-04.

FMT-10.19 Master key change settings. `MasterKeyChanged` is the time the composite key was last changed. `MasterKeyChangeRec` is the number of days after which a key change is recommended. `MasterKeyChangeForce` is the number of days after which a key change is forced. -1 turns each one off (default). `MaintenanceHistoryDays` (default 365) is stored and written back. The reference reads and writes all four, but no code in the reference source acts on `MasterKeyChangeRec`, `MasterKeyChangeForce` or `MaintenanceHistoryDays`: a search of the whole source tree finds them only in the metadata model (getters, setters, defaults) and in the XML reader and writer. Parity row SF-13 in plan/security.md says the reference reminds or forces a master key change; that does not match the source. Flagged for E1-S7: SF-13 should read "stores and round-trips the key change days; no reminder in the reference", and App's reminder becomes an App extra, decided in MOD-13. This card keeps its SF-13 link, because the file fields are what SF-13 rests on. App behavior is in MOD-13.

FMT-10.20 Unknown elements. The reference skips every unknown element (it logs the element name) and does not write it again, so unknown elements are lost on its next save (observed for unknown children of `Meta` and of `[ROOT]`). Parity row SD-06 in plan/security.md says the reference keeps data it does not understand; it does not. It drops unknown document elements (this rule, FMT-11.44), unknown outer header fields (FMT-02.21), unused KDF map keys (FMT-03.19) and unknown inner header fields (FMT-09.3). Flagged for E1-S7: SD-06 becomes an App extra (the reference drops unknown parts). This card keeps its SD-06 link for App's own rule. App keeps them (SD-06):
- App keeps each unknown child of `[ROOT]`, `Meta`, `MemoryProtection` and `Root`: its local name, its attributes (as below) with their order and values, its child elements, and its text, as FMT-10.27 defines. A namespace prefix on an element name is not kept (the name is written without it, FMT-10.7). Of the attributes, App keeps only those whose name has no prefix (no `:` in the name). These name and attribute rules apply to the kept element and, in the same way, to every element inside it, at any depth. Every attribute with a prefix is dropped, whatever the prefix: `x:k`, `xml:lang`, and namespace declarations `xmlns:...`; the default namespace declaration `xmlns` is dropped too. The written document therefore never holds an undeclared prefix, and attribute names on a kept element stay unique (XML 1.0 constraint Unique Att Spec; Namespaces in XML section 6.3 treats `x:k` and `k` as different attributes, so keeping `x:k` without its prefix could clash with `k`). This attribute rule is App's own (SD-06); the reference drops the whole element.
- On write, App writes the kept unknown children of a parent after all of that parent's known children, in the order they were read. For `Meta` this means after `CustomData` (or after the last known element written). The layout is FMT-10.27; attribute values are escaped per FMT-10.28.
- Protected values inside an unknown element: FMT-09.14 is the only rule, for reading and for writing (decided: spec/decisions.md LD-24). This card adds nothing to it. In short: a kept unknown element takes no keystream bytes, even when it carries `Protected` and holds text. On read App keeps its raw text exactly as read and never decrypts it. On save App writes that raw text back unchanged, with its attributes as read (so `Protected` stays), and takes no keystream bytes for it. Re-encrypting it at its position is never allowed. This is what the reference does on read: it skips unknown elements without decrypting them and without taking keystream bytes (observed for an unknown `Meta` child and, in FMT-09, for an unknown entry child), so the protected values after a kept element stay in step in both apps.
- Unknown attributes on known elements (for example `<Meta foo="1">`) are not kept. The reference ignores and drops them too (decided: spec/decisions.md, default rule).
- Comments and processing instructions are not kept, inside or outside kept elements. The text on both sides of a dropped comment is joined (FMT-12.23).

FMT-10.21 Header hash (version 3). `HeaderHash` holds the base64 form (FMT-12.21) of the SHA-256 hash of the outer header bytes: from file offset 0 through the last byte of the end-of-header field, that is the two signatures, the version, and every header field including the end field (FMT-02, FMT-17).
- Read, version 3 files (3.0 and 3.1): after the whole document is read, take the value of the last `HeaderHash` element (FMT-10.13), decoded with FMT-12.20. If there is none, or it decodes to zero bytes, nothing is checked and the file opens, as in the reference (decided: spec/decisions.md LD-11). Otherwise it must equal SHA-256(header bytes), or the file is rejected (the reference reports that the header does not match its hash). App compares in constant time (Rust rule 6). The reference's own version 3.0 test vault `Format300` has no `HeaderHash` and opens.
- Read, version 4 files: `HeaderHash` is read and ignored, never checked (observed: a wrong value opens). Header integrity in version 4 is FMT-05.
- Write: App never writes `HeaderHash` (it writes version 4 only). The reference writes it only in version 3 files, as the second child of `Meta` right after `Generator`, and only when it writes a vault file (not in its plain XML export).

FMT-10.22 Generator. For a vault it creates, the reference writes `[REFNAME]`. For a vault it opened, it writes back the `Generator` value it read and does not replace it with its own name (observed: `OtherApp 1.0` is kept on save). When `Generator` is missing on read, the default is the reader's own name. App writes `App` for vaults it creates and when the element is missing, and otherwise keeps the value it read (decided: spec/decisions.md, default rule; the name changes in the D1 rename pass).

FMT-10.23 Version gates on write. `SettingsChanged` is written only in version 4.0 and later. `HeaderHash` and `Binaries` are written only in version 3. `CustomIcons` is always written. Its 4.1-only parts (icon name and last-modification time) are in FMT-14. `CustomData` is written in every version when not empty, which in App's saves is always (FMT-10.25). Its 4.1-only part (item times) is in FMT-14. Apart from custom icon names and times, which raise the file version to 4.1 (FMT-16.10), no `Meta` element raises the version. `Meta` custom data does not raise it (it is written in version 3 too), and its item times are written only in 4.1 (FMT-14). Kept unknown elements (FMT-10.20) are the one exception on App's side: while App keeps any, it writes at least the version the file was read as (FMT-16.24), even if no known content needs it: a file read as 4.2 is written as 4.2 (decided: spec/decisions.md LD-09; FMT-16 chooses the number). The reference drops them and chooses from known content only (FMT-16.20).

FMT-10.24 "...Changed" times outside reading. After a vault is open, App sets a "...Changed" time to the current UTC time only when the matching value really changes: name sets `DatabaseNameChanged`; description sets `DatabaseDescriptionChanged`; default user name sets `DefaultUserNameChanged`; the recycle bin group sets `RecycleBinChanged`; the templates group sets `EntryTemplatesGroupChanged`. Setting a value to what it already is changes nothing. The reference behaves the same for these five (from the source: its setters compare old and new). `MasterKeyChanged` and `SettingsChanged` are different:
- The reference sets `MasterKeyChanged` every time a new composite key is set, without comparing it with the old one: when the key page of its vault settings screen is saved with a key part added, removed or opened for editing (even if the same password is typed again), and when its CLI vault edit command is given a key option (observed: `db-edit -p` with the same password `demo` moved `MasterKeyChanged` to the current time). Opening and saving a vault never move it.
- App sets `MasterKeyChanged` every time the user confirms a key change, without comparing the new key with the old one, the same as the reference (App's choice: comparing would need the old key parts kept in memory and adds nothing). Opening and saving never move it.
- The reference sets `SettingsChanged` every time the general page of its vault settings screen is applied, even when nothing on it changed (from the source: the page's save step sets it without comparing).
- App sets `SettingsChanged` when the vault settings screen is applied and at least one value of the settings group listed in MOD-12.9 differs from its value before. Name, description and default user name are not in that group (they have their own times), so applying only a new name does not move it (decided: spec/decisions.md LD-33; the merge of MOD-11.19 needs this list; App differs from the reference here only in when the time moves, not in the file format).
Details are in MOD-12 and MOD-13.

FMT-10.25 Random item on every save (pointer). On every save the reference sets one `Meta` custom data item, the random padding item, so that the size of the saved file changes from save to save. App writes the same item with a fresh value on every save (decided: spec/decisions.md LD-16). FMT-14.21 owns its key and value format and its effect on `_LAST_MODIFIED`; CRY-03.7 owns how its bytes are drawn. So App's vault custom data is never empty on save, and every App save writes `CustomData`. FMT-10 only fixes where it goes: inside `CustomData`, the last known element of `Meta` (kept unknown children of `Meta` follow it, FMT-10.20).

FMT-10.26 Pointers. `CustomIcons` content is FMT-14. `CustomData` content is FMT-14. `Binaries` content is FMT-13; in a version 4 document its items join the pool per FMT-13.7. Entry and group content is FMT-11. `DeletedObjects` content is FMT-15. The text, time, number, boolean, UUID, color and base64 forms of every value above are FMT-12.

FMT-10.27 Layout of kept unknown elements. The reference drops unknown elements, so this rule is App's own (SD-06). It is chosen so that reading and writing the same document twice gives identical bytes. "Whitespace" here means only the XML whitespace characters SPACE (0x20), TAB (0x09), LF (0x0A) and CR (0x0D), counted after XML decoding (FMT-12.23). On read, App sorts every kept element into one of four kinds by its content (after dropping comments and processing instructions):
1. Empty: no text and no child elements. Written `<Name/>` (with its attributes, if any: `<Name a="1"/>`). `<Name></Name>` is read as empty and written `<Name/>`.
2. Text only: text and no child elements, including text that is only whitespace. Written on one line as `<Name>text</Name>`, the text kept exactly, escaped per FMT-12.26 (so CR is written `&#13;`).
3. Elements only: child elements, and every text part (before the first child, between children, and after the last child) is whitespace only. That whitespace is layout: it is not kept, unless the element sits inside a mixed element (kind 4), where all text is kept. Written per FMT-10.2: the start tag on its own line, each kept child one depth deeper, the end tag on its own line at the start tag's depth.
4. Mixed: child elements and at least one text part that is not whitespace only. Every text part is kept exactly, including whitespace-only parts, and written escaped per FMT-12.26; the element is written on one line at its depth with all its content inline, exactly in the order read, with no line breaks or TABs added anywhere inside it. Its descendant elements are written inline the same way, whatever their own kind; inside a mixed element nothing is added and no whitespace is dropped.
Each written line starts with the TABs for its depth and ends with LF, as in FMT-10.2. A text part that holds LF continues on the next line with no indentation, as in FMT-10.2.

FMT-10.28 Attribute values on write. App writes attribute values in double quotes. In a value it writes `&` as `&amp;`, `<` as `&lt;`, `>` as `&gt;`, `"` as `&quot;`, TAB as `&#9;`, LF as `&#10;` and CR as `&#13;`. Every other character, including the apostrophe, is written as raw UTF-8. The character references for TAB, LF and CR are needed because an XML reader turns a raw TAB, LF or CR inside an attribute value into a space (XML 1.0 section 3.3.3). On read, App keeps the attribute value as its XML reader gives it after that normalization: a raw TAB in a value read from a file is kept as a space, a `&#9;` is kept as a TAB. Attributes written by the defining cards (FMT-10.3) never hold these characters.

## Edge cases and errors

- Wrong root element name, no root element, no `Root`, two `Root` elements, `Root` without `Group`, two `Group` children of `Root`: the document is rejected. App returns `Corrupt` (FMT-10.5, FMT-10.6).
- A value element that holds a child element (for example `<DatabaseName>a<b/>c</DatabaseName>`): rejected (FMT-12.23).
- `HistoryMaxItems` of `-2`: ignored; written back as `10` when no earlier `HistoryMaxItems` was read, otherwise as the earlier value (FMT-10.15). `HistoryMaxItems` empty, `0x10`, `7.0` or `2147483648`: document rejected. `HistoryMaxItems` of ` 7 `, `+7` or `007`: read as 7 (FMT-12.15).
- `MaintenanceHistoryDays` of `-5`: accepted and written back as `-5` (no range check).
- `RecycleBinEnabled` of `1`, `yes` or ` True `: rejected. Empty `RecycleBinEnabled`: False (FMT-12.10).
- `RecycleBinUUID` naming a group that does not exist: no recycle bin, null UUID on save. The reference logs one invalid group reference.
- `Color` of `red`: kept and written back as `red`.
- `Generator` missing: App writes `App`; the reference writes `[REFNAME]`.
- Every "...Changed" time missing: each becomes the open time and is written back as that time. A missing `MasterKeyChanged` therefore restarts the key change clock at open time. App does the same as the reference; MOD-13 decides if App should warn.
- Version 3 file with a wrong `HeaderHash`: rejected. App returns `Corrupt`, not `WrongKey` (the key was already proven by the stream start bytes, the only version 3 `WrongKey` case: decided: spec/decisions.md LD-12; FMT-05, FMT-17).
- Version 3 file with `HeaderHash` present but empty, or with two `HeaderHash` elements where the last one is right: opens (observed).
- Byte `FF` (invalid UTF-8) directly after `</[ROOT]>`: the reference rejects the document, App opens it; the same byte after 9,000 spaces: both open (FMT-10.5). A known difference: list it in the AT-A11 known differences.
- Document with a `<!DOCTYPE`: the reference opens it; App rejects it (FMT-10.9). A deliberate difference: list it in the AT-A11 known differences.
- Document declared as ISO-8859-1 or latin1, or detected as UTF-16 or UTF-32 from its first bytes (with or without a byte order mark): the reference opens it; App rejects it as `Unsupported` (FMT-10.8). A deliberate difference for the AT-A11 known differences.
- Document declared `encoding="utf-8"` (lowercase), `encoding="UTF8"` or `encoding="u-t_f.8"`: both open it. Declared `US-ASCII`: both reject it, App as `Unsupported`. Declared `_utf8`: both reject it, App as `Corrupt` (FMT-10.8).
- Declaration `version="1.1"` or `version="1.00"`: both reject it, App as `Unsupported`. `version="2.0"`, a missing `version`, `<?XML`, white space before `<?xml`, `standalone` before `encoding`, or `standalone="maybe"`: both reject it, App as `Corrupt` (FMT-10.8).
- Text, a comment or a processing instruction directly inside `Meta`, `MemoryProtection` or `Meta/Binaries`: ignored by both, not kept by App (FMT-10.5).
- Kept unknown element with mixed content, for example `<FooBar>x<Baz/></FooBar>`: written inline on one line exactly as read; a second save gives the same bytes (FMT-10.27).
- Kept unknown element with a prefixed attribute, for example `<Ext x:k="1" k="2"/>` with `x` declared: written `<Ext k="2"/>`; the prefixed attribute is dropped, so no undeclared prefix and no duplicate `k` (FMT-10.20).
- Kept unknown element whose attribute value holds a TAB written as `&#9;`: written back as `&#9;`, never as a raw TAB, which the next read would turn into a space (FMT-10.28).
- Error texts. The reference reports these document errors to the user: no root group, an invalid number value, an invalid boolean value, the header does not match its hash, and its XML parser's error with line and column. App maps all of them to `Corrupt` and shows the plain message from APP-06. Detail goes to the debug log without values (Rust rule 8).

## Security notes

- Random item (SF-07, AT-B03; decided: spec/decisions.md LD-16). The value of the item in FMT-10.25 must be new on every save. Never carry over the value read from the file: a stale value would let two saves of one vault be matched by size.
- Hostile documents (AT-A07, AT-A08). App rejects `<!DOCTYPE` before any entity work. It never resolves external entities, and caps document size, element depth, text node size and element count from `limits.rs` before allocating. The reference's XML toolkit limits entity expansion (observed with the installed CLI: an internal entity expanding to 1,000 characters was accepted, one expanding to 10,000 characters was rejected, reported as no root group), but the reference sets no depth or size limits of its own. App rejects `<!DOCTYPE` outright in any case (FMT-10.9). The numbers are in FMT-08.12, the only limits table (decided: spec/decisions.md LD-22); this card sets none.
- Dangling and hostile group references (AT-A08). A UUID in `RecycleBinUUID` and the others must never cause a lookup panic or point outside the tree. Unresolved means none (FMT-10.16).
- Header hash (SF-05, AT-A02). In version 3 the header hash is the only thing that protects header fields not used in the key derivation, such as the protected-stream key and the compression flag. App must check it whenever a non-empty value is present, and compare in constant time. Never treat a mismatch as a wrong key.
- Unknown data (SD-06). The reference drops unknown parts, so keeping them is an App extra (FMT-10.20; flagged for E1-S7 to reword SD-06). Kept unknown elements are written back as data only and never interpreted. Their size counts against the limits. The layout rule (FMT-10.27) and the attribute escaping (FMT-10.28) make sure a kept element does not change from save to save.
- Protected values in kept unknown elements (SF-08, AT-A11). Under FMT-09.14 (decided: spec/decisions.md LD-24) App never decrypts such a value and never takes keystream bytes for it, on read or on write, exactly like the reference. What must never happen: App taking keystream bytes for a kept unknown element on read or on write. On read that would decode every later protected value wrongly. On write it would make the reference decode every later protected value in App's file wrongly, passwords included. The kept raw text was encrypted under the old file's stream key, and App saves with a new stream key, so after a save nobody can decrypt that text any more. It stays opaque data and leaks nothing, because the old stream key is not in the new file. A file whose writer did take keystream bytes for an unknown element decodes wrongly in both apps (FMT-09.14). No AT-A11 difference here. This card states no rule of its own; FMT-09.14 owns it.
- Logs (AT-C06). The reference logs skipped element names and stripped code points. App logs only counts. It never logs element text, names read from the file, metadata values, or anything from a protected value.
- Screen (AT-E01). `DatabaseName`, `DatabaseDescription`, `DefaultUserName` and `Color` are attacker-controlled text when a hostile vault is opened. The screen sets them as text, never as HTML. `Color` is used as a color only when it matches FMT-12.18.
- Key change settings (SF-13). The reference source does not act on them (FMT-10.19), so the parity row's claim of a reminder is wrong for the reference. Flagged for E1-S7 to reword SF-13 before MOD-13 is built. Whatever MOD-13 decides, App must store and write back the three values unchanged, so the reference and other apps see the same settings.

## How this was learned

- Read in the reference source: the document reader (top structure, `Meta`, memory protection, value readers), the document writer (write order, version gates, layout settings, text stripping), the metadata model with its defaults, the version 3 and version 4 file readers (where the header hash is checked or ignored), the file writer that picks the version, the save routine (the random custom data item), the database settings screen (which values set which "...Changed" time), and a whole-tree search for code that uses the key change settings. Read the reference format tests and its XML test documents `NewDatabase`, `EmptyUuids`, `BrokenNoRootGroup`, `BrokenTwoRoots` and `BrokenTwoRootGroups`. The reference's strict reading mode is used only by those tests; normal opening uses the non-strict mode described here.
- Ran the installed reference CLI (version 2.7.11, built on an older major version of its UI toolkit than the source) on demo data only, in `/tmp/spec-fmt10-12/`. A scratch script built version 3.1 and version 4.0 demo vaults (AES-KDF, password `demo`) holding hand-made XML documents. They were opened with the CLI `export -f xml` to see what was read and written, and saved with the CLI `mkdir` command. The scratch script then decrypted the saved files to see the exact in-vault XML bytes (declaration, tabs, LF, order, version gates). The CLI's plain XML export uses the same writer as the vault file, except that it never writes `HeaderHash` and writes protected values in plain text.
- Decrypted the reference test vaults `Format300`, `ProtectedStrings`, `Compressed` and `BrokenHeaderHash` (read only, passwords from the reference tests) to check the header hash rule, and opened them with the CLI.
- Review round 1 additions, again on demo vaults only: the declaration encoding names `utf-8`, `Utf-8`, `UTF8` (opened), `US-ASCII` and `ascii` (rejected); a valid `HistoryMaxItems` followed by `-2` (the first value kept); internal entities expanding to 1,000 and 10,000 characters (the first opened, the second rejected). Read in the source: the version choice in the file writer (custom icon names and times raise it to 4.1), the save step of the general vault settings page (it sets the settings-changed time without comparing), and the metadata setters (the other six "...Changed" times move only on a real change).
- Review round 2, demo vaults only (version 4, inner stream key all zero, in `/tmp/spec-fmt10-12/r2/`): an unknown `Meta` child `<X Protected="True">` followed by a protected entry password. The CLI decoded the password from keystream byte 0 when `X`'s writer took no bytes, and showed it garbled when `X`'s writer did take bytes. Both times it dropped `X`. FMT-10.20 now points to FMT-09.14, which follows LD-24 (never decrypt, no keystream bytes, raw write-back).
- Review round 3, demo vaults only, in `/tmp/spec-fmt10-12/r3/`: `x:Protected`, `protected` and `PROTECTED` on `DatabaseName` before a protected `DatabaseDescription` (all-zero inner stream key; each name read literally, the description from keystream byte 0); CLI `db-edit -p` with the unchanged password `demo` (moved `MasterKeyChanged`). Read in the source: the database's set-key routine (it sets the key-changed time whenever its update flag is on, the default, without comparing keys), its callers (the key settings page, the CLI edit command; the file readers and writers turn the flag off), the metadata setters (they compare), and the save step of the general vault settings page (recycle bin turned off).
- Review round 4, demo vaults only, in `/tmp/spec-fmt10-12/r4/` (version 4, password `demo`): byte `FF` directly after the root end tag (rejected) and after 9,000 and 20,000 spaces (opened); raw 0x01 and `garbage<` after the root end tag (opened); two `MemoryProtection` containers (merged flag by flag). Read in the source: the memory-protection reader sets only the flags it finds.
- Cross-check round, demo vaults only, in `/tmp/spec-fmt10-12/r5/` (version 4, password `demo`): the declaration and encoding cases of FMT-10.8 (UTF-8 name spellings, EncName failures, `US-ASCII`, `latin1`, version values, broken declarations, single quotes, white space before the declaration) and the eight UTF-16 and UTF-32 starts with and without a mark; stray text, a comment and a processing instruction directly inside `Meta`, `MemoryProtection` and `Meta/Binaries` (FMT-10.5); `Protected` on the `Meta` containers before a protected `DatabaseName` (FMT-10.11). Read in the source: the root, `Meta`, memory-protection and pool readers loop over start elements only, skipping every other token; a whole-tree search for the key change settings (FMT-10.19) found them only in the metadata model and the XML reader and writer. Parity rows SF-13 and SD-06 were found to describe the reference wrongly and are flagged for E1-S7 (FMT-10.19, FMT-10.20).
- Close-out round, demo vaults only, in `/tmp/spec-fmt10-12/r6/` (password `demo`): a version 3.1 vault with no `HeaderHash` element opened; version 4.1 and 4.0 vaults with no 4.1 content and an unknown `Meta` child were both saved by the CLI `mkdir` command as 4.0, without the unknown child. The lead rulings in spec/decisions.md were written into the rules (LD-01, LD-02, LD-07, LD-09, LD-11, LD-12, LD-16, LD-22, LD-24, LD-33 and the default rule).
