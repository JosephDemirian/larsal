# FIL-05 Encrypted-folder screens and flows

Status: **reviewed, 2026-11-05 (E23-S1 specification and static proposals only)**; seven second-Spec corrections and fresh independent Verify APPROVE have no required findings. Exact conditional adoption/closure binding: the research [Review and proof](../research/encrypted-folders.md#review-and-proof) footer.
Epics: E23-S4, E23-S5, E23-S6
Parity: FOLD-P3/P4/P5; all todo, runtime proof OPEN.

## What it does

Larsal's own window creates/unlocks/browses an encrypted folder and adds, opens, saves out, renames and deletes files and folders. It can use its own password without an open password vault, or an explicitly chosen password kept in one. Finder is a separate S5 integration. [Research](../research/encrypted-folders.md) supplies public F01–49 and R1–7 (LD-372–378); behavior below does not grant new API crossings or weaken original acceptance.

## Inputs and outputs

Explicit root/source/destination selection, secure password input or opaque protected-entry selection, node/session generations and lifecycle signals. Swift holds cleaned plain-text names, sizes/status and opaque handles. Rust owns all retained credentials/content. Password-entry UI uses existing secure fields and the named transient input review, never an all-vault password list or persistent Swift secret. Demo names in static frames are illustrative.

## Rules

FIL-05.1 File menu has New Encrypted Folder… and Open Encrypted Folder…; welcome view offers both. A folder opens only after explicit selection, no automatic root detection, recursive home scan or downloaded-key fetch. Existing vault/attachment/E22 drops retain their routing; the folder's dedicated Add Files drop target is separate. F15, APP-08/R1.

FIL-05.2 Create chooses a parent and new folder name, shows storage location and classic profile help, then Own Password or Generate and Save in Vault. Never convert/delete/encrypt an existing source folder in place. Exclusive new root creation, initialize with journal; on failure preserve originals, remove only proven owned incomplete objects or surface cleanup failure. FIL-06.6/.7, F37/F38/R1/R4.

FIL-05.3 Own Password uses secure password/repeat, length/strength and mismatch help; weak confirmation has Cancel default. Optional Save in Vault is explicit and on only when a writable unlocked vault exists. Generated-and-saved mode requires writable vault/group/title and durable protected-entry save before root publication; cancellation after save keeps that entry and says so. Never infer/use the master password. FIL-01.6, APP-05/R5/R6.

FIL-05.4 Unlock has two explicit choices, Folder Password and Choose from Vault…. Selection is bound to protected entry id/revision and vault/session generation; if that vault is locked ask its normal unlock first, Cancel changes nothing. Manual password works with all password vaults closed. No Touch ID/Keychain shortcut or remembered password is invented; the folder stays locked on failed/cancelled/late unlock. APP-02/06/11, LD-220/R5.

FIL-05.5 Unlocked list has breadcrumb, Up, Refresh, Add Files…, New Folder…, Open, Save Out…, Rename…, Delete… and Lock Folder. Show per-item type/size/storage-time labels accurately; storage dates are untrusted observations, not authenticated author times. Selection uses opaque IDs plus revisions, never a path made from displayed text. Empty state is a working Add/drop target; selection-dependent controls disable with named help. F15/F04/R4.

FIL-05.6 Add accepts explicitly selected regular local files and a bounded explicit folder-tree import, preserving originals. Preflight each name/type/collision and show count/size; links/packages/devices/unknown remote URLs fail visibly, no archive or mount inference. Same-name item offers Keep Both or Cancel, never silent overwrite. Partial batch completion lists completed/pending items; cancellation removes only the active uncommitted owned item and retains completed encrypted items. FIL-06.2/.3/.6/R4.

FIL-05.7 Open deliberately opens the selected revision in a first-party Larsal file/document view after complete stable-input validation. No readable disk copy, external launch, shell/URL interpretation, background preview, Quick Look or clipboard. Preserve functional Open and exact byte navigation for arbitrary supported files; text shows readable text, images a real image, PDFs readable pages/page navigation, binary an offset/byte view. Byte view supplements these presentations; hex-only is not a passing semantic preview. Rust retains credentials/content and bounded working buffers; only the explicitly requested presentation enters the named reviewed rendering route, no password/key crossing. F43–49, APP-10/R2/R3.

FIL-05.8 Opened Files lists all first-party live document/view handles, bound selected encrypted revisions and changed/unchanged state. Text changes, if made through the selected first-party editor route, remain Rust-owned; Save Back as New Version rechecks the base and preserves conflicts; Save Out remains explicit export. Close closes/revokes every view/provider/handle of that document, with save/discard review for a live edit and Cancel default. No external app handoff or managed Finish substitute. Required core read/write and functional Open are not reduced by presentation choice. FIL-06.10/.15, named route review below/R3/R4.

FIL-05.9 Retain unchanged original S4 functional Open, no-readable-copy-after-close and lock-closes-files checks OPEN. No disk plaintext for Open, including framework caches/indexes/state restoration; close/lock revokes all first-party providers/views/handles and clears user-requested UI content. Prove each selected API route rather than infer safety from “first-party”. MSG-FOLDER-CLEANUP reports failed view/buffer release as failure, never closure PASS; an unexpected readable disk copy violates this Open contract and needs a finding. APP-10’s real OS capture limit remains; no universal screenshot/memory-erasure claim. Save Out and separate signed S5 Finder copies have their own custody. F43–49/R3.

FIL-05.10 Save Out… asks for a new filename/destination and states “This saved copy is not encrypted. It stays after Larsal locks.” No overwrite or decrypted filename-to-path instruction. Whole-input validation and exclusive output ownership precede release under FIL-06; success offers Done and selected path as plain text, no automatic reveal/launch. F37/F38, FIL-03/R2.

FIL-05.11 Rename… works on file or folder, with named secure-content-free name field, live invalid/collision help and Cancel default on collision. New Folder… has a distinct sheet with parent breadcrumb, labelled name, invalid/collision help, Cancel and Create Folder; same name validation, not a Rename sheet plus an unrelated button. Delete… names selected item/count, warns cloud history may retain it and offers Cancel default/Delete. Empty-folder deletion and nonempty recursive deletion require explicit scope/count review and FIL-06 journal/recovery; deleting an unknown/unreadable/link node is not automatic repair. No secure-delete text. F02/F28, FIL-06.2/.12/R4.

FIL-05.12 Show separate progress phases: Preparing encrypted copy, Checking file, Adding encrypted file, Saving readable copy, Saving changes and Closing file view. Known phase bytes/counts use bounded progress; unknown hydration is indeterminate with “Waiting for this file to download.” Cancel remains available; no 100%/success before sync/close/journal/cleanup. UI stays responsive; no guessed ETA or background retry forever. FIL-06.8/.16/.17, APP-05/R7.

FIL-05.13 Conflict view states “Both versions are kept. Choose how to keep them.” Show names/revisions and storage dates as untrusted; Keep Both default, Save Selected Copy… and Cancel. Deletion/edit conflicts say deletion is pending and retain the edited file. Do not choose a winner by clock or offer one-click destructive Replace in this draft. Recovery view derives clear names only in the live authorized Rust session and names retained ciphertext revisions and separate explicit discard review; no content/password shown and no clear names retained after lock. FIL-06.10–.14/R4.

FIL-05.14 Explicit lock/all-lock, enabled idle/screen-lock/sleep/user-switch/minimize triggers, quit, folder close/switch, password-vault close/switch/lock, credential/draft/root replacement all revoke outstanding work before any save/unlock question (lifecycle revocation cannot be cancelled by that question). This includes own-password folders with no password vault and pending KDFs. Hide names/content/secret input immediately, invalidate generations, prohibit new writes/content releases/completions, wipe workers at safe boundaries, close/revoke every first-party view/provider/handle and wipe owned presentation buffers. An already issued OS call may finish; no auto-resume after wake/unlock. Sleep handler must establish revocation before returning; pending synchronous KDF wipe timing remains explicit. APP-02/11, FIL-06.8/R3/R5.

FIL-05.15 Every input has persistent label/error association; every action has an accessible name, keyboard path and visible focus. List rows convey selection/type/status without color alone, multi-select and Delete require deliberate review. Return never confirms weak/delete/discard danger; Escape cancels. VoiceOver announces phase/error/coarse progress at≤1Hz, no names/password/content in notifications or logs. Restore focus to invoker after cancel; actual native accessibility proof remains S4. APP-08/10, Option A/R5.

FIL-05.16 Reuse locked Option A components/tokens in both themes; new frames are isolated additions to proposals.html only. Stable error/progress space, readable wrapping, no decorative animation needed. Reduce Motion gives equivalent static progress, live changes do not restart work. Every created Larsal window applies APP-10's legacy capture-property/readback/secure-input behavior with the stated OS capture limit; no guaranteed screenshot exclusion. APP-10/R5.

FIL-05.17 Finder cases stay E23-S5, after S4,D7,W-02: signed same-team File Provider extension, reviewed app-group/IPC/entitlements and opaque session-bound Rust authorization. macOS11+ API fits macOS14; materialized content/cache/indexes need actual custody/lock tests. Remove/hide location content on lock and reject stale fetch/edit callbacks, test existing open descriptors/offline copies and deletion conflicts; a removed icon alone is not PASS. FSKit is a later user-space alternative available15.4+, no deployment-baseline change or kernel extension. Exact entitlement/signing/distribution proof remains OPEN; no account/extension install here. F30–35/R6.

FIL-05.18 Foreign folder created by a conforming approved peer uses the same unlock/list/Open/Save Out/add/rename/delete success flows; reverse direction is independently required. Display compatibility help and limits at creation/unlock: “Names and file contents are encrypted. File counts, sizes and dates are visible to storage. Anyone with the encrypted folder can test password guesses. Keep a backup.” Include replay/object-swap, explicit-export and OS-capture limits in accessible Details. All original runtime capabilities remain OPEN, no success-by-refusal or unsupported format migration. FIL-04.14/.15, F04/F05/F15/R1/R6.

## Named first-party data/API review (S4 OPEN)

This is a selected design and finite review inventory, not an API grant. LD-220’s Show/attachment precedent explains explicit user-requested content only; it never grants passwords, keys or arbitrary retained file bytes to Swift. Before implementing each route, the existing named API/sensitive review must record actual FFI names, Secret classification, ownership, copies, error paths and destruction on both targets. No blanket content export, homemade decoder or unreviewed dependency.

| Route | Candidate public API and owned content | Required review/proof; FIL-05 cases |
|---|---|---|
| Exact bytes for every supported file | Rust session/revision-bound ranged read, checked offset/length, bounded wiping scratch after FIL-06 full validation; opaque view handle. CGDataProvider direct getBytesAtPosition/releaseInfo callbacks, no whole-data pointer or provider.data copy, F43/44. | Recheck authorization serialized at every callback; support seek/end/large files with bounded reads; callback queues, retained clients and no data after close/lock. No plaintext path/URL. T07/T09/T14. |
| Text and any first-party text edit | Rust decodes bounded UTF-8 pages and owns edit data. Core Text CTFramesetterCreateWithAttributedString for a visible page, F49; explicit text input returns only the selected edit to Rust. | At most64KiB source text per presentation page, bounded layout/no unbounded typesetter mode; name actual CFString/attributed-string/IME/undo/accessibility copies and their lifetime. No spelling/grammar/cloud services, links, autosave, restoration, indexing or logging; drop page/layout/input objects on replacement/close/revoke. Exact byte view retains original bytes and encoding; T07/T08/T09/T14/T15. |
| Images (including required PNG/JPEG) | Image I/O CGImageSourceCreateWithDataProvider, explicitly false kCGImageSourceShouldCache where supported, bounded CGImageSourceCreateThumbnailAtIndex and viewport rendering, F45–47. | Decode meaningful image with dimensions/zoom rather than hex; preserve exact bytes independently. Validate actual option coverage, malformed/huge compressed image bounds, tile/downsample limits, decoder buffers and retained image/layer/autorelease copies; no URL/cache file. Disabling one decoded-cache option is not disk/wipe proof. T07/T09/T14/T16. |
| PDF | CGPDFDocument(CGDataProvider), page(at:), drawing selected CGPDFPage into a bounded viewport, F48; no filename/URL initializer. | Multi-page readable page navigation, exact byte access; no scripts/actions/attachments/external resource launch, print or export outside Save Out. Prove parser/render/cache memory, callback lifetime and no disk/index materialization for actual macOS route. Release page/document/provider/layers on close/revoke; T07/T09/T14/T16. |
| Arbitrary binary | Rust formats selected bounded offset/hex/printable-byte page; same reviewed transient text renderer. | Navigate first/middle/last bytes of large/empty binary with exact offsets and no whole-file allocation. Supplement image/PDF/text presentation; never replace their required semantic success. T07/T09/T14. |

Total Rust non-KDF buffers remain≤16MiB; UI source page≤64KiB and at most two1024×1024 RGBA viewport buffers (8MiB total) are proposed limits, with framework/decoder/layout overhead separately bounded and measured, not hidden inside those figures. Arbitrary file size requires bounded byte access, not whole-file UI Data/String. Supported image/PDF presentations must still succeed for the required fixtures and sizes; resource refusal is not a passing preview. If a candidate cannot meet no-disk, memory or teardown requirements, state that exact API/object/requirement to Lead and replace the candidate within this selected design, without silently dropping the type/function or adding a general owner gate. APP-10 property/readback and real capture limits apply to all content windows. Memory remnants in opaque framework/system buffers are an explicit unproved review site, not declared wiped by reference release.
