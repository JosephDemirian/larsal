# FIL-06 Folder limits, output custody and conflicts

Status: **reviewed, 2026-11-05 (E23-S1 specification and static proposals only)**; seven second-Spec corrections and fresh independent Verify APPROVE have no required findings. Exact conditional adoption/closure binding: the research [Review and proof](../research/encrypted-folders.md#review-and-proof) footer.
Epics: E23-S3, E23-S4, E23-S5, E23-S6
Parity: FOLD-P2/P3/P4/P5; all todo, runtime proof OPEN.

## What it does

Bound hostile folder work, retain every observed/locally created revision, keep writes and cleanup within proven ownership, and disclose classic authentication, first-party view lifetimes and separate exported-copy limits. Original acceptance and Order remain unchanged; all runtime checks **OPEN**. [Research](../research/encrypted-folders.md) contains F sources, R1–7 (LD-372–378) and final attack/parity catalog identifiers. Rules below are security relevant.

## Inputs and outputs

Untrusted filesystem objects/metadata/cloud events, explicit user operation, stable root/node/destination capabilities and revision/generation handles. Outputs are bounded typed status/errors and owned effects. Names, costs and storage timestamps are not trusted authority. Counter arithmetic and every I/O result are checked; no source data is logged.

## Rules

FIL-06.1 Before allocation/KDF: configuration≤64KiB,key file≤64KiB,JSON depth≤16,members≤64,encoded scalar≤16KiB,password≤1MiB before/after normalization; exact masterkey/wrap lengths; FIL-04’s scrypt salt/cost/memory/work limits and RFC7914 N<2^(16*r), checked without overflow before allocation/KDF; normative validity does not follow from meeting resource ceilings. Read weak N<2^18 warns only after authentication, never silently rewrites metadata. Bound decoded values too; duplicate/unknown-required fields and integer overflow fail generically. One KDF/operation at a time. Proposed non-KDF owned-buffer budget16MiB,≤4 workers and≤8 queued chunks; KDF dominant128Nr≤1GiB plus overhead measured later. F01/F20,R5.

FIL-06.2 Names are single UTF-8 components, NFC,1–255 bytes after normalization and within actual destination limit. Reject empty,dot/dotdot,NUL,slash,backslash,colon,control/bidi-format characters; never strip characters to produce a different saved name. Check filesystem case/normalization equivalence and portable reserved device/trailing-dot/space names on creation/export; refuse collisions, never collapse two items. Display hostile names only as escaped plain text, no Markdown/links; raw selected capabilities stay in Rust. If a foreign name is valid in its source but unsafe here, show an unsupported-name row and require explicit new safe Save Out name, never silently rename or omit it. F12/F28/R4.

FIL-06.3 Operate descriptor-relative below a selected root; reject symlinks at every traversed component, hardlinked mutable files,devices,FIFOs,sockets,mount escapes and changed root identity. No recursive scan follows aliases or package links; explicit regular-directory import is depth≤128,≤1,000,000 nodes,≤10,000 immediate children,≤4096 plaintext path bytes. Enumerate/page≤256 items; bound work counts before recursion, detect repeated directory IDs/cycles and duplicate references. A limit is a visible refusal, not successful whole-folder import. F37/R4.

FIL-06.4 For any read/Open/Save Out/edit base, capture the selected ciphertext through one verified nonblocking regular-file descriptor into a fresh local0700 directory, exclusive0600 ciphertext-only scratch. Check actual bytes and identity/size/times before/after capture; mismatch/I/O aborts. Seal by closing every writable handle and removing its writable name, retain one read capability. No original-path reopen, writable snapshot alias or plaintext staging for validation. Same-UID arbitrary process/fd/memory compromise is outside this candidate; mere mode bits do not prove exclusive custody. E22 FIL-03,F37/R2.

FIL-06.5 Validate all captured available header/name/object authentication and complete legal chunk structure into bounded wiping discard buffers, then use the **same** sealed descriptor/credential/profile to return/write bytes. Validation hash-at-end cannot retract released plaintext. On first-seen authentic classic truncation/replay/substitution there is no missing cryptographic signal: do not claim validation detects it. Exact custody/replay/cleanup mechanism and original S3 one-changed-byte/generic-error/no-plaintext check stay OPEN unchanged under R2; authentic whole-chunk cut/replay/substitution are distinct S6 handling/disclosure cases. Unauthenticated representations are itemized in FIL-04.7, not blanket-authenticated or waived. No fallback to whole-file RAM. F02/F05/R2.

FIL-06.6 Mutations create ciphertext in an owned exclusive sibling staging location, check writes/flush/sync/close, preserve durable base and new ciphertext in local private recovery, recheck target identity/digest under available local coordination, then publish using reviewed ownership-safe platform primitives. Create/Save Out never replaces an existing file. A normal rename without target/parent protection is insufficient; advisory lock/NSFileCoordinator is not distributed CAS. No truncate/direct-write fallback. Update pins only after confirmed commit; uncertain commit reports MSG-FOLDER-UNCERTAIN and retains recovery. APP-05,F37/F38/R4.

FIL-06.7 Journal folder create/rename/delete and shortened-name multi-object transitions; keep source/old subtree reachable until new state is durable. Cancellation/error removes only proved owned incomplete scratch/staging/output, never another user's replacement at the same path. Bind cleanup to descriptor/inode and custody, not check-then-unlink or recursive sweep; when safe ownership cannot be established, preserve and report cleanup failure. Crash/power/sync errors may leave ciphertext recovery/staging; startup never overwrites or removes foreign/unrecognized nodes. Original no-plaintext-on-initial-corruption and closed-copy checks are not passed by a warning. F37/F38,R2/R3/R4.

FIL-06.8 Bind root,selected node/revision,target parent/name,credential revision,vault/folder/operation generations at confirmation. Serialize new write/content-release/completion authorization with revocation; a flag check followed by unsynchronized effect fails. Revoke on every FIL-05.14 event, including standalone passwords; clear UI at once, bounded worker cleanup at safe points, no waiting for a remote peer or rendering callback. Check before/after synchronous KDF and each chunk/I/O. An already authorized OS call may finish; no late success or automatic resume. APP-02,R3/R5.

FIL-06.9 Keep bounded local known-history ciphertext/config digests and durable recovery state outside synced storage, bound to validated vault identity/root and credential generation. A mismatch is Changed, not proof of which version is newer. A known older digest stops automatic use, prompts review and preserves both; first-use/unseen replay, lost local pins, storage forks and malicious password holders remain undetectable in general. No trusted wall-clock comparison or automatic “repair” of metadata. Password rewrap never deletes historical keys/backups. F05/F13/F42,R2/R4.

FIL-06.10 Conflict key is validated folder identity,parent directory ID,NFC filename; versions identified by full SHA256 of captured ciphertext. For two different observed versions from the same base, default Keep Both, no last-writer/time winner: retain the lexicographically smallest full digest under the original name and every other version as `conflict-<full64hex>.bin` in the same clear directory, recording the original encrypted name and parent directory identifier in local recovery; recover the clear name only in a live authorized Rust session. Encrypt the generated name normally, retaining the content ciphertext byte-for-byte; no plaintext conflict name is stored in the cloud. If that reserved name is occupied by different data, stop publishing and report collision, retaining all recovery; never overwrite or truncate digest suffixes. Deduplicate only byte-identical ciphertext after bounded streaming comparison, never guessed plaintext identity. Both arrival orders with the same version set must converge. APP-05,R4.

FIL-06.11 Before saving an edit, compare the exact base snapshot digest with current storage. If different/missing, keep the edit as a conflict rather than replace/delete the remote version; preserve every observed variant first. Two offline Macs retain local base+new ciphertext independently; upon later seeing both branches, use .10. Provider conflict files/NSFileVersion are candidates only: bound/authenticate their names and objects before association, never trust a suffix alone or trash them automatically. If a provider permanently withholds/destroys another Mac's sole version, no complete convergence/no-loss claim is possible. Proposed R4 qualification is unadopted. F13/F37/F38,R4.

FIL-06.12 Delete-versus-edit keeps edited content and marks deletion Pending conflict; rename-versus-edit and two different renames retain both source identities/variants until explicit resolution. Recursive delete preflights bounded affected nodes, durably preserves observed ciphertext and stops if any target changes; never recursively follow a foreign directory ID. Invalid/unreadable nodes do not become deletion authority. No nonempty folder is declared removed before all intended transitions are confirmed; partial outcome is visible/recoverable. APP-05,R4.

FIL-06.13 Local recovery uses app-owned0700 directory and0600 objects, ciphertext only plus minimal bounded operation metadata; never a synced cloud location. Recovery metadata bodies, filenames and logs hold no decrypted names or content; retain only ciphertext objects, original encrypted name, parent ID and minimal bounded nonsecret/ciphertext association identifiers. Clear names are derived only after unlock in Rust and wiped on revocation. Retain per-operation base/new snapshots until explicit reviewed discard; no age/quota auto-prune. Preflight a proposed10GiB recovery ceiling and actual required space before mutation; if one operation needs more, stop with MSG-FOLDER-RECOVERY, no half-discard/automatic higher limit. A file larger than quota may still read/Save Out with adequate scratch/output space; original large-file speed/CRUD requirements stay OPEN where this policy would block. S3 must settle the quota versus required large-file matrix without silently shrinking acceptance. R4/R5.

FIL-06.14 Recovery/delete/discard UI binds exact owned records and expected digests. External substitution,forged journal/symlink/reused operation directories and bad owner/mode prevent cleanup. Stop rather than deleting unknown files; show cleanup/uncertain error with location separately as cleaned text. Restart scans only proven app-owned namespaces, never broad temporary/user/cloud folders. Local recovery is not a backup against whole-Mac loss and is not uploaded by Larsal. APP-05,F37/R4.

FIL-06.15 First-party Open creates no readable disk copy. All selected file bytes, edit state and bounded read buffers are Rust-owned; only reviewed transient user-requested rendering/input copies from FIL-05’s named route inventory exist while a live authorized view needs them. No plaintext path, materialization, autosave/state-restoration/index/cache file, external launch or managed Finish contract. Close revokes the document and all its providers/views/handles, clears presentation objects and wipes owned buffers; lock and enabled lifecycle triggers do this before prompts and cannot be delayed by a view. Late provider/render callbacks cannot return bytes or restore pixels. On crash there is no Open plaintext file to clean; encrypted recovery follows .13/.14. Save Out is explicit persistent export; arbitrary-app Finder is S5. Failure to prove an API’s cache/teardown behavior remains an exact S4 OPEN issue, not a waiver, refusal PASS or assertion all framework memory wipes. APP-10 OS-capture limits preserved. F43–49/R3.

FIL-06.16 Byte counts/offsets use checked signed64-bit bounds; classic GCM lifetime per fresh file key additionally≤2^32 invocations including retries, so no enormous single-file key lifetime or nonce budget wrap. No file-size-derived allocation or executable/script execution; selected presentation parsing requires FIL-05’s named bounded API review. Scratch/output/recovery free-space estimates include all copies, overhead and multi-object staging; estimates are advisory, later I/O failures checked. Worker count≤4/chunk queue≤8,total non-KDF buffers≤16MiB; exact RSS and stack/backend copies remain S3 proof. F20/F21/R5/R7. The shared encryption masterkey also encrypts classic headers and optional encrypted directory-ID backups. NIST SP800-38D §8.3 limits random-IV GCM to2^32 invocations per given key across all instances: count files, rewrites, failed/cancelled attempts, sessions, devices and directory-ID backups cumulatively; fresh content keys do not reset this header-key budget. S3 must specify/prove conservative Larsal accounting with durable reservations before encryption, no refund for possibly used IVs, restart/rollback/exhaustion and concurrent-instance cases. Local accounting cannot certify unknown peers’ past/future key use; disclose that limit. No invented wire marker, service/global enforcement, blanket foreign refusal or new permission gate.

FIL-06.17 Remote hydration/coordinated reads stay off main thread; known dataless placeholders show wait state, no automatic recursive download. A user-triggered operation may request only selected files. After30s without byte/phase progress show MSG-FOLDER-WAIT and keep Cancel; no unbounded retry (≤3 explicit attempt cycles, then user action). Raw filesystem-derived research targets are future release requirements, not measured encryption performance. Capture/validate/save/KDF/hydration timings and cancellation latency are separate. Original S3 speed proof stays OPEN. APP-05,F30/R7.

FIL-06.18 Cryptographic/credential/hostile-structure/limit failures share MSG-FOLDER-OPEN; no upstream reason,cost,node text,secret or offset in logs/errors. Explicit input,I/O,collision,conflict,cleanup and uncertain outcomes use the fixed inventory below. Uniform wording is not whole-operation constant-time behavior. No no-metadata,no-replay,no-third-party-copy/secure-erasure promise. Proposed attacks need valid success controls and private-copy mutants; static/guard/PNG evidence signs no runtime security or original acceptance row. LD-340/371,F04/F05/R2–7.

## How this was learned

Public standards, current official format/security/platform documentation and existing Larsal output/lock patterns. Concurrency and custody policies are our stated inferences, not a copied implementation or a claimed distributed-lock guarantee. No runtime/crypto/interop/native/memory/attack fleet ran in S1; seven second-Spec findings corrected and fresh independent Verify APPROVE for the exact specification/static proposals. Historical proposed/unadopted wording inside unchanged rules/cases describes the submission; current metadata is in the research footer. No runtime case is passed.
