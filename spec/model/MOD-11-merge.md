# MOD-11 Merge rules

Status: reviewed
Epics: E4-S12 (also used by E4-S15 for the merge after a change on disk, E11 for shared groups and remote sync, E12 for the command line `merge`, E15-S2 and E15-S4 for the same-vault deletion pass, the retired-key rule and conflict copies, E16-S7b for the newer key in server sync, SYN-03)
Parity rows: SD-03, SD-04, SD-05, SD-06, SI-01, SI-09, SR-07

## What it does

A merge copies the changes of one vault (the **source**) into another (the **target**). Only the target changes. The source is read only.

This card owns:
- how objects are matched (by id) and which side wins (by modification time);
- how entry histories are joined;
- what happens to moved entries and groups, to new and missing objects, to deleted objects;
- what happens to custom icons, vault custom data and the rest of the vault metadata;
- the change list the merge reports, the dry run, and the merge flows in the window and the command line tool;
- where the reference loses data, and what App does instead.

Other cards: APP-05 owns how a change on disk is noticed and when the user is asked; this card owns the merge that follows. INT-08 owns shared groups, INT-09 remote sync, FEA-08 the import wizard; each calls this merge with the options in MOD-11.1. FMT-15 owns the deleted-objects list and the deletion pass (FMT-15.11). FMT-14 owns the custom data format and the merge facts FMT-14.24. MOD-03 owns history limits.

Notation: id(xx) as in FMT-11 (16 bytes, all 0xxx). "Newer" means a strictly later time. Times are compared in whole seconds (FMT-12; the reference drops milliseconds before comparing entries). T0 = 2026-01-01T00:00:00Z, T1 = 2026-02-01T00:00:00Z, T2 = 2026-03-01T00:00:00Z, T3 = 2026-04-01T00:00:00Z. "Mod" is an object's `LastModificationTime`, "Loc" its `LocationChanged` (FMT-11).

**Same-vault merge** (the one definition in this card; every same-vault rule uses it: the Loc of a replaced entry in MOD-11.11, the deletion pass of MOD-11.15, the metadata of MOD-11.18 to MOD-11.20 and the key of MOD-11.19 limit 2; decided: spec/decisions.md LD-60, LD-264, LD-265, LD-267 (2); design: spec/research/sync-server.md P2, P3). A merge is a same-vault merge when all four hold:
1. the source root group and the target root group have the same id (two copies of one vault);
2. the other copy was opened with this vault's own key, or with credentials the user gave for that copy (MOD-11.29, APP-05.29, the unlock dialog of MOD-11.27). The key, or the user's own credentials, is the proof; the root group id alone is not. For a shared vault (SHR-01), a copy also counts as the same vault when it passed SHR-03.12 and opens with the key of the epoch its checked upload names (SHR-01.13; LD-290 (2));
3. both start groups are the root groups;
4. the kind is not a shared-group import or the import wizard, whatever the root group id: a share opens with the share password, not with the vault's key.
So the merge after a change on disk, a cloud conflict copy (APP-05.17), the rollback guard's merge (APP-05.26), server sync (SYN-03) and a merge from another copy of this vault (MOD-11.27, MOD-11.28) are same-vault merges when they pass these tests. Why: only a key holder can make a copy that opens with the vault's key, so its deletions, metadata and key are the user's own (LD-265).

**Except a copy under a key this Mac retired** (MOD-11.31; LD-267 (2), LD-269 (3)): it can pass all four tests, but it is never a same-vault merge, so it never gives its deletions, its metadata or its key.

Every other merge is "not same vault".

## Inputs and outputs

- In: the source vault (open, read only), the target vault (open), the start groups (normally both root groups; for a shared group: the source root and the target's shared group), the mode, two options.
- Mode: keep-newer (the default and the only mode for every merge except a shared-group import) or synchronize (shared-group import only).
- Options: skip vault custom data (yes for shared-group imports and the import wizard); dry run (compute the change list, change nothing).
- Out: the changed target, and the ordered change list (MOD-11.24). The change list is empty exactly when nothing changed.
- Limits: the merge walks each source object once. Its work is linear in the number of objects plus history items. It must never loop forever (MOD-11.9).

## Rules

### Kinds of merge

MOD-11.1 **Merge kinds.** Every merge uses the rules of this card. They differ only in source, target, mode and options:

| Kind | Source | Target | Mode | Skip vault custom data | Who owns the flow |
|---|---|---|---|---|---|
| Merge from another vault (menu action `merge.from_vault`, command line `app merge`) | the chosen vault | the open vault | keep-newer | no | this card (MOD-11.27, MOD-11.28) |
| File changed on disk while the open vault has unsaved changes, user picks merge; or an older disk version (the rollback guard, APP-05.26) | the vault in memory | the version just read from disk; the result then replaces the vault in memory | keep-newer | no | APP-05; direction in MOD-11.29 |
| Cloud conflict copy (App, APP-05.17; spec/research/sync-server.md P18 (3)) | the conflict copy | the open vault | keep-newer | no | APP-05.17 |
| Remote sync (two-way) | first the local vault into the remote copy, then the remote copy into the local vault; both are saved when either merge changed something | | keep-newer | no | INT-09 |
| Shared-group import | the share's root group | the group that holds the share | synchronize | yes | INT-08 |
| Import wizard into a new vault | the imported vault | the new empty vault; afterwards the new root group takes the imported root's name and notes | keep-newer | yes | FEA-08 |

The reference stores no merge mode in the file. A group's mode is "inherit"; the root's inherited mode is keep-newer. Only the shared-group import forces synchronize.

MOD-11.2 **Order of steps.** (1) groups and entries (MOD-11.3 to MOD-11.16); (2) deletions: the deletion pass, in a same-vault merge and in synchronize mode (MOD-11.15); (3) metadata: custom icons, then vault custom data, then (App, same vault only) the other metadata (MOD-11.17 to MOD-11.19). The change list follows this order. Deletions come after the group step because the group step may first bring back an object that the deletion step then removes.

MOD-11.3 **Walk order.** Start with the source start group mapped to the target start group. For each mapped pair: first each entry of the source group, in stored order; then each child group of the source group, in stored order. A child group is handled (created, moved or updated) and then its whole subtree is walked before the next child. So the walk is depth first, and every source object is visited once.

### Matching and new objects

MOD-11.4 **Matching by id.** A source entry matches the live target entry with the same id, wherever it sits in the target tree (any group, the recycle bin included). History items are never matched. A source group matches the target group with the same id anywhere in the target tree, the target root included. Entries and groups are looked up separately, so an entry id that equals a group id is not a match. The two start groups are never compared with each other: the source root's own fields (name, notes, icon, times) are never copied in the reference (App: MOD-11.20). The source root's entries and child groups are walked into the target start group.
- Shared-group import (App, decided: spec/decisions.md LD-61): ids are looked up only inside the target start group (the shared group and its subtree). A source entry or group whose id is found elsewhere in the target is not merged: it is not moved, not changed and not added a second time, and App records one Conflict change for it. For such a group its subtree is not walked. The reference looks ids up in the whole target vault, so a share can move an outside entry into the shared group, where the next export carries it, or overwrite it (source).

MOD-11.5 **New entry.** A source entry with no match is copied whole into the mapped target group, appended after the group's existing entries: same id, every field, custom data, attachments, Auto-Type settings, tags, times (Loc included) and the whole history. The history is not cut to the target's MOD-03 limits at this point (observed: 4 history items arrived in a target whose item limit was 2). Change: Added (entry).

MOD-11.6 **New group.** A source group with no match is copied into the mapped target parent, appended after its existing child groups: same id and all of the group's own fields (name, notes, icon, times with Loc, tags, Auto-Type and search settings, default sequence, previous parent, custom data including any shared-group settings). Its entries and child groups are not copied with it; the walk adds them one by one. Change: Added (group), with the number of entries directly in the source group.

### Location changes

MOD-11.7 **Entry moves.** When a matched target entry's Loc is older than the source entry's Loc, and the target entry is not already in the mapped target group, it is moved there (appended at the end). Change: Moved, naming the previous group. The move does not change any Mod or access time of the entry or of either group, and adds no deleted object. It sets the entry's previous-parent-group field to the old group (used by MOD-04 restore). The reference does not copy the source Loc into the moved entry; the entry gets the source Loc only if the source version also wins the conflict (MOD-11.11), because then the whole source entry replaces it (observed). App copies the source Loc into the moved entry (decided: lead decision D-11-8 default; same as groups). In a shared-group import only entries inside the start group are matched (MOD-11.4), so a move never pulls an entry in from outside the shared group.

MOD-11.8 **Group moves.** The same rule for groups: a matched target group whose Loc is older than the source group's Loc, and whose parent is not the mapped target parent, is moved there (appended) and gets the source Loc. Its previous-parent-group field is set to the old parent. Change: Moved. In the reference the detail text names the moved group itself instead of its previous parent (source); App names the previous parent's path. In a shared-group import only groups inside the start group are matched (MOD-11.4).

MOD-11.9 **No cycles, root stays.** A group move that would place a group inside itself or inside one of its own descendants is not done. The group stays where it is, a Conflict change is recorded (App), and the walk goes on into that group as usual. The target root is never moved: a source child group whose id equals the target root's id is treated as the target root for the walk (its entries and child groups merge into the target root) and none of its own fields are copied. The reference has no such guard. Observed: base vault with sibling groups P and X; the target moved P into X (P Loc = 2026-06-01), the source moved X into P (X Loc = T3). The installed command line merge hung with no output and was stopped after 20 seconds; the vault file was unchanged. App must finish (AT-A08). App (LD-129): moves skipped as cycles are tried again once the walk is done, because a later move can remove the cycle; the result never depends on walk order.

### Groups and entries that exist on both sides

MOD-11.10 **Group fields.** Only when the source group's Mod is newer than the target group's Mod.
- Reference: copies name, notes, icon and expiry time, then sets the target Mod to the source Mod. Change: Modified, listing the fields that differed. It does not copy the expires flag, tags, custom data, Auto-Type settings, default sequence or search setting (observed: tags `x` and custom data `k = target` stayed; expiry time moved to T3 while the expires flag stayed off). Icon quirk: when the source group has standard icon 0, only the custom icon ids are compared, so a source change to standard icon 0 is never copied (observed: target icon 7 stayed).
- App (lead decision D-11-3, recommended): copies every own field of the group: name, notes, icon exactly as in the source (standard number or custom id), tags, expires flag and expiry time, Auto-Type enabled and default sequence, search setting, custom data, and Mod. Never copied: parent and Loc (MOD-11.8), children, previous parent, the view-state fields `IsExpanded` and `LastTopVisibleEntry` (FMT-11), and the shared-group settings item (key `4B 65 65 53 68 61 72 65 2F 52 65 66 65 72 65 6E 63 65`, stored encoded, name rule), which keeps the target's value or absence. MOD-02.8 agrees.
- App never copies the group's creation time, last access time or usage count; they stay the target's, as in the reference.
- Equal or older source Mod: nothing is copied.

MOD-11.11 **Entry conflict: who wins.** Compare the two entries' Mod in whole seconds.
- Only matched entries take part; in a shared-group import that means entries inside the start group (MOD-11.4, LD-61).
- Source newer: the target entry is replaced by a full copy of the source entry (all fields, times, custom data, attachments, Auto-Type, tags, previous parent), in the target entry's current group (after any move by MOD-11.7). Its Loc: in a merge that is not same vault (Notation), the source's Loc, even when it is older than the target's (decided: spec/decisions.md LD-68); in a same-vault merge, the later Loc of the two sides (decided: spec/decisions.md LD-287 (1)). Why: the entry stays in the target's group (D-11-7), so the later Loc tells where it is, the reverse merge agrees on the place, and the deletion pass still sees a move the target made after a deletion item (MOD-11.30). Its history is the joined history of MOD-11.12 or MOD-11.13. Change: Modified, listing the fields that differ plus History, noting that the source version is now current and the target version was kept in history.
- Target newer or equal: the target entry's fields stay. Only its history is joined. Change: Modified (same field list, noting that the source changes went into history) only when the history changed.
- Position: the reference removes the old target entry and appends the copy, so a replaced entry moves to the end of its group (observed: order Bank, OnlyA, Mail after Mail was replaced). App keeps the entry at its old position (lead decision D-11-7, recommended).

MOD-11.12 **History join, reference.** Let W be the side whose current version wins (MOD-11.11) and L the other. Times are whole seconds.
1. Take W's history items, keyed by Mod. Two items with one Mod keep the later one (a log warning only).
2. Add L's history items. An item whose Mod is already present is skipped (log warning when they differ). So on a Mod collision the winner's item stays, and of two L items with one Mod the first stays.
3. Add L's current version, keyed by its Mod, unless an item with that Mod is already present. When W and L have the same Mod, nothing is added (log warning when their content differs).
4. Order the items by Mod, oldest first.
5. Change check: the new list replaces W's history only if the check finds a difference. The check compares, from the newest end, the old and new items at positions 1 to (item limit − 1) only. With the vault's item limit at −1 (no limit), 0 or 1 it compares nothing and reports no difference.
6. When replaced, the history is cut to the target vault's limits (MOD-03).

Data loss that follows (all observed with the installed command line tool, target state below): with item limit −1, 0 or 1, when the source wins, the copy keeps only the source history, so the target's current version is lost; when the target wins, the source version is not added to history. Also lost: the source's current version when both have the same Mod (step 3), and one of two different history items with the same Mod (steps 1 and 2).

MOD-11.13 **History join, App** (lead decision D-11-1, recommended: fix the loss). Two versions are **the same** when they have the same id and equal content in every field, ignoring `LastAccessTime`, `UsageCount`, Loc, the previous-parent field and their own history. Then: App (LD-129): field protection flags are ignored when comparing versions (App always protects passwords, MOD-12.17), and "equals the winner's history" compares the set of versions, so a merge that adds nothing never re-sorts a history whose clock went back.
1. Start with the target's history items in stored order.
2. Append each source history item, in stored order, unless the list already holds the same version.
3. Append L's current version (as a history item, without history of its own) unless it is the same version as W's current or the list already holds the same version.
4. Sort by Mod, oldest first; the sort is stable, so items with equal Mod keep the order of steps 1 to 3 (target items, then source items, then L's current).
5. If the list equals W's existing history, nothing changes. Otherwise prune it with the target vault's limits (MOD-03.8, cut from the oldest end); if the pruned list still equals W's existing history, nothing changes; else it replaces W's history (the history changed). This keeps a second merge of the same source empty (MOD-11.30).
The item limit −1 means no limit; App never skips step 3 because of a limit. Items with equal Mod but different content are all kept.

MOD-11.14 **Same time, different content** (lead decision D-11-2, recommended). When the two current versions have the same Mod but are not the same version (MOD-11.13), the target's current stays current, the source's current goes into the history by MOD-11.13 step 3, and App records one Conflict change for the entry, in place of the Modified record of MOD-11.11. The reference keeps the target and loses the source version without a change record (observed: stderr warning only).

### Missing objects and deletions

MOD-11.15 **Missing objects and deletions.**
- Keep-newer mode, same-vault merge (Notation; App, decided: spec/decisions.md LD-265, LD-267 (2); design: spec/research/sync-server.md P2): after the group step, the deletion pass of FMT-15.11 runs over the whole target vault, from its root group, with the target's list and then the source's. So an entry or group deleted for good on either side stays deleted, unless either side changed or moved it after the deletion (a move counts as a change: in this whole-vault pass an object's time is the latest Mod or Loc that either side holds, read per kind (an entry's times for an entry, a group's for a group: they may share an id, MOD-11.22), and only a time strictly after the item keeps it; FMT-15.11 steps 3 and 4, LD-271 (2), LD-287 (2), LD-288 (1)). The pass only reads the source copy's times; it never writes them into the target, so reading them adds no change record of its own (MOD-11.26). The rebuilt list becomes the target's list. Its erases add no deleted objects (FMT-15.8). An object that the group step added in this merge and the pass then erases leaves no change record (App): the target is as before for it, so a stale copy that only still holds deleted objects gives an empty change list and no save (MOD-11.26, MOD-11.30). Why: only a key holder can make a copy that opens with the vault's key, so its deletions are the user's own (LD-265). The reference never reads the list in these merges; App goes beyond it (parity row SD-03).
- Keep-newer mode, not same vault (another vault, a copy under a key this Mac retired (MOD-11.31), the import wizard): an entry or group that exists only in the target stays. No deleted-objects list is read or changed (FMT-15.10). An object the target deleted for good comes back when the source still has it, and the target's deleted-object item for it stays. This is the reference behavior for every keep-newer merge.
- Synchronize mode (shared-group import only): after the group step, the deletion pass of FMT-15.11 runs. Its erases add no deleted objects (FMT-15.8). Reference: the pass searches the whole target vault. App (lead decision D-11-9, recommended, see FMT-15 security notes; the same scope as LD-61): the pass erases only entries and groups inside the target start group (the shared group). It still erases by Mod alone: an object's time is the Mod the target holds after the group step, and neither Loc nor the share's own times count (LD-287 (2) changes the same-vault pass only; T73). Before the pass, each item of the share's list dated later than the import time takes the import time (App, decided: spec/decisions.md LD-271 (1)), so every item the import keeps is dated no later than the import. An item whose id names an entry or group outside the shared group erases nothing: when it comes from the share's list it is dropped from the rebuilt list; when it is the target's own item it stays as it was. An item whose id names nothing in the target, or names an object inside the shared group that the pass erases, stays in the rebuilt list (FMT-15.11 steps 1 and 3; the share round trips of FMT-15.12 need it). A later same-vault merge then runs the whole-vault pass with that item, and that pass keeps an object whose last change or last move (Mod or Loc) is later than the item's time (LD-271 (2)): an entry that another copy moved out of the shared group after the import stays (T65). Known limit (LD-271 (3); SI-09; spec/research/sync-server.md P2): a member can delete an entry that was shared with them, and if another copy moved it out of the shared group earlier than that deletion, the later same-vault merge erases it. A member can only name ids it was shown, because ids are 128 random bits. App accepts this limit. A record on this Mac of the items a share import placed is not taken: it does not travel with the vault file, so another Mac would still apply the item (LD-271 (4)). A shared-group import and the import wizard never run the whole-vault pass of a same-vault merge, whatever their root group id (Notation).
- An object in the target's recycle bin is matched like any other (MOD-11.4). It leaves the bin only by the move rule (MOD-11.7, MOD-11.8): a source edit alone does not move it out, a newer source Loc does (observed: an entry the target had put in its bin at T1 and the source had edited at T2 with Loc T2 moved back to its group).

MOD-11.16 **Recycle bins.** The bin mapping below applies only when both start groups are roots; in a shared-group import the source bin is an ordinary group inside the shared group, and nothing is moved to or created in the target vault's own bin (LD-130).
- Reference: the source's recycle bin is an ordinary group to the merge. If the target has no group with its id, it is added as a new group (same name, icon 43), and the target's own recycle bin setting and group stay as they were. Result: two groups that look like recycle bins, only one of them real (observed: target bin id(5A) kept as the bin, source bin id(5B) added as a normal group holding the entry the source had deleted).
- App (lead decision D-11-4, recommended): when the source group being walked is the source vault's recycle bin and the target has no group with that id, it is not added. Its entries and child groups are walked into the target's recycle bin instead. If the target has no recycle bin and its recycle bin setting is on, the target bin is created first by MOD-04.2. If the target's recycle bin setting is off, the reference behavior applies.

### Metadata

MOD-11.17 **Custom icons.** For each source icon, in the source's icon order: if the target has no icon with that id, it is appended with its id, image bytes, and (4.1) name and time. Change: Metadata, "new icon" with the id as 32 lowercase hex digits. An icon id present on both sides keeps the target's image, even when the images differ (reference test; no change record). Entries and groups that reference a custom icon keep the reference. A deleted-object item for an icon id in the target does not stop the icon from being added: the reference's keep-newer merge never reads the list (FMT-15.10; observed for entries, read in the source for icons), and App's deletion pass looks only at entries and groups (FMT-15.11).

MOD-11.18 **Vault custom data.** Skipped entirely when the option says so (MOD-11.1). Otherwise FMT-14.24 applies:
- the source wins when the target container has no `_LAST_MODIFIED` item, or both container times are valid and the target's is older;
- when the source wins, each target key missing from the source is removed, except protected keys (those starting with `4B 50 58 43 5F 42 52 4F 57 53 45 52 5F`, stored encoded, name rule; the bare key `_CREATED_`; `FDO_SECRETS_EXPOSED_GROUP`; and `4B 50 58 43 5F 52 45 4D 4F 54 45 5F 53 59 4E 43 5F 53 45 54 54 49 4E 47 53`, stored encoded, name rule); then each source key whose value differs is set, except `_LAST_MODIFIED` and the padding key `4B 50 58 43 5F 52 41 4E 44 4F 4D 5F 53 4C 55 47` (stored encoded, name rule); a source key with an empty value is not added to a target that lacks it; a set item gets the merge time as its item time; each removal and set refreshes the target's `_LAST_MODIFIED`;
- browser association keys (keys with the browser prefix above) are set from the source only in a same-vault merge (decided: spec/decisions.md LD-60). In any other merge a source key with that prefix is neither added nor changed, and the target's keys stay. The reference copies them in every merge where the source wins (source);
- one Metadata change per removed key and per set key.

Which times are compared:
- Reference: on read it replaces every non-empty container's `_LAST_MODIFIED` with the read time (FMT-14.18 (a)). So the vault that was read later wins, whatever its file says. Observed with the command line tool: target `_LAST_MODIFIED` 2024, source 2018; the source took about 1.6 s to open after the target, so the source won: target-only keys `TargetOnly` and `_CREATED_demo` were removed, `Shared` changed from `t` to `s`, `SourceOnly` was added, and the source key `Empty` (empty value) was not added. When both opened within the same second, nothing changed. In the window's merge the source is always read later, so the source always wins; in the merge after a change on disk the target (the disk version) is read later, so the target always wins.
- App (lead decision D-11-6, follows FMT-14 L14-2): compares the stored values, as read from the files and refreshed by App's own changes and saves (FMT-14.18 (c), FMT-14.21). The same two vaults give the same result every time.

The reference keeps the removed and set values in the change list text (MOD-11.24); App does not.

MOD-11.19 **Other vault metadata.** (Decided: spec/decisions.md LD-60, LD-71, LD-132: a change of KDF family is never applied silently; it is recorded as a Conflict and the target keeps its KDF unless the user confirms, as MOD-12.12 asks.)
- Reference: nothing else is merged. The target keeps its name, description, default user name, color, history limits, maintenance days, key change settings, protection flags, recycle bin setting and group, templates group, last selected and top visible groups, generator, public header data, cipher, KDF, compression and composite key.
- App, not a same-vault merge (Notation): the same as the reference.
- App, same-vault merge (decided: spec/decisions.md LD-60, which settles D-11-5): each value below takes the source's value, together with its time, only when the source's time is newer, with the two limits after the table:

| Values | Time that decides (FMT-10) |
|---|---|
| name | `DatabaseNameChanged` |
| description | `DatabaseDescriptionChanged` |
| default user name | `DefaultUserNameChanged` |
| recycle bin group (only if a group with that id exists in the merged target; otherwise the target's stays) | `RecycleBinChanged` |
| templates group (same existence rule) | `EntryTemplatesGroupChanged` |
| the settings group of MOD-12.9: recycle bin on or off, history limits, maintenance days, `Color`, the five protection flags, key change days (MOD-13), compression, cipher, KDF settings, public display name, colour and icon | `SettingsChanged` |
| composite key and the force-once flag (MOD-13), only as limit 2 below allows | `MasterKeyChanged`; on equal times the force-once flag is true when either side has it (LD-62, MOD-13.14) |

Never merged: generator, last selected and top visible groups (view state of the target), kept unknown `Meta` parts.

Limit 1, no downgrade (LD-60). A merge never lowers the cipher, the KDF cost or the protection flags. When the settings group wins, App takes every other value of the group, and for these three it compares first:
- protection flags, one by one: a flag on in the target stays on; a flag off in the target takes the source's value;
- KDF: the source's KDF settings are taken only when they are not lower: Argon2 (either variant) replacing AES-KDF; Argon2 with memory and iterations each at least the target's; AES-KDF with at least the target's rounds. Anything else (AES-KDF replacing Argon2, less memory, fewer iterations or rounds) is lower. The salt or seed never counts; every save draws a new one (CRY-03);
- cipher: every cipher App reads uses a 256-bit key (CRY-01), so a change between them is not lower and is taken.
For each value kept this way the target keeps its value and App records one Conflict change for the vault (naming the setting, never a value). `SettingsChanged` takes the source's time all the same, so the next merge does not ask again. This applies in every same-vault merge, the merge after a change on disk included: a deliberate local lowering that is not yet saved shows as a Conflict and the user applies it again in vault settings (MOD-12.12).

Limit 2, the key needs the user or the newer key time (LD-60; changed for sync by LD-264 and LD-267 (2); design: spec/research/sync-server.md P3). The composite key, `MasterKeyChanged` and the force-once flag travel together (MOD-13.14). When the source's `MasterKeyChanged` is newer:
- the merges that keep the newer key without a question (LD-264): the merge after a change on disk (MOD-11.29), the cloud-folder merges (a cloud conflict copy, APP-05.17, and the rollback guard's merge, APP-05.26) and server sync (SYN-03): taken automatically. When the target's time is newer, the target keeps its key, as for every merge. So in these merges the result always holds the newer of the two keys, by the vault's own `MasterKeyChanged`. This holds only when the merge is a same-vault merge by the Notation's one definition; credentials the user gave for the other copy count (MOD-11.29, APP-05.29). For a shared vault the upload always takes the current epoch's key instead (SHR-01.14);
- window merge (MOD-11.27): the preview lists one Metadata record saying the vault key will be taken from the source; after Merge, App asks `merge.ask.key` (our ID; default No). Yes takes the key; No merges everything else, keeps the target's three values and records a Conflict;
- remote sync (INT-09): asks first, as INT-09.24 says;
- a flow with no preview and no question (the command line `app merge`): never taken; a Conflict is recorded.
Never taken, whatever the times: from a copy under a key this Mac retired (MOD-11.31; it is not a same-vault merge, so it gives no key even with a key-change time in the future), and in a shared-group import or the import wizard, whatever their root group id (Notation, MOD-11.20). Why: without the newer key, a password change on one Mac is undone by the next upload or save from another, and the old password opens the vault again; a server or a cloud folder without the key cannot make a copy that opens, so taking the newer key gives it no new power (LD-264).
On equal times the key and the time stay the target's, and the force-once flag is true when either side has it (decided: spec/decisions.md LD-62; MOD-13.14).

When the composite key is taken from the source (limit 2), the key change side effects of MOD-12.10 step 8 apply, except that `MasterKeyChanged` takes the source's time instead of now: this vault's quick unlock data is removed (APP-04, SR-04), and the next save derives the key again (CRY-03).

MOD-11.20 **Root group, same vault** (part of D-11-5, decided LD-60). In a same-vault merge (Notation) App treats the two root groups as a matched group for MOD-11.10 (fields by Mod; a root is never moved). In every other merge the target root's fields never change, as in the reference, even when a share's root or an imported root has the target root's id.

### Times, positions, ids

MOD-11.21 **Times are not touched.** A merge never sets an object's Mod, access time, usage count or Loc to the merge time. It only copies source values as the rules above say. It adds no deleted objects for moves or erases. One exception: a recycle bin that App creates by MOD-11.16 gets the merge time as a new group (MOD-04.2). Reference side effect: a group updated by MOD-11.10 gets its `LastAccessTime` set to the merge time when its name, notes, icon or expiry time changed (source); App does not do this.

MOD-11.22 **Ids of the other kind.** A source entry whose id equals a target group id (or the reverse) is added as new with that id, as in the reference. App's model invariant is "ids are unique per kind" (entries among entries, groups among groups), so this is allowed (lead decision D-11-12; LD-26 covers duplicates of one kind).

MOD-11.23 **Unknown parts.** An entry or group copied from the source carries its kept unknown parts (FMT-10.20, FMT-11.45). Unknown parts of the source's `Meta` and top level are never merged; the target's stay. When a merge copies an entry or group that carries kept unknown parts, the version App remembers for the target (FMT-16.24) becomes the higher of the target's read version and the source's read version, so the next save writes at least the version the parts were read as (LD-09; decided: spec/decisions.md LD-68). FMT-16.24 says the remembered version never changes during a session; this merge case is the one exception and FMT-16.24 should name it.

### Change list, preview, flows

MOD-11.24 **Change list.** One record per change, in walk order (MOD-11.2, MOD-11.3).

| Kind | Object | When |
|---|---|---|
| Added | entry or group | MOD-11.5, MOD-11.6 |
| Moved | entry or group | MOD-11.7, MOD-11.8 |
| Modified | entry or group | MOD-11.10, MOD-11.11 |
| Deleted | entry or group | an erase by the deletion pass (FMT-15.11; same-vault merge or synchronize mode, MOD-11.15), with a note saying whether the object was deleted directly or with its parent |
| Metadata | vault | new icon, custom data removed or set, deleted-objects list changed (deletion pass), App's same-vault metadata and the key to be taken (MOD-11.19) |
| Conflict | entry, group or vault | App only: MOD-11.9, MOD-11.14, an id outside a shared group (MOD-11.4), a setting not lowered or a key not taken (MOD-11.19) |

Each record holds: kind; group path (the full path from the root, `/` before each group name, for example `/Root/G1`; for a group record the group's own path; at most 1,024 bytes, cut at a character boundary and ended with `…`, so a hostile file cannot make the list grow without bound, F-164, LD-302); entry title (entries only); id; details. Group path and title come from the source object, except for an entry Modified record, which uses the target entry (reference).
- Entry details list the fields that differ, in this order: Title, Username, Password, URL, Notes, custom fields, Icon, Color, Expiry, one-time password, Custom data, Attachments, Auto-Type, Tags, then History. The reference lists custom fields only when no standard field differs; App lists them whenever they differ (part of D-11-10).
- Group Modified details list: name, notes, icon, expiry, (App: tags, Auto-Type, search, custom data), modification time.
- Text line, command line tool: TAB, the kind, `: `, the group path in single quotes, then for entries `/` and the title in single quotes, then a space and the id as lowercase hex with dashes inside `[{` and `}]`, then a space and the details in parentheses when there are any. Example layout (observed): `Modified: '/Root/G1'/'Mail' [{0a0a0a0a-0a0a-0a0a-0a0a-0a0a0a0a0a0a}] (Password, History (...))`. A vault record has no path, title or id, so two spaces follow the colon.
- Values: App's records never hold a field value, an attachment, a custom data value or any secret (lead decision D-11-10). The reference writes custom data values into the text (observed: the key name followed by its value in brackets).

MOD-11.25 **Dry run.** A dry run computes the same change list without changing the target. Then running the merge for real on the same two vaults gives an equal list. App tests this for every merge test case. The reference's window uses its dry run for the preview, then merges for real and only logs a warning when the lists differ. Its command line dry-run flag runs the real merge in memory and simply does not save.

MOD-11.26 **After the merge.** If the change list is not empty, the target is marked changed and normal saving follows (APP-05). If it is empty, the target is not marked changed and nothing is saved (reference test: no change signal when nothing differs).

MOD-11.27 **Window flow** (reference from the source, not run: check with Verify).
1. Menu action `merge.from_vault`, only for an unlocked vault. File dialog for any file, filtered to vault files first, starting in the folder last used for merging.
2. The chosen file is unlocked in an unlock dialog (APP-06). Any key combination works; the source's credentials need not match the target's. When the credentials match a key this Mac retired (MOD-11.31), App shows `MSG-DISK-OLD-KEY` (APP-05.29) before the preview: Skip (default) ends the flow and changes nothing; Merge anyway goes on to the preview with the content merge of MOD-11.31.
3. A preview dialog shows the dry-run change list as a table with columns Group, Title, id (hidden by default, can be shown from the header menu), Change and Details; buttons Merge and Cancel. The dialog blocks every window of the app while open.
4. Shared-group synchronization of the target is paused from the start of step 3 until the dialog closes (INT-08).
5. Merge: the merge runs; then message `merge.msg.done` (the vault was merged) or `merge.msg.none` (nothing changed). Cancel: message `merge.msg.cancelled` (nothing changed).
App keeps these steps and the three messages, in its own words.

MOD-11.28 **Command line tool** (reference, observed). `merge [options] <target> <source>`.
- Options: same credentials for both vaults; key file of the source; no password for the source; hardware key slot of the source; dry run; quiet. The target's key options are the common ones (INT-10).
- With the same-credentials option, the source is opened with the target's key; failure prints a "cannot read the merge file" error with the reason and exits 1.
- Output: one line per change (MOD-11.24). Then, if there were changes and no dry run: the vault is saved atomically (APP-05), then a success line naming both paths; a failed save prints the reason and exits 1. Otherwise (no changes, or dry run): a line saying the vault was not changed. Exit 0.
- App's `app merge` keeps these options, outputs and exit codes; INT-10 owns the exact wording.

MOD-11.29 **Merge after a change on disk** (APP-05 decides when). Reference (from the source, not run: check with Verify): the disk version is the target and the vault in memory the source; the result replaces the vault in memory, and is saved at once when the merge was started by a save. If the disk version cannot be opened with the current key, the user is asked for credentials first. Consequence in the reference: everything in memory that the merge does not carry is lost, including unsaved changes to the vault name, settings, encryption settings and the composite key (MOD-11.19). App keeps this direction (lead decision D-11-11), so equal-time ties go to the disk version, and carries metadata by MOD-11.19, so newer local changes survive. App asks for the credentials the disk version opens with, never for "the new" ones (APP-05.29, LD-264); a disk version opened that way is the same vault by the Notation when its root group id matches, and one under a key this Mac retired is never merged on its own (MOD-11.31, LD-267 (2), LD-269 (3)). The merge runs the deletion pass (MOD-11.15), so a deletion made on either side is kept.

MOD-11.30 **Idempotence and no lost data.** Merging the same source into the target a second time records no change (reference test). For E4-S12 the property test checks, on random pairs of vaults derived from a common base, after one keep-newer merge: Exception (LD-129): a move-cycle Conflict (MOD-11.9) is recorded again on every merge until the user resolves it.
- every entry id and group id of either side exists in the result, except the erases of the deletion pass (MOD-11.15);
- in a same-vault merge (LD-265): no entry or group deleted for good on one side (an item at time t in that side's list) is in the result unless one side changed or moved it after t (LD-271 (2)), and no entry is lost that is live on one side and was not deleted on the other after its last change or move. Here an object's time is the latest Mod or Loc that either side holds for it, read per kind (an entry's times for an entry, a group's for a group, MOD-11.22), and only a time strictly after t keeps it (LD-287 (2), LD-288 (1); T67 to T72);
- each entry's current version is the newer side's current version (target on ties);
- the older side's current version is in the result's history, unless MOD-03 limits removed it as the oldest item;
- the group tree has no cycle and passes the model invariants;
- a dry run gave the same change list (MOD-11.25);
- a second merge of the same source gives an empty change list.
The property test's random edits never make the bring-back state of FMT-15.5 (a side that holds a live object whose id is also in its own list, as a merge that is not same vault leaves it); T67 to T72 test that state, each with a second merge of the same source (decided: spec/decisions.md LD-287 (3)).

### Copies under a retired key

MOD-11.31 **A copy under a key this Mac retired** (App; decided: spec/decisions.md LD-267 (2), LD-269 (2), (3); design: spec/research/sync-server.md P2, P3). A key this Mac retired is a composite key it replaced: by its own credential change (MOD-12.10), or when a merge took the other copy's key (MOD-11.19). For each one, this Mac keeps in local state that is never synced (never in a vault, never next to one) a record: a salted SHA-256 of the transformed key `T` (FMT-04.11), with a fresh salt from app-crypto's random source (never the file's master seed `S`, FMT-04.13), plus the KDF settings and seed `T` was made with. Every save writes a fresh seed (FMT-04.17), so App runs the credentials given for a copy through each record's KDF settings and seed and compares the result with the record's digests. When the retired key holds a password plus another part (a key file or a hardware key), its record also holds a second salted digest, of the transformed key made from the password alone with the record's salt and the same KDF settings and seed (one more KDF run, skipped for a version 3 key whose only parts are a password and a hardware key, whose T already is the password-alone key (FMT-04.15) at the credential change, when the user waits anyway), and credentials match the record when their transformed key matches either digest (decided: spec/decisions.md LD-288 (2); built by E15-S4). Why: a password leaks more often than a key file or a hardware key, so a planted copy keyed by the old password alone must not count as the same vault and give its key (LD-264). No other subset of the parts gets a digest: that would cost up to seven KDF runs, for parts that do not leak the way a password does. A record of a version 3 file keyed by a password plus a hardware key also matches the password alone, because version 3 keeps the hardware part out of `T` (FMT-04.12, FMT-04.15): the safe side. A record holds no key or password bytes, and neither digest equals `K_enc` or `K_mac`. A copy whose credentials match a record is never merged on its own: App first shows the replaced-password message (`MSG-DISK-OLD-KEY`: APP-05.29, APP-05.17, MOD-11.27 step 2, INT-09.18 step 5; `MSG-SYNC-OLD-KEY`: SYN-03.9), Skip the default; a flow with no question never merges it. "Merge anyway" runs the content merge only: a merge that is not same vault, with vault custom data skipped (MOD-11.1 option) and, in every flow, this Mac's open vault as the target and the copy as the source (also after a change on disk, unlike MOD-11.29), so it adds and updates groups, entries, history and custom icons (MOD-11.3 to MOD-11.14, MOD-11.16, MOD-11.17), but the result never takes the copy's key, deletions or metadata. When it adds back an entry or group whose id an item of this Mac's own deleted-objects list (FMT-15) names, the recycle bin it makes again with the copy's bin id (MOD-11.16) included, it also drops that item: the user chose to keep the object, and a stale item left beside it (the state FMT-15.5 keeps on read) would let the next merge erase it or decide differently a second time (MOD-11.30; F-173, LD-313). Why: a password change often follows a leak; whoever knows the old password must not bring it back, delete entries or change entries without the user's click. The honest case still converges: the other Mac merges its own edits and deletions under the new key once it has the new password (spec/research/sync-server.md P2, P3). A shared vault keeps no retired-key records: a re-key to a new epoch makes none, its versions are checked by SHR-01.13, SHR-01.14 and SHR-03.12 instead, and `MSG-SYNC-OLD-KEY` never shows for it (LD-290 (2)). The command line tool's `merge` (INT-10.40) keeps no records either and makes no check: this is App's rule (LD-283 (4)).

## Edge cases and errors

- Source and target are the same file: allowed. Two identical copies give an empty change list.
- Source cannot be opened (wrong key, corrupt file): the merge does not start; the error comes from the open (APP-06, FMT-05). Nothing in the target changes.
- Target cannot be saved after the merge (command line tool): error, exit 1; the file on disk is unchanged (atomic save, APP-05).
- Entry in the source root, new to the target: added to the target start group (observed: `InRootB` added to the target root, whose name `RootA` and notes stayed).
- Source group new, holding entries that already exist in the target elsewhere: the group is added, then each entry is moved into it only by MOD-11.7 (newer source Loc).
- Entry deleted for good in the target, still in the source: in the reference, and in App when the merge is not same vault, it comes back and the target's deleted-object item stays (observed: item for id(0C) at T1 still listed after the merge). Merge anyway (MOD-11.31) is the exception: it drops this Mac's item for each entry or group it adds back, the recycle bin included (LD-313, LD-315). In App's same-vault merge it stays deleted unless the source changed or moved it after the deletion (MOD-11.15, T21, T66).
- An entry that an earlier merge that was not same vault brought back while its id stayed in the list (FMT-15.5): the next same-vault merge erases it unless either copy changed or moved it after the item's time (FMT-15.11 step 3, LD-271 (2), LD-287 (2); T67, T68). The backup of APP-05.19 holds the copy before that save.
- Entry whose custom icon id exists in both vaults with different images: the entry keeps its icon id and shows the target's image (MOD-11.17).
- Group move cycle (MOD-11.9): App records a Conflict and finishes; the reference hangs.
- Hostile source with millions of objects: bounded by the open limits (LD-22); the merge itself is linear.
- An entry that is in the target recycle bin and newer in the source (Mod only, Loc older): replaced by the source version but stays in the bin.
- A source that changed only the vault name (different vaults): no change record; target name stays.
- Not on Mac: the Linux secret service key `FDO_SECRETS_EXPOSED_GROUP` is still a protected key in MOD-11.18 and is never removed.

## Security notes

- **No lost data (SD-03, AT-I05).** A merge keeps every entry of both sides, except an entry that the same vault's deleted-objects list removed after its last change (FMT-15.11, LD-265). Only a same-vault merge applies such deletions over the whole vault (MOD-11.15), because only a key holder can make a copy that opens with the vault's key, so its deletions are the user's own; a copy under a key this Mac retired gives none (MOD-11.31, LD-267 (2)). Keep-newer never drops a version on purpose. App fixes the reference's losses: history join with limits −1, 0 and 1 (MOD-11.13), same-time conflicts (MOD-11.14), group fields (MOD-11.10), metadata in a merge after a change on disk (MOD-11.19, MOD-11.29). What must never happen: a merge that ends with fewer entries than the union of both sides, less the entries the deletion pass erased; a newer version gone; or a deletion taken from a copy that is not the same vault (one known limit: a share's item that an approved share import kept in the list, dated no later than the import, see the SI-09 note below and T65).
- **No hang, no crash (AT-A08, AT-A10).** A hostile or simply unlucky source can make the reference move a group into its own child and hang. App's cycle guard (MOD-11.9) and the root rule are required. A fuzz target that merges two mutated vaults must run without panics or hangs.
- **Synchronize mode erases and share scope (SI-09).** A share can name any id in its deleted-objects list, and any id in its tree. App erases, moves and changes only inside the shared group (D-11-9, LD-61). Synchronize runs only for approved shares (INT-08.31) and only inside the share group (LD-61); with D-INT08-1 option (b) a signed container must also pass the trust list (INT-08.29). A share is never a same-vault merge, even when its root group id equals the vault's (Notation): it opens with the share password, which every member holds, not with the vault's key. Only a key holder can make a copy that opens with the vault's key, so only a same-vault merge applies deletions outside the shared group (LD-265), and a share's item that names an object outside the shared group on this Mac is dropped from the rebuilt list (MOD-11.15). An item whose id names nothing here, or an object inside the shared group that the import erased, stays in the list, but with a time no later than the import: the import clamps a future-dated item to the import time (LD-271 (1)). The whole-vault pass of a later same-vault merge keeps every object whose last change or last move (Mod or Loc) is later than the item's time (LD-271 (2)), so such an item cannot erase later edits, and an entry that another copy moved out of the shared group after the import stays. Known limit (LD-271 (3)): a member can delete an entry that was shared with them, and if another copy moved it out of the shared group earlier than that deletion, the later same-vault merge erases it; a member can only name ids it was shown, because ids are 128 random bits (MOD-11.15, T65; spec/research/sync-server.md P2).
- **Shared-group settings arriving by merge (SI-09).** A new group copied from a source carries its shared-group settings item (MOD-11.6), and App never copies that item into an existing group (MOD-11.10). INT-08 must not start importing or exporting a share that arrived by merge until the user confirms it, so a merged hostile vault cannot make App export a group to a path the attacker chose.
- **Protected custom data (SI-01).** Browser associations, the Linux secret service group and remote sync settings are never removed by a merge (MOD-11.18). Remote sync settings hold commands that App runs as the user (started directly, without a shell, INT-09.8): a source that wins can still change or add them, so INT-09.20 shows a changed sync's full commands and asks before its first run. Browser association keys come from the source only in a same-vault merge (MOD-11.18, LD-60), so another vault cannot add an association the user never confirmed.
- **Change list and logs (AT-C06, AT-E01).** Records hold no values (MOD-11.24). Titles, group names and paths come from the source, which may be hostile: the preview sets them as text, never as markup. The reference's log warnings name entry titles and ids; App's logs hold only counts and ids, never titles or values.
- **No downgrade, no takeover (AT-A09).** A merge never lowers the cipher, KDF cost or protection flags. It takes the source's newer key without a question only in a same-vault merge after a change on disk, in a cloud-folder merge (a conflict copy or the rollback guard's merge) and in server sync, so the result holds the newer of the two keys (MOD-11.19 limit 2, LD-264, LD-267 (2)); elsewhere only with the user's yes (the window merge, remote sync), and never in a flow with no question (MOD-11.19, LD-60). Taking the newer key gives a server or a cloud folder no new power: without the key it cannot make a copy that opens. A share or an imported vault never touches the vault settings or key, whatever its root id (Notation, MOD-11.20). A copy under a key this Mac retired never gives its key, metadata or deletions, whatever its key-change time, and is merged only after the user's click (MOD-11.31, LD-267 (2), LD-269 (3)).
- **Credentials of the source.** The source is unlocked with its own key; its key and derived keys are wiped when the merge flow ends (SR-07). With the same-credentials option the target's key is used and never copied.
