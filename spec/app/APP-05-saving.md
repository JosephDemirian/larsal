# APP-05 Saving, backups, changes on disk

Status: reviewed
Epics: E4-S15, E5-S10, E15-S3, E15-S4
Parity rows: SD-01, SD-02, SD-03, SD-09, SD-10, SD-12, SF-07, SR-16

## What it does

This card owns when App writes an open vault back to its file, how the write is made safe, the backup copy made before each save, and what happens when the file changes on disk while the vault is open (another app, another Mac through a sync service, a second App window). It also owns how App reads and writes files that a cloud service manages (coordinated access, "Still downloading"), the conflict copies such services make, and the rollback guard against an older file put back (spec/research/sync-server.md P18). It also owns the one-time notice when a vault read from a version 3 file is first saved as version 4 (spec/decisions.md LD-07).

Other cards own the rest: the bytes that are written (FMT-01 to FMT-16), the fresh random values of every save (CRY-03), the version chosen (FMT-16), the merge used after a change on disk and for conflict copies (MOD-11.29; what a same-vault merge is: MOD-11's Notation; a copy under a key this Mac retired: MOD-11.31), locking and its save-or-discard question (APP-02.15), the unlock screen and the recent-vaults list (APP-06), the menus and their shortcuts (APP-08), the per-vault autosave delay control (MOD-12.8), the command line tool's saves (INT-10).

Words used here. **Data change**: any change to vault content or vault settings that the user (or an integration acting for the user) commits: an entry or group editor applied, an entry or group added, moved, deleted or restored, vault settings applied, an import or merge result, a login saved by the browser bridge (INT-02). Typing in an open editor is not a change until the editor applies. **View-state change**: a change that is stored in the file but is not user data: a group expanded or collapsed in the sidebar (MOD-02.5) and an entry moved up or down in its group's stored order (MOD-02.24). **Changed**: the vault has data changes that are not yet in the file. **Real path**: the vault's path with every symbolic link resolved. **Checksum**: SHA-256 (approved crate) of the first 1,024 bytes of the file (all bytes when it is shorter), together with the file length.

## Inputs and outputs

App settings (APP-01 owns the inventory; if APP-01 gives one of these a different ID, APP-01 wins; the first three IDs are already used by APP-02):

| `save.after_every_change` | Each data change is saved | on | on | on / off |
| `save.on_lock` | Save unsaved changes when locking, closing or quitting | on | on | on / off |
| `save.non_data_on_lock` | Save view-state changes silently when locking | on | on | on / off |
| `save.safe` | Safe saving: write a new file, then swap it in | on | on | on / off |

Outputs: the vault file (and a backup file), the vault's changed state, the "changed on disk" event, and the messages listed under Edge cases. App's per-vault save state, kept in the session only: the last-known checksum, the "ignore disk changes until saved" flag, the consecutive-failure count, the version the file was read as (FMT-16.24), whether the LD-07 notice was shown, and whether this vault was switched to `save.unsafe_method` (APP-05.14), and the conflict copies already merged or kept (APP-05.17). Kept on this Mac across sessions, in local state that is never synced and never written into a vault or next to one (decided: spec/decisions.md LD-267 (2), (3), LD-269 (2), (4)): per vault, the rollback guard's values (APP-05.26), and this Mac's retired-key records (MOD-11.31).

## Rules

### When App saves

APP-05.1 **What triggers a save.** Data changes trigger saves under APP-05.2 and APP-05.3. View-state changes trigger nothing while `save.non_data_on_lock` is on: they do not make the vault changed and are written with the next save, or silently at lock (APP-05.4). While `save.non_data_on_lock` is off, a view-state change counts as a data change. Unlocking, searching, selecting, Show and Copy never trigger a save.

APP-05.2 **Saving each change.** When `save.after_every_change` is on and the vault autosave delay is off, the first data change starts a 150 ms window; every change inside the window joins it; when the window ends, one save starts. Only one save of a vault runs at a time (SD-01): a save requested while one runs is queued, several requests make one queued save, and it starts when the running save ends, whatever that save's result. Reference: the same 150 ms window (the first change starts it, later changes do not extend it); after a failed save, its next change is not saved (only the one after), which App does not copy.

APP-05.3 **Autosave delay.** When `save.after_every_change` is on and the vault's autosave delay is N > 0 minutes, each data change restarts a timer of N minutes, and the save starts when the timer ends without a further change. If the user turns `save.after_every_change` off or sets the delay to 0 while the timer runs, nothing is saved when it ends. Any save of the vault (manual, lock, quit) stops the timer. The reference behaves the same (from the source).

APP-05.4 **Save on lock, close and quit.** Locking runs APP-02.15 step 8: with `save.on_lock` or `save.after_every_change` on, a changed vault is saved; if that fails, a manual lock asks and an automatic lock writes a recovery copy and locks (APP-02.16; Decided: spec/decisions.md LD-50). Closing a vault locks it first, and quitting locks every vault (APP-02.11), so both save the same way. A vault with only view-state changes is saved silently at lock when `save.non_data_on_lock` is on; a failure of that save is ignored and shows nothing.

APP-05.5 **Linked settings.** Turning `save.after_every_change` on also turns `save.on_lock` and `save.non_data_on_lock` on and greys both out until it is turned off again (same as the reference). Turning it off leaves both as they are and makes them editable.

APP-05.6 **Manual save actions** (menus and shortcuts: APP-08).
- `action.save` Save: enabled while the shown vault is unlocked and changed. Starts a save at once (it ends any running window or delay timer of APP-05.2 and APP-05.3).
- `action.save_as` Save As: enabled while the shown vault is unlocked. A save panel opens in the folder of the current file, with the current file name. After a successful write the vault's path becomes the new path, the watcher moves to it (APP-05.24), the recent list is updated (APP-06) and the old file stays as it was. A save happens even when the vault is not changed. No pre-save check (APP-05.10) is made on the new path; the save panel asks before replacing an existing file (macOS standard).
- `action.save_copy` Save a copy: enabled while the shown vault is unlocked. Writes the vault as it is in memory, unsaved changes included, to a path from a save panel, with the safe method of APP-05.11. The vault keeps its path and its changed state; no backup, no pre-save check. The reference writes this copy with direct write (APP-05.16) and keeps the changed state the same way.

APP-05.7 **Changed indicator.** While a vault is changed, the main window shows the macOS "edited" mark (the dot in the close button) when that vault is shown, and the vault switcher shows a dot after its name. View-state changes never show it. The reference adds `*` to the tab and window title.

APP-05.8 **Never saved, never overlapping.** App never saves a locked vault, a vault being reloaded (APP-05.25), or a vault without any key part (`NoCredentials`, FMT-04.16); none of these is an error the user sees, except `NoCredentials`. A save takes one consistent snapshot of the vault when it starts. Building the file (key derivation, encryption, CRY-02.15) and writing run on a worker thread; the vault stays usable, and changes made meanwhile go into the next save. The reference disables its whole window for the length of every save (about 1 second with default settings).

### How App writes

APP-05.9 **Which file.** App writes to the real path. A symbolic link at the vault path stays a link, and the file it points to is replaced (observed in the reference: the link survived and its target got a new inode). The temp file, the swap and the backup all use the real path's folder. A vault path whose target no longer exists is written as a new file at the path as given. A vault path or Save As target that exists and, with links followed, is not a regular file (a FIFO, a device, a folder) is refused before any open: the save fails with `MSG-SAVE-FAILED` "This vault's path is not a file App can write." and writes nothing. Every read of the vault file (the pre-save check, the backup, the direct method, reload, unlock) opens it without blocking (`O_NONBLOCK`) and checks the open file with `fstat`, so a pipe planted at the path never holds App (F-101, LD-228 (4)).

APP-05.10 **Pre-save check.** Before writing to the vault's own path, unless the "ignore disk changes until saved" flag is set (APP-05.27) or the vault has no last-known checksum yet (never read from or written to this path), App computes the checksum of the file now on disk (in a coordinated read, APP-05.24):
1. The file does not exist: no check; the save writes it anew and then shows `MSG-SAVE-RECREATED`.
2. The file exists but cannot be opened or read: the save fails with `MSG-SAVE-FAILED`, reason "the vault file cannot be read". Nothing is written.
3. The checksum differs from the last-known checksum: nothing is written, no backup is made, and APP-05.28 starts. This refusal does not count as a failure for APP-05.14 and shows no failure message.
4. Equal: continue.
When this check ran, then just before the rename (or the direct write), after the backup (APP-05.19) and the temp file are written, App takes an exclusive advisory lock (`flock`) on the file now on disk, checks the checksum again under it (a change starts APP-05.28 as in step 3, but the backup this save made stays) and holds the lock to the rename, so two writers (two App processes, App and the command line tool) take turns and the second one's check sees the first one's save (F-110). The lock makes no lock file (APP-05.17); on a file system without such locks the save goes on as before. A writer that does not get the lock within 5 seconds fails with `MSG-SAVE-FAILED` "Another program is writing this vault's file. Try again." and leaves the vault file as it was (its temp file is removed; a backup this save made stays); this failure does not count for APP-05.14 (F-124, LD-242, LD-228 (4)).
The lock covers one Mac only (spec/research/sync-server.md P18 (4), section 3). On a cloud or network folder (iCloud Drive, Dropbox, OneDrive, Google Drive, an SMB share, a Finder-mounted WebDAV share) `flock` keeps out only writers on this Mac; a writer on another Mac never sees it. Across Macs the signals are the change on disk (APP-05.24) and the cloud's conflict copy (APP-05.17). A save from another Mac that lands between the check under the lock and the rename is replaced; only the cloud's conflict copy or the backup (APP-05.19) keeps it.
Reference: the same check on the first 1,024 bytes with an MD5 hash and no length; it reports a read error when a file of 1,024 bytes or more gives fewer bytes.

APP-05.11 **Safe save** (`save.safe` on, and the vault not switched by APP-05.14). After APP-05.10, and after the backup (APP-05.19): App (LD-129): copying the creation date, Finder tags and access control list to the temp file before the rename (D-A05-1 b) is done by app-platform in E5-S10; standard Rust has no safe way to do it.
1. Stop the watcher for this vault (APP-05.24).
2. Build the file bytes from the snapshot (fresh random values CRY-03; the version of FMT-16; the save fails if the derived key did not change, SF-07).
3. Create a temp file in the real path's folder, named `.` + the file name + `.` + 8 random characters from `a`–`z` and `0`–`9` + `.tmp`, with exclusive create and no link following, mode 0600 from the start.
4. Write every byte, check that every write completed, then flush to the device (on macOS a full sync, `F_FULLFSYNC`).
5. Give the temp file the old file's permission bits (0600 for a new file) and the old file's creation date.
6. Rename the temp file over the real path in one step, inside a coordinated write with `.forReplacing` (APP-05.24) (the same folder, so the rename is atomic: AT-I01). Then sync the folder.
7. Store the checksum of the bytes written as the last-known checksum, clear the changed state (unless changes arrived after the snapshot), reset the failure count, clear the "ignore disk changes" flag, restart the watcher, and update the recent list (APP-06).
The command line tool saves the same way, without backup and without a watcher (INT-10). The reference's safe save: a new file next to the vault, then a rename; it keeps permissions (observed: 0644 stayed 0644) but the creation date was not kept in the installed version (observed: it became the save time; the source tries to keep it; Verified 2026-10-28, V-A05-1: since 2.7.0 the source asks its toolkit to give the new file the old creation date, yet on this Mac the installed 2.7.11 command line tool saved a demo vault whose creation date had been set to 2020-01-01, and the date became the save time, with a new inode) and extended attributes were dropped (observed: a test attribute was gone after a save). Lead decision D-A05-1: (a) drop extended attributes as the reference; (b) copy only the Finder tags attribute (`com.apple.metadata:_kMDItemUserTags`) and the ACL to the temp file before the rename. Recommended: (b), so user tags survive every save. Decided: spec/decisions.md LD-200 (as recommended).

APP-05.12 **Permissions and links.** A new vault file gets 0600 (SD-09, AT-I06; the reference does the same, observed). A re-save keeps the existing permission bits, as the reference does. A vault with more than one hard link: the rename gives the vault path a new file and the other links keep the old content (observed in the reference); App never writes into the other links (AT-I04).

APP-05.13 **When a write fails.** The temp file is removed and the old file is left untouched (AT-I02, AT-I03). The vault stays changed, `MSG-SAVE-FAILED` names the reason from the operating system (for example no space left, permission denied, the file is not writable), shown in the vault's banner for 15 seconds with a close button (the reference uses the same time). The watcher resumes with the checksum it had (the reference stops watching after a failed save until the next good save; App does not copy that). A read-only vault file (mode 0444) is never saved over, as in the reference, even though a rename could replace it; App says the file is read-only (LD-129).

APP-05.14 **Repeated failures.** App counts consecutive failed saves of a vault (automatic and manual; APP-05.10 refusals do not count). The count resets on a successful save, on unlock and on a reload. When a safe save fails and the count reaches 3, App asks `MSG-SAVE-UNSAFE-ASK`: saving this vault failed several times, which can happen when a sync service holds the file; turn off safe saving for this vault and try again? Buttons Cancel (default) and Turn off. Turn off switches this vault alone to `save.unsafe_method` for as long as it stays open in this session, and saves again at once; the app setting `save.safe` and every other vault are unchanged (Decided: spec/decisions.md LD-52). Cancel leaves everything as it is. App does not ask, and does not count, a failure whose reason is "permission denied", "read-only file system", "the file is not writable", "no space left", "the path is not a regular file" (APP-05.9) or "another program is writing this vault's file" (the APP-05.10 lock, which every method takes; F-124, LD-242): the unsafe methods cannot help there and direct write could make it worse (lead decision D-A05-2, recommended; decided: spec/decisions.md LD-200 (as recommended); the reference asks for every failure).

APP-05.15 **Unsafe method `temp_move`.** Build the bytes, write them to a temp file (mode 0600) in App's private temp folder, flush it, delete the vault file, move the temp file to the real path (a copy when the folders are on different volumes), then give it the old permission bits and creation date. If the move fails: when a backup was made by this save, App copies the backup back to the real path (keeping the old permission bits) and reports `MSG-SAVE-FAILED`; when no backup exists, App keeps the temp file and reports `MSG-SAVE-FAILED` with the temp file's path, so the user can recover it. This method is not atomic: a crash between delete and move leaves no vault file at the path. Same as the reference (from the source).

APP-05.16 **Unsafe method `direct`.** Build the bytes; read the current file's bytes into memory (bounded by FMT-01.31); truncate the file and write the new bytes in place; check that every write completed; flush. If any step after the truncation fails, write the old bytes back and report `MSG-SAVE-FAILED`. The inode, hard links and extended attributes stay. Reference (from the source): it does not check the result of the in-place write, so a full disk can leave a cut-off file while it reports success. App's check and restore are stricter (data safety).

APP-05.17 **Cloud folders, conflict copies, lock files, leftovers.** App treats every folder the same (no folder detection rule, LD-269 (4)): it creates no lock file next to a vault (the reference creates none either), and does not delete leftover temp files of an interrupted save (they hold only encrypted vault bytes; the reference leaves its leftovers too). The only lock file App makes is the single-instance one (APP-09). App looks for the conflict copies that sync services make when two Macs save at once, and merges them (decided: spec/decisions.md LD-264, LD-265, LD-267 (2), LD-269 (3); design: spec/research/sync-server.md P18 (3), section 3). The reference does not look for them; its user merges them by hand.
1. **When.** After each unlock, and on each watch event or 30-second tick of APP-05.24, at a time APP-05.25 allows (never while the vault saves, reloads, unlocks or has an editor open, and never while a "changed on disk" event is pending).
2. **iCloud.** The conflict versions of the real path (`NSFileVersion.unresolvedConflictVersionsOfItem(at:)`), each read in a coordinated read (APP-05.24).
3. **Other clouds and folders.** Files in the real path's folder with the same extension whose name starts with the vault's file name without its last extension (`{FILE_NAME}` of APP-05.20), the vault itself left out. A name only makes a file a candidate: Dropbox and OneDrive name their copies differently, and Google Drive's pattern is not confirmed (E15-S5 records it), so names are never trusted.
4. **Never listed, never opened.** Every file that matches this vault's backup pattern (the current `save.backup.path` and the default `{FILE_NAME}.old.appvault`, each matched as APP-05.33 matches it, a time placeholder matching any text, also while backups are off), and App's temp files (APP-05.11 step 3). Why: the backup is a same-vault copy that opens with the current key; without this rule it would be merged and offered for the Trash, and the user would lose the safety copy.
5. **Each candidate, by what opens it.**
   - It opens with the current key and has the vault's root group id: it is merged into the open vault at once (MOD-11.1, kind "Cloud conflict copy"). This is a same-vault merge, so the deletion pass runs (MOD-11.15).
   - It does not open with the current key: it is listed as "Needs its password" and left alone until the user gives the credentials it opens with (Unlock… opens the unlock sheet with `MSG-DISK-NEW-KEY`, APP-05.29; MOD-11.29). Then, when its root group id matches, it is merged, and the result keeps the key LD-264 picks (MOD-11.19).
   - The credentials the user gave for it match a key this Mac retired (MOD-11.31): it is never merged on its own. It is listed as "Uses a replaced password" with the choice of `MSG-DISK-OLD-KEY`: Skip (the default) leaves it alone; Merge anyway runs the content merge only, never its key, its deletions or its metadata.
   - It has another root group id, or cannot be read (the reasons of APP-05.30): it is not merged and not listed.
6. **The OK.** After the merges, and after the merged vault was saved (APP-05.2), App shows `MSG-DISK-COPIES`: each listed copy with its state (Merged, Needs its password, Uses a replaced password), and a check box, checked, on each merged copy. Move to Trash moves the checked copies to the Trash; for iCloud it marks each merged version resolved (`isResolved`) and, once no unresolved version is left, calls `removeOtherVersionsOfItem(at:)`. Keep (the default) moves nothing. A copy is never deleted outright and never moved without this OK. A copy that was merged or kept is not merged or listed again in this session until its checksum changes (APP-05.24).

APP-05.18 **Read-only vaults.** Neither app has a read-only open mode. App checks after each unlock whether the real path is writable (the file and its folder). If not, the vault's banner shows `MSG-SAVE-READONLY` (changes cannot be saved to this file; use Save As to keep them), edits stay possible, and auto-save attempts are skipped until the user saves manually or the file becomes writable. Lead decision D-A05-3: (a) as the reference: no check, every save fails with an error; (b) the check above; (c) a true read-only mode that blocks edits. Recommended: (b). Decided: spec/decisions.md LD-200 (as recommended).

### Backups

APP-05.19 **When.** With `save.backup.enabled` on, every save to the vault's own path whose real path exists first copies the file on disk, byte for byte, to the backup path, after APP-05.10 passed and before the new bytes are written. This includes automatic saves, so with the default pattern the backup always holds the version before the last save. Save As backs up the file it replaces at the target path, with the pattern applied to the target path; Save a copy makes no backup. A new vault's first save makes no backup. The reference makes the backup at the same point; on Save As it names the backup after the vault's old path (from the source).

APP-05.20 **Path pattern.** The backup path is `save.backup.path` with these placeholders replaced, in one pass from left to right; replaced text is never scanned again:

| Placeholder | Replaced with |
|---|---|
| `{FILE_NAME}` | the vault's file name without its last extension (`Personal.appvault` gives `Personal`; `a.b.appvault` gives `a.b`; a name with no dot stays whole; `.appvault` gives the empty text) |
| `{TIME}` or `{TIME:}` | the local time of the save as `dd_MM_yyyy_HH-mm-ss` |
| `{TIME:f}` | the local time formatted with `f` (tokens below); `f` may not contain `{`, `}` or `\` |
| `\{` and `\}` | a literal `{` or `}`; a placeholder never starts at an escaped brace |

Any other text, an unknown placeholder such as `{NO_MATCH}` and an unclosed one such as `{FILE_NAME` stay as written. Time tokens (longest match first; numbers only, so the result never depends on the language): `yyyy` year with 4 digits, `yy` last 2 digits, `MM`/`M` month with/without a leading zero, `dd`/`d` day, `HH`/`H` and `hh`/`h` hour 0–23, `mm`/`m` minute, `ss`/`s` second, `zzz` milliseconds; text between single quotes is copied as is (`''` gives one quote); every other character is copied as is. The reference has the same two placeholders under its own names and formats the time with its toolkit's date format, of which these tokens are the numeric part.

APP-05.21 **Path resolution.** A pattern result that starts with `~/` is taken from the user's home folder (App only; the reference has no `~`). A relative result is taken from the folder of the vault's real path. Missing folders are created. An existing file at the backup path is replaced. The backup file gets mode 0600 (SD-09 App goes further; the reference gives it the vault's permission bits). The pattern "Choose folder" button in the settings fills in `<chosen folder>/{FILE_NAME}.old.appvault` (the reference does the same with its default).

APP-05.22 **How many are kept, and failures.** One backup per distinct backup path: a pattern without `{TIME}` keeps exactly one file, which each save replaces; a pattern with `{TIME}` makes a new file for every save that falls in a new time slot, and App never deletes old ones (the reference neither). If the backup cannot be made, the save goes on, and App shows `MSG-SAVE-BACKUP-FAILED` with the reason once per vault per session (the reference ignores the failure silently).

APP-05.23 **Backup as recovery.** The backup made by a save is what APP-05.15 restores when its move fails. It is never read by App otherwise; the user can open it like any vault.

### Changes on disk

APP-05.24 **Detection.** For each unlocked vault App watches the real path's folder (so a writer that replaces the file is still seen) and the file itself (for a writer that edits it in place) with the system's kqueue file watch (Decided: spec/decisions.md LD-216), and also checks every 30 seconds. On a watch event (events within 500 ms are joined into one) or a timer tick, App computes the checksum on a worker thread. If the file cannot be opened, the result is the last-known checksum, so a missing file or a network share that is briefly away causes no event. If the checksum differs from the last value the watcher knows, the watcher stores the new value and raises "changed on disk" for that vault. The watcher is stopped during App's own save and restarted with the checksum of the bytes App wrote, so App's own saves never raise the event. It is paused while the "ignore disk changes until saved" flag is set. Reference: a system file watch plus a 30-second check of the first 1,024 bytes (SHA-256), with the same "cannot open, no event" rule (from the source).
**Coordinated access** (App; design: spec/research/sync-server.md P18 (1), section 3). Every read of the vault file runs in a coordinated read (`NSFileCoordinator`): the unlock read (APP-06), the reload and merge reads of APP-05.26 to APP-05.29, the checksums of APP-05.10 and of this watcher, and the conflict copies of APP-05.17. The save's rename of the temp file over the real path (APP-05.11 step 6) runs in a coordinated write with `.forReplacing`. Each runs on a background queue (`coordinate(with:queue:byAccessor:)`), one coordinator per operation, with the Rust file I/O inside the accessor; no file call runs on the main thread. Why: a cloud service's file provider sees only coordinated changes, and file calls on iCloud Drive, other file providers or SMB can take an unknown time. The kqueue watch and the 30-second check stay (LD-216).
**Still downloading** (App; design: spec/research/sync-server.md P18 (2)). Before each read App tests `SF_DATALESS` in the file's `st_flags` (`stat`). When it is set, App reads nothing yet: it shows `MSG-DISK-DOWNLOADING` (APP-05.30) and starts the download (`startDownloadingUbiquitousItem(at:)`, or lets the coordinated read fetch it off the main thread); the read runs when the file is on this Mac. A 30-second tick is the one exception: when it finds `SF_DATALESS` it reports no change and starts nothing; only a watch event, the unlock, a reload, a merge or a save read shows "Still downloading" and starts the download. The tick never fetches a file: it turns fetching off on its own thread (`setiopolicy_np` with `IOPOL_MATERIALIZE_DATALESS_FILES_OFF`), so a file that turns dataless between the test and the read gives `EDEADLK`, which also counts as "no change".

APP-05.25 **When the event is handled.** The event is dropped for a locked vault. While the vault is saving, reloading, being unlocked, or while its entry or group editor is open, or while the file is still downloading (APP-05.30; spec/research/sync-server.md P18 (2)), App keeps one pending event and handles it when that ends (editor closed, applied or cancelled). The reference drops the event in all these cases; the next save's pre-save check then catches the change (lead decision D-A05-4, recommended: keep it pending; decided: spec/decisions.md LD-200 (as recommended)). While an event is handled, the vault's views are disabled and the banner shows `MSG-DISK-RELOADING`; a lock waits until it ends (APP-02.15 step 3).

APP-05.26 **No unsaved changes.** When the vault is not changed and has no view-state changes, App first applies the rollback guard below. For a disk version that passes it: with `disk.auto_reload` on, App reloads silently: it opens the file with the vault's current key (no KDF prompt; CRY-02.14 still applies) and replaces the open vault with it. With `disk.auto_reload` off, App first asks `MSG-DISK-ASK-RELOAD` (the file "<file name>" was changed by another program; load the changes?) with Load (default) and Keep. Keep marks the vault changed; nothing is written until the next save, which then runs into APP-05.28.

**Rollback guard** (App; decided: spec/decisions.md LD-267 (3), LD-269 (4); design: spec/research/sync-server.md P18 (6)). For every vault App opens, in any folder, App keeps on this Mac, in local state that is never synced, per vault (its root group id):
- the newest change time seen: the latest of every entry's and group's Mod and Loc, every deleted-object time (FMT-15) and the vault's metadata change times (FMT-10; the times MOD-11.19 lists, `MasterKeyChanged` included), over every version of this vault App read or wrote;
- the SHA-256 of the last bytes App read from or wrote to the vault file;
- the newest file version (FMT-16) and the strongest KDF settings seen (compared as in MOD-11.19 limit 1).

A disk version with the vault's root group id is **older** when its newest change time is earlier than the stored one. App never reloads an older disk version silently, whatever `disk.auto_reload` says. It merges it as a same-vault copy (MOD-11's Notation; the disk version is the target and the open vault the source, as MOD-11.29), so the deletion pass runs and no newer entry, deletion or KDF setting is lost (MOD-11.15, MOD-11.19 limit 1), and saves the result at once, whatever `save.after_every_change` says, so the older copy does not stay on disk for other Macs to read (spec/research/sync-server.md P18 (6)). Once that save succeeds, App shows `MSG-DISK-ROLLBACK`; a failed save is handled by APP-05.13 (`MSG-SAVE-FAILED`, the vault stays changed). A disk version that is not older but has a lower file version or weaker KDF settings than stored loads as above and shows `MSG-DISK-WEAKER`, naming the setting, never a value. At unlock the guard only warns: an older file opens as it is and App shows `MSG-DISK-ROLLBACK-UNLOCK`; a weaker one shows `MSG-DISK-WEAKER`. A file whose bytes equal the stored SHA-256 is the one App last read or wrote and needs no compare. The stored values only move up, after each read App accepts and each save, except that a change the user makes on this Mac in Vault Settings (MOD-12.12) sets the stored file version and KDF settings to the new ones. Why: a vault with no unsaved changes reloads a changed file silently; an older copy put back by a cloud service, a hostile folder or a stale Mac that chose Overwrite (APP-05.28) would then drop newer entries and raised KDF settings, and the next save would spread that to every Mac. A rollback with no conflict copy never reaches APP-05.17, and only local state stops a full rollback (spec/research/sync-server.md P4, section 6; spec/research/business-model.md section 3, "Guard against rollback"). A vault anywhere can be rolled back, so the guard has no folder detection rule (LD-269 (4)).

APP-05.27 **Unsaved changes.** When the vault is changed or has view-state changes, App asks `MSG-DISK-UNSAVED`: the file "<file name>" was changed by another program; how to go on? Before it asks, App reads the disk version with the current key and runs the rollback guard's compare (APP-05.26; LD-267 (3); spec/research/sync-server.md P18 (6)). For a version the guard finds older, the question also shows the "went back in time" line of `MSG-DISK-ROLLBACK`, so Discard never loads an older version without the user knowing. A version that opens only with other credentials is compared once they open it (APP-05.29). Buttons, default Merge:

| Button | Effect |
|---|---|
| Merge | open the file with the current key, merge the open vault into it (MOD-11.29: the disk version is the target; a same-vault merge when the root group ids match (MOD-11's Notation), so a deletion made on either side is kept, MOD-11.15), and replace the open vault with the result; then save under APP-05.2 (a save follows when `save.after_every_change` is on) |
| Ignore | keep the open vault; set "ignore disk changes until saved", so the watcher pauses and the next save skips APP-05.10 and replaces the disk version |
| Discard | replace the open vault with the disk version; unsaved changes are lost |
| Cancel | keep the open vault and mark it changed; nothing is written until the next save, which then runs into APP-05.28 |

APP-05.28 **Changed on disk, found by a save.** When APP-05.10 step 3 refuses a save, App asks `MSG-DISK-ON-SAVE` with Merge then save (default), Overwrite, Discard, Cancel. As in APP-05.27, App first runs the rollback guard's compare, and for an older disk version the question also shows the "went back in time" line of `MSG-DISK-ROLLBACK`. Merge then save: as Merge in APP-05.27, then saves at once. Overwrite: sets "ignore disk changes until saved" and saves at once, replacing the disk version (banner `MSG-DISK-OVERWRITTEN`). Discard and Cancel: as in APP-05.27. If the save was part of a manual lock, close or quit, the lock waits for the answer, and Cancel makes the lock fail (APP-02.15 step 8). An automatic lock asks nothing: App writes a recovery copy and locks (APP-02.16; Decided: spec/decisions.md LD-50).

APP-05.29 **Disk version needs other credentials** (decided: spec/decisions.md LD-264, LD-267 (1), (2), LD-269 (3); design: spec/research/sync-server.md P2, P3). When the disk version gives `WrongKey` with the current key (for example the copy was saved under another password or key, newer or older), App shows the unlock sheet for that file over the vault with `MSG-DISK-NEW-KEY` (this copy opens with another password or key; enter the password or key this copy opens with). The sheet works as APP-06, including Touch ID only if it holds a slot for that file. Cancel acts as Cancel in APP-05.27. When the credentials given open the file, App first tests them against this Mac's retired-key records (MOD-11.31):
- They match a key this Mac retired: App merges nothing on its own and shows `MSG-DISK-OLD-KEY` (this copy uses a password or key that was replaced on this Mac) with Skip (default) and Merge anyway. Skip: nothing of the copy is taken; App keeps the open vault and saves it over the copy at once, as Overwrite in APP-05.28 (with backups on, APP-05.19 first keeps the copy as the backup). Merge anyway: the content merge of MOD-11.31 (the open vault is the target), then a save over the copy at once, as Overwrite; the vault keeps this Mac's key. Why: a password change often follows a leak, so a copy under the replaced password must not bring that password back or change or delete entries without the user's click.
- Otherwise, when its root group id matches, the disk version is the same vault (MOD-11's Notation; with another root group id, a merge is not same vault), and App goes on with the chosen action, Merge or Discard. A silent reload (APP-05.26) becomes Merge here, because the open vault may hold edits and deletions made under the other key; this is how the other Mac's case converges (spec/research/sync-server.md P3). The rollback guard of APP-05.26 still compares: for an older version App shows the "went back in time" line of `MSG-DISK-ROLLBACK`, and a Discard chosen before the compare is asked once more, with Merge the default. After a merge the vault keeps the key LD-264 picks; after a discard it takes the disk copy's key.

APP-05.30 **Disk version unreadable, or still downloading.** When the disk version cannot be read for any other reason (`Corrupt`, `NotAVault`, `Unsupported`, `TooLarge`, or the file vanished between event and read), App keeps the open vault unchanged and does not mark it changed, and shows `MSG-DISK-UNREADABLE` (App could not read the file on disk; your open copy is unchanged). A later "changed on disk" event is handled again from APP-05.25. A later save runs into APP-05.28, where App then offers only Overwrite (default) and Cancel, because there is nothing to merge or load. A dataless file (APP-05.24) is not unreadable: App keeps the open vault unchanged and not changed, and shows `MSG-DISK-DOWNLOADING` ("Still downloading") in the vault's banner, where `MSG-DISK-UNREADABLE` shows; the event stays pending (APP-05.25) and is handled when the download ends. At unlock the same text shows under the unlock form, and the unlock goes on when the download ends (spec/research/sync-server.md P18 (2)). Reference: its reload does nothing for such a file; a merge choice then asks for other credentials (from the source).

APP-05.31 **After a reload or merge.** App keeps the selected group and entry when they still exist (by id; else the root group and no entry), runs auto-open again (APP-06), resets the failure count, stores the disk version's checksum as the last-known checksum, and shows `MSG-DISK-RELOADED` (or `MSG-DISK-CANCELLED` after a Cancel) for 2 seconds. Then the views are enabled again.

### Version 3 vaults

APP-05.32 **The one-time notice** (decided: spec/decisions.md LD-07). Before the first save to its own path of a vault read from a version 2 or 3 file (the version remembered with the vault, FMT-16.24), App shows `MSG-SAVE-V4-NOTICE`: from now on this vault is saved in the newer file format; apps that only read the older format cannot open it any more; the unlock time stays the same (FMT-16.21); when backups are on, the old file is kept as the backup. One button, OK; then the save goes on. It is shown at most once per vault per session, even if that save fails. Once the file is written as version 4, later opens are version 4 and never show it again. Save As and Save a copy do not show it (the old file stays as it was). Lead decision D-A05-5: (a) a notice with OK only, as written; (b) a question with Save in new format and Cancel, where Cancel keeps the vault changed and pauses auto-save for it. Recommended: (a); LD-07 asks to tell, not to ask, and the backup keeps the old file. Decided: spec/decisions.md LD-200 (as recommended).

### After a key change

APP-05.33 **Old copies after a key change** (Decided: spec/decisions.md LD-53). After the save that writes a vault's new composite key (MOD-12.10), App shows `MSG-KEY-OLD-COPIES` when backups are on or when at least one copy below exists: backups and recovery copies made before the change still open with the old credentials, and so do copies outside App (Time Machine, sync history). App lists the copies it made of this vault that still exist: the files in the folder of this vault's backup pattern (APP-05.20, APP-05.21) whose names match the pattern, each time placeholder matching any text, and this vault's recovery copy (APP-02.16). Each listed file has a check box, all checked. Buttons Delete checked and Keep, Keep being the default. Delete checked removes the checked files and reports any that could not be removed; Keep removes nothing. With nothing listed, the notice has only OK. The backup the key-change save itself made (it holds the old key) is listed too.

Other cases:
- Two Macs, or App and another program, edit one vault (App never runs two copies on one Mac, LD-47): each sees the other's saves through APP-05.24 and merges per APP-05.27. The merge keeps every entry of both sides, except an entry that the same vault's deleted-objects list removed after its last change (FMT-15.11, LD-265; AT-I05). When both save at once, the cloud's conflict copy is merged by APP-05.17.
- A sync service replaces the vault with an older copy: the checksum differs, so it is handled as a change. With no unsaved changes, the rollback guard (APP-05.26) merges it as a same-vault copy, saves the result at once and then shows `MSG-DISK-ROLLBACK`; it is never reloaded silently. With unsaved changes, the question of APP-05.27 or APP-05.28 shows the "went back in time" line, so Discard never loads it without the user knowing.
- A sync service truncates the file to 0 bytes: the length differs, APP-05.30 applies; the next save offers Overwrite. Reference: no length in its check, but the first bytes differ, so it notices too.
- A file changed only after byte 1,024 with the same length: not noticed. No real writer does this, because every save changes the header's master seed (CRY-03), which lies in the first 1,024 bytes.
- The vault is moved in Finder while open: App keeps the old path; the next save writes a new file there (`MSG-SAVE-RECREATED`). Same as the reference, without its notice.
- Quit while a save runs: the quit waits for it (APP-02.15 step 4).
- Disk full during a safe save: the temp file is removed, the old file is intact, `MSG-SAVE-FAILED` "no space left on device" (AT-I02).

## Security notes

- A save must never leave a broken vault (AT-I01): the safe method writes a complete temp file, syncs it, then renames. Never write into the real file in place unless the user turned safe saving off, and then only with the old bytes kept for a restore (APP-05.16).
- Never overwrite a file that changed on disk without the user's choice (SD-03): APP-05.10 runs before every save to the vault's own path, and only Ignore and Overwrite (also through Skip and Merge anyway of `MSG-DISK-OLD-KEY`) skip it. The `flock` of APP-05.10 covers one Mac only; across Macs the conflict copy and the change on disk are the signal.
- A merge keeps every entry of both sides, except an entry that the same vault's deleted-objects list removed after its last change (FMT-15.11, LD-265; SD-03, AT-I05). Only a key holder can make a copy that opens with the vault's key, so the deletions of a same-vault copy are the user's own.
- A copy under a key this Mac retired is never merged on its own (APP-05.29, APP-05.17; LD-267 (2), LD-269 (3)): a password change often follows a leak, and whoever knows the old password must not bring it back or change or delete entries without the user's click. The retired-key records hold no key or password bytes (MOD-11.31).
- An older file never silently replaces newer content (APP-05.26; LD-267 (3), LD-269 (4)). The guard's state is local and never synced, because only local state stops a full rollback.
- The conflict-copy finder never lists App's own backups or temp files (APP-05.17), so the safety copy is never offered for the Trash, and a copy moves to the Trash only after the user's OK.
- The temp file is 0600 from its creation and created exclusively, so no other user can read it and no planted link can redirect the write (AT-I04, AT-I06).
- Backups hold the full encrypted vault. A backup made before a master key change still opens with the old key; changing the key does not protect old backups. Recovery copies (APP-02.16) are the same. After a key change App says so and offers to delete the copies it made (APP-05.33; parity row SD-12; Decided: spec/decisions.md LD-53). Backups are 0600.
- Leftover temp files and the `temp_move` copy in App's private temp folder hold only encrypted bytes.
- The checksum is not a security check: integrity of the content is proven only by the header and block checks when the file is read (FMT-05, FMT-06).
- No message, log line or error value holds vault content or key material; reasons come from the operating system and name paths only.
- Parity rows: SD-01 (safe save, fallbacks, links, creation date, no overlapping saves), SD-02 (backup), SD-03 (changes on disk), SD-09 (permissions), SD-10 (auto-save), SD-12 (old copies after a key change), SF-07 (fresh values, key changed), SR-16 (save before lock). Attacks: AT-I01 to AT-I06.
