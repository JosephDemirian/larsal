# FEA-10 Show as QR Code

Status: DRAFT (2026-11-04); no second Spec review or Verify sign-off
Epics: E21-S1 (this card and proposals only); E21-S2, E21-S3, E21-S4, E21-S5 after review and their board dependencies
Parity rows: SR-07, SR-13, SC-05, SD-07, SD-09; proposed extensions, not new verification claims

## What it does

Shows the one value the user selected as an ordinary QR symbol, locally, so another device can scan it. A separate action on a Wi-Fi entry makes a join code. A QR image is readable secret material, not encryption. Anyone with the picture can recover its content. The picture can be saved or shared only after a warning on every attempt (LD-336, LD-337 (1), (2)). Encrypted links are E21-S6, outside this card.

This draft does not authorize an implementation story. E21-S1 can start without an already-reviewed card; its successors cannot build from this draft. Technical proposals go to the lead, who decides from the sources below. No new general owner-approval gate is introduced. The locked Option A files stay locked. Proposed frames are not owner-approved; the existing one-pass proposal review and any still-pending owner choices stay pending (LD-268, W-18).

## Inputs and outputs

Input: an unlocked vault/session, one entry and one field selected by the user, or an explicit Wi-Fi join selection. Output: one square module matrix including its quiet zone, its dimension and a non-secret purpose label, or a typed error. The matrix is secret-equivalent. It is not a URL to a service, a file, an attachment, clipboard content or a stored preview. No master key, password text or full entry record is needed by the renderer.

Owners of related behavior: [MOD-01](../model/MOD-01-entry-fields.md) fields; [MOD-08](../model/MOD-08-references-placeholders.md) Show resolution; [FEA-02](FEA-02-password-generator.md) and [FEA-03](FEA-03-passphrases.md) generator limits; [FEA-04.23](FEA-04-one-time-passwords.md) authenticator setup QR; [APP-02](../app/APP-02-lock.md) lock; [APP-08](../app/APP-08-menus-shortcuts.md) menus, shortcuts and access; [APP-10](../app/APP-10-screen-protection.md) window guard; [INT-10.28](../integrations/INT-10-command-line.md) command-line Show; [INT-11](../integrations/INT-11-browser-extension.md) extension authorization. No WEB card exists at this base: E20 and [browser-and-web](../research/browser-and-web.md) B15, B19 to B22, B26 are the current web contract, including WEB-02's intended strict CSP.

## Rules

FEA-10.1 **One deliberate action.** ACT-QR-SHOW is visible beside the Password in the entry view, and beside every protected standard/custom text field, masked or already shown, including protected notes. It is enabled for one existing nonempty value in an unlocked vault; no bulk QR, hover reveal or automatic display. Missing/empty fields cannot reveal a previous matrix. Programmatic calls still check the field and session. A focused editor field may show its current unsaved text without saving it; the Rust draft is the source. This does not add actions to master-key, account-key, passkey or other non-exportable credential controls.

FEA-10.2 **Every entry point.** The entry list's selected-row actions, Entry menu, entry view's More actions and entry-row context menu expose ACT-QR-SHOW for that entry's Password. Right-clicking a protected field targets that field, never a fallback password. Proposed default shortcut is ⌃⌥⌘Q on Mac, scoped to the active Larsal window: a focused protected field wins, otherwise the one selected entry's Password. No selection, multiple selection, locked session or open unrelated sheet disables it. APP-08 custom shortcut conflict and reserved-key rules still apply. The extension popup adds the same labelled action to each login row and to its entry Password and every protected field it exposes; the web vault does likewise in its entry list/view. If a protected field is not otherwise exposed, an entry's “Show Field as QR Code” submenu lists its name and acts on that one field, without fetching every value. Browser versions offer the shortcut while their own page has focus, subject to browser-reserved keys; no global command, page keystroke or content script can reveal it.

FEA-10.3 **Exact value as text.** Encode the exact UTF-8 byte sequence that the existing Show operation would return for the selected value: fully resolved under MOD-08.25 for a saved entry; literal current text for an editor draft, as Show in the editor. No label, field name, newline, prefix, BOM, normalization, trimming, case change, HTML escape, replacement character, base64, compression or extra envelope is added. Whitespace, LF, CR, NUL and other controls in a generic field remain bytes in the QR, never terminal commands. Empty result gives MSG-QR-EMPTY. Resolution errors use Show's existing refusal; nothing partial is encoded. A scanner may offer to act on text resembling a URL; Larsal itself never follows or executes it.

FEA-10.4 **Wi-Fi selection and fields.** ACT-QR-WIFI appears beside a Wi-Fi entry's network/security information and in its context menu; its Password's ACT-QR-SHOW still gives only the password. The join action explicitly authorizes the configuration's fields as one requested picture. Reuse `UserName` for SSID, `Password` for the credential and `Security` for the type. Proposed optional custom fields: `Hidden` (absent = false; exact `true`/`false`), `EAP Method`, `Identity`, `Anonymous Identity`, `Phase 2 Method`. Read these stored values literally, as the existing Wi-Fi path does; no placeholder resolution, guessed SSID from Title, probing of the current network or saved change. SSID must be nonempty; control characters U+0000 to U+001F and U+007F in join fields, malformed Hidden or missing required enterprise fields give MSG-QR-WIFI-INVALID. Unknown security is never treated as WPA.

FEA-10.5 **Wi-Fi wire format.** Use the maintained [Wi-Fi format](https://github.com/zxing/zxing/wiki/Barcode-Contents#wi-fi-network-config-android-ios-11), a de facto join convention, not a new Larsal protocol. Stable order is `WIFI:T:‹type›;S:‹ssid›;P:‹credential›;H:‹boolean›;;`; open networks omit P entirely. WPA2-EAP inserts `E:‹method›;I:‹identity›;` after H and optional nonempty `A:‹anonymous identity›;PH2:‹phase 2›;` in that order, then the extra terminating semicolon. Each value escapes each original backslash, semicolon, comma, double quote and colon with one backslash in a single pass. Delimiters/field keys are not escaped. No percent or URL encoding. A value consisting entirely of ASCII hex digits with even length is enclosed in unescaped double quotes *after* escaping, to distinguish literal text from hex; original quote characters are escaped inside that wrapper. Preserve spaces, Unicode and leading/trailing whitespace of SSID/password. Count UTF-8 bytes only after escaping/wrapping. The code's content stays local until explicit export.

FEA-10.6 **Network variants.** Exact Security values `WPA`, `WPA Personal`, `WPA2 Personal`, `WPA/WPA2 Personal` and `WPA2/WPA3 Personal` map to wire T `WPA`; `WEP` maps to `WEP`; `Open` or `nopass` maps to `nopass`, with no P even if the entry contains a stale password. Use this explicit set when offering the join action too, including open networks that the current WPA/WEP-only entry classifier misses. Missing Security is invalid, not implicitly open. `WPA2-EAP` requires nonempty EAP Method, Identity and Password; EAP method and optional phase 2 are literal non-control text, not executable options. WPA/WEP require nonempty Password. `WPA3 Personal` (SAE-only), OWE, certificate-only enterprise (including EAP Method `TLS`) and all unknown types give MSG-QR-WIFI-UNSUPPORTED; never advertise a downgraded join code. Hidden true and false work with every supported type. The format describes a join request; scanner/network support, especially enterprise and transition networks, needs real interoperability proof and is not guaranteed by decoding the text. These additions require the lead's ruling; the old Wi-Fi path currently defaults any non-WEP type to WPA and has no hidden/open handling.

FEA-10.7 **Existing OTP code unchanged.** ACT-OTP-QR remains FEA-04.23's separate authenticator setup action: form U URI from current settings and unresolved title/username; smallest fitting normal version, byte mode, H, four-module quiet zone, MSG-OTP-QR-CUSTOM for custom/Steam, MSG-OTP-QR-ERROR then close if too long, 44-second countdown and close on lock. Its URI Copy button and Cmd+C remain under APP-03. Do not replace it with the current six-digit code, generic field text, a Wi-Fi code or a link; do not add these new Save/Share actions to that existing screen in E21. FEA-10's no-clipboard rule is for the new actions, not removal of the existing OTP Copy. The capture limit in .21 applies to any displayed secret, including the existing OTP screen; it changes no OTP content or generation rule.

FEA-10.8 **Encoding and verified Unicode.** New value/join codes use normal QR versions 1 to 40, error correction H, one ECI designator 26 (UTF-8) followed by one byte-mode segment, with the smallest version that fits. No Micro QR, automatic numeric/alphanumeric/Kanji switching, structured append or silent fallback to a lower correction level. [ISO public scope](https://www.iso.org/standard/83389.html), [originator's versions](https://www.qrcode.com/en/about/version.html), and the installed qrcode 0.14.1 `Bits` API support these choices. The installed API has `push_eci_designator`, `push_byte_data`, `push_terminator`, `QrCode::with_bits`, `width`, `to_colors`; ECI is not automatically supplied by the current ffi byte-only helper. Preserve the OTP route's existing bitstream (.7). Verify must test ECI 26 *and* raw recovered bytes: a successful ASCII scan alone does not prove Unicode. This is a proposed encoding ruling, not evidence that Core Image or every camera has already passed it.

FEA-10.9 **Hard capacity, no truncation.** At version 40 H there are 10,208 data bits; the published byte-only maximum is 1,273 bytes ([originator's table](https://www.qrcode.com/en/about/versionPage/versionPage31_40.html)). ECI 26 costs 12 bits, and byte mode plus the version-40 count costs 20: floor((10,208 − 12 − 20) / 8) = **1,272 UTF-8 payload bytes**. Check the bound after resolution/join escaping and before encoder allocation. At 1,273 or more return MSG-QR-TOO-LARGE and no matrix/file/share. Invalid encoding or allocation/encoder failure gives MSG-QR-FAILED, never a partial or previous symbol. Generator, imported-field and vault-format limits stay unchanged. This refusal defines safe behavior; it does **not** satisfy E21-S2's contradictory longest-generator acceptance (D-10-1 below).

FEA-10.10 **Matrix boundary and lifetime.** Reuse the pinned, default-features-off qrcode matrix path in Rust, not an image/network service or JavaScript QR package. LD-198's current importer restriction is ffi `edit.rs` `qr()` only; its extension to CLI and wasm needs an explicit lead amendment and Checker review before those builds, without enabling image/svg/pic. On Mac and in the extension's native host, selection, resolution, join construction and encoding happen in Rust secret types under the existing zeroing allocator. Return only the requested matrix/dimension to the authorized renderer, never the source text. This is the narrow QR-picture class of LD-220, not permission for arbitrary entry records to cross. New export names must be named in API.md and the lead's LD-220 clarification before implementation. On wasm, Rust owns/wipes input, working bits and matrix, then the JS renderer clears/drops its bounded matrix/pixel buffers; the wasm session's existing lock wipe stays. No secret Debug, Clone, errors, console, analytics or crash strings. Drop all app-owned copies at dismissal; Swift/JS/system/GPU copies cannot be promised to be securely erased by dropping a reference.

FEA-10.11 **Popup and animation.** One popup/dialog per session/window, title MSG-QR-TITLE, purpose line, image, exposure/capture lines, countdown, then Save Image…, Share…, Done. The Done button is initial focus and default. Opening a different QR first destroys the prior one; no stack, detachable window, keep-open setting or underlying revealed text. Proposal uses Option A's `dlg`, tile, button, text and focus parts. Enter uses Done; Escape, window close, click outside the popup or a new entry/vault selection dismisses. Animate the *container* on open over 160 ms: opacity 0 to 1 and vertical offset 6 pt to 0, ease-out; no bounce, scale, rotation, looping scan pulse or animated modules. Reserve final image geometry from the start. With Reduce Motion, open/close are immediate and stationary; honor live changes ([Apple popovers](https://developer.apple.com/design/human-interface-guidelines/popovers), [Reduce Motion](https://developer.apple.com/documentation/swiftui/environmentvalues/accessibilityreducemotion), [WebKit](https://webkit.org/blog/7551/responsive-design-for-motion/)). All dismissal clears pixels immediately, with no exit animation retaining a secret.

FEA-10.12 **Size and contrast.** Matrix side N includes four white modules on each edge: N = 17 + 4v + 8, at most 185; only the inner square contains code modules. Square black (#000000) modules on solid white (#FFFFFF), in light and dark themes (LD-192 (4)); no transparency, tint, rounded cells, logo, border/text inside the quiet zone or interpolation. Contrast is 21:1; surrounding text/focus follow Option A/APP-08. Prefer a 296 pt square including quiet zone. At display scale d, choose integer physical module pitch s = floor(296d/N), minimum 3 physical pixels; if s < 3 grow to N×3 physical pixels within the available content area. Align origin to backing pixels and use exact size Ns/d, with no fractional physical modules; recompute on screen/backing-scale change. If that size cannot fit, draw no image, show MSG-QR-SIZE and disable exports until it fits. Compact browser layouts may use the available width if it still fits pitch ≥ 3 physical pixels. Never crop or scroll just the symbol. These pitches are proposed product targets, not an ISO guarantee of camera scan distance ([four-module margin](https://www.qrcode.com/en/howto/code.html/index.html), [correction tradeoff](https://www.qrcode.com/en/about/error_correction.html)).

FEA-10.13 **Keyboard and accessibility.** Dialog has a name and modal semantics; background is inert while it is open. Tab/Shift-Tab cycle Save Image…, Share… (if available), Done; full keyboard access and visible focus ring follow APP-08.25. The image is one element named “QR code for ‹purpose›”; its accessible label, help, tooltip, DOM attributes and hidden text contain neither payload nor a textual transcript. VoiceOver announces the title, exposure/capture lines and initial expiry once; the countdown is available to read but does not interrupt speech every second. Do not automatically speak an already-shown value. On close, restore focus to the invoker if it still exists, otherwise the entry list (unlock control on lock). The warning focuses Cancel, traps focus and returns to its triggering button if cancelled. Long field names wrap as plain text; large text must not overlap/crop controls. Each new scan needs a fresh action after expiry, keeping the existing 44-second secret-exposure bound; access never requires scanning or a mouse to operate Save/Share/Done.

FEA-10.14 **Expiry.** Opening establishes a 44-second deadline from the first displayed frame. Display ceil(remaining seconds), initially 44, then 43 … 1; at zero immediately clear and dismiss. Use elapsed time/deadlines, not a count of delivered timer callbacks: sleep, background timer throttling, resize, warning/save/share UI, keyboard/mouse activity and refocus do not extend it. No automatic regeneration or restore after dismissal. A late Rust/bridge result carries the request/session generation and is discarded if its request expired, selection changed or the vault locked.

FEA-10.15 **Lock and hidden window.** Clear/dismiss on any lock request for the source vault *before* save/discard prompts or delayed locking can keep it visible (APP-02.15 step 5); also on close, quit, sleep, screen lock, user-session switch, app hide (Cmd+H), miniaturize, order-out or moving to a hidden window/Space. Apply regardless of whether APP-02's lock-on-minimize option is off or its lock delay is running. Native lifecycle hooks include app hide/deactivation, miniaturize, the app's own order-out routes and window occlusion changes; no visible occlusion bit means dismiss, but it is not a capture detector. Larsal deactivation dismisses too, except transition into the user's explicitly confirmed save panel or share picker: clear the QR view first; .16 governs the remaining authorized export. The extension destroys the matrix on popup close, disconnect, navigation or vault-lock notice, never restores it on reopen. Web clears on visibilitychange to hidden, pagehide, blur to an unrelated window, lock/session loss, selection change or wasm trap; returning from the back-forward cache never redraws it. Browser/system suspension can prevent callbacks and is a real limit, so check deadline/session *before* any repaint or export as well. Sources: [Apple occlusion notification](https://developer.apple.com/documentation/appkit/nswindow/didchangeocclusionstatenotification), [Apple visibility limits](https://developer.apple.com/library/archive/documentation/Performance/Conceptual/power_efficiency_guidelines_osx/WorkWhenVisible.html), [HTML visibility/focus](https://html.spec.whatwg.org/multipage/interaction.html#page-visibility).

FEA-10.16 **Every export warns, once per attempt.** Save Image… shows MSG-QR-SAVE-TITLE and MSG-QR-EXPORT-WARNING; Share… shows MSG-QR-SHARE-TITLE plus both warning lines. Cancel is default; Return/Escape/window close cancel, with no output. Confirmation is tied to the current matrix, source session generation, action and deadline and consumed once. No “don't ask again”, saved preference, reused consent, double-click bypass, menu/shortcut/drag alternative or direct export API may bypass it. A second click, retry, changed matrix or Save after Share requires a new warning. Lock, hide, source change or expiry cancels a pending warning, picker, panel and uncommitted export. Check that the request remains live immediately before encoding export pixels, writing the selected file or handing an item to a service; cancellation cannot recall an already handed-off or saved copy.

FEA-10.17 **Save Image.** Only after confirmation and an explicit destination does Larsal write one lossless PNG named `Larsal QR.png` by default (never a password, field value or entry title as filename). Export pure black/white pixels with quiet zone at exactly 8 pixels/module, no metadata, transcript, vault path or thumbnail sidecar. Owner-only 0600 on Mac; reuse safe export/overwrite handling and refuse symlink destinations rather than following them. Cancellation writes nothing. Do not pre-render into a disk cache, temp file, autosave, drag file, clipboard or attachment. A failed write shows MSG-QR-SAVE-FAILED and removes only its own incomplete temporary output; do not replace an existing file with partial content. Browser explicit downloads are saves: the chosen browser/OS destination and permissions apply, so no 0600 or secure-deletion promise there. A new download request still needs the warning; no automatic retry. After save, .14's original deadline remains.

FEA-10.18 **Share without an implicit image file.** Use a memory-backed image item with a generic name through the Mac system sharing picker, only after the warning; exclude Copy, clipboard, Print, automatic Save and unsupported services requiring Larsal to materialize a file. No direct provider API, upload or send on merely opening Share. The user chooses the destination and completes any system compose flow ([Apple activity views](https://developer.apple.com/design/human-interface-guidelines/activity-views), [AppKit image items](https://developer.apple.com/documentation/appkit/nssharingservicepicker/init(items:))). Clear the on-screen symbol before handing off; retain only the authorized in-memory item until completion/cancel/expiry/lock, then release it. External services may persist it or affect their own clipboard; Larsal cannot erase or audit those copies. Do not claim the OS/service writes no files. If the zero-Larsal-file/no-clipboard contract cannot be met by a service, omit it; if none remain show MSG-QR-SHARE-UNAVAILABLE, do not silently save. Browser Share requires a supported memory-backed PNG `File`, `navigator.canShare({files})`, transient user activation from the warning's confirm, and allowed policy ([Web Share](https://www.w3.org/TR/web-share/)). The web's current deny-by-default Permissions-Policy needs a lead-reviewed `web-share=(self)` addition, not weaker CSP. Where unavailable/restricted, keep Share visible disabled with MSG-QR-SHARE-UNAVAILABLE as accessible help; Save is the explicit fallback the user can choose. Test target support before offering; no new browser permission, download permission or outside package just for QR.

FEA-10.19 **No automatic storage or clipboard.** Show, dismissal, animation, resize, warning, Cancel, failed encoding and unsupported Share write no image file and never read, write or clear any clipboard, including checking its metadata. No Copy button, Cmd+C handler, browser image context-menu copy/save, dragging, print rendering, external image URL, blob URL for the displayed image, persistent canvas serialization, local/session storage, IndexedDB, cache/service-worker storage or browser sync record. Draw the bounded matrix directly on a non-draggable canvas/native view; PNG bytes exist in memory only after an export confirmation and are dropped afterwards. A user-controlled OS screenshot or third-party share target remains outside this guarantee. FEA-04's existing Copy stays solely on its own screen (.7).

FEA-10.20 **Extension/web trust boundary.** The extension asks the native Rust host for the selected matrix through INT-01's authenticated encrypted channel with INT-02's existing association/site-access checks; a displayed match alone grants nothing. Only the trusted extension popup sender can request/receive the matrix, never an in-page frame, content script, visited page, URL parameter or DOM event forwarded from a page. Drop background transit copies immediately after delivery; popup close revokes its pending request. E21-S4 uses only packaged drawing code, no new QR package or wasm compilation permission. E21-S5 uses larsal-web's Rust encoder/memory wipe with the same bounded matrix; it never links ffi or weakens WEB-02/B21 CSP or Trusted Types to draw an image. Generic protected fields need a narrowly scoped request with exact field identity and policy checks, not a new whole-entry secret reply. The page's own JS can read wasm memory and a hostile serving origin can change the page (B19/B22): QR does not fix or expand that existing trust limit. Show itself adds no network traffic except the existing local extension bridge; explicit Share can leave the device after confirmation.

FEA-10.21 **Supported capture policy and limits.** On Mac apply APP-10's per-window guard from creation, including popup/warning windows, respecting its run-only Permit Screen Capture toggle/start flag. Keep this for legacy parity; read-back `.none` or sharing state 0 is *not* proof pixels cannot be captured. [Apple's current enum documentation](https://developer.apple.com/documentation/appkit/nswindow/sharingtype-swift.enum) calls none legacy; [Apple DTS on macOS 15.4+](https://developer.apple.com/forums/thread/792152) says no public capture-prevention API exists. ScreenCaptureKit, recordings/shares and a camera may see the code. Do not use private capture APIs, DRM/secure-text-field tricks, permissions prompts or an invented capture-detection signal. Browser extension/web pages cannot exclude themselves from OS/browser capture; hiding on blur/visibility is exposure reduction, not prevention. Terminal output/scrollback belongs to the terminal and cannot be reliably erased by Larsal. MSG-QR-CAPTURE communicates the real graphical limit. Current SC-05 and AT-D04 already record path-specific results; APP-10's broader claim needs a scoped lead correction, not a promise here. Real capture-path trials require separately authorized visible QA; not part of this spec-only task.

FEA-10.22 **Command line selection and authorization.** Add `larsal show --qr VAULT ENTRY` with INT-10's existing unlock/no-echo/stdin credentials, error/quiet/stream rules and Show field matching/resolution. `--qr` selects presentation, not authorization: default Password needs `-s`; one explicit `-a NAME` authorizes that field as INT-10.28 does, without `-s`; `--totp` alone selects the current code exactly as existing Show does, never OTP setup credentials. Add `--wifi` with `--qr` only for an explicit join request, requiring `-s` for its protected configuration; text Show stays unchanged. Reject --all, --show-attachments, repeated -a, or combinations of -a/--totp/--wifi before unlock with MSG-QR-CLI-OPTIONS. Without required explicit disclosure use MSG-QR-CLI-AUTH; field matching/missing/ambiguous errors remain INT-10. Neither default hidden marker nor labels may accidentally become a QR payload. Same in INT-10's interactive shell; no GUI session or QR Share/PNG command is added.

FEA-10.23 **Terminal presentation and pipe opt-in.** Require stdout to be a TTY before printing QR; otherwise MSG-QR-CLI-PIPE, empty stdout, exit 1. New `--stdout` explicitly permits the block-character representation to a pipe/file; it is valid only with --qr and does not authorize the selected secret. No auto-open, terminal image protocol, clipboard or image file. Represent two vertical modules per cell using space/U+2580/U+2584/U+2588 (upper/lower/both dark), preserving all four quiet-zone modules, and a white pad row when the matrix side is odd. Terminal mode uses fixed black-foreground/white-background SGR and reset only, no payload-derived escape sequence or label. Refuse before printing if known terminal columns/rows cannot fit N columns and ceil(N/2) rows plus final LF; if dimensions cannot be obtained, refuse with MSG-QR-CLI-SIZE instead of wrapping. --stdout emits the same matrix cells plus LF per row, without SGR or prose; tests reconstruct modules independently of terminal theme. Successful terminal display gives MSG-QR-CLI-NOTE on stderr even under -q; explicit pipe output has the same note on stderr. No countdown, terminal-clearing escape, alternate-screen trick or promise of scrollback removal; Larsal exits 0 after output and drops Rust buffers. I/O failure exits 1 using INT-10's safe error conventions, with possible partial output acknowledged.

FEA-10.24 **Proof and proposal boundary.** All tests use demo values, run hidden/offscreen in isolated test storage; never the general pasteboard or its metadata. E21-S1 checks this card's rule-to-case map, links and unique proposal IDs/theme structure and runs the name guard in a fresh private source copy under a cap below 1,800 seconds; no build/full check or visible capture. Actual decoder, lifecycle, memory, filesystem, clipboard-instrumentation and accessibility assertions are future implementation/Verify work. E21-S2 retains the exact 1,000-value acceptance, including longest generator output, until the lead resolves D-10-1; do not replace an oversize readback with a refusal and call it PASS. Recover raw bytes/ECI from Core Image's [symbol descriptor](https://developer.apple.com/documentation/coreimage/ciqrcodefeature/symboldescriptor-swift.property) and [error-corrected payload](https://developer.apple.com/documentation/coreimage/ciqrcodedescriptor/errorcorrectedpayload-swift.property), parsing the segment header/count/ECI and excluding terminator/padding; `messageString` alone is insufficient proof for NUL/Unicode. Cross-check a second independent offline decoder and supported device scanning later; do not install a decoder in this story. The frame drawing below is not a decoder test.

## Edge cases and errors

All messages above are literal UI text except the marked placeholders. Error/announcement text never contains payload bytes. Errors leave the vault/draft unchanged, destroy any prior matrix, disable Save/Share, and offer Done. Failure after an external share handoff cannot recall that handoff. A lock request wins over warning confirmation or a late result. No clipboard cleanup is necessary because the new flow never owns clipboard content.

## Security notes

- SR-07/AT-C01/AT-C02: matrix, codewords, PNG bytes and share item are reversible secrets. Wiping Rust temporaries does not erase a saved photograph, screen backing store or service copy. LD-198 allocator condition stays.
- SR-13/AT-E03: field selection does not bypass existing unlock or site access. Reject cross-vault IDs, expired requests, malformed dimensions (N not 29 to 185 in steps of 4), nonbinary cells or length other than N² before drawing. The quiet zone must actually be white.
- SC-05/AT-D04: setting a window property is parity behavior, not capture-proof security. A screenshot of this proposal proves only layout. No real capture trials or permission prompts in E21-S1.
- SD-07/SD-09 and AT-I03: export consent is per attempt; Mac saved image is owner-only, with safe path/overwrite handling. External services and browser-managed downloads have the stated limits. No blank PNG or hidden stale code after failure.
- AT-E01, AT-F01/AT-F04/AT-F05: hostile field names and values remain text/bytes; the visited page cannot ask for a matrix. The web serving-origin limit remains B22. No QR content goes to a generator service, telemetry, URL, pasteboard or storage just by showing it.

## How this was learned

Read only Larsal's cards/plan/design and installed approved qrcode 0.14.1 API/capacity table; no reference source, app, CLI, handoff, vault or keychain access. Public sources checked 2026-11-04, paraphrased here; no paid standard purchased. ISO's public [2024 edition description](https://www.iso.org/standard/83389.html) gives scope, not the unavailable full normative text. Originator pages and the installed bit table support the numerical/scaling claims; exact screen pitches/time/shortcut are proposed Larsal policy.

Primary product precedents: [Proton's Wi-Fi sharing guidance](https://proton.me/blog/how-to-share-wifi-password) describes phone QR joining and the risk of unencrypted sharing; [Bitwarden's integrated authenticator](https://bitwarden.com/help/integrated-authenticator/) treats OTP setup separately. Those do not prove a universal arbitrary-password QR feature or this implementation's correctness. Existing LD-198/220 and browser-and-web research supply the established Rust/matrix and client-trust decisions. The [qrcode maintainer's API](https://docs.rs/qrcode/latest/qrcode/struct.QrCode.html) identifies version 0.14.1; local `vendor/crates-io/qrcode-0.14.1/src/bits.rs` and `lib.rs` were the precise API inspected. Browser expiry/sharing rules use the HTML and W3C sources cited above; current Apple HIG/platform sources are linked at the rules they support. Sources containing disallowed names must remain external proof only; none is required in this card's citations.
