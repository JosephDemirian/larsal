# SYN-03 Client sync and the rollback guard

Status: reviewed
Epics: E16-S7a (the loop, its timing, the rollback guard, the status), E16-S7b (the key-file part, the key-change cases), E15-S2 (the merge it calls), E16-S9 (the screens and words), E17-S1 (upload signatures, the wrapped key-file part)
Parity rows: SD-03 (Larsal goes further: the newer key and the deletion pass in server sync). Larsal's own rows: SV-01 to SV-03 (plan/security.md); AT-L01, AT-L04, AT-L08 (plan/attacks-and-checks.md)

## What it does

Larsal keeps a vault in step with its copy on Larsal's server. A run downloads the server copy, merges this Mac's open vault into it with MOD-11 (a same-vault merge, so deletions stay deleted and the newer key wins), saves the result on this Mac and uploads it with `If-Match`. If another Mac uploaded first, the server answers 412 and Larsal tries again, at most 3 times in all. Local state that never leaves this Mac refuses a server copy that went back to an older version.

From E16-S7b, a vault put on the server gets a second secret: a random key-file part, so nothing on the server can be guessed from the master password. When the server copy opens with other credentials (a password changed on another Mac), Larsal asks for the credentials that copy opens with and uploads nothing until it opens.

Other cards: SYN-01 owns the routes, SYN-04 sign-in, MOD-11 the merge (its Notation holds the one meaning of "same vault"), MOD-11.31 copies under a retired key, APP-05 the local save and APP-05.26 the rollback guard for the local file, SYN-06 the wrap of the key-file part from E17-S1.

Design and sources: spec/research/sync-server.md P2, P3, P4, P7 (decided: spec/decisions.md LD-263 (2), (3), (6), LD-264, LD-265, LD-267 (2), LD-269 (2) to (4), LD-273 (1), (3), (5), (9)).

## Inputs and outputs

- In: an unlocked vault linked to a server vault; the pinned server (SYN-01.2); a session (SYN-04); the triggers of SYN-03.4.
- Out: the merged vault, saved on this Mac and uploaded; the state of SYN-03.3; the status of SYN-03.13 and the messages below.
- Limits: the vault limit of SYN-01.10; at most 3 tries per run (SYN-03.6).

## Rules

SYN-03.1 **Putting a vault on the server** (P7). For an unlocked vault the user puts on a server:
1. A vault without a key file gets a random 32-byte key-file part `F` from larsal-crypto's random source. A vault that already has a key file gets no second part (FMT-04.5 has one key-file slot): the `F` of that key file (the output of FMT-18) is the part that goes with the vault, its key, its `MasterKeyChanged` and its name stay, and when it has no field 12 its file stays as it is.
2. `F` goes into the device store for this server vault (SYN-04.1's store; this device only once W-02 is answered), as `SecretBytes`, and where it is goes to SYN-03.3's state, before anything of the vault changes. A store or a state that refuses stops the step with nothing changed. `F` is never written into the vault, the local state file, a log or the pasteboard. For a vault without a key file, `F` is then added through the credential change (MOD-12.10, FMT-04.3, FMT-04.5): the master password and any hardware key stay; `MasterKeyChanged` becomes now (MOD-13.11). Any field 12 goes (LD-427). Larsal saves the vault on this Mac (APP-05) when either changed it; a save that fails stops the upload.
3. Larsal draws a `vault_id` (SYN-01.6) and uploads the saved file, checked as in SYN-03.5 step 2, with `If-None-Match: *`; on 201 it writes SYN-03.3's state. A file that fails is not sent: the request is refused with the words of that step's message, and no link is written.
After step 3's upload fails, the vault keeps its part: it opens as before, and the next try sends the same part. From E17-S1, `F` is also wrapped to the account's own key (SYN-06.9), so the other Macs of the account get it from the server. Before that, the E16-S7a test helper puts it into the second test client's device store (tests only, LD-266 (2)).

SYN-03.2 **The server vault on another Mac.** The user picks a vault from `GET /v1/vaults`; Larsal downloads it, asks where to save it (the save panel; never over a file without the panel's own question), and opens it with the unlock sheet (APP-06), which from E16-S7b takes `F` from the device store and asks only for the rest of the key, normally the master password. When the download is written, before the call returns, Larsal writes SYN-03.3's state: the file's part pointer, and its link when the bytes are an exact frame (FMT-02; a file with more after its final block gets the pointer only, T64). The link's root group id is not known yet. The first run after an unlock that opened exactly the downloaded bytes (same SHA-256) gives the link that root, that unlock's measures, and this Mac's retired-key records for that root. When the unlock opened other bytes, or another link or a transfer names that root or that server vault, the link goes and the pointer stays, so the file still opens (F-288). A link with no root yet that no run can give one goes too, its pointer kept: its file is gone or moved, or holds other bytes than the download, and no vault unlocked now opened the downloaded bytes from that file. A file that does not read for a moment (macOS refuses the read) keeps its link, and so does a download unlocked now. Larsal drops such a link before a download, a put, the list of server vaults and every run, and the list does not show that vault as linked. A new download of the same server vault replaces a link with no root yet once it commits, its pointer kept; a download refused before that (the file exists, a network error) keeps the link. A vault unlocked now that opened that link's downloaded bytes keeps it, and the new download is refused, as for a linked vault (F-284). From E16-S7b, every later unlock of a linked vault takes `F` from the device store the same way, shown as "Key part kept for sync". The device store gives the part, never the whole unlock: with nothing typed, a vault keyed by its key file alone stays locked and asks for that file. A file that does not open with the part gets the open it has without one: the save that adds the part failed, or another file came to that path. Such an unlock holds no part, so nothing of it goes up (SYN-03.5 step 2). A wrong password then costs two key derivations. A key file typed for a linked vault is taken only when its bytes are the part; any other gets `MSG-SYNC-PART-OTHER`, and while the device store gives no part a key file typed alone gets `MSG-SYNC-PART-UNREAD`. Typed with the password or hardware key, a key file is the part only when the file holds the bytes last synced: the unlock goes on and the part goes back into the device store; any other file gets `MSG-SYNC-PART-UNREAD` and stays locked (SYN-03.12).

SYN-03.3 **Local state** (P4; larsal-sync `state.rs`; never synced, never in or next to a vault). Per server: its address and its pinned certificate fingerprint (SYN-01.2), written when the user adds the server, before any vault is linked (SYN-01.2, SYN-06.11 step 2, SYN-06.12). Per linked vault: the server it is linked to (it points to that server's entry); the `vault_id`; the local file (a security-scoped bookmark) and the vault's root group id; the highest version seen; the SHA-256 of the server bytes of that version; the newest change time (as APP-05.26 measures it), the file version and the KDF settings of the last server version this Mac accepted or uploaded (SYN-03.7); the SHA-256 of the local file right after the last run; from E17-S1 the upload signature last checked; for shared vaults (E18) the key epoch and the member list's sequence number and hash (SHR-01, SHR-02). Per file that needs a key-file part, from step 2 of SYN-03.1, so also after a failed upload and after the link goes: the file, the vault's root group id and the part's label in the device store, never the part. Per vault, by its root group id: the retired-key records of MOD-11.31 (LD-267 (2)), as salted digests: from the link, the records of that vault, and later any key this Mac retires from it. The retired check reads these records and this Mac's own records of MOD-11.31, so a key retired while one of the two files could not be written still counts. When neither could be written (both live in the settings folder), the record of that change lives in this session's memory only: after a restart that key reads as not retired, and a copy under it, given its password in a sheet, merges as any copy does and can give its key back when its key time is newer (LD-264). A password given for a copy of a vault with a part is tested with the part and without it, so a key retired before the part came still counts. A key file given is tested without itself too when its bytes are a part this Mac keeps for that vault's root group id: Larsal compares it in constant time with every part the device store holds under a label this Mac knows for that root, from the sync state's pointers and links and from this Mac's vault state, which keeps those labels (public: they name a server and a vault id, never the part). So a key retired before the put still counts in a Finder copy of the vault and after the sync state is lost. On the server road of a linked vault the unlock's key file is the part (SYN-03.12), so the given password is tried without it there whatever the device store gives. In a sheet a key file this Mac never kept is never taken for a part. The copy sheet (MOD-11.27) and the disk sheet (APP-05.29) run this same check as SYN-03.8's sheet. This card also reads and updates APP-05.26's rollback guard record for the vault, which guards the local file only (SYN-03.7). The state is written atomically (temp file and rename) with mode 0600 in Larsal's settings folder. The highest version and the newest change time only move up; the file version and the KDF settings are those of the last server version accepted or uploaded. A link's values go only when the user removes the link (SYN-03.15).

SYN-03.4 **When a run starts** (P3; a hosted password manager's rhythm, spec/research/business-model.md 3.4). After the vault is unlocked; 2 s after a save (a burst of saves gives one run); every 60 s while the vault is unlocked; and on Sync now. Never while the vault is locked, saving, reloading or unlocking, has unsaved changes or an open editor, or a "changed on disk" event is pending (as APP-05.25): such a trigger waits, and the next save starts a run anyway. One run at a time per vault; a trigger during a run asks for one more run after it.

SYN-03.5 **A run.** One try is:
1. `GET /v1/vaults/{vault_id}` with `If-None-Match` set to the ETag of the highest version seen.
2. 304 (the server holds that version): Larsal reads the local file once and checks those bytes first, with no key derivation: (a) their SHA-256 equals the SHA-256 of the file bytes this unlock last opened with its own key parts or wrote itself; (b) the open vault's root group id is the one it had at unlock; (c) the frame is exact: the outer header is byte for byte what the header writer makes of the values it read, and the block stream ends at the file's last byte (FMT-06). (d) this unlock holds a key-file part, the one the device store holds for the file (compared in constant time); a file without one, or with another, is `MSG-SYNC-LOCAL-FILE`, so a password-only copy never goes up (F-321). While the device store gives no part this check fails too and the run reads `MSG-SYNC-LOCAL-FILE`, which is not true then (Verify: C1R5-02, C2R5-1; E16-S9 gives the words). (e) the bytes hold no field 12 entry; a file with one is `MSG-SYNC-SAVE-FIRST`, and a Larsal save writes it without (LD-427, F-322). A merge with no part in this unlock merges nothing. The values themselves are not judged (the security note below). A file that fails (a) or (b) (plain text, another vault's file, a corrupt copy, no file) is not sent: the status is Error with `MSG-SYNC-LOCAL-FILE`. A file that fails only (c) opened, and opening stays as FMT-01.20, FMT-02.3, FMT-02.21 and FMT-03.6 say, but it holds room the reader skips: it is not sent either, the status is Error with `MSG-SYNC-SAVE-FIRST`, and any Larsal save writes it without the room. Neither refusal changes anything APP-05.24's check reads, so the check still gives its event. Then, when the local file's SHA-256 equals the one recorded after the last run, the run ends (Synced). Otherwise Larsal uploads the bytes it read and checked with `If-Match` (step 4).
3. 200 with version `v`: the guard of SYN-03.7 first. Then Larsal opens the bytes with this Mac's key (when they do not open: SYN-03.8). It merges the open vault (the source) into the server copy (the target), the way APP-05.27 Merge does: a same-vault merge by MOD-11's Notation, so the deletion pass runs (MOD-11.15) and the result holds the newer of the two keys (MOD-11.19 limit 2, LD-264). The merge, the replacement of the open vault by the result and the local safe save (APP-05) are one step under the vault's lock, as a save is. When the merge's change list is empty (this Mac had nothing the server copy lacks), Larsal uploads nothing and records `v`, the server bytes' SHA-256 and the new local file's SHA-256. Otherwise it uploads the bytes it just saved with `If-Match: "v"`.
4. The upload answers 200 or 201 with a version above the one it replaces: Larsal records the new version and, for both the server and the local hash, the SHA-256 of the bytes it sent. A reply whose version does not move up is a protocol error (`MSG-SYNC-ERROR`), and nothing of it is recorded. 412: the next try (SYN-03.6). Any other reply: SYN-03.10.

For a shared vault, SHR-01.13 and SHR-03.12 replace SYN-03.8, SYN-03.9 and SYN-03.11, and SHR-01.14 keys every upload.

SYN-03.6 **Tries** (LD-263 (2); E16-S7a). A run makes at most 3 tries in all (P3's "retry at most 3 times" is read as 3 tries, as LD-263 (2) and E16-S7a's check word it). Before the 2nd and the 3rd try Larsal waits a random time from 1 to 3 s (jitter, from larsal-crypto's random source), so two Macs that collided do not collide again. When the 3rd try ends with 412, the run stops with `MSG-SYNC-BUSY` in the status line; the next trigger starts a new run.

SYN-03.7 **Rollback guard** (P4, P18 (6); LD-267 (3), LD-269 (4)). Only local state stops a full rollback (ETH paper section 6, sync-server.md section 6).
- Before opening: a version lower than the highest seen, or the highest seen with other bytes (another SHA-256), is refused: nothing is merged or uploaded, Larsal shows `MSG-SYNC-ROLLBACK` and the status is Error. The same holds when `GET /v1/vaults` lists a lower version: Larsal downloads nothing.
- From E17-S1, a version whose upload signature does not verify by SYN-03.11 is refused the same way.
- After opening: Larsal compares the copy, by APP-05.26's measures (the newest change time; the file version; KDF settings compared as in MOD-11.19 limit 1), with the values SYN-03.3 keeps for the last server version this Mac accepted or uploaded. It never compares a server copy with APP-05.26's record: that record also holds this Mac's own saves that were not yet uploaded, which no server copy can have. A copy whose newest change time is earlier than the stored one (an old file the server renumbered) is not refused, because the merge keeps everything newer: Larsal merges it as step 3 says, uploads the result and shows `MSG-SYNC-WENT-BACK`. A copy with a lower file version or weaker KDF settings than stored is merged as step 3 says and only warns, as APP-05.26 does with `MSG-DISK-WEAKER` (LD-269 (4)): `MSG-SYNC-WEAKER` names the setting, never a value. The result's KDF settings follow MOD-11.19: the server copy is the target, so its settings stay when its settings time is newer (limit 1 guards only settings taken from the source), and this Mac's stronger ones are taken when this Mac's settings time is newer.
- After each version Larsal accepts or uploads, SYN-03.3's values for the link are set from that version.

SYN-03.8 **The server copy opens with other credentials** (LD-264; MOD-11.29, APP-05.29). When the bytes give `WrongKey` with this Mac's key:
- Larsal uploads nothing for this vault until the copy opens, and the status is Needs password.
- Larsal shows the unlock sheet for the server copy with `MSG-SYNC-OTHER-KEY`. It asks for the password or key this copy opens with, never for "the new" one: the copy may be older or newer. The key-file part comes from the device store (SYN-03.2). On a 60-second tick Larsal does not show the sheet again; the status line and Sync now do. The sheet takes a password: the part and any hardware key are this Mac's. The password is used in the next run and then wiped. A copy under another part stays Needs password until E17-S1 brings that part.
- The credentials open the copy. With another root group id, Larsal shows `MSG-SYNC-OTHER-VAULT` and merges and uploads nothing. That test needs no key derivation, so it comes first; a file of another vault then never reads as a replaced key. With the same id, Larsal tests them against this Mac's retired-key records in SYN-03.3 (MOD-11.31). A match goes to SYN-03.9. Otherwise the copy is the same vault (MOD-11's Notation: opened with credentials the user gave for that copy), and the try goes on at step 3's merge. When the result takes the copy's newer key, this Mac's old key becomes a key it retired (MOD-11.31). A copy with an older `MasterKeyChanged` merges and the result keeps this Mac's key.
- Cancel: nothing is merged or uploaded; the status stays Needs password.

SYN-03.9 **A server copy under a key this Mac retired** (LD-267 (2), LD-269 (3); MOD-11.31). Larsal merges nothing on its own. It shows `MSG-SYNC-OLD-KEY` with Skip (the default) and Merge anyway; the 60-second timer never answers it, and the status is Uses a replaced password until the user does.
- Skip: nothing of the copy is taken. Larsal uploads this Mac's vault with `If-Match` of the copy's version, so the server copy again has this Mac's key (the server keeps the replaced one as an old version, SYN-02.5).
- Merge anyway: MOD-11.31's content merge: this Mac's open vault is the target and the server copy the source (the other way round from step 3), never the copy's key, deletions or metadata. Larsal saves and uploads the result.
For either answer Larsal records the copy's version and hash for the upload's `If-Match`, never its measures and never an older version over a newer one, so a planted copy's time reaches no record. The next run uploads and records the vault's measures from before the answer; until then the status is Syncing. A vault that left its linked file (Save As) before the answer takes nothing, and the copy goes.
Either way the result keeps this Mac's key, whatever the copy's `MasterKeyChanged` says, also one in the future. Why: a password change often follows a leak, so whoever knows the old password must not bring it back or change or delete entries without the user's click (LD-269 (3)).

SYN-03.10 **Other replies.**
- 401: Larsal signs in again once (SYN-04.6) and repeats the try; a second 401 sets the status Signed out with `MSG-SYNC-SIGNED-OUT`.
- 403: `MSG-SYNC-NO-WRITE`; the changes stay on this Mac.
- 404 for a linked vault: `MSG-SYNC-GONE`; the link stays until the user removes it, and Larsal never makes the vault again on its own with `If-None-Match: *`.
- 413: `MSG-SYNC-TOO-LARGE`.
- 400, 411 or 428: a protocol error (a bug on one side): `MSG-SYNC-ERROR`.
- 429: Larsal waits `Retry-After`, at most 300 s, in place of SYN-03.6's random wait, before the next try; the try that got the 429 counts as one of the run's 3 (SYN-03.6). A 429 on the 3rd try ends the run with the status Offline, as a 5xx does; the next trigger tries again. A `Retry-After` that is missing or not a whole number of seconds (for example an HTTP date) counts as 300 s, and so does a whole number over 300, however many digits it has.
- A network error, a timeout, a TLS error other than a changed certificate, or 5xx: the status is Offline, with no message box; the next trigger tries again.
- A changed certificate: `MSG-SYNC-CERT-CHANGED` (SYN-01.2); no run for that server until the user acts.
In every case the vault on this Mac is never left half merged: either the merged result was saved (step 3) or nothing changed.

SYN-03.11 **Upload signatures** (from E17-S1; P4, P11). Every downloaded version must carry `Upload-Signer` and `Upload-Signature` that verify (CRY-04.3) over the SYN-01.7 field list built from the `vault_id`, the version the server sent and the SHA-256 of the bytes received, with a key allowed to write: for a personal vault, the account's own identity key, pinned at sign-up or at the approval of this Mac (SYN-06.6). Otherwise Larsal refuses it as in SYN-03.7. Every upload sends its signature (SYN-01.7). Before E17-S1 the version and hash guard applies alone (P4), and so it does for an account with no keys record on the server (`GET /v1/account/keys` gives 404). From E17-S2, a Mac signed in to an account whose keys record exists merges no download until it holds the account's keys: it refuses the version as SYN-03.7 says and reports that the account must be restored (the lead's E17-S1 ruling (a); until then a Mac that holds no account keys checks no signature, the findings row of Checker 1 F1, F-715).

SYN-03.12 **The key-file part stays in the key** (P3, P7). A credential change of a linked vault (MOD-12.10) keeps its key-file part; Larsal offers no way to drop it while the vault is linked (Vault Settings shows "Kept for sync"). So when another Mac asks for the credentials the server copy opens with, the part is already in its device store. Larsal can save the part as a key file through the save panel, so the vault opens in another app with the master password and that file (P7). This is the one exception to FMT-18.21's fresh bytes: the file holds the part already in the key, its own 32 bytes, in the XML 2.0 layout of FMT-18.20; FMT-18.20, FMT-18.22 (no overwrite, mode 0400) and FMT-18.23 (read back; `F` equals the part) apply. Vault Settings refuses Remove, Choose and New key file on a linked vault with `MSG-SYNC-PART-KEPT`, and leaves no new file behind. Save As takes the part along: the new file has the vault's key.

A vault whose file has a part pointer, linked or not (a first upload that failed), keeps a typed factor: a key change that would leave it with no password and no hardware key is refused with `MSG-SYNC-TYPED-KEPT`, and nothing changes. The device store gives the part to whoever runs as the user, so the part alone must never open the vault: an unlock with nothing typed opens nothing (SYN-03.2), no key change in Larsal leaves such a vault with the part alone, and neither the copy sheet nor the disk sheet takes the key of a copy that opens with a part this Mac keeps and nothing else: that copy gets MOD-11.31's content merge only, the vault keeps its key, and Larsal shows `MSG-SYNC-TYPED-KEPT`. This holds for keys Larsal makes or takes. A vault that went up keyed by its own key file alone (SYN-03.1 step 1 keeps that key), or a file another app wrote at the vault's path, opens with that key file typed, as any key file vault does. Save as key file works for such a vault, linked or not.

No sheet replaces the part of a linked vault. A key file typed at unlock (APP-06), in the copy sheet (MOD-11.27) or in the disk sheet (APP-05.29) is taken only when its bytes equal the part; any other is refused with `MSG-SYNC-PART-OTHER`, and the part stays. While the device store gives no part (the item is gone, or macOS refuses the read), the sheets take nothing: any answer to the copy sheet or the disk sheet of a linked vault, a password alone included, is refused with `MSG-SYNC-PART-UNREAD`, and so is a key file typed alone at unlock. The way back is the unlock, on the file as it was last synced: when the file at the path holds the bytes a link of it last synced (same SHA-256, checked before the key work and on the bytes opened), the password or hardware key with a key file that opens it proves that key file is the part, since those bytes went up keyed by the password and the part. The unlock goes on and Larsal puts the part back into the device store under the file's pointer label, only when the store has no item there. The answer to the cost question (APP-06.14) does the same while the device store still gives no part; when the store gives a part again before the answer, the answer opens with the key file typed without comparing it with the part, though it never stores that key file and nothing of it goes up (Verify: C1R5-01, open, E16-S9). Any other file at a linked path, opened with a typed key file while the device store gives no part, fails closed: `MSG-SYNC-PART-UNREAD`, the vault stays locked, and nothing is stored or sent. A key file that does not open the vault fails as any wrong key. The sheets of any copy of a vault whose parts the device store gives none of, a Finder copy included, take no key either: the content merges only when the vault's own key opens the copy, and the sheet gives `MSG-SYNC-PART-UNREAD`. A second Mac that downloads the vault before E17-S1 gets its part the same way, from the key file saved with Save as key file.

For a vault that had a key file of its own when it went up, the part is that key file's `F` (SYN-03.1 step 1), so the server copy is as strong as that key file and no stronger. Larsal draws a 256-bit part only for a vault with no key file.

SYN-03.13 **Status** (E16-S9). Per linked vault, one of: Synced (with the time of the last run that ended well), Syncing, Offline, Needs password, Uses a replaced password, Signed out, Error (with the message of the last failure). The status line shows it; Sync now starts a run.

SYN-03.14 **What leaves the Mac.** Only SYN-01's requests: the vault's encrypted bytes, ids, versions, sizes and signatures; from E17-S1 the wrap records of SYN-06. Never the master password, the key-file part, any private or secret key or anything from inside the vault in plain form, in any request, header or log. The outer header of those bytes is in clear by format, and it carries no field 12 (LD-427): linking removes it, a save of a linked vault writes none, and `Session::sync_read` refuses a file that holds any field 12 entry with `MSG-SYNC-SAVE-FIRST`. So nothing a user typed goes up in clear.

SYN-03.15 **Stop syncing.** It removes this Mac's link for the vault from the state and nothing else: the vault keeps its key, its key-file part stays in the device store (the vault still needs it to open), and the server copy stays. Once the vault is no longer linked, a normal credential change may drop the part. A shared vault (SHR-01) offers no Stop syncing: its only key is the group's, so its way out is Leave (SHR-01.7, SHR-04.11).

## Edge cases and errors

- The vault is edited during a run's download: the run stops before its merge (SYN-03.4 forbids a run with unsaved changes), and the save that follows starts a new run.
- The server copy holds a deletion this Mac's vault does not: the deletion pass erases the entry here, unless this Mac changed or moved it after the deletion (MOD-11.15, LD-271 (2)).
- Both Macs deleted the same entry: one item for it stays in the result (FMT-15.11 step 2).
- A server copy with the vault's root group id under another password, given by the user, with an older `MasterKeyChanged`: the result keeps this Mac's key, and the other Mac asks for this Mac's key at its next run (MOD-11.19 limit 2).
- The local vault file is also in a cloud folder: APP-05's change-on-disk and conflict-copy rules apply to the local file as well; both paths are same-vault merges.
- 304 while the local file's SHA-256 changed only because Larsal saved it again with a fresh seed (FMT-04.17): Larsal uploads it once, as any local change; the next run sees 304 and equal hashes.
- The same `vault_id` linked on this Mac to two local files: refused at link time; one link per server vault per Mac.
- Something else overwrites or removes the local file while the vault is unlocked: SYN-03.5 step 2 refuses it at every run until the next save writes the open vault over it, or APP-05.24's check opens a good copy of this vault with this Mac's key. A corrupt copy with the same first 1,024 bytes and the same length gives no disk event (APP-05.24 reads only those); the status stays Error until the next save.
- Save As while linked: the new file has no link, so its saves send nothing, and the link stays on the old file, whose status comes back when it is opened again. Moving a link to a new file belongs to E16-S9 with the security-scoped bookmark (LD-355).
- A Save As during a run: the run belongs to the file the vault left. It reads and merges nothing more, and its report does not reach the new file. Bytes it already read go up under the old link; they are this session's encrypted vault. A first upload that read before the Save As can leave those bytes under a fresh `vault_id` with no link.
- An unlock during a run, with a Save As or another root's file before it or with nothing: the run began under the unlock before it, so it ends the same way, and the run the unlock asks for reads as usual (T61).
- A vault Larsal never wrote (from the reference app, say): putting it adds the part and saves it, so it goes up as Larsal's own save (T59). With a key file of its own and no field 12, and an exact frame, it goes up as it is. With room in it, one Larsal save, then it goes up. A version 3 file goes up only after its notice and a save, as it did.
- Plain bytes in the outer header of a file made with the key, or after its final block: it opens, and it goes up only after a save (T45 to T48). A file with field 12 goes up only after a save too, which writes it without (LD-427).

## Security notes

- **Rollback (SV-02, AT-L01).** A hostile server can hold back, replay or renumber old versions. The version and hash guard refuses a lower or changed version; the newest-change-time compare catches an old file under a new number, and the merge keeps everything newer; from E17-S1 the upload signature binds the bytes to their version. Fork across Macs of one account: each Mac's guard only moves up, so a server that keeps two Macs on two histories is found when one sees the other's newer upload; a fork across members is a known limit (LD-266 (4)).
- **What the upload check covers, and no more (SYN-03.14, LD-340).** Anything on this Mac can write the vault's file, and the server keeps old versions (SYN-02.5), so plain bytes that reach it stay. The check of SYN-03.5 step 2 runs on the bytes that are sent, read once, with no key derivation per tick and no new secret. The hash says this unlock opened or wrote this file; opening authenticates every byte up to the final block (FMT-05, FMT-06). The exact frame refuses what opening skips: bytes past the final block and room in the outer header. So a writer without the key cannot add a byte that goes up. A file of another vault under this vault's own password opens, so the root group id is checked as well. The check does not read values. A writer with the key can put any bytes in the minor version, the master seed, the IV, a salt or the ciphertext, and they go up; such a writer can read the vault anyway. A file with field 12 is refused and a save writes it without (LD-427).
- **Nothing guessable on the server (SV-03).** The server copy needs the master password plus the part (P7). For a vault that had no key file the part is 256 random bits, so a stolen server copy cannot be attacked with password guesses (T01, F-321). For a vault that went up with a key file of its own, the part is that key file, and the server copy is only as strong as it. A file with no part in this unlock goes up by no path (SYN-03.5 step 2).
- **The newer key gives the server nothing (LD-264).** A copy that opens only with a key the server does not have cannot be made by the server; taking the newer key closes the case where an upload from a stale Mac undoes a password change.
- **A replaced password is never taken back (LD-267 (2), LD-269 (3)).** A copy under a key this Mac retired gives no key, no deletions and no metadata, and is merged only after the user's click (AT-L04).
- **No plain text off the Mac but the outer header (AT-L08).** A test reads every request and reply a client handles, on T13's run, and finds no master password (`demo`, `demo2`, also as UTF-16), no key-file part, and no entry password or title of 6 bytes or more, raw or as upper or lower hex or padded or URL base64 (T24). It does not search user names, URLs or notes, titles and passwords under 6 bytes, or any other encoding; those stay inside the encrypted file. The header goes in clear by format, without field 12 (SYN-03.14).

Sync stays off in the app build until E16-S9 turns it on: `scripts/build-core.sh` and `scripts/repro-build.sh` never ask for the `sync` feature, and `scripts/check-sync-link.sh` goes red if either names `sync` or `--all-features`. This is a text match: it cannot see a feature assembled at run time, one set from an environment variable or a wrapper, one asked by another script, or one from Cargo config.

## How this was learned

- Public sources only; the reference app has no server, so its merge facts come from the existing cards (MOD-11, FMT-15, APP-05).
- spec/research/sync-server.md P2, P3, P4, P7, P18 (6), sections 1 (Enpass's client-side merge; Bitwarden's sync rhythm and its "out of date" refusal), 2 (RFC 9110 conditional writes, SUNDR) and 6 (rollback needs local state: Scarlata, Torrisi, Backendal, Paterson, USENIX Security 2026, section 6, <https://www.usenix.org/system/files/conference/usenixsecurity26/sec26_prepub_scarlata.pdf>).
- spec/research/business-model.md section 3 ("Guard against rollback"; Bitwarden's sync rhythm, 3.4).
- RFC 9110: <https://www.rfc-editor.org/rfc/rfc9110.html>.
- Larsal's own values, decided: spec/decisions.md LD-273 (1) (P3 says only "debounced" and "with jitter"; no proven client's numbers found): a run 2 s after a save (SYN-03.4, pinned by T09); a wait of 1 to 3 s before the 2nd and the 3rd try (SYN-03.6, pinned by T08); a `Retry-After` of at most 300 s (SYN-03.10, pinned by T29).
- Larsal's own rules, decided: spec/decisions.md LD-273 (9): a 429 on the 3rd try ends the run as Offline, as a 5xx does (SYN-03.10, pinned by T29); a `Retry-After` that is missing or not a whole number of seconds counts as 300 s (SYN-03.10, pinned by T30). RFC 9110 section 10.2.3 lets `Retry-After` be an HTTP date or a number of seconds; Larsal takes the number only, so a wrong clock on either side cannot change the wait: <https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3>.
- SYN-03.5 step 2's check (E16-S7a, 2026-11-06). The pattern: a proven manager's client downloads the encrypted vault, opens it, merges and uploads only when it has its own changes, and the cloud is a plain drive (spec/research/sync-server.md section 1, Enpass). What is compared and how is Larsal's own: no research note covers a file check before an upload, so the hash, the root compare and the exact frame come from this project's cards (FMT-01.20, FMT-02.3, FMT-02.21, FMT-03.6, FMT-06, LD-01, LD-21) and are not claimed as what other managers do.
