# SYN-01 Wire protocol

Status: reviewed
Epics: E16-S3 (transport, health route, limits, fuzz target), E16-S4 (vault routes), E16-S5 (sign-in routes), E16-S6 (the client's certificate pin), E16-S7a (the client side), E17-S1 to E17-S3 (account, device and upload-signature parts)
Parity rows: none in the reference app (it has no server). Larsal's own rows: SV-01 and SV-02 (plan/security.md); AT-L01 to AT-L03, AT-L05, AT-L09, AT-L11 (plan/attacks-and-checks.md)

## What it does

Larsal talks to Larsal's own sync server over HTTPS. The server stores locked vault files and never opens them (spec/research/sync-server.md P1, P16). This card fixes the protocol both sides build from `larsal-proto`: the transport and the certificate pin, every path, method, header and status, the ETag rules, how records are written, the limits, the timeouts and the rate limits.

Other cards: SYN-02 owns the server's store, SYN-03 the client's sync loop and its messages, SYN-04 sign-in, sessions and devices, SYN-05 the code two screens compare, SYN-06 accounts and a new Mac, CRY-04 the crypto. The sharing cards of E18 (SHR-01 to SHR-04) add the group, member and invite routes.

Design and sources: spec/research/sync-server.md P1, P3, P14, P16, P17, P25 (decided: spec/decisions.md LD-263 (1), (2), (13) to (15), LD-267 (7), LD-273 (1), (7)).

## Inputs and outputs

- Transport: HTTP/1.1 over TLS 1.2 or 1.3, on 127.0.0.1 in this build.
- In and out: requests and replies of the routes in SYN-01.4. Records are JSON objects (RFC 8259) in UTF-8; vault bytes travel as raw bodies, never as JSON.
- Limits: SYN-01.10, in `larsal-proto` `limits.rs`, checked before anything is allocated.

## Rules

SYN-01.1 **Transport** (P14). HTTPS only: HTTP/1.1 (hyper, `http1` and `server`) over TLS 1.2 or 1.3 (tokio-rustls with ring). No HTTP/2, no WebSocket, no push channel (P3: push needs APNs and the paid Apple account). The server binds 127.0.0.1 by default (plan/architecture.md, "Rules for this part" 5). A plain HTTP request on the server's port gets no HTTP reply: the TLS handshake fails and the server closes the connection.

SYN-01.2 **Demo certificate and the pin** (P17). At its first start the server makes a self-signed certificate with rcgen (a P-256 key; subject names `localhost` and `127.0.0.1`), stores it in its data folder (SYN-02.1) and prints its fingerprint: the SHA-256 of the certificate's DER bytes as 64 uppercase hex digits in 8 groups of 8. To add a server, the user gives its address; Larsal makes one TLS handshake, reads the certificate, closes the connection without sending a request, and shows the fingerprint in the same form with `MSG-SYNC-FINGERPRINT` (compare this with the code the server printed). Only after "They match" does Larsal pin it (local state, never synced, SYN-03.3) and send a request. From then on Larsal accepts only that certificate: the SHA-256 of the presented DER equals the pin; names and dates are not checked, the pin is the whole check, and a certificate that macOS trusts is refused too. A different certificate stops every request to that server with `MSG-SYNC-CERT-CHANGED`. A hosted server later uses a CA certificate and macOS trust (P17; not in this build).

SYN-01.3 **Paths and versions.** Every path starts with `/v1/`. An unknown path gets 404; a known path with another method gets 405 with `Allow`. When `GET /v1/health` does not answer as SYN-01.14 says, the client shows `MSG-SYNC-NOT-SERVER` and adds nothing.

The sharing routes and their checks are owned by SHR-01.12 (wraps), SHR-02.8 (groups and entries) and SHR-03.6 (invites).

"Approval code" means `Authorization: Approval <code>`, the one-time code of SYN-06.11, in place of a session. Any route may also answer 429 (SYN-01.12). Before any route runs, a request head that cannot be parsed gets 400, and one over SYN-01.10's head limits gets 414 or 431 as SYN-01.10 says (SYN-01.9).

SYN-01.5 **Session header** (P5; RFC 6750 section 2.1). `Authorization: Bearer <token>`, where `<token>` is the 32-byte session token of SYN-04.5 as 43 characters of base64url without padding. A missing, malformed, unknown, expired or revoked token gets 401 with `WWW-Authenticate: Bearer` and the same body for every reason. A token is never put in a URL, a cookie, a log or an error body.

SYN-01.6 **Vault routes and ETags** (P1, P3; RFC 9110 sections 8.8.3, 13.1.1, 13.1.2, 15.5.13; RFC 6585 section 3).
- `vault_id`: 32 lowercase hex digits (128 bits), drawn by the client from larsal-crypto's random source at the first upload (SYN-03.1). It is not the vault's root group id, so the server learns nothing from inside the file.
- ETag: always strong, `"` + the version in decimal + `"`. The version is a u64 that starts at 1 and goes up by 1 with each accepted PUT. The server compares ETags with the strong compare only; a weak ETag (`W/"3"`) never matches.
- `GET /v1/vaults`: `{"vaults":[{"id":…,"version":…,"size":…}]}`, the vaults this account may read, sorted by id. Nothing else: no names, no times, no item counts.
- `GET /v1/vaults/{vault_id}`: 200 with the bytes exactly as uploaded, `Content-Type: application/octet-stream`, `Content-Length` and `ETag`. With `If-None-Match` equal to the current ETag: 304 with no body. An unknown id and a vault this account may not read get the same 404, except that a former member of the vault's group gets 403 (SHR-04.5).
- `PUT /v1/vaults/{vault_id}`: the body is the whole vault file. It needs exactly one precondition: `If-Match` with one strong ETag (an update) or `If-None-Match: *` (a new vault). Neither, or `If-Match: *`, gets 428 (the server never takes a blind overwrite). Both, or a list of ETags, gets 400. `If-None-Match: *` for an id that exists gets 412. `If-Match` that differs from the current ETag, or names an id that does not exist, gets 412. A vault this account may not read gets the reply an id that does not exist gets (412), except a former member of its group, who gets 403 (SHR-04.5); with `If-None-Match: *` it gets 412 as any id that exists does, and nothing is stored. A PUT whose head has no `Content-Length` (a chunked body, or a head with neither length field) gets 411 (LD-321 (2)). A PUT with `If-None-Match` set to an ETag (not `*`) gets 428. An `If-Match` or `If-None-Match` value that is neither `*` nor an entity tag gets 400. A version tag that is not in canonical form (for example `"03"`) gets 412. On a GET, an `If-None-Match` that does not parse is ignored (200) (LD-321 (3)). A `Content-Length` over SYN-01.10's vault limit gets 413 before one body byte is read. Success: 201 for a new vault, 200 for an update, each with the new `ETag` and the body `{"id":…,"version":…,"size":…}`. 403 when the account may read this vault but not write it (roles come with E18: SHR-03.11 runs for every PUT of a shared vault, and a former member of a group gets 403 for that group's vaults, SHR-04.5; a personal vault never gives 403 for roles to its own account), and when the upload signature does not verify (SYN-01.7).
- The server never reads or checks the bytes beyond their length (P16, SYN-02.9).

SYN-01.7 **Upload signature** (from E17-S1; P4, P11). From E17-S1 every PUT of a vault carries `Upload-Signature: <base64url of 64 bytes>`, the uploader's Ed25519 identity key signing the CRY-04.2 field list (`sync-upload-v1`, the 16 bytes of `vault_id`, the new version as a u64 big endian, the SHA-256 of the body). The new version is the `If-Match` version plus 1, or 1 for a new vault. The server stores it with the version (SYN-02.3) and returns it on `GET /v1/vaults/{vault_id}` as `Upload-Signature` with `Upload-Signer: <the signer's id, 32 lowercase hex>`. The server refuses a PUT whose signature is missing (400) or does not verify with the account's identity key (403); the client's check of SYN-03.11 is the one that counts (P11: clients trust signatures, never the server's word). Before E17-S1 neither header is sent and the server needs none. Header names carry no `X-` prefix (RFC 6648). For a shared vault, SHR-03.10's signature and headers take the place of this one.

SYN-01.8 **Records.** Every record is one JSON object (RFC 8259), UTF-8, `Content-Type: application/json`, read and written with larsal-model `json.rs` (P14, LD-263 (14)).
- Field names are lower case with underscores. Byte strings are base64url without padding (RFC 4648 section 5); ids are 32 lowercase hex digits; times are whole seconds since 1970-01-01T00:00:00Z as JSON integers; versions and sizes are JSON integers from 0 to 2^53 − 1.
- Refused (400 on the server; a protocol error on the client, `MSG-SYNC-ERROR`): a body that is not one JSON object; a missing field; a field of the wrong type; a duplicate key; a byte string or id of the wrong length or with a character outside its alphabet; a number outside its range; nesting deeper than 8 levels.
- A field the reader does not know is ignored, so a later `/v1` server may add one.

SYN-01.9 **Errors.** Every 4xx and 5xx reply from the server has the body `{"error":"<code>"}` with one code from this list: `bad_request`, `unauthorized`, `forbidden`, `not_found`, `method_not_allowed`, `conflict`, `length_required`, `precondition_failed`, `too_large`, `precondition_required`, `rate_limited`, `server_error`. The one exception is a reply to a request head, written before any route runs and with no body, as hyper writes it or by Larsal's own head check before routing in the same form: 400 when the head cannot be parsed, and 414 (RFC 9112 section 3) or 431 (RFC 6585 section 5) when it is over SYN-01.10's head limits, as SYN-01.10 says. An error body never holds a token, a key, a request body, another account's id or a stack trace. The client never shows text from the server: it maps the status to its own words (SYN-03.10), because the server may be hostile.

SYN-01.10 **Limits** (architecture "Rules for this part" 4; `larsal-proto` `limits.rs`; tests can lower them). Checked before any memory is allocated for the part. Each limit is a proven server's default or follows from Larsal's own record sizes:
- the request line and each header field: at most 8 KiB; the request head in all: at most 32 KiB (nginx's default `large_client_header_buffers 4 8k`; 8 KiB is more than the 8,000 octets of request line that RFC 9112 section 3 asks every recipient to take); at most 100 header fields (hyper's default `max_headers`). A head over 32 KiB or with more than 100 header fields gets 431 (RFC 6585 section 5), whatever its request line. Within those, Larsal checks the request line first: over 8 KiB, it gets 414 (RFC 9112 section 3; RFC 9110 section 15.5.15; nginx answers 414 too); then each header field: over 8 KiB, it gets 431 (RFC 6585 section 5). Each has no body (SYN-01.9), then the connection closes, before any route runs. hyper checks the complete head against `max_header_size` (set to 32 KiB, start line included) and the field count against `max_headers`, and answers 431 itself, before it looks at the request target's length. A head that is not complete is checked too: hyper answers 431 once its buffer of an unfinished head reaches `max_header_size` (`Buffered::parse` checks it before `max_buf_size`, which keeps its default); `max_header_size` needs hyper 1.12.0 or later. Its own checks of one part are far above Larsal's: a header name of 65,536 bytes or more is `Parse::TooLarge` (431), a request target over 65,534 bytes is `Parse::UriTooLong` (414), and it checks neither one header value nor the request line as a whole. Each of those parts is over 32 KiB, so the head check answers first and these two never apply; the two 8 KiB checks are Larsal's own, made on the parsed head before routing;
- a JSON body or reply: at most 1 MiB (nginx's default `client_max_body_size 1m`). The vault list is the largest JSON reply: one item is at most 93 bytes (an id of 32 digits and two numbers of at most 16 digits), so 1 MiB holds more than 11,000 vaults; no item count is checked apart from the bytes;
- a wrap record (CRY-04.6): at most 4 KiB, which holds CRY-04's largest wrap (1 KiB of HPKE plaintext) in base64url with room to spare;
- a vault body: at most FMT-01.31's 1,140,850,688 bytes (LD-263 (13), LD-267 (7)).
The client applies the same limits to the server's replies: a reply over its limit is a protocol error and the client reads no further.

SYN-01.11 **Timeouts.** Server: the TLS handshake within 30 s, then the request head within 30 s (hyper's default `header_read_timeout`, 30 s, which runs only when the builder has a timer: larsal-server gives it hyper-util's `TokioTimer` through `Builder::timer`; it times the head only, so the handshake's 30 s is Larsal's own value, set equal to it, a timer the server puts on the tokio-rustls accept); no gap over 60 s between two reads of the body or two writes of the reply (nginx's defaults `client_body_timeout` and `send_timeout`, 60 s); an idle keep-alive connection closes 30 s after its last reply, because hyper (1.6.0 and later, <https://github.com/hyperium/hyper/pull/3828>) starts `header_read_timeout` again when a connection goes idle; Larsal adds no idle timer of its own. Client: no wait over 60 s for the connection or for more bytes while sending or reading (URLSession's default `timeoutIntervalForRequest`, 60 s, a timer that starts again whenever data arrives). A timeout ends the request; on the server nothing is stored (SYN-02.4); on the client it counts as offline (SYN-03.10).

SYN-01.12 **Rate limits** (RFC 6585 section 4). Over a limit, the server answers 429 with `Retry-After` in seconds and does nothing else. The limits, per IP address and minute, are the defaults of a proven open source password manager server (its `appsettings.json` files): 10 requests to the sign-in routes (`POST /v1/accounts`, `/v1/signin/challenge`, `/v1/signin`, `/v1/recovery/challenge`, `/v1/recovery/signin`, `/v1/approvals/claim` and `/v1/invites/claim`), as its identity server allows its sign-in route `post:/connect/token`; on every other route, 60 POST, PUT or DELETE requests and 200 GET requests, as its API server allows. These are server constants in `limits.rs`.

SYN-01.13 **No caching, quiet logs.** Every reply has `Cache-Control: no-store` (RFC 9111 section 5.2.2.5), except the head replies that hyper writes itself (SYN-01.9's exception): they have no body, and RFC 9111 section 4.2.2 lets no cache store a 400 or a 431 by heuristics (LD-314). Larsal's own replies, its 414 included, all carry it. The server logs the method, the route name, the status, the size and the time taken, never the `Authorization` header, a token, a nonce, a signature, a code or a body. The client logs counts and statuses only (Rust rule 9).

SYN-01.14 **Health route.** `GET /v1/health`, no session: 200 `{"service":"sync","api":1}`. Larsal calls it once after the pin (SYN-01.2) to confirm the address is a Larsal server.

SYN-01.15 **Fuzz targets.** Every parser of this card has a fuzz target: the request head and the headers `If-Match`, `If-None-Match`, `Authorization`, `Upload-Signature`, `Upload-Epoch` and `Upload-List-Head` (SHR-03.10); the `entries/{from}` segment (SHR-02.8) and the wrap DELETE path (SHR-01.12); each JSON record, the SHR records included; and on the client each reply record (architecture "Rules for this part" 4; P25).

## Edge cases and errors

- `If-None-Match` on a GET that names an older version: 200 with the current bytes.
- PUT with `If-Match: "0"`, a negative or a non-number version: 412 (no such version).
- Two PUTs with the same `If-Match` at once: one gets 200, the other 412 (SYN-02.4's compare-and-swap).
- A body shorter than its `Content-Length` (the connection closes): nothing stored, no version change.
- A JSON record with an extra field: the field is ignored.
- A record with the same key twice, for example two `device_id` fields: 400.
- A reply whose `Content-Length` is over the limit, or that has none on a vault GET: the client stops reading and treats it as a protocol error.
- No route deletes a vault from the server in this build; "Stop syncing" is local (SYN-03.15).

## Security notes

- **What the server sees (SV-01).** Account ids, device public keys and names, session token hashes, vault ids, versions, sizes, upload times, IP addresses, and from E17 the public keys and wrapped blobs of SYN-06. It never sees a password or a value made from one, except the account blob of SYN-06.4, which also needs the account secret (plan/architecture.md, "Rules for this part" 2), and never a vault key, a key-file part or vault contents in plain form (plan/architecture.md, "What the server sees").
- **Lost updates.** A PUT without a precondition could overwrite another Mac's version; 428 makes the precondition required, and 412 sends the client back to merge (RFC 9110 section 13.1.1, the lost update problem).
- **Hostile server.** The client never shows the server's words, bounds every reply, and trusts only the pinned certificate (SYN-01.2) and signatures (SYN-01.7, SYN-03.11).
- **Pin, not trust.** A demo server's self-signed certificate is pinned by its fingerprint after the user compares it, as Enpass's Wi-Fi sync code compare does (sync-server.md section 1). A certificate macOS trusts is still refused, so a CA mistake cannot reach a pinned server.
- **No blind overwrite.** `If-Match: *` gets 428, so no client bug can replace the server copy without naming the version it merged.
