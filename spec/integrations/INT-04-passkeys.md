# INT-04 Passkeys

Status: draft
Epics: E7-S5 (the Passkeys report screen is built in E5-S7 from INT-04.52 and INT-04.53)
Parity rows: SI-05, SF-09, SD-07, SD-09, SR-16, SI-01, SI-04

## What it does

Larsal acts as a software WebAuthn authenticator for the browser extension. A site asks the extension to create a passkey (registration) or to sign in with one (authentication). The extension draws the prompt in the page from the entries Larsal lists for that page (INT-11.38, INT-02.20). After the user's Save Passkey or Continue, it sends the request with the user's choice over the browser bridge: where the new passkey goes, or which entry signs in. Larsal checks the request and the choice, asks its own questions where one is needed (exclude list, overwrite, vault, group), verifies the user with Touch ID or with the vault's password, checked in Rust (INT-04.56), then creates or uses a key pair, and replies with the WebAuthn response. The private key and the account data live in entry fields of the vault, so passkeys sync and merge like any other entry data.

Larsal also lets the user import and export single passkeys as `.passkey` files, remove a passkey from an entry, and list all passkeys on the Passkeys tab of the Reports screen.

Neighbor cards: INT-01 (bridge envelope, association, bridge error replies, action names), INT-02 (the entry-keeping steps INT-02.13, hide-from-browser and association restriction options, search in all vaults, the vault picker, the create-group prompt, window raise), INT-03 (public suffix list; the relying party field as an additional URL), FMT-14.22 (field keys and their protection), MOD-01.8 (passkey fields left out of custom-field lists), MOD-03 (history), MOD-06 (icon 13), MOD-07.11 (the "Passkey" tag), FEA-01 (search), FEA-07.13 (passkey count), FEA-08.47 (passkeys inside the JSON import), FEA-09 (other exports), APP-01 (setting S-BRW-19, last-folder role), APP-02 (lock), APP-04 (the Touch ID slot that INT-04.56 reads), APP-06 (the unlock panel's verify use, APP-06.31), INT-11 (the extension's two passkey frames, INT-11.38).

Public standards a Builder needs: W3C Web Authentication Level 2 and 3 (client data, authenticator data and its flags, attestation object, "none" attestation, user presence and user verification), FIDO Alliance CTAP 2.2 (the `up` and `uv` options), RFC 8949 (CBOR), RFC 9052 and RFC 9053 (COSE keys), RFC 8230 (COSE RSA keys), RFC 8032 (Ed25519), FIPS 186-5 and RFC 6979 (ECDSA), RFC 8017 (RSASSA-PKCS1-v1_5), RFC 5958 and RFC 8410 (PKCS#8), RFC 5915 (EC private keys), RFC 5280 (SubjectPublicKeyInfo), RFC 7468 (PEM), RFC 4648 section 5 (base64url), the WHATWG HTML rule "is a registrable domain suffix of or is equal to", the Public Suffix List.

## Inputs and outputs

**Entry fields** (stored as entry strings; FMT-14.22 owns the keys and protection flags). "Prefix" below means the 12 characters `KPEX_PASSKEY`.

| Field key | Value | Protected | Larsal writes it |
|---|---|---|---|
| `KPEX_PASSKEY_RELYING_PARTY` | RP ID, for example `example.com` | no | yes |
| `KPEX_PASSKEY_USERNAME` | the site's `user.name` | no | yes |
| `KPEX_PASSKEY_CREDENTIAL_ID` | credential id as base64url text without padding (Larsal: 32 random bytes, 43 characters) | yes | yes |
| `KPEX_PASSKEY_USER_HANDLE` | the site's `user.id` exactly as received (base64url text, not decoded) | yes | yes |
| `KPEX_PASSKEY_PRIVATE_KEY_PEM` | unencrypted PKCS#8 private key in PEM (INT-04.3) | yes | yes |
| `KPEX_PASSKEY_FLAG_BE`, `KPEX_PASSKEY_FLAG_BS` | `1` | no | yes (not in installed 2.7.11) |
| `KPEX_PASSKEY_GENERATED_USER_ID` | credential id written by another password manager | as read | never |
| `4B 50 58 43 5F 50 41 53 53 4B 45 59 5F 55 53 45 52 4E 41 4D 45` (stored encoded, name rule) | passkey user name written by other apps | as read | never |

**Bridge requests** (inside the box, INT-01.21): `passkey.create` (registration) and `passkey.get` (authentication), INT-01.30. The reference uses its own action and member names; INT-01.32 maps them (aligned in the second review of INT-01, LD-189).

| Member | Register | Get | Type |
|---|---|---|---|
| `public_key` | creation options | request options | JSON object with WebAuthn member names; binary values are base64url text |
| `origin` | yes | yes | text, the page origin as the extension sees it |
| `target` | yes | no | object: where the user chose to save the new passkey: `{"vault","id"}` for an existing entry; for a new entry `{"vault","group"}` (a group id), `{"vault"}`, or `{}` for Larsal's choice (INT-04.20, INT-04.24; R04-1) |
| `entry` | no | yes | object `{"vault","id"}`: the entry the user chose to sign in with (INT-04.42; R04-1) |
| `group` | withdrawn | no | the group path gave way to `target`'s group id (R04-1); sent on its own it is an unknown member and ignored (INT-01.21) |
| (none) | | | no association member: the vault must hold the session's proven identification key (INT-01.28, INT-01.29); the reference sends a list of association pairs here |

Members of `public_key` that Larsal reads. Register: `challenge`, `rp.id`, `rp.name`, `user.id`, `user.name` (`user.displayName` is ignored), `pubKeyCredParams`, `attestation`, `authenticatorSelection` (`authenticatorAttachment`, `residentKey`, `requireResidentKey`, `userVerification`), `excludeCredentials`, `extensions`, `timeout`. Get: `challenge`, `rpId`, `allowCredentials`, `userVerification`, `extensions`, `timeout`. Unknown members are ignored. Size: bounded by the bridge message limit (SI-01, INT-01).

**Bridge replies**: a normal encrypted reply whose `response` member holds either the credential object (INT-04.27, INT-04.43) or `{"errorCode": n}` (INT-04.54).

**Files**: `.passkey` JSON files (INT-04.47 to INT-04.50).

**Setting**: S-BRW-19 `browser.passkeys_localhost` (APP-01), default off.

**Crypto** (larsal-crypto, `sign.rs`): make a key pair for ES256, EdDSA or RS256; read and write PKCS#8 PEM; give the public key as COSE parts and as SubjectPublicKeyInfo DER; sign a message. Private key bytes live only in secret types (AGENTS rule 4).

## Rules

### Storage

INT-04.1 **Fields.** A passkey is the set of fields in the table above, plus the tag "Passkey" (MOD-07.11). The three protected fields are always written protected, whatever the vault's protection flags say (SF-09). The two foreign fields are kept as read and never created.

INT-04.2 **"Has a passkey".** An entry has a passkey when at least one of its string fields has a key that starts with the prefix (case-sensitive; any key that starts with those 12 characters counts, also the key with bytes `4B 50 45 58 5F 50 41 53 53 4B 45 59 58`, stored encoded (name rule)). The encoded foreign user-name field alone does not count. This test drives: the Remove passkey action (INT-04.46), the overwrite question (INT-04.6), the passkey lookup (together with the RP match, INT-04.41), the detail and edit rows (INT-04.51), the `passkey` flag of the bridge's entry summaries (INT-02.20; when `logins.find` carries `rp_id`, together with INT-04.41's RP match) and the statistics count (FEA-07.13). The report uses another test (INT-04.52).

INT-04.3 **Private key form.** PKCS#8 without encryption, PEM label `PRIVATE KEY`.
- **Larsal writes**: the header line `-----BEGIN PRIVATE KEY-----`, the DER in standard base64 in lines of 64 characters, the footer line `-----END PRIVATE KEY-----`, LF line ends, and a final LF.
- **DER Larsal writes**: ES256: `id-ecPublicKey` with `prime256v1`, holding an EC private key of version 1 with the 32-byte scalar and the `[1]` public key, without `[0]` parameters (138 bytes: `30 81 87`, a sequence of 135 bytes; base64 starts `MIGHAgEAMBMGByqGSM49AgEGCCqGSM49AwEHBG0wawIBAQQg`). EdDSA: RFC 8410 version 1, 48 bytes: `30 2E 02 01 00 30 05 06 03 2B 65 70 04 22 04 20` then the 32-byte seed. RS256: `rsaEncryption` with an RSA private key, 2048-bit modulus, public exponent 65537. That the reference writes exactly these forms and this line layout: from the source, not run (check with Verify, V-INT04-4).
- **Larsal reads**: any whitespace or none between header and footer (the JSON import writes none, FEA-08.47), CR LF line ends, EC keys with or without the public key and the `[0]` parameters, Ed25519 keys of version 1 or 2.
- **Algorithm from the key**: EC on P-256 signs as ES256, RSA as RS256, Ed25519 as EdDSA. Any other curve or key type cannot sign (error 31). The reference loads any EC curve and signs with SHA-256 anyway; Larsal refuses curves other than P-256.

INT-04.4 **Which id and name an entry answers with.** Credential id: the value of `KPEX_PASSKEY_GENERATED_USER_ID` when that field exists (even empty), else the value of `KPEX_PASSKEY_CREDENTIAL_ID`. Passkey user name: the value of the encoded foreign field when it exists, else `KPEX_PASSKEY_USERNAME`. All id, user-handle and RP comparisons in this card are exact, case-sensitive text compares of stored text; nothing is decoded first.

INT-04.5 **Backup flags** (R04-1 rewrite, D-INT04-19). Each flag comes from its own field. Value exactly `1` or `true`: set. Any other value (`0`, `TRUE`, empty): clear. Field missing: clear. Installed 2.7.11 neither writes nor reads these fields and sends both flags clear, so a passkey it registered has neither field, and the site was told BE clear when it registered it. WebAuthn fixes BE at registration (Level 3 §6.1.3: "The value of the BE flag is set during authenticatorMakeCredential operation and MUST NOT change"), and a site that keeps the backup state in its policy refuses a sign-in whose BE differs from the one it stored (Level 3 §7.2, under its condition "If the credential backup state is used as part of Relying Party business logic or policy": "If credentialRecord.backupEligible is set, verify that currentBe is set." and "If credentialRecord.backupEligible is not set, verify that currentBe is not set."). Larsal writes both fields `1` for every passkey it makes (INT-04.6 step 3) and for both imports, a `.passkey` file's (INT-04.48) and FEA-08.47's JSON import, neither of which carries flags. The flags are present-tense (the lead's ruling on review R5-01): Larsal registers every passkey with BE and BS set, and a credential's BE never changes after its registration (Level 3 §6.1: "The BE flag SHALL be set if and only if the credential is a multi-device credential." and "This value MUST NOT change after a registration ceremony as defined in § 6.1.3 Credential Backup State."). A passkey in Bitwarden's JSON export was registered there as a synced credential: Bitwarden's authenticator sets `backupEligibility: true,` and `backupState: true, // Credentials are always synced` for every registration and every sign-in (`generateAuthData`, D-INT04-19), and the passkey lives on in a vault that Larsal copies, syncs, merges and exports, so it is a multi-device credential in Larsal too. Known limit: a passkey that Bitwarden registered before pull request 7947 (merged 2024-02-16) reached its releases was registered with BE clear; after FEA-08.47's import it signs with BE set, as Bitwarden itself signs it now, and a site that keeps the backup state in its policy refuses that sign-in (Level 3 §7.2). The reference's development source reads a missing field as set (D-INT04-19). A further known limit (review R6-01): a passkey that another app put into an entry without the flag fields, such as one from the reference's Bitwarden import, which writes no flag fields, signs with BE clear though its maker may have registered it with BE set, and a site that keeps the backup state in its policy then refuses that sign-in until the user registers a new passkey there; Larsal cannot tell such an entry from one that installed 2.7.11 registered, so a missing field stays clear.

INT-04.6 **Storing a passkey into an entry.**
1. If the entry has a passkey (INT-04.2), ask the overwrite question MI04-01, which names the entry title and its passkey user name, with Replace (MI04-11) and Cancel, Cancel the default. Cancel stops here (INT-04.23 says what the site then gets).
2. Larsal removes every field with the prefix and the encoded foreign user-name field (decided by default, D-INT04-11). The reference only overwrites the seven fields it writes, so a kept `KPEX_PASSKEY_GENERATED_USER_ID` would still win (INT-04.4) and the entry would answer with the old id and the new key.
3. Set the seven fields: RP ID, passkey user name, credential id, private key, user handle, `KPEX_PASSKEY_FLAG_BE` = `1`, `KPEX_PASSKEY_FLAG_BS` = `1`.
4. Add the tag "Passkey" (MOD-07.11).
Steps 2 to 4 are one edit session (MOD-03.4). Title, user name, password and URL do not change.

INT-04.7 **New passkey entry.** In the chosen group: a new random id, title "‹name› (Passkey)", user name = passkey user name, URL = the origin (registration) or the file's `url` (import), icon 13 (MOD-06), empty password. Then INT-04.6 steps 3 and 4, then the history is emptied (MOD-03.5). ‹name› is `rp.name` for a passkey saved from the browser (INT-04.23) and the RP ID for imports (MI04-17). When ‹name› is empty after trimming, Larsal uses the RP ID (decided by default, D-INT04-14); the reference writes " (Passkey)".

INT-04.8 **The RP field as a URL.** The value of `KPEX_PASSKEY_RELYING_PARTY` joins the entry's additional URLs for login matching and for any list of the entry's URLs (INT-03 applies its rules for an additional URL without a scheme). So a passkey entry for `example.com` is also offered for password fill on `example.com`.

### Checks on every request

INT-04.9 **Origin gate.** Done after the bridge checks of INT-01 and after the check that `public_key` is a non-empty object (else error 24), both as bridge error replies. The origin passes when its text starts with `https://` (case-sensitive). With S-BRW-19 on, these also pass: text starting with `file://`, and any origin whose host is `localhost` or `localhost.` or ends with `.localhost` or `.localhost.`, whatever the scheme. Else error 25. In practice `file://` and hosts ending with a dot then fail INT-04.10 with error 27. Larsal also requires the serialized origin form: scheme, `://`, host, optional `:port`, nothing after it, scheme and host in lower case; else error 25 (decided by default, D-INT04-9).

INT-04.10 **Effective domain.** The origin's host, lower case, in IDNA ASCII form (punycode); the port is dropped. Empty origin: error 26. The host must be a valid domain, else error 27. A valid domain is not empty, is ASCII only, does not end with `.`, holds no whitespace and none of `^ # | / : < > ? @ [ ] \`, and is not an IPv4 or IPv6 address (with or without brackets). Installed 2.7.11 takes the host in Unicode form, so every internationalized host fails with error 27 (differs in installed version).

INT-04.11 **RP ID.** Register reads `rp.id`, Get reads `rpId`. Missing or null: the RP ID is the effective domain. Otherwise, with R = the given RP ID and H = the effective domain, all compared in lower-case ASCII form, and PS(x) = the public suffix of x by the Public Suffix List, ICANN and private sections, with the default rule that an unlisted last label is a public suffix (INT-03 owns the list):
1. R empty: error 28.
2. R equals H: accept.
3. R not a valid domain (INT-04.10): error 28.
4. H does not end with "." + R: error 28.
5. PS(R) equals R (R is itself a public suffix): error 28.
6. PS(H) empty: error 28.
7. PS(H) ends with "." + R: error 28.
8. R does not end with "." + PS(H): error 28.
9. Accept.
The accepted RP ID is H when R equals H. Otherwise the reference keeps R exactly as the site wrote it, case and Unicode included, and hashes and stores that text; Larsal uses the lower-case ASCII form (decided by default, D-INT04-8). A given RP ID with a scheme, port or path is error 28 in Larsal; the reference compares only its host part and hashes the whole text (check with Verify, V-INT04-8).

INT-04.12 **Challenge.** Register: `challenge` must be text of at least 16 characters, else error 32. The length is counted in characters of the base64url text, not in decoded bytes (16 characters are 12 bytes). The reference does not check the challenge on Get. Larsal applies the same check on Get, and on both accepts only base64url characters (`A`–`Z`, `a`–`z`, `0`–`9`, `-`, `_`), else error 32 (decided by default, D-INT04-9).

INT-04.13 **User id.** Register: `user.id` decoded from base64url must be 1 to 64 bytes, else error 33. The reference skips characters that are not base64url while decoding; Larsal decodes strictly (padding optional) and treats a decode failure as error 33 (D-INT04-9).

INT-04.14 **Algorithm.** From `pubKeyCredParams`, keep the items whose `type` is `public-key` and whose `alg` is -7 (ES256), -257 (RS256) or -8 (EdDSA), in the site's order. List missing or empty: use [-7, -257]. List not empty but nothing kept: error 29. The key type is the first kept item. RS256 needs an RSA crate, which is not on the approved list (lead decision D-INT04-2).

INT-04.15 **Attestation.** Every value of `attestation` is accepted. The response always uses the "none" format with an empty statement. Error 20 is never sent.

INT-04.16 **Authenticator selection.** `authenticatorAttachment` must be missing, empty, `platform` or `cross-platform`, else error 30. The response's attachment is the requested value, or `platform` when none was requested. `residentKey` and `requireResidentKey` are accepted with any value: every passkey Larsal makes is discoverable, because it is an entry. `userVerification`: missing means `preferred`; `required` and `preferred` mean "verification wanted"; `discouraged` and unknown values mean "not wanted"; an unknown value is only logged. Larsal verifies the user for every request whatever the value (INT-04.56; R04-1), so the flags never depend on it (INT-04.33); it only sets the time limit's default (INT-04.18).

INT-04.17 **Extensions.** Of `extensions`, only `credProps` counts; all other members are dropped. Client extension results: when `credProps` is `true`, `{"credProps":{"rk":true}}`; otherwise `{}`. Since the R04-1 rewrite `uvm` is dropped too: W3C removed it from WebAuthn Level 3 because "there are no production client implementations of the `uvm` extension" (w3c/webauthn issue 2069, closed by pull request 2085 on 2024-06-26), and its output `[[1,1,1]]` named a presence check as the way the user was verified, which is no longer true once INT-04.56 verifies the user (LD-381: truthful extension output). The authenticator extension data is in INT-04.36.

INT-04.18 **Time limit** (R04-1 rewrite: Larsal shows no countdown). Larsal's prompts for one request (INT-04.29's list) share one time limit of `timeout` milliseconds divided by 1000, rounded down, in seconds. It starts when the request's first prompt shows. When it ends while a prompt is open, the prompt closes and the reply is error 22; nothing is made, stored or signed. A prompt's own shorter limit still applies (the group question's 60 seconds, INT-04.24). The reference counts its confirm dialog down from the site's number as it is: no upper bound, and a missing value or a value under 1000 gives a countdown of 0, which closes the dialog about one second after it opens (from the source, not run: check with Verify, V-INT04-2). Larsal: a missing value, or one of 0 or less, means 300 seconds (120 seconds when verification is not wanted, INT-04.16); every value is then held between 30 and 600 seconds (decided by default, D-INT04-6).

### Registration

INT-04.19 **Order of steps** (R04-1 rewrite, 2026-11-23). The user already chose Save Passkey in the extension's frame (INT-11.38). Larsal then:
1. Bridge checks (INT-01), `public_key` present (24), origin gate (25).
2. Option checks: challenge (32), user id (33), effective domain (26, 27), RP ID (28), algorithm (29), attestation, authenticator selection (30), extensions, time limit (INT-04.18). The first failure is the reply.
3. The target (INT-04.20): error 18.
4. Exclude list (INT-04.21): the notice MI04-02, then error 21, or error 22 when the notice is closed.
5. Vault picker, for a new entry whose target names no vault (INT-04.20): Cancel gives error 1.
6. Checks of the vault, now known, before any question: a new entry without a group gets INT-04.24's default group, which must pass INT-04.20's group checks, or, while it does not exist, the root's `BrowserRestrictKey` that it would take (error 18); the vault must be able to verify the user (INT-04.56 step 3; error 23). When the target names the vault (INT-04.20: an existing entry, or a new entry with `vault`), the vault is known when the request arrives, so this step runs then, before step 4, and its error 18 or 23 comes before the exclude notice (INT-04.29, review R4-07); for a target that names no vault, the vault is known at step 5.
7. Overwrite question MI04-01, for an existing entry that has a passkey (INT-04.6 step 1): Cancel gives error 22.
8. Group question MI02-08, when the default group of step 6 does not exist yet (INT-04.24).
9. User verification (INT-04.56): error 22 when it does not pass.
10. Check steps 3, 4, 6 and 7 again on the vault as it is now, and the group a Cancel at step 8 chose (INT-04.57): their error, 18, 22 or 23 (an id of `excludeCredentials` that arrived, or a target entry that gained a passkey, gives 22 with no notice and no question), and nothing is made or stored. Then make the key pair and the response (INT-04.25 to INT-04.27). A failure here: error 31.
11. Store the passkey (INT-04.23: INT-04.6 steps 2 to 4, or INT-04.7 with the group of step 8 made now), restore Larsal's earlier state (INT-04.28), reply.
Steps 4 to 9 show their prompts one after another, in one turn of INT-04.29's line; a request that step 6 ends has shown at most the picker. The reference runs its vault picker first, so the picker can open for a request that then fails, and it checks that `excludeCredentials` is a list only after the user's confirm: a request without it fails with error 31 after the user pressed Register in its dialog (from the source, not run: check with Verify, V-INT04-6). Larsal runs the steps in the order above and treats a missing `excludeCredentials` as an empty list (decided by default, D-INT04-7). WebAuthn's authenticator runs its checks in the same order: the exclude list (Level 3 §6.3.2 step 3), then, "If requireUserVerification is true and the authenticator cannot perform user verification", "ConstraintError" (step 5; Larsal's error 23 also for `preferred` and `discouraged` is its own stricter rule from ruling R04-1 (3), INT-04.56 step 3), then the user's consent with user verification (step 6), then the new credential (step 7). Larsal's picker comes before step 6 because that step needs the vault, and MI04-01 and MI02-08 are part of the user's consent. The one change of that order, step 6 at arrival for a target that names the vault, follows WebAuthn's client: for a request whose `userVerification` is `required` it never asks an authenticator that cannot perform user verification (Level 3 §5.1.3 step 22: "If pkOptions.authenticatorSelection.userVerification is set to required and the authenticator is not capable of performing user verification, continue."), so that authenticator never runs its exclude check; and error 23 tells the site less than the notice's error 21 (review R4-07). Step 10 checks steps 3, 4, 6 and 7 again because the user or a merge can change the vault while the prompts show (INT-04.57, reviews R3-06 and R5-02).

INT-04.20 **The target and the vault** (R04-1 rewrite; LD-191). `target` is where the user chose to save the passkey in the extension's frame (INT-11.38). Larsal checks it before any prompt. Each failure below is the boxed error 18 (INT-01.40), and nothing shows.
- **Form.** A JSON object in one of these forms. Existing entry: `{"vault": V, "id": E}`. New entry: `{"vault": V, "group": G}`, `{"vault": V}` or `{}`. V is a vault id (INT-01.31); E an entry id and G a group id, each 32 lowercase hex digits (INT-01.30). Error 18: `target` missing or not an object; an `id` or a `group` that is not 32 lowercase hex digits; an `id` or a `group` without `vault`; `id` together with `group`; a member of the wrong JSON type (error 18 here, not INT-01.21's "counts as missing", so a broken choice never turns into another one). Unknown members are ignored (INT-01.21).
- **Vault.** V must be a usable vault of the request (INT-02.10: unlocked, holding the session's proven identification key, not behind MOD-13's forced prompt); an empty text names no vault. Else error 18.
- **Entry.** E must name an entry of V that INT-02.13 keeps for the page, with the request's `origin` as the page URL and `http_auth` false. Else error 18. It need not have a passkey: a login entry keeps its password and gains the passkey (INT-04.6; the frame's line "the entry keeps its password").
- **Group.** G must name a group of V that INT-02.13 steps 1 to 3 let the page use: not the recycle bin, not inside it, and not the templates group (step 1, INT-02.12, MOD-02.28); not hidden from the browser by its resolved `BrowserHideEntry` (step 2, INT-02.14, MOD-02.17); its resolved `BrowserRestrictKey` empty or one of the names under which V holds the session's key (step 3). Else error 18. INT-04.24's default group is checked the same way once the vault is known (INT-04.19 step 6).
- **Which vault.** Existing entry, or a new entry with `vault`: V. Else, with S-BRW-14 on and more than one usable vault, INT-02.27's vault picker with the title MI04-19 (the shown vault selected), at step 5 of INT-04.19 (Cancel: error 1); else the one usable vault. No usable vault: error 1, which INT-01.30 already sends before any step of this card.
Reference difference: it has no target (its own dialog lists the entries), and its picker lists every unlocked vault, associated with the browser or not and whatever its search-all setting, and the passkey goes into the one chosen. Larsal never writes a passkey into a vault the browser is not connected to.

INT-04.21 **Exclude list.** Take the `id` text of every item of `excludeCredentials`. If any candidate entry for the RP ID (INT-04.41, in every usable vault, whatever the target) answers with one of these ids (INT-04.4), Larsal shows the notice MI04-02 with one OK button, then replies error 21. Closing the notice, the time limit (INT-04.18) or a lock gives error 22 instead, so only the user's OK tells the site that this vault holds one of its credentials. No entry is made or changed, and no verification follows. INT-04.57 runs this check again after the last prompt: an id that a candidate answers with by then, one that arrived while the prompts showed, gives error 22 with no notice, so a site learns nothing from it either (review R5-02). The reference replies at once, with no dialog, so a site can probe which of its credential ids this vault holds; Larsal's notice is decided by default (D-INT04-10). WebAuthn asks the same of an authenticator (Level 3 §6.3.2 step 3: a gesture with a test of user presence first, then "InvalidStateError" when the user confirms and "NotAllowedError" when not).

INT-04.22 **Withdrawn** (R04-1, 2026-11-23). It listed the candidates whose user handle equals `user.id` and opened Larsal's dialog in its "existing" mode. The extension's frame now offers the page's match ("Add to ‹title›", INT-11.38), and storing into an entry that already has a passkey asks MI04-01 (INT-04.6). A new entry for an account that already has a passkey is a second passkey beside the first (Edge cases). The number is retired and never reused.

INT-04.23 **Outcomes** (R04-1 rewrite).

| Target (INT-04.20) | The user | Result |
|---|---|---|
| any | cancels or closes Larsal's verification (INT-04.56); or a prompt is still open when the time limit ends (INT-04.18); or a vault the request uses locks (INT-04.29) | error 22; nothing made or stored |
| existing entry without a passkey | passes the verification | the passkey is stored into the entry (INT-04.6); its title, user name, password and URL stay |
| existing entry with a passkey | Replace (MI04-11) at the overwrite question MI04-01, then passes the verification | the new passkey replaces the old one (INT-04.6) |
| existing entry with a passkey | Cancel at MI04-01 | error 22; the entry unchanged; no verification asked |

When the user answers Cancel to the overwrite question, the reference still sends the new credential to the site although nothing was stored, so the site believes a passkey exists. Larsal replies error 22 instead (decided by default, D-INT04-5). The choices of Larsal's old dialog (Register, Pick an entry…, Replace, Add another; INT-04.45, withdrawn) have no counterpart: the user chose the place in the extension's frame. Cancel at the group question sends the new entry to INT-02's default login group (INT-04.24); when that group may not be used (INT-04.20's group checks), at the question or when INT-04.57 checks it again after the verification, the reply is error 22, and nothing is made or asked after it. A target entry that gained a passkey while the prompts showed, so that no MI04-01 asked for it, and an id of `excludeCredentials` that arrived meanwhile end the request the same way after the verification: error 22, nothing stored and no new prompt (INT-04.57, review R5-02).

INT-04.24 **Group for a new entry** (R04-1 rewrite). The group is the target's G (INT-04.20): the group of the entry the save frame offers in "Add to", which its "New entry" line names (INT-11.38). Without G, it is Larsal's default "Browser Passkeys" (decided by default, D-INT04-12): the path `Browser Passkeys` by the path rules below, so the first group directly under the root whose name is exactly that. The reference's default is the name `4B 65 65 50 61 73 73 58 43 2D 42 72 6F 77 73 65 72 20 50 61 73 73 6B 65 79 73` (stored encoded, name rule), which Larsal never writes.
- G given: use it, no question; INT-04.20 has checked it.
- Default found: use it, no question, when it passes INT-04.20's group checks (INT-04.19 step 6); else error 18.
- Default missing: the new group would take the root's resolved `BrowserRestrictKey` (MOD-02.17), so step 6 checks the root's: when the page may not use it, error 18 and no question. Else INT-02's create-group question MI02-08 (INT-02.26, SI-12), at step 8 of INT-04.19, before the verification. Create: the group "Browser Passkeys" is made directly under the root with a new random id, the group custom data `BrowserHideEntry` = `false` (FMT-14) and icon 13. Cancel, or no answer within 60 seconds (INT-01.45): the entry goes to INT-02's default group for new logins (INT-02.26: the first group named "Browser Sign-ins" in tree order outside the recycle bin), which is made under the root without a question when missing; when it exists and fails INT-04.20's group checks, the reply is error 22 and nothing is made (INT-04.23), and INT-04.57 checks it again after the verification (review R4-06).
- Path rules (INT-02.26's `groups.create` reads paths by them): relative to the root, `/` separates levels, a leading or trailing `/` is optional, names match exactly (case-sensitive), and the first match in tree order wins. Since R04-1 a passkey request names no path: its target names a group by its id.
- Groups are made only when the passkey is stored (INT-04.19 step 11), so a request that ends before makes none (R04-1 rewrite: the verification now comes after the question).
- Installed 2.7.11 creates missing groups in the current vault even when another vault was chosen, so the passkey then lands in the chosen vault's default login group (differs in installed version).
- The locked save frame's "New entry / In Banking", the group of the PayPal entry it offers in "Add to", is what Larsal does (D-INT11-4, settled by ruling R04-1 (1) and (2)).

INT-04.25 **Key pair.** Made only after the user verification passed (INT-04.56), from larsal-crypto's random source.

The reference drops leading zero bytes, so about 1 key in 128 gets a 31-byte coordinate (from the source and its crypto library's number encoding, not run: check with Verify, V-INT04-1).
- EdDSA: a random 32-byte Ed25519 seed.
- RS256: a 2048-bit RSA key with public exponent 65537 (D-INT04-2).

INT-04.26 **Credential id.** 32 random bytes. Stored and sent as 43 base64url characters without padding.

INT-04.29 **One prompt at a time, and lock.** Larsal's passkey prompts (the notice MI04-02, the vault picker, the overwrite question MI04-01, the group question, and INT-04.56's Touch ID sheet and verify panel) are bridge dialogs and share INT-02.15's line: a passkey request that arrives while any bridge dialog shows waits its turn, at most 4 waiting requests per session and 16 in all; beyond that: boxed error 42 (INT-01.44). A request takes a turn only when it has a prompt to show, and keeps it from its first prompt to its last, so its prompts never mix with another request's; a request that ends before its first prompt (a failed check of INT-04.19 steps 1 to 3 and 6, or of INT-04.40 steps 1 to 5) replies at once and never waits. For a target that names the vault, step 6 thus runs before step 4, so its error 18 or 23 comes before the exclude notice (INT-04.19, review R4-07, T98); for a target that names no vault, the vault is known only at step 5, after the exclude check. Its time limit (INT-04.18) starts when its first prompt shows.

### Byte layouts

INT-04.30 **Client data.** UTF-8 bytes of exactly this text, with no spaces and members in this order:
`{"type":"‹T›","challenge":"‹C›","origin":"‹O›","crossOrigin":false}`
‹T› is `webauthn.create` for registration and `webauthn.get` for authentication. ‹C› is the `challenge` text and ‹O› the `origin` text, both exactly as received. The reference inserts them without JSON escaping; Larsal's checks (INT-04.9, INT-04.12) make escaping unnecessary.

INT-04.31 **RP ID hash.** SHA-256 of the UTF-8 bytes of the RP ID (INT-04.11). `example.com` gives `A3 79 A6 F6 EE AF B9 A5 5E 37 8C 11 80 34 E2 75 1E 68 2F AB 9F 2D 30 AB 13 D2 12 55 86 CE 19 47`.

INT-04.32 **Authenticator data.**

| Offset | Bytes | Field |
|---|---|---|
| 0 | 32 | RP ID hash (INT-04.31) |
| 32 | 1 | flags (INT-04.33) |
| 33 | 4 | signature counter, big-endian, always `00 00 00 00` |
| 37 | 16 | AAGUID (registration only, INT-04.34) |
| 53 | 2 | credential id length, big-endian: `00 20` |
| 55 | 32 | credential id bytes |
| 87 | 77, 42 or 271 | COSE public key (INT-04.35) |
| end | rest | extension data, only when flag ED is set (INT-04.36) |

Total without extensions: registration 164 bytes (ES256), 129 (EdDSA), 358 (RS256); authentication 37.

INT-04.33 **Flags** (R04-1 rewrite, 2026-11-23; LD-381). Bits: UP `01`, UV `04`, BE `08`, BS `10`, AT `40`, ED `80`. WebAuthn Level 3 §6.1: "The UP flag SHALL be set if and only if the authenticator performed a test of user presence. The UV flag SHALL be set if and only if the authenticator performed user verification." Larsal sets UP and UV only after INT-04.56's verification passed: a fingerprint (Touch ID) or the vault's password, checked in Rust, is user verification, and the touch or the typing is also a test of user presence. A click in the extension's frame is user presence only, never user verification, and Larsal makes and uses no key on a click alone: every response it sends comes after that check passed, so it has UP and UV set, and both are true. BE and BS: registration sets both (INT-04.6 step 3); authentication reads the entry's stored flags (INT-04.5: a missing field is clear, D-INT04-19). BE clear with BS set is a combination WebAuthn does not allow (§6.1.3: "This combination is not allowed."): Larsal does not sign and replies error 31, as INT-04.E24.07 refuses it for E24. AT is set only in registration. ED is never set (INT-04.36).

| Case | Flags |
|---|---|
| registration | `5D` |
| authentication, both backup flags set (INT-04.5) | `1D` |
| authentication, BE set, BS clear | `0D` |
| authentication, BE clear, BS set | none: error 31, nothing signed |
| authentication, both clear, or both fields missing (INT-04.5) | `05` |
| installed 2.7.11: registration / authentication | `45` (`C5`) / `05` (`85`) |

What R04-1 changed in the bytes (the ruling's point 6): `5D`, `1D`, `0D` and `05` keep their values, but each now stands for a passed verification, so the old cases that show them (T09, T31, T32, T46, T55, T56, T57) prove this rule only when run again under it. Gone from Larsal's rows: `DD`, `9D`, `8D` and `85` (no extension data, INT-04.17), which changes T52, and `15` (BS without BE, now error 31, T90). T08 changes from `1D` to `05`, because its entry has no flag fields and a missing field is now clear (INT-04.5, D-INT04-19); T94 is new, and so is T104, where a passkey that FEA-08.47 imported signs with `1D` (review R5-01).

INT-04.34 **AAGUID.** The reference sends its own registered AAGUID `FD B1 41 B2 5D 84 44 3E 8A 35 46 98 C2 05 A5 02`. Larsal never sends it. Larsal sends its own fixed AAGUID `75 8D 40 80 A2 83 44 BA BC 65 8D 03 9D 85 27 32` (UUID 758d4080-a283-44ba-bc65-8d039d852732; lead decision D-INT04-1).

INT-04.35 **COSE public key** (CBOR map, keys in this order, shortest integer forms).

| Algorithm | Bytes | Length |
|---|---|---|
| ES256 | `A5 01 02 03 26 20 01 21 58 20` ‹x, 32 bytes› `22 58 20` ‹y, 32 bytes› (kty 2 EC2, alg -7, crv 1 P-256) | 77 |
| EdDSA | `A4 01 01 03 27 20 06 21 58 20` ‹public key, 32 bytes› (kty 1 OKP, alg -8, crv 6 Ed25519) | 42 |
| RS256 | `A4 01 03 03 39 01 00 20 59 01 00` ‹modulus, 256 bytes› `21 43 01 00 01` (kty 3 RSA, alg -257, n, e) | 271 |

INT-04.36 **Extension data.** Larsal writes none and never sets ED (R04-1 rewrite: before it, Larsal wrote the `uvm` map `A1 63 75 76 6D 81 83 01 01 01` when `uvm` was `true`; INT-04.17 now drops `uvm`). The reference also puts `credProps` there: its map holds one pair per member left after its filter (`credProps` and `uvm`), `credProps` first (`69 63 72 65 64 50 72 6F 70 73 A1 62 72 6B F5`, "credProps" → {"rk": true}), then `uvm`; it writes nothing when neither is `true`. WebAuthn defines `credProps` as a client-only result, so Larsal keeps it out of the authenticator data (decided by default, D-INT04-4). The reference's map header counts members, not written pairs, so `{"credProps": true, "uvm": false}` gives a malformed map (from the source, not run: check with Verify, V-INT04-5).

INT-04.37 **Attestation object.** The CBOR map `A3 63 66 6D 74 64 6E 6F 6E 65 67 61 74 74 53 74 6D 74 A0 68 61 75 74 68 44 61 74 61` ("fmt" → "none", "attStmt" → {}, "authData" →), then the authenticator data as a CBOR byte string: header `58 A4` for 164 bytes, `58 81` for 129, `59 01 66` for 358 (`58 nn` below 256 bytes, `59 nn nn` from 256). Size: 30 + the authenticator data for lengths 24 to 255.

INT-04.38 **Signature** (authentication only). The message is the authenticator data followed by the SHA-256 of the client data bytes. ES256: ECDSA on P-256 with SHA-256, encoded as a DER sequence of r and s. RS256: RSASSA-PKCS1-v1_5 with SHA-256, 256 bytes. EdDSA: Ed25519 over the message itself (not pre-hashed), 64 bytes. The reference's ECDSA signatures are deterministic (RFC 6979); a site only verifies, so any valid signature is correct.

INT-04.39 **Base64url.** Everything Larsal sends in binary form is base64url (RFC 4648 section 5) without padding: credential ids, client data, authenticator data, attestation object, signature, public key.

### Authentication

INT-04.40 **Order of steps** (R04-1 rewrite, 2026-11-23). The user already chose an entry and Continue in the extension's frame (INT-11.38). Larsal then:
1. Bridge checks (INT-01), `public_key` present (24), origin gate (25).
2. A usable vault (INT-02.10) exists; INT-01.30 answers error 8 or 1 before this step. The reference needs its current vault unlocked and sends error 1 inside `response`.
3. Effective domain (26, 27), RP ID (28), challenge (Larsal only, 32), extensions, verification, time limit.
4. The chosen entry and the allowed list (INT-04.42): error 18 or 15.
5. The chosen entry's vault must be able to verify the user (INT-04.56 step 3): error 23, and no prompt shows.
6. User verification (INT-04.56): error 22 when it does not pass.
7. Check steps 4 and 5 again on the vault as it is now (INT-04.57): their error, 18, 15 or 23, and nothing is signed. Then sign with the chosen entry: read its private key, id (INT-04.4), user handle and backup flags (INT-04.5). BE clear with BS set (INT-04.33), or a key that cannot sign (INT-04.3): error 31. Otherwise build the authenticator data and the signature and reply (INT-04.43).

INT-04.41 **Candidate entries** (used by INT-04.21 and INT-04.42).
- Vaults: the usable vaults of INT-02.10 (the shown vault, or with S-BRW-14 on every unlocked vault, holding the session's proven identification key, INT-01.28; none behind MOD-13's forced prompt), in the order they are open.
- Groups in tree order (pre-order from the root, children in their stored order); vaults in the order they are open. Groups in the recycle bin, groups hidden from the browser, and groups restricted to an association that is not among the matching ones are skipped (INT-02, SI-04).
- Entries in group order; recycled entries and entries hidden from the browser are skipped (INT-02).
- The entry must have a passkey (INT-04.2) and its `KPEX_PASSKEY_RELYING_PARTY` must equal the RP ID exactly. There is no parent-domain fallback.
- Expired entries are candidates, so the exclude list (INT-04.21) still finds the credentials they hold. To sign, the chosen entry must also pass INT-02.13 (INT-04.42), so an expired entry signs only with S-BRW-13 on, as for password fill (SI-04). R04-1 changed this, because the extension lists passkeys from `logins.find`, which leaves expired entries out (INT-02.13 step 6), and Larsal checks the chosen entry the same way.
- No site-access question (SI-02) and no remembered allow: Larsal's verification (INT-04.56) takes their place. A remembered deny (INT-02.17) keeps an entry from signing (INT-02.13 step 7).
- INT-02.20's `passkey` flag uses the same RP match when `logins.find` carries `rp_id` (review R3-10): it is true only for an entry whose `KPEX_PASSKEY_RELYING_PARTY` equals `rp_id` exactly, so an entry that fits the page by its URL but holds a passkey for another RP ID is no sign-in row (INT-11.38, T103).

INT-04.42 **The chosen entry and the allowed list** (R04-1 rewrite). `entry` is the row the user chose in the extension's frame (INT-11.38). Larsal checks it before any prompt:
- `entry` must be a JSON object `{"vault": V, "id": E}`, both members texts of the right form (a wrong type is error 18, as in INT-04.20): V the vault id (INT-01.31) of a usable vault (INT-02.10), E the entry id (32 lowercase hex digits) of an entry of V that is a candidate (INT-04.41) and that INT-02.13 keeps for the page (the request's `origin` as the page URL, `http_auth` false). Anything else, a missing `entry` too: boxed error 18 (INT-01.40), and nothing shows.
- An item of `allowCredentials` is accepted when its `type` is `public-key`, its `id` is not empty, and `transports` is missing, empty, or holds `internal`, `nfc` or `usb`.
- Items given but none accepted: error 15.
- Some accepted: the chosen entry's id (INT-04.4) must equal an accepted id, else error 15.
- `allowCredentials` missing or empty: the chosen entry must have the `KPEX_PASSKEY_USER_HANDLE` field (any value), else error 15.
The extension cannot see credential ids, which are protected (SF-09), so it lists every entry whose summary from `logins.find` with the request's RP ID (`rp_id`) has `passkey` true (INT-02.20, INT-04.41, INT-11.38, D-INT11-6). A chosen entry that the site's list does not allow gets error 15, and the browser's own flow runs (INT-11.21).

| `authenticatorAttachment` | always `platform` |

INT-04.44 **No change on use.** Signing changes nothing in the vault's data: no field, no modification time, no history item, no usage count. The counter stays 0. The only write is INT-02.9's last-use record (a sign-in records it like a registration), a view-state change that does not mark the vault changed. The reference records no use.

### User verification

INT-04.56 **User verification** (R04-1, ruled 2026-11-23; W3C WebAuthn Level 3, the terms "User Present" and "User Verified" and §6.3.2 step 6; FIDO CTAP 2.2 §6.1, the options `up` and `uv`). Every passkey request, after its checks and questions (INT-04.19 steps 1 to 8, INT-04.40 steps 1 to 5), verifies the user in Larsal before any key is made or used. Nothing is made, stored or signed before the verification passes and INT-04.57's checks pass again, and each request verifies anew: no grace period, nothing remembered. The click on Save Passkey or Continue in the extension's frame (INT-11.38) is user presence only, never user verification. The vault is the target's (INT-04.20) or the chosen entry's (INT-04.42): that vault's slot and that vault's password verify, never another open vault's.
1. **Touch ID**, when quick unlock is available (APP-04.1; it needs E6-S3's signed build), the vault has a slot (APP-04.3) whose item carries the biometry constraint (APP-04.5; a watch-only item does not count), and biometry can be evaluated now. Only a fingerprint counts; an Apple Watch approval and the Mac's login password do not (decided by default, D-INT04-18). After APP-04.7's check of the biometry state, Larsal evaluates the biometry-only policy `LAPolicy.deviceOwnerAuthenticationWithBiometrics` with the reason MI04-37 (sign-in) or MI04-38 (save), which names only the RP ID, then reads the slot's Keychain item with that same evaluated context (`kSecUseAuthenticationContext`), so macOS asks once and never offers the item's watch branch. The context is this attempt's own and is dropped after the read, so APP-04.11's rule against an earlier context holds. Rust decrypts the slot's memory part with the item's `W`, which passes only when the tag checks (APP-04.12), and wipes `W` and the plain parts at once; no hardware key is asked, no KDF runs and nothing opens. The tag checks: verified, and no Larsal panel shows. The sheet cancelled, its fallback button (`userFallback`), Touch ID failed, or Touch ID not usable right now (APP-04.13; APP-04.14, second row): the slot stays and step 2 follows. The item missing or invalidated, the biometry state changed, or the tag wrong (APP-04.7; APP-04.14, first row): the slot is deleted and step 2 follows with `MSG-QU-GONE` in the panel's error line.
2. **The vault's password**: the unlock panel in its verify use (APP-06.31) for the vault, with the purpose line MI04-39 (sign-in) or MI04-40 (save). It asks for the password only (D-INT04-20). Rust adds the key file part kept since unlock (FMT-04.17; the file is not read again) and, for a vault that uses a hardware key, a fresh answer from the kept slot, and checks the result against the header of the vault file Larsal last opened or saved (APP-06.31), as an unlock checks a file: every attempt costs one KDF run, and the password part kept for saving is never compared. A match: verified. A wrong password keeps the panel open with M06-06.
3. **No way to verify**, decided as soon as the vault is known, before any question (INT-04.19 step 6, INT-04.40 step 5). A vault whose credentials hold no password, or only the empty one (APP-06.12: a key file or a hardware key alone, or the blank password), and that has no usable slot cannot verify the user: error 23, and no prompt shows. For a registration whose `userVerification` is `required` this is WebAuthn's own rule (Level 3 §6.3.2 step 5: "If requireUserVerification is true and the authenticator cannot perform user verification", the authenticator returns "ConstraintError"); §6.3.3, the sign-in, has no such step (its step 7 asks for a gesture that includes user verification when `requireUserVerification` is true). Error 23 for every other request, a registration with `preferred` or `discouraged` and every sign-in, is Larsal's own stricter rule from ruling R04-1 (3): Larsal never makes or uses a key without verifying the user (review R3-03). The same holds from a change of the vault's credentials until the vault is saved (MOD-12.10 step 8): the slot is gone, and APP-06.31 has no header made with the new credentials to check against, so error 23. With a slot, every outcome of step 1 but a pass (a cancel, a failure, a slot deleted) ends a request for a vault without a password with error 22, because it has no step 2.
4. Cancel, Escape or closing the panel, the time limit (INT-04.18), or a lock (INT-04.29): error 22; nothing made, stored or signed.
Only a passed verification sets UP and UV (INT-04.33). A key file or a hardware key alone is something the user has, not user verification ("a touch plus pin code, password entry, or biometric recognition", Level 3, term "User Verification"), which is why step 3 does not accept them and step 2 asks for the password; the key file part and the hardware key answer only rebuild the vault's key for the check.

INT-04.57 **Checks again after the prompts** (reviews R3-06, R4-06 and R5-02, 2026-11-23). While a request's prompts show, the vault can change: the user can recycle, delete or move the target entry, the chosen entry or a group, change a group's browser options, change the vault's credentials (MOD-12.10), give the target entry a passkey, or add a passkey whose id `excludeCredentials` names, in Larsal's own windows or through a merge (MOD-11). So after the last prompt, before any key is made or used, Larsal checks again on the vault as it is then: for a registration INT-04.19 step 3 (INT-04.20's target: error 18), step 4 (INT-04.21's exclude list in every usable vault: an id that a candidate answers with now gives error 22, not 21, and no notice; review R5-02, T101), step 6 (INT-04.24's default group: error 18; the vault able to verify the user, INT-04.56 step 3: error 23, for example after a credential change not saved yet) and step 7 (a target entry that has a passkey now, INT-04.2, while this request asked no MI04-01 for it: error 22, and no question; review R5-02, T101), and after a Cancel at the group question the group INT-04.24 then chose (INT-02.26's "Browser Sign-ins" by INT-04.20's group checks, or, while it does not exist, the root's `BrowserRestrictKey` that it would take: error 22, as INT-04.23 says; review R4-06, T101); for a sign-in INT-04.40 step 4 (INT-04.42's chosen entry and allowed list: error 18 or 15) and step 5 (error 23). The first failure is the reply; nothing is made, stored or signed, and no prompt shows again. These checks and the store or the signature that follows them run as one step of the core, so nothing can change the vault between them. A change that the checks still allow changes nothing: a target entry moved to another group the page may use still gets the passkey (T101).

## Edge cases and errors

- **Passkey and password in one entry.** Allowed. Password fill and passkey use are independent; the RP field also makes the entry match the RP's site for password fill (INT-04.8).
- **Several passkeys for one site and account.** "New entry" in the extension's frame makes another entry with the same RP and user handle (INT-04.23). The extension lists both at sign-in (INT-11.38); with an `allowCredentials` list only the listed id signs, and the other gets error 15 (INT-04.42).
- **Field present, value empty.** An empty user handle field still makes the entry discoverable (INT-04.42); the reply carries an empty `userHandle`. An empty private key gives error 31 at signing.
- **Foreign id field.** An entry with `KPEX_PASSKEY_GENERATED_USER_ID` answers with that id everywhere (INT-04.4), also in exports.
- **Hostile vault.** Passkey fields are data. A malformed PEM, a huge PEM (bounded by FMT limits) or an unknown key type gives error 31 at signing; nothing crashes, and nothing about the key is logged.
- **RP ID with a different case in a stored entry** (for example `Example.com` from an import): it never matches Larsal's lower-case RP ID (INT-04.41); the user must fix the field.
- **Origin on a port** (`https://example.com:8443`): the effective domain is `example.com`; the client data holds the full origin with its port.
- **Time limit and site timeout.** The site may give up before the user verifies; Larsal still stores a passkey verified within its own time limit (INT-04.18), and the site never learns of it. Same in the reference.
- **No Touch ID yet.** Until E6-S3's signed build, quick unlock is never available (APP-04.1), so every passkey request asks for the vault's password (INT-04.56 step 2). After it, so does every request for a vault without a slot, and every request on a Mac whose Touch ID cannot be used right now, a Mac with only an Apple Watch included (D-INT04-18). The sign-in frame's locked line MI11-82 ("Larsal confirms with Touch ID before it signs in.") names Touch ID all the same: lead decision D-INT11-5.
- **Parent, sibling and other ports.** A passkey for the RP ID `example.com` is offered and signs at `https://example.com` and at every subdomain, also at one other than the origin it was made at: the RP field is one of the entry's URLs (INT-03.2 step 3, INT-04.8), read as `https://example.com` (INT-03.3), which fits that host and its subdomains (INT-03.7). Larsal is narrower than WebAuthn, which ignores ports: at `https://example.com:8443` only an entry with a URL that names that port fits (INT-03.6), so a passkey made on port 443 is not listed there and a request that names it gets error 18; the user can add the URL with its port to the entry (T93).
- **Two accounts on one site.** At registration the save frame's "Add to" offers the summary whose user name equals the site's `user.name` exactly, checked; with no such summary it offers the first one, not checked, and New entry is checked (INT-11.38, review R3-09). At sign-in the frame lists every entry that fits the page and holds a passkey for the request's RP ID (`rp_id`, INT-04.41), the first one selected; it cannot tell which one the site's `allowCredentials` allows (credential ids are protected, SF-09, and Larsal marks no row, D-INT11-6), so a row the list does not allow gets error 15 after Continue, before any verification, and the browser's own flow runs (INT-04.42, INT-11.21).
- **A vault without a password.** A vault opened with only a key file or a hardware key verifies only with Touch ID; without a slot its passkey requests get error 23 before any question (INT-04.56 step 3, INT-04.19 step 6), and the extension falls back to the browser's own flow (INT-11.21).
- **Credentials changed, not saved yet.** From a change of a vault's credentials until its save, its passkey requests get error 23 before any question (INT-04.56 step 3); after the save, the new password verifies (T99).
- **Conditional requests** (review R3-01; INT-11.21, D-INT11-7). A `get` with `mediation` `conditional` reaches Larsal only when the user picks a passkey pill in the extension's fill menu (INT-11.31): it is then a `passkey.get` like any other, with the picked entry, and Larsal verifies the user as INT-04.56 says. Before that pick only `logins.find`, with the call's `rp_id`, reaches Larsal, and nothing goes back to the page; the menu's host shows with one size whatever it holds, also before Larsal answers and with no match (INT-11.31, reviews R4-01 and R5-04). A `create` with `mediation` `conditional` comes as a modal one, after Save Passkey; its response has UP and UV set, which WebAuthn allows (Level 3 §5.1.3: the client sets both to false for a conditional create "unless they may be explicitly performed during the ceremony"; §7.1 step 15 checks UP only when `mediation` is not `conditional`). Larsal never sees `mediation`: `public_key` holds only the page's `publicKey` options (INT-11.21). Until E7-S7i lands, no page script exists, and the browser answers every call.
- **The vault changes while a prompt shows** (reviews R3-06 and R5-02). The target, the chosen entry, their groups, the group a Cancel at the group question chose, the vault's credentials, the exclude list and the overwrite question are checked again after the last prompt (INT-04.57): an entry recycled, deleted or moved where the page may not use it, a group recycled or hidden, or credentials changed and not saved gives the card's error (error 22 for the group a Cancel chose, review R4-06, and for a target entry that gained a passkey or an id of `excludeCredentials` that arrived, for example through a merge, MOD-11, review R5-02), and nothing is made, stored or signed; no question or notice shows after the verification.
- **The JSON import's `b64.` ids** (FEA-08.47): the reference keeps only the hex digits and decodes them, which gives a wrong id for ids in the `b64.` + base64url form (V-INT04-7). FEA-08 owns the fix.
- **Not on Mac.** On Windows and Linux the reference lowers its window after a prompt (or hides it again when it was hidden), instead of reactivating the previous app; on Linux and Windows it brings the window to the front only when forced.

## Security notes

- **Private keys never leave Larsal over the bridge.** Only the public key, the credential id, the user handle and the signature go out (SI-05). Private keys, user handles and credential ids are stored protected (SF-09). They are never logged, never put in an error text, and never sent to the screen; the screen only shows RP and user name (INT-04.51, AGENTS rule 4).
- **Every use needs the user, twice.** A click in the extension's frame that passed INT-11.18's checks (user presence), then Larsal's own verification, a fingerprint or the vault's password, checked in Rust (INT-04.56). There is no remembered consent, no grace period and no "always allow" (SI-05). A lock closes the prompt (INT-04.29, SR-16), and the entry, its group, the vault, the exclude list and the overwrite question are checked again after the last prompt (INT-04.57).
- **Wrong site (AT-F08).** The RP ID comes from the extension's origin and must be the origin's host or a registrable parent of it (INT-04.11), so `evil.example` cannot ask for `example.com` (error 28), and lookalike or punycode hosts get different RP IDs with no matching entries (error 15). Entries match by exact RP field, never by parent domain (INT-04.41). Plain http is refused (error 25) unless the user turned on S-BRW-19, and then only for localhost.
- **Subdomains.** The RP ID's host and any subdomain of it may use the RP's passkeys; WebAuthn intends this. In Larsal the chosen entry must also fit the page (INT-02.13, INT-04.42); it does at every such host through its RP field (INT-03.2 step 3, INT-04.8), whatever origin it was made at, but on a port other than the scheme's default only through an entry URL that names that port (INT-03.6): narrower than WebAuthn, and it fails closed (Edge cases). The public suffix list keeps tenants of shared hosting suffixes apart (INT-04.11 steps 5 to 8).
- **The origin is only as trustworthy as the extension.** Larsal cannot check it. The association (SI-01, INT-02) is the trust boundary; a compromised associated extension can request a passkey for any site and name any entry, still behind Larsal's verification, whose prompt names the RP ID (INT-04.56); Larsal signs only with an entry whose RP field equals the RP ID and that INT-02.13 keeps for the origin (INT-04.42).
- **What the flags claim.** UP and UV are set only after INT-04.56's verification passed in Rust, so a site's reading "the user was verified" is true; a click alone never sets UV (R04-1, LD-381). BE is fixed when a passkey is registered (Level 3 §6.1, §6.1.3), so Larsal sends it as the passkey was registered: set for the passkeys it makes and for both imports, a `.passkey` file's and FEA-08.47's, whose passkeys come from another manager's vault and live on in Larsal's, so they are multi-device credentials (review R5-01), and clear for an entry without the field, such as one that installed 2.7.11 registered (INT-04.5, D-INT04-19). An entry without the field can also hold a passkey that another app imported, such as one from the reference's Bitwarden import, which writes no flag fields; it signs with BE clear though its maker may have registered it with BE set, a known limit (INT-04.5, D-INT04-19, review R6-01). BS says the credential is backed up: it "may become present on an authenticator other than" the one that made it, and "Backup can occur via mechanisms including but not limited to peer-to-peer sync, cloud sync, local network sync, and manual import/export" (Level 3, term "Backed Up"). A Larsal passkey lives in a vault file that Larsal copies before each save (APP-05.19, on by default), that can sync and merge, and whose passkeys can be exported (INT-04.50); Bitwarden sets both flags for the same reason ("Credentials are always synced"). A stored BS without BE is refused (INT-04.33). Larsal sends no extension data (INT-04.36). The counter is always 0, so a site cannot detect a copied vault.
- **Leftover copies.** Replacing or removing a passkey can leave older private keys in history items (MOD-03); deleting history removes them. Exported `.passkey` files hold the private key in plain text: Larsal warns (SD-07) and writes them owner-only (SD-09).
- **Probing.** The exclude list must not answer silently (INT-04.21): only the user's OK tells the site that a credential is here; a closed notice answers like any cancel, and so does an excluded id that arrives while the prompts show (INT-04.57). Before the user acts, the page learns nothing of the vault from the extension's frames either: whether a frame shows, and its size, do not depend on what the vault holds (INT-11.38, D-INT11-7); a conditional sign-in shows Larsal's passkeys only as pills inside the fill menu, whose host shows on every click with one size whatever it holds, also before Larsal answers and with no match (INT-11.31, reviews R4-01 and R5-04), and Larsal's answer reaches the page only after the user picked a pill (INT-11.21); and error 15, 18 or 23 can come only after the user's Save Passkey, Continue or pill pick, when the browser's own flow then runs as it does after Use another device, or, for a conditional sign-in, goes on as it was.
- **Who chooses the entry.** The extension names it and Larsal checks it again (INT-04.20, INT-04.42): an entry of another site, one hidden from the browser or in the recycle bin, a group for a new entry that is hidden, in the recycle bin or restricted to another browser, or anything in a vault the browser may not use gets error 18, and nothing shows (AT-F08).
- **Parsing.** The bridge message is bounded (SI-01). Import files are bounded (INT-04.47). PEM and DER parsing goes through larsal-crypto's approved crates and never panics. Key bytes are wiped after each signature (SR-07).
- **Signing.** Only the approved crates sign (`p256`, `ed25519-dalek`, and an RSA crate only if D-INT04-2 adds one). Each signature is computed only after INT-04.56's verification passed, over client data Larsal built itself.

## E24-S1 proposed extension — 2026-11-05

Status: DRAFT, unadopted. Builds E24-S4/S5/S6; full order and capability map in [research](../research/passkeys-and-ssh.md). This appendix changes none of the preceding implemented requirements, IDs, T01–T82 or historical evidence. Where proposed behavior conflicts, Lead must explicitly amend the old clauses before implementation; proposed conflict aftertexts are outside this tree. Source links P01–P17 are primary reads dated 2026-11-05, with release/draft status and custody gates stated there. All cases below are new, unrun obligations.

### E24 proposed rules

INT-04.E24.01 **Platform capability.** The native provider accepts create/get requests on macOS 14.0 or later, after user enablement and a signed build. Exchange separately requires macOS 26.0 or later. Intel and Apple silicon targets use the same contract; platform/device success is unproved. Older OS, missing entitlement, disabled provider, unavailable account and unsupported request return an explicit unavailable/error state, never a browser fallback labelled native success. D7/W-02 gate S4, not S1. Source: [P02](../research/passkeys-and-ssh.md#p02).

INT-04.E24.02 **Signed target.** Use a distinct embedded credential-provider extension, the extension point and both-app/extension AutoFill entitlement of P03. Enable sandbox on extension; reuse the existing team-qualified E7 group relay with a distinct endpoint, matching app-group entitlement on each participant. Set ProvidesPasskeys=true in the credential-provider capability dictionaries of both the host app and its extension; provide extension configuration UI. Do not add associated domains for every credential site, private key access groups or general network entitlements. Provisioned identifiers/profile, exact bundle signing and distributed-route eligibility require G01; enabling a plist flag alone is insufficient. Source: [P03](../research/passkeys-and-ssh.md#p03).

INT-04.E24.03 **Enablement and suggestions.** Settings shows Enable in System Settings as an explicit user action and distinguishes disabled, enabled, locked and unavailable. Publish identities only from eligible unlocked vaults with browser visibility restrictions honored; no private key in identity store. Remove identities on lock/close/remove/replacement/feature-off and rebuild only after unlock. OS cache retention and purge latency are OPEN measurements; locked stale suggestions never produce a credential or label leaks from Larsal. Source: [P05](../research/passkeys-and-ssh.md#p05).

INT-04.E24.04 **Rust boundary and relay.** Reuse E7 local authenticated transport/owner-only group socket and existing session ownership, with a provider purpose distinct from browser association. Check peer code/team identity, same user, bounded authenticated request ID and fresh vault generation. Swift controller receives view data and opaque request/entry handles only; no master key, private key, passphrase or raw protected entry field. The Rust-held vault is authoritative; no decrypted app-group file or Keychain mirror. Missing verified transport is an implementation gate, never permission to serialize secrets in Swift. Source: [P04](../research/passkeys-and-ssh.md#p04).

INT-04.E24.05 **Trusted native request.** Use ASPasskeyCredentialRequest/Parameters from the OS. Bind RP ID, clientDataHash, user handle, assertion allowed IDs, any OS-supplied registration exclusion list, algorithms and request kind to one operation; assertion allowed IDs are not registration exclusions; do not reconstruct clientDataJSON/origin from a service URL or trust a process-supplied app title. OS validates associated-domain entitlement for native relying apps; Larsal independently applies RP/credential equality and bounds. Service identifiers alone authorize no passkey. Source: [P05](../research/passkeys-and-ssh.md#p05).

INT-04.E24.06 **Choice and matching.** Native picker lists only live non-recycled eligible entries of the bound RP and allowed IDs, comparing canonical decoded bytes for IDs/user handles. Empty allow-list permits discoverable credentials. Display account and vault/group, never credential/user-handle/private bytes. Selecting another entry/vault invalidates a prior selection. Browser E7 association rules remain independent and cannot be bypassed by presenting a native handle. Source: [P01](../research/passkeys-and-ssh.md#p01).

INT-04.E24.07 **Verification and flags.** For each E24 create/get require deliberate consent and fresh Touch ID after E6-S3 signing is available, otherwise a vault-password verification performed in Rust through existing protected input. Failure/cancel signs nothing. An already unlocked vault or confirm click is not fresh verification. UV/UP and BE/BS describe actual ceremony/storage semantics; BS without BE is refused, no invented attestation or extension output. Old .16/.33/.36 and R04-1 conflicts remain UNADOPTED amendments; do not claim their old cases prove this rule. Source: [P01](../research/passkeys-and-ssh.md#p01).

INT-04.E24.08 **Create and commit.** After the required privacy-preserving consent/verification, check registration exclusions against live credentials using the same RP/type and canonical credential-ID bytes. A match prevents generation, overwrite, save and registration success; cancellation must not disclose credential existence. Create a key in approved Rust crypto only if no exclusion matches. Empty or absent exclusions and nonmatching RP/ID cases retain the valid registration success path. Save using existing protected passkey entry layout and writable-vault/group/overwrite validation; never drop unrelated password/code fields. Bind source draft revision and vault generation. Persist with normal atomic save before completing OS registration; save/collision/lock failure yields no success response. Cancellation before commit discards draft. A cancellation arriving after durable commit leaves a clearly reported saved credential, never deletes an unacknowledged key silently. Source: [P01](../research/passkeys-and-ssh.md#p01).

INT-04.E24.09 **Assertion and lifecycle.** An assertion performs no credential-key/counter mutation beyond existing allowed view-state use record. Capture request/entry/key revisions and vault generation; recheck before signing and immediately before response handoff. Lock request, sleep, user switch, close, replacement, delete, provider disable, session loss, OS cancellation or deadline revokes queued/in-flight work. Wipe Rust transient buffers; close own UI; no automatic resume/retry after unlock. A response already delivered cannot be recalled. Source: [P05](../research/passkeys-and-ssh.md#p05).

INT-04.E24.10 **Bounds and concurrency.** Inherit E7 message bounds; native envelope and response at most 256 KiB, at most 4 waiting requests per client and 16 overall, one visible ceremony at a time. Proposed native UI deadline: earlier of OS deadline and 60 seconds from admission, including queue; never extend it on a re-render. Validate types/lengths before allocations/crypto. Full queue, unsupported extension/algorithm or malformed values returns bounded error; no cryptographic downgrade or fake extension support. Source: [P01](../research/passkeys-and-ssh.md#p01).

INT-04.E24.11 **OS response custody.** Rust produces only the public WebAuthn registration/assertion outputs needed by ASPasskeyRegistrationCredential/AssertionCredential. OS response can contain credential ID/user handle, signature and public key, never a private key. Bind completion once; account labels/IDs are retained outside Rust only for the operation and cleared on closure. Document OS/accessibility/capture retention; never claim OS object deallocation proves wiping or that a static frame excludes capture. Source: [P05](../research/passkeys-and-ssh.md#p05).

INT-04.E24.12 **Exchange profile.** Implement CXF 1.0 with 2026-03-09 errata, and explicitly record the OS negotiated format version and protected transport. CXF alone is a readable data model; base64/PKCS#8 is not encryption. CXP 1.0 linked by FIDO is a 2024-10-03 working draft; do not label it a final standard or claim Apple wire equivalence without proof. No homemade encryption, archive scheme or readable legacy export is an E24 exchange fallback. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.13 **Exchange API and availability.** For supported macOS 26+ use ASCredentialExportManager requestExport(for:) then exportCredentials(_:); receive the exported exchange-activity value (P08 documents the article/SDK symbol-name mismatch) with ASCredentialImportToken UUID and call ASCredentialImportManager.importCredentials(token:). Configure SupportsCredentialExchange and SupportedCredentialExchangeVersions=["1.0"] plus NSUserActivityTypes as P08 states. Recheck version and selected target, reject stale/replayed/wrong-recipient tokens. API/entitlement runtime failure leaves the feature unavailable with a retry path; no unsupported-platform PASS. Source: [P08](../research/passkeys-and-ssh.md#p08).

INT-04.E24.14 **Selection and authorization.** Before migration show eligible selected sites/accounts and destination provider, warn that the recipient can use and retain the keys, and require fresh verification for this exact export/import. Bind receiver identity from OS chooser, selection IDs/revisions, vault and generation; do not trust a supplied display name as receiver identity. Cancel is default. Unselected/hidden/recycled/history credentials never ride along; importer chooses writable vault/group explicitly. Source: [P08](../research/passkeys-and-ssh.md#p08).

INT-04.E24.15 **Lossless passkey mapping.** Map CXF RP, credential ID, handle and key exactly to existing protected fields through Rust; PKCS#8 DER converts only in Rust to the established protected representation. Keep username/display name distinct using Larsal metadata if necessary (G02 schema review); URL is not RP authority. Preserve supported FIDO2 extension state losslessly and scoped to the same credential. Unknown optional data is ignored only as CXF permits and disclosed if it prevents lossless round trip; required unsupported state blocks that item and cannot pass its migration case. No key/RP/id edits to make a rejected key appear compatible. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.16 **Hostile import transaction.** Treat decrypted exchange data as hostile input even after OS transport succeeds. Use bounded secret-aware Rust parsing, not larsal-model JSON's public-data path. Proposed cap 16 MiB total decoded credential metadata/private-key data, 10,000 selected credentials, nesting 32 and 1 MiB per key; check before allocation/KDF/DER work and surface documented limits. Validate every selected passkey, RP/id/handle types, key/public consistency, version and allowed algorithm; unknown non-passkey items are excluded with count. Broken selected input fails the entire staged batch with nothing saved; no path writes, URL execution or network fetch from data. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.17 **Duplicate and conflict policy.** Identity is (RP ID, credential-ID bytes). Same identity and same key/handle is a duplicate: preserve existing entry and report skipped count. Same identity with different key or handle fails the entire selected import; never overwrite. Different credential ID for same RP/account is a distinct passkey and can be added. Recheck concurrent revisions at commit; changed vault/target restarts review, never last-writer-wins. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.18 **Imported success.** Import commits all validated new items through existing atomic vault save before publishing native/extension identities or reporting success. Imported counters are zero and never incremented. Complete only when saved; later sign-in through E7 demo pages and native provider must verify with the original relying-party public key. OS transport completion is not import persistence proof. Original provider keeps its copy unless the user separately removes it. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.19 **Export exclusions and completion.** Export only selected live credentials the standard permits. Nonzero-counter/device-bound/non-exportable or unsupported-extension entries have named excluded counts before consent; do not silently omit them. Never rekey, reset a nonzero source counter or export history. No automatic source deletion after success. Receiver acceptance and Larsal durable import result are separate results; errors/rejection are explicit. Required eligible success cases stay OPEN until real peer interoperability. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.20 **Secret custody gate.** Private migration data remains Rust-owned/wipeable inside the protected exchange operation until the precisely identified OS handoff. No private key appears in Swift view/controller state, JS/DOM, ordinary Codable/JSON values, log, crash report, clipboard, readable file or temp. P09 shows a Swift data API, so the bridge/allocation/OS protection review is OPEN; this rule describes required final behavior, not an achieved route. Keep the original single-Show exception unchanged; private passkey export has no Show escape. If no compliant route exists, escalate the acceptance conflict to Lead rather than reducing S5. Source: [P09](../research/passkeys-and-ssh.md#p09).

INT-04.E24.21 **Handoff, cancel and lock.** The first API call that receives readable credential material is the custody boundary, possibly before the OS reports success. Before it, cancellation/lock/revision change prevents handoff and wipes stage. After it, revoke new operations and close own view, request supported cancellation, but disclose that OS/recipient may retain or use delivered data; do not promise recall/secure erasure. Late token/completion callbacks cannot mutate a new/locked vault. The receiving user's local key custody does not give Larsal servers a secret, password hash or offline password verifier (LD-340). Source: [P07](../research/passkeys-and-ssh.md#p07).

INT-04.E24.22 **List and delete everywhere.** Mac app, extension, web vault and larsal CLI list live passkeys with title, RP, account and vault/path; empty/error/locked states explicit. Delete Passkey removes credential data through existing Rust edit/save and confirms what remains; deleting whole entry uses MOD-04. Removal makes no call to the relying site and cannot revoke copies in history/backups/other providers. Purge native identities and invalidate active operations on the removed revision. Web deletion is an E20 encrypted Rust/Wasm edit/save boundary, not an HTTP private-key management API. Source: [P01](../research/passkeys-and-ssh.md#p01).

INT-04.E24.23 **Display and command boundaries.** Proposed CLI commands: larsal passkey list VAULT, larsal passkey show VAULT ENTRY_ID, larsal passkey remove VAULT ENTRY_ID (interactive confirmation or explicit --yes). Show means public metadata, no private/credential-ID/user-handle dump, including --all/--show-protected flags. No private-key export/copy/reveal through generic attributes, attachments, history or web APIs for E24 data. Keep legacy .49/.50/.55 and T73/T81 unchanged as an unadopted conflict requiring explicit Lead amendment and regression checks; they are not permission for a new bypass. Source: [P06](../research/passkeys-and-ssh.md#p06).

INT-04.E24.24 **Keyboard, accessibility and capture.** Use Option A tokens/assets/parts, light/dark, labelled native controls and VoiceOver order. Tab/Shift-Tab reach every actionable element; Escape cancels, Return chooses Cancel in destructive/migration prompts; sign/verify requires deliberate focused activation and never consumes the keystroke that opened the dialog. Site/account names are plain text with direction/control characters neutralized and full RP available. Source: [P17](../research/passkeys-and-ssh.md#p17).

Start again; This request could not be completed; Credential exchange requires macOS 26 or later; These credentials could not be imported. Nothing was saved; Transfer cancelled before handoff; Transfer may have reached the other app. Check there. Source: [P02](../research/passkeys-and-ssh.md#p02).
