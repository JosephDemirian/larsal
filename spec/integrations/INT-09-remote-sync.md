# INT-09 Remote sync

Status: draft
Epics: E11 (scope decided by the owner after this card: D-INT09-1 and "Owner summary"); the import kind IMP-REMOTE of FEA-08 (E4-S13 screens) only if E11 includes it
Parity rows: SI-13, SD-01, SD-03, SD-09, SR-07, SR-14, SN-01; attacks AT-A05, AT-A06, AT-A08, AT-A10, AT-C06, AT-E01, AT-I05, AT-I06, AT-I07, AT-I08

## What it does

Remote sync keeps a vault in step with a copy that lives somewhere App cannot open as a file (a server reached with `scp`, `sftp`, `rsync` or `rclone`, for example). The vault holds a list of named **syncs**. Each sync has a download command and an upload command that the user writes, each with an optional text fed to the command's standard input and a timeout. App never talks to the network itself: it runs the user's own commands.

A run, started from the Vault menu:
1. The download command writes the remote copy to a path App gives it through the placeholder `{TEMP_DATABASE}`.
2. App opens that copy with the vault's key (or asks for the copy's own credentials), merges both ways (MOD-11, "Remote sync" row) and saves both.
3. The upload command sends the merged copy back.

The same download step also serves the import assistant's "Remote vault" kind (IMP-REMOTE, FEA-08), which can open the copy as a temporary vault.

Where it comes from. The reference added remote sync in its 2.8.0 release line (changelog entry under 2.8.0-beta1, 2026-09-23; the 2.8.0 tag of 2026-10-21 carries the same code as the source studied). The installed reference (2.7.11) has none of it (FMT-14, checked by Verify in Sprint 2). Everything here is from the source; nothing of the reference's remote sync could be run (Not run, below).

Other cards: FMT-14.20 owns the custom data item that stores the syncs; MOD-11 owns the merge (MOD-11.1 "Remote sync (two-way)" row; MOD-11.18 vault custom data and protected keys; MOD-11.19 and limit 2 for the key); APP-05 owns saving; APP-06 owns the unlock form reused for the copy's credentials; MOD-12.1 lists the Remote sync page of vault settings; APP-08 places the menu item (its Vault menu note); FEA-08 owns the import assistant (FEA-08.2 fields, FEA-08.3 targets, FEA-08.4 review, FEA-08.5 to FEA-08.7 import into a new or existing vault); APP-01 lists App settings; INT-06 is the SSH agent the help text points to; INT-10 has no remote sync.

Notation: id(xx) is a 16-byte id with every byte 0xxx (as in MOD-11). V is a demo vault at `/tmp/spec-int09/v.appvault`, password `demo-v`, root id(01). R is the folder `/tmp/spec-int09/remote/`, the "remote place" of every test; `R/v.appvault` starts as a copy of V. D1 = `/bin/cp /tmp/spec-int09/remote/v.appvault {TEMP_DATABASE}`, U1 = `/bin/cp {TEMP_DATABASE} /tmp/spec-int09/remote/v.appvault`. S1 is the sync named `Home server` with D1, U1, both inputs empty, both timeouts 10,000 ms. P is the copy's path that App gives a run (INT-09.10). T0 = 2026-01-01T00:00:00Z, T1 = 2026-02-01T00:00:00Z, T2 = 2026-03-01T00:00:00Z. Every test command is local: `/bin/cp`, `/bin/sh`, `/bin/sleep`, `/usr/bin/false` and the like; no test reaches another host.

## Inputs and outputs

| In or out | Type | Limits and notes |
|---|---|---|
| Sync list | the vault custom data item of FMT-14.20 (INT-09.1) | read with FMT-14's limits; a bad value gives an empty list (INT-09.2) |
| Name | text | not empty; one sync per name |
| Download command, upload command | one line of text | split into a program and its arguments (INT-09.8); no shell |
| Download input, upload input | text, may be several lines | written to the command's standard input with one `\n` added (INT-09.12) |
| Download timeout, upload timeout | whole milliseconds | page: 1 to 300 seconds, default 10; stored values outside are bounded when run (INT-09.2) |
| The copy | a vault file of our format at P | written by the user's download command; read with the limits of every vault file (FMT-01.31, FMT-08.12, CRY-02) |
| Credentials of the copy | the vault's composite key, or the parts the user types for this run | wiped when the run ends (SR-07) |
| Approval records | App settings `sync.approved` (INT-09.20) | outside the vault |
| Out | the merged vault (saved, APP-05), the merged copy (uploaded), one result message (INT-09.23) | no file is left in the temp folder (INT-09.10) |

## Rules

### The stored sync list

INT-09.1 **Where and what.** The syncs are stored in the vault's own custom data (vault level, FMT-14.20) under the key `4B 50 58 43 5F 52 45 4D 4F 54 45 5F 53 59 4E 43 5F 53 45 54 54 49 4E 47 53` (stored encoded, name rule). The value is a JSON text (RFC 8259): an array with one object per sync, with these members:

| Member | JSON type | Meaning | Default when missing |
|---|---|---|---|
| `name` | string | The sync's name, shown in the menu | empty (INT-09.2) |
| `downloadCommand` | string | Download command line | empty |
| `downloadCommandInput` | string | Download input | empty |
| `downloadTimeoutMsec` | number | Download timeout in milliseconds | 10000 |
| `uploadCommand` | string | Upload command line | empty |
| `uploadCommandInput` | string | Upload input | empty |
| `uploadTimeoutMsec` | number | Upload timeout in milliseconds | 10000 |

The value is stored as plain text inside the encrypted vault, like every custom data item; it is not a protected field (FMT-14.17).

INT-09.2 **Reading.** App reads the value leniently, as the reference does:
- A value that is not JSON, or whose top level is not an array, gives an empty list. The vault opens normally.
- Array elements that are not objects are ignored (the reference turns each into a sync with an empty name and the defaults; source).
- A missing or non-string text member counts as empty. Unknown members are ignored. Reference (source): a number or a boolean in a text member becomes its text (`"name": 5` gives a sync named `5`).
- A sync whose name is empty is ignored: not shown, not run, and left out the next time App writes the list (the reference keeps it and shows a menu item with no text; source).
- Two syncs with the same name (exact, case-sensitive): the last one wins and takes its own position; the earlier one is dropped (reference: the same, through its name-keyed table; source).
- Timeouts: a JSON number is taken in whole milliseconds, rounded down. A missing member, a non-number, or a value of 0 or less gives 10,000; a value above 300,000 gives 300,000. Reference (source): it runs the stored number as is (a fraction is turned into a whole number by its toolkit's conversion), so 0 stops the command at once and a negative number waits without limit; it also reads a decimal string such as `"5000"` (App: the default). Check with Verify.
- The reader is a fuzz target (AT-A10).

INT-09.3 **Writing.** App writes the item only when the list was changed on its Remote sync page and the user applied the vault settings (INT-09.6). It writes compact JSON (no spaces or line breaks), one object per sync in App's list order, members in the order `downloadCommand`, `downloadCommandInput`, `downloadTimeoutMsec`, `name`, `uploadCommand`, `uploadCommandInput`, `uploadTimeoutMsec` (the reference's JSON library sorts members by name; check with Verify), timeouts as JSON integers, text as JSON strings with only the escapes JSON requires. An empty list is written as `[]`, not removed, so the removal reaches the other copies through the merge (MOD-11.18 never removes this key). FMT-14 refreshes the item's and the container's times.
Reference (source): it rewrites the item on every Apply of the vault settings, even without a change, in the order of its name-keyed table, which is not stable between runs; App writes only on a change and keeps its own order.

INT-09.4 **The list travels with the vault.** Every copy of the vault carries the list. A merge never removes the item (protected key, MOD-11.18), but changes it when the source's custom data wins (MOD-11.18), in every merge that does not skip vault custom data: a window merge from another vault, the merge after a change on disk, a remote sync run itself. So anyone who can write any copy of the vault, or any vault the user merges in, can change the commands App would run. App never runs a changed sync without the user's approval (INT-09.20).

### Remote sync page (vault settings)

INT-09.5 **Page.** A page "Remote sync" in vault settings (MOD-12.1), opened also by the menu item "Set Up Remote Sync…" (INT-09.17). It shows:
- the list of syncs (names, as text) with a Remove button; the first row is selected when the page opens and the list is not empty; Remove is disabled while the list is empty;
- Name, with a Save button;
- two tabs, Download and Upload, each with Command (one line of text: Return adds no line break; the field wraps and grows with its text, then scrolls, so no part of the text is hidden past its right edge), Input (several lines) and Timeout (1 to 300 seconds, default 10); the Download tab also has a Test button (INT-09.7);
- help (MI09-12) and examples: `scp user@host:Passwords.appvault {TEMP_DATABASE}` and `scp {TEMP_DATABASE} user@host:Passwords.appvault`; for an input: `get Passwords.appvault {TEMP_DATABASE}` with the command `sftp user@host`.
Hidden characters: in Command and Input every control or format character (Unicode classes Cc and Cf) shows as a visible code, as in MI09-04 (`⟨U+202E⟩`, `⟨U+0009⟩`); only a line break in Input shows as a line break. A code is one character when editing (one Delete removes the character it stands for); the stored text holds the character itself, never the code's letters. Reference (source): one-line text fields that show such characters as they are, so a right-to-left override reorders what the user sees and a long command hides its tail.
Seen texts (for INT-09.6 and INT-09.7): each of the four texts of the fields counts as seen when it is empty, when it was loaded from a sync that has a matching approval record (INT-09.20), or when the user edited that field on this page (typing, pasting, deleting, dropping) since its row was selected. Save keeps, with the sync in the page's list, which of its four texts count as seen.
Editing:
- Selecting a row fills the fields with that sync (timeouts shown in whole seconds, rounded down, at least 1). Field edits not yet saved with Save are dropped without a question when another row is selected, as in the reference (source).
- Save with an empty name shows MI09-07 and changes nothing. Otherwise Save puts the fields into the list under that name: a sync with the same name is replaced in place; a new name is added at the end and selected. Changing the name of a selected sync and pressing Save adds a second sync and keeps the old one, as in the reference; the user removes the old one.
- Remove removes the selected row. Then the first row is selected, or, with an empty list, the fields are cleared and the timeouts show 10. Reference (source): Remove removes the sync whose name is in the Name field, which after an edit of the name may be another sync or none.
- When neither the download command nor the download input contains `{TEMP_DATABASE}`, the page shows MI09-11 (App only).

INT-09.6 **Apply and Cancel.** When the vault settings are applied (MOD-12.2) while the Name, a command, an input or a timeout was edited since the last Save, App asks MI09-10: Save (default) runs Save and goes on, Discard drops those edits and goes on, Cancel stops the Apply and shows this page. Then App writes the list if it changed (INT-09.3) and stores an approval record (INT-09.20) for every sync added or changed on this page whose four texts all count as seen (INT-09.5). Any other sync, such as one that arrived by merge and whose name or timeout alone was changed here, or whose download was edited but whose upload was never looked at, stores no record and still shows MI09-04 at its first run. Cancel on the vault settings drops every unapplied change of this page. Reference: the same question and the same three answers (source).

INT-09.7 **Test.** The Test button runs only the download step (INT-09.8 to INT-09.16) with the fields as they are on screen, saved or not. An empty download command shows MI09-08 and runs nothing. When the download command and the download input both count as seen (INT-09.5), the test starts at once; otherwise the Test form of MI09-04 comes first, showing the download command and input only: Cancel (default) runs nothing and makes no folder; Test runs this one test and stores no record (the upload part was not shown). On success App also checks that the copy starts with the vault signatures of FMT-01 (no key needed) and shows MI09-09 "worked"; otherwise MI09-09 "failed" with the reason of INT-09.23. App then deletes the copy and its folder. Reference (source): it checks only that a non-empty file exists, and leaves the downloaded copy in its temp folder (INT-09.10).

### Running one command

INT-09.8 **Splitting the command line** (D-INT09-2, recommended option (a)). App never runs a shell. It splits the command text into words by these rules, which are the reference's (its UI toolkit's command splitter, as that toolkit's documentation describes it):
1. White space outside quotes ends a word. White space is the Unicode White_Space set (space, tab, line breaks, no-break space and the other space characters), which is what Rust's `char::is_whitespace` tests; the toolkit's character test covers the same characters. Runs of white space count as one; leading and trailing white space is ignored.
2. A double quote `"` starts or ends a quoted stretch, in which white space is part of the word. The quote marks are not part of the word, and a quoted stretch may sit inside a word (`a"b c"d` is the one word `ab cd`).
3. Three double quotes in a row stand for one literal `"`.
4. Two double quotes in a row add nothing; an empty word cannot be written (`x "" y` is two words).
5. Single quotes, backslashes, `$`, `~`, `*`, `|`, `;`, `&`, `>` and `<` are ordinary characters. No variable, home folder, wildcard or pipe is expanded.
The first word is the program; the rest are its arguments, passed as they are. A command that gives no words (empty, white space only, or only `""`) counts as empty: a run's download is MI09-02 (a) (INT-09.18 step 2), the import assistant's download is MI09-02 (b), and an upload with no words is skipped (INT-09.18 step 8). Reference (source): only an empty text counts as empty; a command of white space only starts nothing and is reported at once as "did not finish in time" (INT-09.11). A user who wants a shell writes it out: `/bin/sh -c "…"`.

INT-09.9 **The placeholder.** In every word of the command (after splitting) and in the input text, App replaces each `{TEMP_DATABASE}` (exactly this text, case-sensitive) with P. Nothing else is replaced: no entry placeholder (MOD-08), no `~`, no environment variable. Reference (source): it replaces in the whole command text before splitting; because P never holds white space or a double quote (INT-09.10), both orders give the same words, except for a placeholder written with quote marks inside it (`{TEMP_""DATABASE}` is one word `{TEMP_DATABASE}` after splitting, which App replaces and the reference does not).

INT-09.10 **A private folder for the copy.** For each run (and each Test), App makes a new folder with an exclusive create in the per-user temp folder that macOS gives the account (app-platform `user_temp_dir`, the folder of `getconf DARWIN_USER_TEMP_DIR`, mode 0700, observed), named `app-sync-` plus 8 random letters and digits, mode 0700. P is `<that folder>/remote.appvault`. App does not create P; the download command does. P must consist only of `A`–`Z`, `a`–`z`, `0`–`9`, `/`, `.`, `_` and `-`; otherwise App runs nothing and the run fails with MI09-02 (o). So P is safe in any word and in any input that a tool or a shell parses.
App deletes the folder with everything in it when the run ends, in every outcome: success, failure, Cancel, lock, quit. The only exception is a temporary vault (INT-09.27), whose folder lives until that vault closes. At start, before any vault opens, App deletes every folder named `app-sync-*` left in the per-user temp folder by a crash (only App makes them; one App runs at a time, APP-09).
Reference (source): the copy is `RemoteDatabase-` plus a random UUID (lowercase, with dashes) plus `2E 6B 64 62 78` (stored encoded, name rule), directly in its toolkit's temp folder (on a Mac the same per-user temp folder, taken from `TMPDIR`; elsewhere often the shared `/tmp`); it is never deleted, so each run and each Test leaves one encrypted copy behind (SI-13).

INT-09.11 **Starting the program.**
- Lookup (D-INT09-4, recommended option (a)): a program word that holds `/` is used as a path; otherwise App looks for it in the folders of the `PATH` App was started with. For App started from Finder or the Dock that is the macOS default `/usr/bin:/bin:/usr/sbin:/sbin` (the SDK's standard path; check with Verify), so tools installed by Homebrew need their full path. A program that cannot be started (not found, not executable, any start error) fails the step at once with MI09-02 (c), which names the full-path fix. Reference (source): a start failure is reported as "did not finish in time", at once.
- The child runs as the user, with App's environment unchanged (so `SSH_AUTH_SOCK` and `HOME` reach `ssh` and `scp`), no terminal, its working folder the user's home folder (reference: App's own working folder, `/` for an app started from Finder), and in a new process group of its own (Rust `process_group(0)`), so that INT-09.15 can stop it with everything it started.

INT-09.12 **Input.** When the step's input is not empty, App writes the input (placeholder replaced, INT-09.9) as UTF-8, then one `\n`, to the child's standard input, then closes it. When the input is empty, the child's standard input is `/dev/null`, so a command that waits for typed input ends at once instead of waiting for the timeout. Writing counts toward the step's timeout, so a child that never reads cannot block App. Reference (source): the same text and newline, then close; with an empty input it leaves standard input open, so such a command waits until its timeout. A tool that reads commands until its input ends (such as `sftp` in batch use) stops after the last line, so a closing `exit` line is harmless but not needed in either app (the reference's help text asks for one; check with Verify).

INT-09.13 **Output.** App reads the child's standard output and standard error until both close, so a talkative child never fills a pipe and never grows App's memory. Standard output is thrown away. Of standard error App keeps only the last 4,096 bytes, in memory, for the failure message's Details (D-INT09-6, recommended option (b)); they are wiped when the message closes and never logged (INT-09.29). Reference (source): it keeps both outputs whole in memory and never shows them.

INT-09.14 **Result of a step.** A step succeeds when the program ends normally with exit status 0 before its timeout. Exit status n ≠ 0 is the failure MI09-02 (d); ended by signal n is MI09-02 (e) (reference: reported as an exit status; check with Verify); the timeout is MI09-02 (f).

INT-09.15 **Timeout and stopping.** The step's timeout (INT-09.2) runs from the program's start. When it expires, or when a run is cancelled (INT-09.21, INT-09.22), App sends SIGTERM to the child's process group, waits up to 2 seconds, then sends SIGKILL to the group, and collects the child's exit. Only that process group is signalled (AGENTS rule 11). Reference (source): it sends SIGKILL to the program only, so programs it started (the copy tool under `sh -c`, for example) keep running and may still write the copy later. Observed with a local fake in python3: `sh -c 'sleep 30 & …; wait'` killed alone left the `sleep` running; a group kill ended both. A program that leaves the group on purpose (a new session, as `ssh` does for a shared connection) is out of reach; App waits only for its own child.

INT-09.16 **Download check.** After a successful download step, P must exist, be a regular file and not be empty; otherwise the run fails with MI09-02 (g). Reference (source): it checks that the file exists and is not empty.

### A sync run

INT-09.17 **Menu.** The Vault menu (APP-08) gets a submenu "Remote Sync" with "Set Up Remote Sync…" (opens vault settings at the Remote sync page), a separator, then one item per sync of the shown vault, by name (as text), in list order. The submenu is enabled while the shown vault is unlocked; the sync items are enabled only when that vault has a file and no run of it is going on. Reference (source): "Database > Remote Sync…" with "Setup Remote Sync…", a separator and one item per sync in the order of its name-keyed table; the submenu is enabled only while the vault view or the vault settings are shown (not while an entry or a group is being edited); it also offers the syncs of a vault that has no file yet, whose save inside the run then needs a file chooser.

INT-09.18 **Steps.** Picking a sync item:
1. Approval (INT-09.20). No approval: nothing runs. The run then keeps its own copy of the sync's four texts and two timeouts, as approved. A change of the list during the run, by this run's own merge included, does not change what this run runs (its upload included); it shows in the list after the run, and a changed sync needs a new approval before its next run. Reference (source): the same; the run keeps the values it read at its start, and its list is read again after every change of the vault.
2. A download command with no words (INT-09.8) fails the run with MI09-02 (a), and the upload is not run either, as in the reference: a sync with only an upload command always fails.
3. Download step (INT-09.8 to INT-09.16). Progress MI09-03 "Downloading…".
4. Open the copy with the vault's current composite key (password, key file and hardware key parts, FMT-04; a hardware key is asked again, with the copy's seed). Wrong key (`WrongKey`): ask for the copy's credentials (INT-09.19). A hardware key reason (missing, not touched in time): the run fails with that reason (APP-06 texts). Any other read error (not our format, damaged, too large, a KDF cost above the CRY-02 limits, which is refused without asking): the run fails with MI09-02 (h) and the reader's reason. Reference (source): any open error leads to its unlock dialog for the copy.
5. Another vault (D-INT09-9, recommended option (a)): when the copy's root group id differs from the vault's, the run fails with MI09-02 (i). So every remote sync merge is a same-vault merge (MOD-11 Notation, LD-60, LD-265), with one exception: a copy whose credentials, given in INT-09.19, match a key this Mac retired (MOD-11.31; decided: spec/decisions.md LD-267 (2), LD-269 (3); design: spec/research/sync-server.md P2, P3). For such a copy App shows `MSG-DISK-OLD-KEY` (APP-05.29) before any merge, Skip the default, with the remote copy named as in MI09-05 (the sync's name), never P. Skip ends the run with MI09-02 (p): nothing is merged, saved or uploaded. Merge anyway runs only the content merge of MOD-11.31, with the vault as the target and the copy as the source, in place of the two merges of step 6; the copy is then replaced by the merged vault, with the vault's key, which counts as a change of the copy (step 7 saves it, step 8 uploads), so the remote copy no longer opens with the replaced password. MI09-06 never shows for such a copy, so App never offers its key. Reference (source): it merges any vault it can open.
6. Merge. Progress "Merging…". First the vault into the copy, then the copy into the vault: keep-newer, vault custom data not skipped (MOD-11.1 "Remote sync (two-way)" row, MOD-11.18 to MOD-11.20, limit 1 and limit 2 of MOD-11.19 with INT-09.24).
7. Save. When either merge changed something, or the vault had unsaved changes: first the vault, through the normal save of APP-05 (backup, safe save, the change-on-disk check of SD-03). Then, when the first merge changed the copy: the copy, atomically (APP-05.11 in its private folder), without a backup, with mode 0600. A vault save that fails ends the run with MI09-02 (k): the copy is not saved and nothing is uploaded; the vault stays changed in memory. A copy save that fails ends the run with MI09-02 (l). Reference (source): saves both, the vault first, when the two change lists together are not empty; its message for a failed vault save carries an empty reason.
8. Upload (D-INT09-5, recommended option (b)): only when the upload command has words (INT-09.8) and the first merge changed the copy. Progress "Uploading…". A failed upload is MI09-02 (m). Reference (source): it uploads whenever the download worked and an upload command exists, changed or not.
9. Done: MI09-01, and the folder is deleted (INT-09.10).

INT-09.19 **Credentials of the copy.** When the copy does not open with the vault's key (step 4), App shows the unlock form of APP-06 (password, key file, security key) as a sheet over the vault, titled with MI09-05, never with P. A wrong entry keeps the sheet open with APP-06's wrong-key line. Unlock continues at step 5. Cancel ends the run with MI09-02 (j). These credentials serve only this run: they are never stored, never used for the vault, and wiped when the run ends (SR-07, AGENTS rule 4). Reference (source): its usual unlock dialog opens on the copy's path; cancel gives the error "Remote database unlock cancelled." (an untranslated text).

INT-09.20 **Approval of commands from the vault** (D-INT09-3, recommended option (a)). App keeps, in App settings (`sync.approved`, never in the vault), one record per approved sync: the vault's root group id (32 lowercase hex digits), the sync name, and a fingerprint = SHA-256 over, in this order, the download command, the download input, the upload command and the upload input, each as a 4-byte big-endian length of its UTF-8 bytes followed by those bytes (64 lowercase hex digits). Timeouts are not part of it (they are bounded, INT-09.2).
- A run whose sync has no record with the same root id, name and fingerprint shows the approval sheet MI09-04 first: vault name, sync name, and the full text of both commands and both inputs in a monospaced, scrollable, selectable view, with every control or format character (Unicode classes Cc and Cf, tab and line break included) shown as a visible code such as `⟨U+202E⟩`. Buttons: Run and Cancel; Cancel is the default and Escape. Run stores the record (replacing an older record of the same root id and name) and starts the run; Cancel runs nothing and makes no folder.
- App's own page approves a sync only when the user has seen all four of its texts there (INT-09.5, INT-09.6). Test skips the sheet only when the download command and input on screen count as seen (INT-09.7). The import assistant needs no record: the user types its command there (INT-09.26).
- So a sync that arrived or changed through a merge, through another device, or through an edit outside App never runs until the user has seen its commands.
Reference: no such check; it runs whatever the vault holds when the user picks the item.

INT-09.21 **One run at a time.** A vault has at most one run going on. The run works off the main thread. While it lasts, App's window keeps the vault readable but blocks every change to it (editing, moving, deleting, merging, importing into it, vault settings), shows the progress line with a Cancel button, and keeps every other open vault fully usable. Cancel during a command step stops it (INT-09.15) and ends the run with MI09-02 (n); during the merge and the saves Cancel is disabled (those steps are short). Reference (source): it disables the whole vault view, the main menus and the toolbar for the run and has no Cancel.

INT-09.22 **Lock, close and quit.** A lock of the vault (APP-02, any trigger), a close of the vault or a quit of App during a run first cancels the run (INT-09.21: the command group stopped, any open credentials sheet closed, the folder deleted), then locks, closes or quits as usual. A run whose merge already changed the vault but whose vault save did not happen leaves the vault with unsaved changes, which APP-02 and APP-05 handle like any other unsaved change.

INT-09.23 **Messages.** A run ends with exactly one message on the vault: MI09-01 for success, MI09-02 for a failure. The success message hides after 6 seconds, as in the reference; a failure message stays until the user closes it (reference: it also hides after 6 seconds). Messages name the sync and the step; they never contain the text of a command or an input, because commands may hold credentials. The one exception is the program word that MI09-02 (c) names, so the user can fix its path. Reference (source): every command failure message quotes the whole command line.

INT-09.24 **Key changes** (D-INT09-7, recommended option (b)). The vault and the copy can have different keys when one was changed on another device. In step 6, when the first merge would give the copy the vault's newer key (the vault's `MasterKeyChanged` is newer, MOD-11.19 limit 2), App asks MI09-06 (a) before saving: "Give It" saves the copy with the vault's key, which counts as a change of the copy (step 8 uploads); "Not Now" keeps the copy's key and records a Conflict. When the second merge would give the vault the copy's newer key, App asks MI09-06 (b), never for a copy under a key this Mac retired, which gets no second merge and never gives its key (INT-09.18 step 5, MOD-11.31, LD-267 (2)): "Use It" takes the copy's key for the vault with MOD-11.19's side effects (quick unlock data removed, APP-04); "Not Now" keeps it and records a Conflict. Both default to Not Now. Reference (source): its merge never moves a key, so after a key change on one device the remote copy keeps the old key and each later run on that device asks for the old credentials (INT-09.19).

INT-09.25 **Writers at the same time** (D-INT09-8, recommended option (a)). A run is not atomic: when another device uploads between this run's download and upload, this upload replaces that copy. That device keeps its own changes and brings them back with its next run (a merge keeps every entry of both sides, except an entry that the same vault's deleted-objects list removed after its last change: FMT-15.11, LD-265), but the remote copy misses them until then. App does not lock or compare the remote copy (the user's command cannot express a conditional upload in general); the page's help says so (MI09-12). INT-09.18 step 8 already skips the upload when nothing changed. Reference: the same race, stated as a warning in its user guide.

### Import assistant: the remote kind

INT-09.26 **Remote vault in the import assistant** (FEA-08 IMP-REMOTE). The Select step shows Command (one line) and Input (several lines) instead of the file field, plus password and key file (FEA-08.2); Next is enabled once the command is not empty. Review runs the download step (INT-09.8 to INT-09.16) with a timeout of 10,000 ms, no approval (the user typed the command here), then opens P with the typed password and key file (an empty password field adds no password part, as for the other FEA-08 kinds). A failed download shows MI09-02's reason in FEA-08.4's error banner; a copy that does not open shows MI09-13 (wrong key) or the reader's reason; in both cases there is no table and Finish stays disabled. After Finish into a new or an existing vault (FEA-08.5 to FEA-08.7), or after Cancel, App deletes the folder.
Reference (source): it sets no timeout, so its new settings value carries 0 ms, and the command is stopped right after its start unless it ended during start-up (check with Verify); after a failed download it still tries to open the missing copy, shows its open error, and hands an empty, unopened vault to the next step, which Finish would import (check with Verify); the copy is never deleted.

INT-09.27 **Temporary vault** (FEA-08.3's third target, shown only for this kind). Finish opens the copy itself as an open vault in App: its name followed by "(Temporary)" wherever App shows the vault's name, the line MI09-14 under its title, never in recent vaults or reopened at start (as the reference). Saving it writes P (APP-05). Its own syncs can run like any vault's (approval included). When it closes (APP-05's question about unsaved changes first), App deletes its folder. Reference (source): the same tab marker and list rules; the copy stays in its temp folder after closing (INT-09.10).

### Other places

INT-09.28 **Command line tool.** The `app` tool has no remote sync, as the reference's tool (INT-10). Its saves keep the item unchanged (FMT-14).

INT-09.29 **Logs and secrets.** App never logs a command, an input, the copy's path, the copy's bytes, or the command's output. A log line about a run holds only the step, the exit status or signal, and the duration (AT-C06, SR-14). Commands, inputs and the error-output tail are held in Rust in wiping types while a run uses them; the page shows commands and inputs only because the user is editing them (AGENTS rule 4).

INT-09.30 **When E11 leaves remote sync out** (D-INT09-1 option (b)). The item is kept byte for byte through every save (FMT-14) and every merge (MOD-11.18); App shows no Remote sync page, no menu submenu and no IMP-REMOTE kind, and runs nothing. This rule holds whatever the owner decides about scope, until the feature is built.

## Edge cases and errors

- **No copy at the remote place yet:** the first download fails (MI09-02 (d) or (g)); the user places the first copy with the tool (for example one `scp` of the vault file). Neither app creates it.
- **A command that asks for a password:** a child has no terminal; `ssh`, `scp` and `sftp` then fail ("Permission denied") or, with an input, read the input. App's empty standard input (INT-09.12) makes any prompt end at once. The help points to SSH keys with an agent (INT-06).
- **Unsaved changes in the vault when a run starts:** they take part in the merge and are saved in step 7 (the reference saves them too).
- **The vault file changed on disk during a run:** the save of step 7 follows SD-03 (APP-05: it refuses to overwrite a file that changed since it was read); the run fails with MI09-02 (k) and that reason; nothing is uploaded.
- **The copy is a version 3 file:** opened and merged; its save follows FMT-16 like any vault.
- **Hostile bytes at the remote place:** whoever controls the remote place can serve any file. Without the key it cannot make a valid vault (FMT-05), so the worst is a refusal: a non-vault (MI09-02 (h)), a KDF cost bomb (refused at once, CRY-02, AT-A05), a decompression bomb (FMT-08.12, AT-A06), a document crafted by someone who has the key (AT-A08), or another vault (MI09-02 (i)).
- **Names:** sync names are text from the vault, possibly hostile; shown as plain text, never markup (AT-E01); long names are cut with an ellipsis in the menu.
- **Several vaults open:** the submenu lists the shown vault's syncs; runs of different vaults may overlap.
- **A sync whose name holds `/` or line breaks:** allowed; the line breaks show as visible codes in the approval sheet only.
- **The same sync item on a Mac without App's approval records** (a new Mac, or App settings reset): every sync asks once (INT-09.20).

Not on Mac: on Windows the reference writes the copy path with backslashes and starts programs through the Windows process API with the same splitting; on Linux nothing differs.

## Security notes

- **Running programs named by vault data (SI-13, AT-I07).** The sync list is data inside the vault. Anyone with the vault's key can change it in any copy; a merge from another vault can change it (MOD-11.18); a run's own merge can change it. In the reference, picking the menu item then runs whatever is stored, as the user, with the user's files and network: a planted command is code execution. App: approval records outside the vault (INT-09.20), the full text shown before the first run, a settings page that cannot get around it (hidden characters shown as codes, the whole command visible, Test and Apply approving only texts the user has seen, INT-09.5 to INT-09.7), and no command runs from opening, merging or saving a vault.
- **No shell (CWE-78).** App starts the program directly with the split words (INT-09.8); the placeholder goes into words, not into a command line, and P has only safe characters (INT-09.10), so neither P nor a sync name can inject anything. A user's own `/bin/sh -c "…"` is the user's choice.
- **Credentials in commands and inputs.** They sit in the vault as readable text (not protected fields), show on the settings page, and a running command's arguments can be read by other programs of the same user (for example with `ps`). App never puts them in messages (INT-09.23) or logs (INT-09.29), and the help recommends SSH keys with an agent (MI09-12, INT-06). The reference quotes the full command in every failure message.
- **The temporary copy (SD-09, AT-I06).** It holds the whole vault, encrypted (FMT-05 to FMT-08). App keeps it in a fresh 0700 folder inside the per-user 0700 temp folder, saves it 0600, and deletes it in every outcome and at the next start after a crash (INT-09.10). The reference leaves one copy per run and per Test in its temp folder and never deletes it (on a Mac that folder is the per-user one, so the copies are the user's own, but they pile up; on systems whose temp folder is the shared `/tmp` other accounts can see the names).
- **Programs that misbehave (AT-I08).** A command that never ends, starts children, floods its output, waits for input, or writes a hostile file: bounded by the timeout and the group stop (INT-09.15), the drained and capped output (INT-09.13), `/dev/null` input (INT-09.12), and the vault reader's limits (INT-09.18 step 4; AT-A05, AT-A06, AT-A08). The reference kills only the direct child and keeps all output in memory.
- **No data loss on failure (SD-01, SD-03, AT-I05).** Nothing is saved before the merge; the vault is saved (safely, with a backup) before the copy and before any upload; a failed vault save stops the run before the copy is saved or uploaded; a failed upload leaves the merged vault saved and says so (MI09-02 (m)); a cancel or a lock before step 6 changes nothing. What must never happen: an upload of a copy whose changes the vault on disk does not have, or a run that ends with fewer entries than the union of both sides, less the entries the deletion pass erased (MOD-11.15, LD-265).
- **Merge limits.** Remote sync is always a same-vault merge (D-INT09-9), except a copy under a key this Mac retired, which gets only the content merge of MOD-11.31 after the user's click (INT-09.18 step 5; LD-267 (2), LD-269 (3)): no downgrade of cipher, KDF or protection flags (MOD-11.19 limit 1, AT-A09), and a key moves only with the user's yes (INT-09.24, limit 2), never from such a copy.
- **Network (SN-01).** App opens no connection for remote sync; the user's program does, and only when the user picks a sync, presses Test or runs the import assistant.
- **Secrets in memory (SR-07, AGENTS rule 4).** The copy's credentials typed for a run, the copy's key and the error-output tail live in Rust wiping types and are wiped when the run ends (INT-09.19, INT-09.13).
- **Distribution.** Running other programs needs an app outside the App Sandbox: under it, child processes inherit the sandbox and could not use the user's tools and keys. App ships without the sandbox (E14-S3), so this is possible; a sandboxed Mac App Store build could not offer remote sync.

## Owner summary

Facts:
- The reference added remote sync in its 2.8.0 release (2026-10-21); the version installed here (2.7.11) has none. App already keeps the stored settings unchanged in every file and merge.
- How it works: the user writes a download and an upload command per sync; App runs them, merges the downloaded copy with the vault both ways, saves both, and uploads. App makes no network connection itself.
- Size if built: about two stories (the command runner and the sync run with approval; the settings page, the menu, the import kind and the temporary vault), plus new frames in the locked design (the Remote sync page, the approval sheet, the progress line), which Option A does not draw today.

Risks, in plain words:
- The commands live inside the vault. Anyone who can change any copy of the vault, or a vault you merge in, can change what runs on your Mac. The reference runs them without asking; App would show them and ask once (D-INT09-3).
- Passwords written into commands sit readable in the vault and can be seen by other programs while a command runs. App never shows them in messages or logs and recommends SSH keys.
- The reference leaves a copy of the vault in the temp folder after every sync; App deletes it.
- Two devices syncing at the same moment can overwrite each other's upload; nothing is lost from the devices, but the remote copy misses changes until the next sync.

Options: (a) build it in E11 with App's safety rules; (b) leave it out, keeping the stored settings intact (INT-09.30). Recommendation for the owner: (b) for the first release, and (a) later from this card if users ask, because parity with the installed reference does not need it, it is the one feature that runs programs named by vault data, and syncing through iCloud Drive or Dropbox folders already works through App's change-on-disk merge.
