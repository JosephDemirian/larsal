## What it does

A shared group copies one group of a vault to a separate file, the **container**, and reads changes back from it. Other people (or the user's other vaults) point one of their own groups at the same container. The container is a normal vault file protected by a **share password**, or a zip archive that holds that vault file plus a signature.

Each shared group has a **mode**:

| Mode | Reads the container | Writes the container |
|---|---|---|
| Inactive | no | no |
| Import | yes: merged into the group when the vault opens, when the share settings change and when the file changes | no |
| Export | no | yes: rewritten after every save of the vault |
| Synchronize | yes, as Import | yes, as Export |

Two app settings switch the whole feature: allow import and allow export. Both are off by default.

Shared groups are not server sharing (E18): the two features never call each other, and the screens use different words. This card's screens say "a group of your vault, shared as a file"; server sharing says "a vault shared through your server" (spec/research/sync-server.md P24).

Other cards: MOD-11 owns the merge (kind "Shared-group import", MOD-11.1; synchronize-mode erase scope MOD-11.15, D-11-9). FMT-14 owns the custom data item that holds a group's share settings (FMT-14.20). FMT-13.17 owns the attachment namespace of shared entries. FMT-15.11 and FMT-15.12 own the deleted-objects list on import and export. MOD-08 owns references (the export's reference rule is here, INT-08.13; a reference inside a share group finds only entries inside it, MOD-08.32). MOD-02.18 defines "shared" for a group and its subtree. MOD-06 owns the badge images. APP-05 owns saving and the change-on-disk watcher. APP-01 lists the settings below. FEA-02 owns the generator button on the share password field.

Notation: id(xx) is a 16-byte id with every byte 0xxx (as in MOD-11). V is a demo vault at `/tmp/spec-int08/v.larsalvault`, password `demo-v`. T0 = 2026-01-01T00:00:00Z, T1 = 2026-02-01T00:00:00Z, T2 = 2026-03-01T00:00:00Z.

## Inputs and outputs

- In: the open vault; each group's share settings item; the two allow settings; the container files on disk; the share passwords.
- Out: the merged group (import); container files (export); messages; badges and labels.
- Limits: a container is read with the same limits as any vault file (FMT-08.12, LD-22); a zip container is read only up to those limits (INT-08.36). Paths are text of any length the file system accepts. Larsal also applies the raw-item and decoded-path bounds of INT-08.4.

## Rules

### Share settings

INT-08.1 **Shared group.** A group is a **share** when its own custom data holds the item with key `4B 65 65 53 68 61 72 65 2F 52 65 66 65 72 65 6E 63 65` (stored encoded, name rule) (FMT-14.20). The group and everything below it are "shared" (MOD-02.18). The root group may be a share: then the whole vault is shared.

INT-08.2 **Item value.** The value is standard base64 (with `=` padding, no line breaks) of a UTF-8 XML text. The reference reads it leniently: characters outside the base64 alphabet are skipped before decoding.

INT-08.3 **XML layout.** One root element, name `4B 65 65 53 68 61 72 65` (stored encoded, name rule), with these children:

| Element | Content | Meaning |
|---|---|---|
| `Type` | empty child elements `Import` and/or `Export` | Import only = Import mode; Export only = Export mode; both = Synchronize; none = Inactive |
| `Group` | base64 of 16 bytes | An id made when the settings were first created. It is not the group's id. The installed version uses it as the attachment namespace of the shared subtree (FMT-13.17); the source build does not use it except to notice changes (INT-08.15) |
| `Path` | base64 of the UTF-8 path text | Container path, absolute or relative (INT-08.5) |
| `Password` | base64 of the UTF-8 share password; empty element for an empty password | Share password, stored readable inside the vault document (Security notes) |
| `KeepGroups` | `True` or `False` | Keep group structure (INT-08.12) |

Writing (reference and Larsal): the declaration `<?xml version="1.0"?>`, with no encoding attribute (confirmed in E11-S1: the reference 2.7.11 writes its signature entry with the same XML writer, and that entry starts with exactly these 21 bytes, the root element right after; the reference writes a share item only from its group editor, which needs its window, so the share item itself and the empty `<Password></Password>` are from the source), then the root, children in the order above, `Import` before `Export`, empty elements written as `<Import/>`, no whitespace or line breaks anywhere, an empty password as `<Password></Password>`.

Reading:
- The first element must be the root named above (exact, case-sensitive); otherwise the settings are invalid (INT-08.4).
- Children may come in any order; unknown children are skipped with their content.
- Inside `Type`, `Import` and `Export` set their flag; reading of `Type` stops at the first other child.
- `KeepGroups` is true only for the exact text `True`. A missing `KeepGroups` means false (old files). New settings made in the editor start with true (INT-08.21).
- A missing `Group` gives a new random id on every read (reference). Because the change check of INT-08.15 step 2 compares that id, every change of the vault then sets such a share up again and imports it again (source). Larsal keeps 16 zero bytes in memory for a missing `Group` and writes a random id the next time it writes the item.
- Where the id comes from (reference, source; the installed version the same): a share made in the group editor starts from one empty-settings value that the app makes once per run, so every share created during one run of the reference carries the same `Group` id, and so does a share whose item was unreadable and is set again in the editor. Larsal gives each new share its own random id (CRY-03 randomness, `larsal-crypto::random`). The reference half is from the source only and stays open (T65): it needs the reference window, owner's go (rule 10, W-08).

INT-08.4 **Valid, importing, exporting.** Importing = the Import flag is set and the path is not empty. Exporting = the Export flag is set and the path is not empty. Valid = mode is not Inactive and the path is not empty. An item that decodes to nothing usable (bad root, empty text, bad base64 giving no root) is **invalid**: the group still counts as shared (it has the key), it never imports or exports, and its label says the reference is invalid (INT-08.24). Larsal rejects a raw item value longer than 256 KiB before any decoding. After bounded decoding, a path longer than 4,096 UTF-8 bytes is invalid too. Values and paths exactly at these bounds remain eligible when otherwise valid. Both invalid cases keep the group shared, never run, and show MI08-25 (F-268, LD-351).

INT-08.5 **Path.** A relative path is resolved against the folder of the vault file; an absolute path is used as is. `~` is not expanded. A vault that has no file yet resolves against the app's working folder in the reference; Larsal refuses to run any share of a vault that has no file yet (no message, the editor shows MI08-17). Conflicts (INT-08.18) compare the path text as stored, not the resolved path.

INT-08.6 **Share key.** A container is opened and written with a composite key that has exactly one part: the share password (FMT-04). The password part is always present, also when the share password is empty: an empty share password gives the "empty password" part `SHA-256("")` = `e3b0c442 98fc1c14 9afbf4c8 996fb924 27ae41e4 649b934c a495991b 7852b855` (FMT-04.2), never "no password". No key file, no hardware key. Confirmed in E11-S1: the reference command line tool opens a container the reference made with an empty share password when given an empty password, and refuses it with no password (T08).

INT-08.7 **Larsal settings.** Stored by Larsal, not in the vault (APP-01):

| ID | Meaning | Default |
|---|---|---|
| `share.allow_import` | Imports may run | off |
| `share.allow_export` | Exports may run | off |
| `share.quiet_success` | Hide sync success messages; problems still show | on (Larsal, D-INT08-10) |
| `share.signer_name` | Signer name written into signed containers (only with D-INT08-1 option b: not built) | the macOS account name |

Reference (source, confirmed in E11-S1): the success-message setting has stored default "show success"; its box is ticked in the page's screen definition, the page never loads the stored value and stores the box on OK. The page is made once per main window, so within one run the box keeps the user's last choice when the page opens again. After a restart it shows ticked whatever is stored, and the next OK on any app settings page stores "quiet". So "show success" stays on only until the reference restarts and its settings are saved again (T10, open: it needs the reference window). Larsal shows and keeps the stored value (D-INT08-10, T09).

### Containers

INT-08.8 **Unsigned container.** A vault file of our format (FMT-01 to FMT-16), nothing else.

INT-08.9 **Signed container.** A zip archive with two entries, written in this order:

| # | Entry name (exact bytes) | Content |
|---|---|---|
| 1 | `container.share.signature` | The signature text (INT-08.10), Latin-1 |
| 2 | `63 6F 6E 74 61 69 6E 65 72 2E 73 68 61 72 65 2E 6B 64 62 78` (stored encoded, name rule) | The unsigned container bytes (INT-08.8) |

Both entries use deflate (method 8). Exact layout of the reference's zip (confirmed in E11-S1 from the bytes of two reference 2.7.11 containers, T14): flags `0x0002` (strongest compression), file time and date 0, no data descriptor. Every local header has version needed 45 and carries a 20-byte ZIP64 extra field (id `0x0001`, data length 16) whose 16 bytes are zero; the local size fields hold the real sizes. The central directory (version needed 20, made by 0, no extra fields, real sizes) and the plain 22-byte end record carry no ZIP64 data; there is no ZIP64 end record and no ZIP64 locator. Readers use the central directory and must skip any local extra field by its length; a reader that took sizes from that extra field would read 0 bytes. larsal-core's ZIP reader (LD-142 (2)), unchanged, reads both reference containers (T66), so it needs no ZIP64 support for them (LD-267 (5)).

Reading (reference): the file is a zip if it opens as one; then only the entry whose name equals entry 2 exactly (case-sensitive) is used; every other entry, the signature included, is ignored; if two entries have that name, the last one wins; if none has it, the vault read fails with an empty input. A file that is not a zip is read as an unsigned container. Confirmed in E11-S1 with crafted zips: an extra member is ignored (T15), the last of two vault entries wins (T16), a bad signature is ignored (T45).

Larsal reads by content: first bytes `03 D9 A2 9A` (FMT-01) mean unsigned; first bytes `50 4B 03 04` mean zip; anything else fails with MI08-04. Larsal takes entry 2 as the reference does, but a second entry with the same name is an error (MI08-04), because no writer makes it.

INT-08.10 **Signature text.** The signature file is XML in the INT-08.3 style (declaration without an encoding attribute), stored as Latin-1 (below), same root element, children:

| Element | Content |
|---|---|
| `Signature` | `rsa|` followed by the signature in lowercase hex. The signature is RSASSA-PKCS1-v1_5 with SHA-256 (RFC 8017) over the exact bytes of entry 2. A 2048-bit key gives 512 hex digits. |
| `Certificate` | two children: `Signer` (the signer name as text) and `Key` (base64 of the public key blob below) |

Public key blob: four parts, each a 32-bit big-endian length followed by the bytes: the 7 ASCII bytes `ssh-rsa`; the exponent e, unsigned big-endian, minimal length, no sign byte; the modulus n, the same way. This is not the standard SSH key form: the standard form adds a 00 byte before a number whose top bit is set, the reference does not. For e = 65537 and a 2048-bit n the blob is 278 bytes, starts `00 00 00 07 73 73 68 2D 72 73 61 00 00 00 03 01 00 01 00 00 01 00`, and its base64 is 372 characters starting `AAAAB3NzaC1yc2EAAAADAQABAAABA`.

The signer name comes from the `USER` environment variable, then `USERNAME`, so it is the maker's account name, in plain text, readable by every member. It is converted to Latin-1 before zipping; characters outside Latin-1 become `?`. When the reference has no usable key, or the signer name is empty (`USER` and `USERNAME` unset or empty), it counts the certificate as missing, writes an empty signature entry (0 bytes) and still writes the zip (seen in E11-S1, T66).

Confirmed in E11-S1 from a container the reference 2.7.11 signed: the signature text starts `<?xml version="1.0"?>`, then `rsa|` and 512 lowercase hex digits; the `Key` is 372 base64 characters starting `AAAAB3NzaC1yc2EAAAADAQABAAABA`, its blob is 278 bytes with the parts 7, 3 and 256 bytes long and no 00 byte before the modulus (top byte `A3`); RSASSA-PKCS1-v1_5 with SHA-256 over entry 2's bytes verifies (T18).

INT-08.11 **Which kind is written.** Reference: a signed container when the resolved path ends with `2E 6B 64 62 78 2E 73 68 61 72 65` (stored encoded, name rule), compared case-sensitively; otherwise unsigned, whatever the extension (confirmed in E11-S1: the signed suffix in capitals gives a plain vault file, T19). Larsal: always unsigned, whatever the suffix (D-INT08-1 (a), INT-08.28).

INT-08.12 **Container content.** Built from the share group G of the source vault:
1. A new vault: recycle bin setting off, name = G's name, other metadata at new-vault defaults (MOD-12).
2. Root group = a copy of G with G's id, fields and times, without the share item.
3. G's entries, copied with id, every field, times and full history.
4. Keep group structure on: every group below G, with id, fields, times and custom data, and their entries as in step 3, in stored order. Off: no groups below G and none of their entries.
5. Each custom icon used by a copied group or entry (MOD-06), with its id.
6. The whole deleted-objects list of the source vault (FMT-15.12).
7. References: INT-08.13.

Reference (confirmed in E11-S1, T11 to T13): the copied groups keep their custom data, so a share nested inside G exports its own share item, path and password included; the whole deleted-objects list is copied. Larsal strips the share item from every copied group (D-INT08-5). Larsal also leaves out the recycle bin and recycled objects when G is the root (D-INT08-8).

INT-08.13 **References on export.** Larsal puts no value from outside the share into a container (decided: spec/decisions.md LD-279 (1), F-140): every field of every copied entry, its history items and its custom fields keep their text as written, field references and placeholders included, with their protection flags. A reference to an entry outside the share stays as its `{REF:...}` text; in a member's vault it finds nothing outside the share group (INT-08.16, MOD-08.32, LD-279 (2)). Larsal adds no history item and keeps the entry's modification time (T20). Reference behavior: each standard field whose whole value is a `{REF:...}` that finds no entry inside the container is replaced with the value the source vault resolves for it, and the entry gets one new history item and the export time as its modification time (E11-S1, kept file a); Larsal does not do this, because it would put a value the user never shared into every member's copy.

Reference (confirmed in E11-S1): it replaces the field inside an update of the container's copy of the entry, so that copy gets one new history item that holds the old `{REF:…}` text, and its modification time becomes the export time; the source vault is not changed. That history item tells every member the id of an entry outside the share, which Larsal's rule avoids.

INT-08.14 **Encryption of a container.** Reference: AES-256 (CRY-01), AES-KDF with 1,000,000 rounds (CRY-02), gzip, and the file version FMT-16 picks: version 3.1 when the content needs nothing newer (confirmed in E11-S1: 3.1 for plain content, 4.0 when a copied group holds custom data such as a nested share item, T21). Larsal (D-INT08-6): the cipher and KDF settings of the source vault (same algorithm and costs, fresh seed or salt, CRY-03), gzip, version 4 by FMT-16.19 to FMT-16.21. This holds also when the source vault's KDF settings lie in the ask band of CRY-02.14, because a save never asks; an importer refuses such a container with no question (INT-08.36; decided: spec/decisions.md LD-281 (1); T67). Unsigned containers are written atomically (APP-05, without a backup) in both apps; a failed write gives MI08-03 with reason MI08-07. The reference writes signed containers straight into the target file (not atomic); Larsal writes them atomically too.

### When it runs

INT-08.15 **Import triggers.** For each open, unlocked vault, while `share.allow_import` is on:
1. When the vault is unlocked or opened: every importing share is imported, in group tree order.
2. When any change of the vault (an edit, a group added or removed, a merge) leaves a group whose share settings differ from those seen last time (mode, path, password or `Group` id; `KeepGroups` alone is not compared): that share is set up again and, if importing, imported at once.
3. When a watched container changes: imported 100 ms later. A second change while one is pending is folded into it.
4. When an allow setting changes: as step 1 for the new state; turning both off stops every watcher. Reference (source): it sets the shares up again only when both settings were off before; turning import on while export was already on imports nothing until a container changes or the vault is opened again.

Watching (each valid share, any mode but Inactive): operating-system file change notices, plus a check every 30 seconds. A change counts only when the SHA-256 of the first 5 KiB (5,120 bytes) differs from the last value seen. A rewrite of a vault always changes its first bytes (CRY-03), so this catches every save.

Changes made by an Export-only share's file are ignored.

Reference at runtime (E11-S1, run hidden): step 1 confirmed (a container's entry was in the vault after unlock) and step 3 confirmed (another process rewrote the container 5 s after start; its new entry was in the vault, through the system's file notice). Not run, still from the source: steps 2 and 4, which need an edit or a settings change in the reference window (owner's go, rule 10, W-08); the 30-second check, the 5 KiB hash and the 100 ms delay, which were not timed (Larsal's own rule: T24, T25).

INT-08.16 **Import steps.**
1. Read the container (INT-08.9); a missing or unreadable file is an error with the system's reason (MI08-02).
2. Open the vault inside with the share key (INT-08.6). Any read error is an error carrying the reader's message (MI08-02).
3. Merge: source = the container's root group, target = the share group, synchronize mode, vault custom data skipped (MOD-11.1, MOD-11.15). Larsal limits the merge to the share group (decided: LD-61, INT-08.32).
4. Changes made: success (MI08-01). No changes: nothing is reported.

References in the share group (decided: spec/decisions.md LD-279 (2), F-142): a field reference in an entry inside a share group finds only entries inside that share group, for every use: fill, Auto-Type, Copy, display and export (MOD-08.32). So a reference that a container brings in as written (INT-08.13) never reads an entry of the member's vault outside the share; the share's own references, such as T20's Alias, still work (T68).

INT-08.17 **Export triggers.** After every successful save of the vault, while `share.allow_export` is on: every exporting share is written, even when its content did not change, in path text order. The watcher of each path is paused during its write and restarted after, so a share never imports its own export. Before any write, INT-08.18 runs; one conflict blocks every export of that save. Reference: export at save confirmed in E11-S1 (the containers were written at the vault's save); the conflict messages of INT-08.18 are from the source (they show in the reference window).

INT-08.18 **Path conflicts.** Among the shares of one vault, by stored path text:

| Case | Reference | Larsal |
|---|---|---|
| Two or more exporting shares, same path | Export blocked for all shares; error MI08-06 per path, listing the group names | Same |
| Two or more importing shares, same path | Warning MI08-05. Every import of that path goes into one of them (the last set up), whichever share asked | Warning MI08-05; the path is imported into none of them until the conflict is fixed (D-INT08-7) |
| One share imports and another exports the same path | Only the editor warns (MI08-13) | Same |

INT-08.19 **Paused during a manual merge.** Sharing for the target vault pauses while the merge dialog of MOD-11.27 is open: no import, no export, no watcher fires. When the dialog closes, Larsal runs step 1 of INT-08.15 for that vault. Reference (source): the pause is only a flag read at the next change of the vault; a container change before that still imports, the first change stops every watcher, and after the dialog closes sharing stays stopped until the next change of the vault, which then sets every share up again and imports it. This reference part stays open: it needs the reference window, owner's go (rule 10, W-08).

INT-08.20 **Messages.** All results of one pass go into one banner, one line each: success lines first, then warnings, then errors. The banner type is error if any error, else warning if any warning, else success. Success lines are left out when `share.quiet_success` is on. See the message table. The reference's banner and its quiet behaviour are from the source and stay open: they need the reference window, owner's go (rule 10, W-08).

### Screens

The reference's screens (INT-08.21 to INT-08.26) and their texts are from the source; seeing them stays open: it needs the reference window, owner's go (rule 10, W-08).

INT-08.21 **Group editor, Sharing page.** Fields:
- Type: Inactive, Import, Export, Synchronize (in this order).
- Path, with a Browse button.
- Password, masked, with the generator button (FEA-02); secure input while focused (APP-10).
- Keep group structure, ticked by default.
- Clear: removes the share item and empties the fields.
Path, Browse, Password and Keep group structure are enabled only when Type is not Inactive. Every field change writes the item into the group being edited; it takes effect when the group edit is accepted. Typing or choosing the path of a share on this page is the user's approval of it, and so is a change on a share this Mac had already approved (INT-08.31). A share that waits for approval stays waiting when only another box changed: the page shows the path, but it does not ask about it, so the sheet still does (RT-7).

INT-08.22 **Browse.** The chooser opens in the folder last used for shares. Import: an open-file chooser. Export, Synchronize: a save-file chooser. Filters: unsigned container, signed container, all files. If the chosen name ends with none of the container extensions (case-insensitive), Larsal adds `.larsalvault` (reference: its own vault extension, `2E 6B 64 62 78`, stored encoded, name rule), adding the dot only if the name does not end with one.

INT-08.23 **Editor warnings**, first match only, shown only while Type is not Inactive (cases 1 to 4 also need a path; the reference the same, source):
1. Path ends with no supported extension (case-insensitive): MI08-10. Larsal's supported extensions: `.larsalvault`, `.larsalshare` (D-INT08-2), `2E 6B 64 62 78` and `2E 6B 64 62 78 2E 73 68 61 72 65` (stored encoded, name rule).
2. Another group of this vault exports the same path, and this one exports: MI08-11 (error).
3. Another group imports the same path, and this one imports: MI08-12.
4. One of the two imports and the other exports the same path: MI08-13.
5. Both allow settings off: MI08-14; only import allowed: MI08-15; only export allowed: MI08-16; both on: no message.

INT-08.24 **Indicators.**
- Badge: a share group that is not expired gets the "share active" badge when it imports with import allowed, or exports with export allowed; otherwise the "share inactive" badge (MOD-06). Only the share group itself gets a badge, not its subgroups.
- Label under the entry list, when the selected group is a share or inside one (the nearest share below the root counts; a root share shows no label): MI08-24 for the share's mode, then a line MI08-16 when the share imports and import is off, and a line MI08-15 when it exports and export is off. An invalid or inactive share shows MI08-25 instead (the reference has an inactive-share text it never reaches, because it counts an inactive share as invalid).
- Group preview: a Share tab, present only on a share group, with the mode name and the path.

INT-08.25 **Vault settings, Shared groups page** (MOD-12.1). A read-only table, one row per share group in tree order: group path without the root, joined by ` > `; mode; path. The reference also has two columns (last signer, certificates) that are always empty; Larsal shows them only with D-INT08-1 option b (signer and trust state).

INT-08.26 **Larsal settings, Shared groups page.** Allow import, Allow export, Hide sync success messages. Signer name, key fingerprint and a Generate button appear only with D-INT08-1 option b (INT-08.30).

### Signatures and trust

INT-08.27 **Reference: no checking.** Neither the source nor the installed version checks signatures, and neither has a trust list. Import ignores the signature file entirely (INT-08.9). The reference still makes a signing key (RSA-2048) the first time its sharing settings are shown or a signed container is written, names the signer after the account name, and writes signatures (INT-08.10). Its settings still define a key for a foreign-certificate list, never read or written. Older reference versions (before 2.7.0) had a trust list: per container path and signer certificate, Trusted or Untrusted, missing meaning Ask; the ask dialog offered Not this time (default), Never, Always, Just this time; an unsigned container always asked, with a warning; the user's own certificate was trusted silently; a bad signature refused the import. Those versions also wrote the signer's full private key into the `Key` element of every signature file. Its user guide still says that signing makes sure the data comes from the expected signer, which the current code does not check.

INT-08.28 **Larsal: signatures** (D-INT08-1, decided: option (a), by the default rule; (b) and (c) are not built). Options:
- (a) No signatures (the decided option). Larsal reads signed containers by taking entry 2 and ignoring the signature, as the reference does, and always writes unsigned containers, whatever the path suffix. The reference reads such a file at any path, because it tries zip first and falls back to a plain vault. Trust comes from INT-08.31 instead. No new crate.
- (b) Verify and sign. Larsal verifies every signed container and applies INT-08.29; writes signed containers for paths ending in `.larsalshare` or the reference's signed suffix (case-insensitive). Needs an RSA crate (not in the approved list; the common one carries a timing advisory for private-key use, so `cargo audit` needs a reviewed exception, AT-J03), a Keychain item for the private key and the screens of INT-08.25, INT-08.26 and INT-08.29.
- (c) Ed25519 signatures of our own (approved crate) and reference RSA signatures treated as unsigned. Not recommended: a second signature format nobody else reads.

D-INT08-2 (decided, default rule): Larsal's own extensions are `.larsalvault` (unsigned) and `.larsalshare` (signed, used only with option b). Placeholders for the rename pass (AGENTS.md naming).

INT-08.29 **Trust list (only with D-INT08-1 option b: not built).**
- A record is (resolved container path, signer key fingerprint) → Trusted or Untrusted. No record means Ask. Unsigned containers use an empty fingerprint. Records live in Larsal settings (`share.trust`), never in the vault.
- Fingerprint: SHA-256 of the public key blob (INT-08.10), shown as 32 uppercase hex pairs joined by `:`.
- A signature that is present but fails, or a `Key` that is not a valid public key blob, refuses the import: MI08-20, no question.
- A `Key` that holds a private key (containers from reference versions before 2.7.0) is treated as unsigned, with MI08-21, because every reader of the file holds that key.
- Larsal's own key is trusted without a record.
- Ask: a non-blocking banner on the share (MI08-22) with Trust always, Trust this time, Not this time, Never. Nothing is merged until the user answers. Not this time and Trust this time are not stored. A new fingerprint for the same path asks again.

INT-08.30 **Signing key (only with option b: not built).** RSA-2048 with e = 65537, made from `larsal-crypto::random` when the first signed container is written or on Generate. The private key is kept in the Keychain (service `app.larsal.vault`, this device only), never in a settings file and never in the vault. Generate replaces it after a confirmation; old trust records elsewhere then no longer match.

### Larsal safety rules

INT-08.31 **Approval of share settings** (D-INT08-4, decided). Larsal keeps, in Larsal settings (`share.approved`), one record per approved share: (vault id = the root group's id, as in INT-09.20; group id; SHA-256 of the mode and resolved path). A share that has no matching record never imports, exports or watches; the group shows MI08-18 with an Approve action that shows mode and full path. The sheet and the group editor's Full path line write out (`\u{202e}`) every character that shows nothing or shows as something it is not: controls, every format character (Cf), the other default-ignorable scalars, spaces other than the plain space, blank glyphs, private use and noncharacters; and the backslash, so a typed `\u{202e}` cannot read as a written-out one. So a path cannot read as another (RT-8); the stored path does not change. Approve approves what the sheet showed: when the mode or the resolved path changed while the sheet was open it refuses, and nothing is approved (RT-5). The sheet also shows the reason the export would be refused, when it can tell (MI08-17, MI08-27, MI08-28). It asks off the screen thread, so a dead folder never holds the sheet's first draw, and the reason shows when the answer comes. In Larsal's group editor, Save approves a share whose path was typed or chosen on the page, and a change of a share already approved; any other Save leaves a waiting share waiting (INT-08.21, RT-7). Clear forgets every record of that group, also when a new path follows it on the same page, so the same mode and path planted later wait for the sheet (RT-6). This covers share settings that arrive by merge (MOD-11.6), by import from another share, or from another app editing the vault.

An approval does not cover the share password (RT-6): a hash of it in Larsal settings would let anyone who reads that file guess the password offline, and to change the password in the vault an attacker already needs the vault's key. INT-08.34's file rule still holds under any password: a file there that this share did not write and that does not open with the new password is left alone.

INT-08.32 **Import stays inside the share** (D-INT08-3, decided: LD-61; the container's own recycle bin: LD-130). The share import's merge matches, moves, updates and erases only entries and groups inside the share group's subtree. A container object whose id belongs to an entry or group outside that subtree (the recycle bin included) is skipped and gets a Conflict record (LD-61, MOD-11), and the import shows warning MI08-19 naming the count. A recycle bin inside the container is an ordinary group of the share; nothing moves to or is made in this vault's own bin (LD-130). Reference: the merge looks ids up in the whole vault (MOD-11.4), so a container can move any entry of the vault into the share group (newer location time) or overwrite it in place (newer modification time); its erase pass also reaches the whole vault (MOD-11.15).

**Rule R6: a share never wins by time, and only a user's stamped move brings an object into a share across a merge** (RT-2). A merge cannot tell what a share brought from an outside object with the same id unless something says so on every Mac, and a marker alone fails open wherever it is lost. So the default is turned round: when two copies count in different shares, the inside copy wins only if the user moved it in and nothing happened later on the other copy; otherwise the outside copy wins. MOD-11.15 has the merge's steps and FMT-15.11 the records.

Rule 9, plainly. What the project's research covers is kept: deleted-object items with times travel between copies of one vault, and a same-vault merge applies them (spec/research/sync-server.md P2, FMT-15), which here means a user's plain records. It does not cover how a merge should treat a share's copy of an outside object, and the reference merges by id and time, which is the hole (MOD-11.4). So R6 is Larsal's own design, proved by search. How far the search goes is below.

Five items of Larsal's own carry the rule, inside the vault under its key:
1. **Stamp.** `app.larsal.share.moved` in an entry's or group's custom data: the share group's id and the time. A user's move into a share writes it, on the object and all it holds, bin items that would come back to it included. It is there only while the object counts inside.
2. **Marker.** `app.larsal.share.origin` in an entry's or group's custom data: an import added this object. Only its presence is read. A left-over marker stays; it counts against the copy that holds it.
3. **Known shares.** `app.larsal.share.known` in the vault's custom data: group ids. The first import or merge that knows a share writes it; a merge reads both copies' lists plus every group with a share item, and stores the union. Setting up and exporting write nothing, since a group with a share item already counts. It outlives the share: a group whose share item went still counts, which fails safe.
4. **Rows.** `app.larsal.share.deleted` in the vault's custom data: a share's deletions, each (record id, share group id, time). Never in the deleted-objects list, which holds only a user's plain records (FMT-15.11).
5. **Private items.** `app.larsal.share.private` in a history item's custom data: a value that lost a merge under this rule, kept on this vault's Macs only. Where the rule takes one copy whole, every value of the losing copy the winner lacks stays as such an item. A same-vault merge carries it like any history item, and drops it once it is the entry's current version again (it is no longer lost; kept, the next edit would hold that version twice on one Mac only). An export takes every such item out, and an import drops any it brings, whole. It has its own budget under the history limits (MOD-03.2), counted apart, so it never pushes out an entry's own versions; pruning may drop it within that budget (limit 17). Together, an entry's own versions and its private items never pass the format's 100,000 history items (FMT-08.12): where they would, pruning drops private items first, oldest first, whatever the history limit, -1 included (tests `g2_private_items_never_pass_the_formats_history_limit`, `r4c2_06_private_budget_within_the_format_history_limit`, `r4c2_09_a_whole_win_at_the_history_cap`). A version takes the tag after its stamp and marker are taken out. One that still holds the format's custom data items (100,000, FMT-08.12) cannot take it: it is dropped, never kept untagged, since an untagged one would go out with its entry. That holds for each version of a copy the rule takes whole, and where a same-vault merge joins the histories: this copy's version of one the other copy holds as a private item takes the tag, or is dropped (tests `g1_a_private_tag_at_the_custom_data_item_limit`, `m8_a_losers_older_version_at_the_item_limit_is_dropped`, `w52_a_whole_win_takes_the_marker_out_before_the_tag`, `j1_a_join_at_the_item_limit_never_exports_the_private_value`).

If no share is known on either copy, none of this runs: the merge is today's, byte for byte.

An object *counts in* the known shares on its way up. A bin item counts where its previous parent is. What each operation does:
- **A user's move** (`edit`): the new shares are those the object counts in after the move and not before. If there are any, every object moved gets a stamp (the innermost new share, now). Else, outside no share, the stamp goes; if its group no longer counts, it names the innermost share left and keeps its time.
- **Bin, restore from the bin, an edit, restoring a version:** as today, stamp and marker stay as they are. Restoring goes to the previous parent if it is there and not in the bin, else the innermost share the object counts in, else the root.
- **Delete for good, empty the bin:** an object that counts inside with no stamp leaves rows, one for each share it counts in, nested ones included, and no plain record. Any other object leaves a plain record. When a group goes, bin items naming it as previous parent name its parent, or its previous parent if it is in the bin.
- **Import** (`SharedImport`): every time in the container is clamped to now: Mod, Loc, every history item, every record. Then today's walk from the share group. An object outside the share group is not touched. It reads and sets no stamp, and an added object gets the marker. Each record the container lists becomes a row, unless a plain record has that id. Its erases reach only objects within the share group, by Mod and stamp. An object a row erases there leaves a row for each share it counted in that lies inside the share group, at the time of that row (a later row already there stays), as a user's delete for good does, so the inner share's own export tells its members; a same-vault merge's erase does the same (below) (C1R4-01; tests `b1_an_outer_members_deletion_in_a_nested_share_reaches_its_member`, `b2_depth_four_an_outer_members_deletion_reaches_inner_members`, `b3_an_import_writes_rows_inside_the_imported_share_only`). An object a plain record erases needs none: plain records go out in every export. For a root share the walk leaves out this vault's recycle bin and what is in it (INT-08.35). Every share item in the container is dropped (INT-08.33), whatever path brought it.
- **Export:** today's subtree, with stamp and marker stripped, every private item taken out and no known list. The container's deleted list is the plain records, plus the rows of this share, plus a row of a share inside it only when the object counts in that inner share on this Mac or is not on this Mac, as (id, time). A list past the format's limit (FMT-15.14) loses its last rows; such a deletion does not reach, and the export saves. Never another share's rows. That closes H13b for a direct member: a member of one share cannot erase, through this Mac's export, an entry this Mac holds in another share. It does not close the relay through a Mac that no longer holds the entry, where a stale member of a nested or side by side share reaches an entry another Mac moved out of that share (limit 18).
- **A same-vault merge:** MOD-11.15, one function in both directions, on all six kinds. Its erases by a share's row write rows as an import's do: an object the row of a share R erases leaves a row for each share it counted in that lies inside R, at the time of that row (a later row already there stays). So a member's deletion of an object in a share nested in R reaches the nested share's members whichever of the user's Macs took the member's file and whichever Mac held the object, at every depth (C1R5-01; tests `m1_held_every_member_of_every_share_hears_a_members_deletion`, `m1_relay_every_member_of_every_share_hears_a_members_deletion`, `x1_relay_through_a_same_vault_merge`, `x1b_both_macs_import_the_file_b_after_the_merge`, `x1r_the_same_vault_erase_writes_the_inner_row`, `x3_a_copy_in_the_outer_share_on_the_importing_mac`, `x4_a_group_relay`). A share outside R, or one the object did not count in, takes no row (`y1_an_erase_never_reaches_a_copy_moved_out`, `y2_side_by_side_inside_the_imported_share`).

None of the five can be planted. Every read and compare of their keys, and of the share item's key, uses the one cleaning function a save uses (FMT-12.25, FMT-14.10): the reader cleans each key, and a key that differs from one of them only by characters a save removes is that key, in entries, groups, history items and vault data. An import, and any merge that is not same vault (another vault, the import wizard, a copy under a key this Mac retired), strip all five from the source first. An export strips them. A save keeps them. A clone is a new object: it carries no stamp and no marker, and keeps its history's private items. A copy into another vault or within this one carries none of the five, and only the custom icons of what it carries. Every write of the five goes through one door: an item goes in only while that custom data holds fewer than the format's custom data items (100,000 per object or for the vault's data, FMT-08.12), so no write of this rule makes an object a save refuses, and no import base takes is refused (tests on real files at the limit and one below: `mark_a_new_entry_at_the_custom_data_item_limit`, `an_imported_newer_copy_at_the_item_limit_keeps_no_stamp`, `g1_a_private_tag_at_the_custom_data_item_limit`, `rows_at_the_vaults_custom_data_item_limit`). For the vault's own custom data the door also counts the two items each save writes there when they are missing (FMT-14.18, FMT-14.21). At that limit: a move writes no stamp, and the move in may then be undone, as in limit 2; an import adds no marker, so a copy a container brought already holding 100,000 items of its own counts as not brought, and a user's move out of it takes its value (limit 7); a container's newer copy keeps none of this copy's stamp and marker, so it counts as a copy a Mac that does not know the share wrote (limits 2 and 11); a losing version takes no tag and is dropped (item 5); with the vault's own custom data at the limit, a known list or a rows item that is not there yet is not written (one that is there is rewritten in its place), so a share counts only while its share item is there and a share's deletion does not reach (as limit 13). An item of the rule can take an object's last free slot, and the format's limit on custom data items in all (10,000,000) is not counted by these writes (limit 20). None is content: they make no new version and no history item, and the editor does not show them.

So no object from a container reaches outside the share at a later same-vault merge on any Mac, and a Mac's next export holds no outside value.

Costs, accepted. A later edit on another Mac undoes a move in: the user moves it again. A member's edit made after the user's move out, or a stale inside edit, stays only as a private history item on the outside copy. Where the rule takes one copy whole (a sibling share's copy, a nested share's, a group move, a moved share group), the losing copy's values stay as private items on this vault's Macs: nothing joins across shares and no typed value is lost. Size: a stamp about 70 to 80 bytes per object a user moved in, a marker about 55 per brought object, the known list 33 per share. A deletion's rows cost 45 bytes for each share that held the object, so a deletion three shares deep costs 135, plus 33 the first time a share has a row; an import's erase costs the same, 45 bytes for the imported share and for each share inside it that held the object, and a same-vault merge's erase by a share's row 45 bytes for each share inside that one that held the object and had no row for it yet (C1R5-01); every row time is clamped between 0 and the import, so a row keeps that size (test `r4_size_a_row_for_each_share_that_held_it`). A private item costs what the value it keeps costs. Each history item of a marked entry copies the marker. No upgrade step: objects already inside have no stamp (limit 12). Time: the rule's work grows close to linearly (4 to 7 times the time for each fourfold size) but on four shapes only the vault's key holder can build, since each known share is the user's own approval (INT-08.31) and a member's container adds at most one row per object: a chain of nested known shares whose innermost entries are erased by rows (at least the square of its depth, as base, at about 3 to 4 times base's time: 67.9 s at 16,000 shares and 50 entries, base 18.7 s; neither ended within 600 s at 64,000), plain groups between two known shares (the square of their number, as base, at about 3 times base's time: 38.0 s at 16,000 groups and 1,000 entries, base 13.5 s), ids chosen so the sets share long paths (up to 128 nodes a set: 8.72 s and 3.5 GB at 64,000 known shares, 0.716 s and 412 MB with random ids) and many groups moved beside a deep way up (12.1 s for 4,000 moved into a bin chain of 4,000 known shares); MOD-11 Limits has every number (C1R6-01, C1R6-02, C2R6-01, C2R6-02).

The limits of R6, in one place. Each holds to the searched depths; the tests are the ones that state it. Limits 18 to 20 came from the checkers' walks and attacks of round 4, and limit 21 from round 5's, not from the model's search.

3. A later edit or a later move inside the share on another Mac beats a move in. A group moved in stays in; the later-edited entry stays out at the group's old parent. 7. Moving a copy out takes its value. A copy holding a member's newer value, not brought, moved out by the user, overwrites an outside copy on another Mac. A moved object's history goes with it, so a value a member of one share wrote can reach another share when a user moves that object there. Never a private item (item 5). A value typed outside every share does go out in one case: when the user's move into a share on one Mac is later than that typing on another Mac's copy outside, the move in wins over that copy and its values join the entry's history as today (h1b), untagged, so the share's next export carries them; with the move between two shares and the typing after a move out, that share is the one moved to (C2R4-06). 10. A losing copy's value stays as one private history item on the winner. It is never exported, also after the user moves the winner into a share; it stays on this vault's Macs. With three copies the order of merges can decide which value is current: a value typed on a brought copy that loses to a copy not brought stays as that private item. The user can restore a private item's version: its values are then the entry's own, every one of them (password, title, notes, fields, custom data, attachments, icon), and they go out with the entry when it is in a share; the app does not mark a version as private, and the private item itself stays (C2R4-05). 18. A stale deletion relayed by a Mac that no longer holds the object (C1R4-02). 19. Two Macs move two groups into each other (each Mac one group into the other): the Macs never agree, whatever the merges, with or without a share. That is base's behaviour: MOD-11.9 does not do a move that would place a group inside its own descendant, so the group stays where that copy had it, and the Macs that made or took different moves keep different trees. With shares known, R6 also moves objects nobody moved: a group inside one of the two (S2 from S into V on two Macs) and an entry in the other (from V into S on the third Mac). Nothing leaves the shares and nothing is lost (C1R4-06). Test `cycle_limit_19_two_groups_moved_into_each_other_three_macs_settle` (it states the limit).
20. The rule's items count toward the format's custom data item limits (FMT-08.12): 100,000 in one object's custom data (an entry's, a group's, a history item's, or the vault's own) and 10,000,000 in all in one vault. Per object, the door lets a rule's item take the last slot: an entry holding 99,999 items of its own holds 100,000 once an import adds the marker or the user's move in adds the stamp, and saves; then the user's next own item on it makes the next save refuse with the format's too-large error for custom data items, where base (which wrote no marker or stamp) saves (C1R5-03). In all, the door counts only the object's own items, so on a vault that already holds 10,000,000 a move in, an import's marker or a private tag makes the next save refuse with "custom data items in all". Either way nothing is lost (the vault in memory keeps every value), and undoing the user's step saves. Base writes none of these items. Tests `k2_limit_20_a_users_own_item_beside_the_rules_item_at_the_limit` (per object) and `limit_20_the_vault_wide_item_count_is_not_checked` (in all, with that limit lowered to the least the vault saves under); they state the limit.
21. A nested share moved out of the outer one, and a stale deletion in it (C2R5). Rows carry no place: a Mac writes an inner share's row where that share sits on its own tree. If one of the user's Macs moved a share S out of a share T (or out of a share between), and a member of T who had not heard of that move deleted an object in S, a Mac that takes the member's file before the move reaches it still holds S inside T: it erases the object and writes S's row, as a user's delete would there. When the Macs settle, S's row erases the object in S, now outside T, on every Mac, and S's next export tells S's members. A deletion by a member of a share the object's share had left, so wins, as in limit 18. Base erases it too (no rows; every export carries every record), and there also when the object itself or a plain group holding it was moved out, which R6 keeps (`x1c_a_plain_group_moved_out_keeps_the_entry`, `x1d_the_entry_itself_moved_out_stays`). Round 4, which wrote no inner rows, kept it, and lost a member's deletion inside T instead (C1R4-01). A fix needs a row to carry where the object sat when it was written, as limit 18's. Tests `x1a_limit_21_a_nested_share_moved_out_before_an_outer_members_stale_deletion`, `x1b_limit_21_a_nested_share_moved_out_after_an_outer_members_deletion`, `x2_limit_21_the_nested_shares_member_after_the_share_left_t`, `x3_limit_21_depth_three_inner_share_moved_out` (they state the limit); bound `x4_moved_within_t_the_deletion_reaches`.

Outside the search, checked on the real code:
- Merges that are not same vault (another vault, the import wizard, a copy under a retired key) run today's walk: the source gives none of the four, the target keeps its own, and the source's Loc or newer value can still move an object into a share or change one there. The user chose that merge (MOD-11.31). Tests `limit_beyond_another_vaults_merge_is_todays_walk_and_takes_none_of_the_items`, `limit_beyond_a_retired_keys_merge_is_todays_walk_and_takes_none_of_the_items`.
- A bin item counts where its previous parent is, so moving its old group into a share reaches it, as the model's rule says. It is not exported from the bin. If a member holds its id and plants a copy, a merge treats the two as inside copies, so the private value can sit in that copy's history and go out in an export. Test `a_bin_item_counts_where_its_previous_parent_is`.
- An entry and a group with one id are two objects: each settles by itself, a list naming the id erases only what counts in that share, and a plain record stays while either object needs it. A share alone changes nothing outside. A plain record names an id and no kind (FMT-15), so a user who moves a brought group out of the share and deletes it for good also erases an older entry with that id, as a deletion of the same kind would; it takes those two acts of the user. A row names an id and no kind too: a user who deletes a brought group erases an older entry with that id in that share, one moved in included, and an outside copy on another Mac stays and comes back. Tests `f8_limit_a_users_record_names_an_id_and_no_kind`, `f8_limit_a_row_names_an_id_and_no_kind_within_its_share`, `f8_a_group_with_an_outside_entrys_id_settles_and_changes_nothing_outside`, `f8_an_entry_with_an_outside_groups_id_settles_and_changes_nothing_outside`, `f8_a_list_with_the_shared_id_erases_only_inside`, `f8_a_users_record_for_an_id_on_a_kept_and_an_erased_object_stays`, `f1_three_copies_any_order` (20,000 rounds, every id on both kinds in its pool).
- A share taken off a group, or the share group deleted, with rows: the group still counts (the known list), rows stay dormant and reach nothing outside, a move back counts, and the copies settle. What the group held leaves rows, the group itself a plain record. Tests `rf8c_real_files_a_share_removed_while_its_rows_stay`, `rf8c_real_files_a_share_group_deleted_for_good_with_rows`.
- A custom icon's removal writes no plain record once a share is known (MOD-06.14), so a stale copy can bring the icon back. Test `f7_an_icon_record_is_not_written_with_a_share_known_and_a_stale_copy_returns_it`.
- A deleted list full of a user's own plain records (1,000,000, FMT-15.14) still blocks a save that adds one, with nothing lost. A container's records no longer fill it. Rows pass the text limit only past 14 shares each at the cap (measured: 4.5 MB of text each, 63 MB at 14, the limit is 64 MiB, FMT-08.12); the fifteenth such import is refused with MI08-02, nothing lost (INT-08.36), test `cr2_07_rows_past_the_text_limit_refuse_the_import`. Tests `cr2_06_real_files_a_full_container_list_no_longer_blocks_a_save`, `cr2_06_real_files_a_full_plain_list_still_blocks_a_save_that_adds_one`, `cr2_06_real_files_two_full_container_lists_merge_and_save`, `cr2_07_rows_past_the_text_limit_refuse_the_import` (ignored in the ordinary run, run by hand).

How far this is proved. A small model, plain Python, searched every operation sequence to a bound: two or three copies, two shares, nested or side by side, an entry and a group holding an entry, on all user, share and merge operations: to depth 4 on two copies with hostile times, depth 6 with honest members, depth 5 on three copies, depth 4 on two side by side shares and on groups, depth 3 on groups in two shares, plus 44 directed flows up to 7 steps. It found no leak (I1), no outside harm (I2) and no outside object erased through a group move (I5). Round 4 added the private items to the model, with two more checks: no value is on no copy while no record names its object (I6), and no private item goes out (I1t). Neither was found at the same depths. The code replays the model step by step, across all six merge kinds, and agrees; a corpus of those traces stays in the tests (`the_models_traces_replay_step_by_step`). Round 5 added the import's rows for the shares inside the imported one to the model; the replay agrees on every step again, and the round 4 model's traces show the change on the new code in 45 traces, every difference one of those rows or what it brings. That is a search to a bound, not a proof for unbounded sequences. It left out history pruning, clock skew, attachments, custom icons, share removal, retired kinds, real files, encryption and size limits; the items above and the tests on real saved files cover what they can.

INT-08.33 **No nested share items** (D-INT08-5). Larsal writes no share item into a container (INT-08.12) and drops every share item found below the root of an imported container before the merge.

INT-08.34 **Path guard.** A share whose resolved path is the vault's own file, the file of any vault open in Larsal, or a backup of one of them never exports or imports; the editor shows MI08-17 with its existing text. A share whose resolved path is a key file never exports or imports either, whether it is the one a vault open in Larsal was last unlocked with or one remembered for any vault (APP-01.16): an exporting one tells MI08-27 at each save, and the editor shows MI08-27's editor text. Backup names match the current `save.backup.path` and the default `{FILE_NAME}.old.larsalvault`, as APP-05.17 step 4 matches them, even while backups are off and even if the destination does not exist. At the write, an export also never replaces an existing backup of an open vault or one of those key files (F-162, F-269, LD-351). The reference has no such check, so an export there overwrites the vault with the container.

All of these compare what the file system compares. When both files exist, by device and inode, so a link and a hard link count. When one does not, by what folder it is in and by name: canonically decomposed with full Unicode case folding, as APFS on a case-insensitive volume does (long s and s, sharp s and ss, the Kelvin sign and k, composed and decomposed accents; dotless i and plain i stay apart, as they do there). A name that cannot be compared (not UTF-8) counts as the same, so it is refused; `old_copies` lists only names it can compare, because its list feeds a delete; on a volume that tells names apart by case, or that does not answer (`pathconf`, `_PC_CASE_SENSITIVE`), it compares them exactly, so it never lists a file the volume keeps apart. The guards keep the folded compare there: they refuse more, which is safe. Only larsal-crypto touches the normalization crate (`text::file_name_key`).

**A share never replaces a file Larsal did not write as this share's container** (RT-1). Before each export, off the session lock:
1. Nothing at the path: it may be created.
2. A regular file there may be replaced when its first 5 KiB hash to `share.written`'s record (S-SHARE-06) of the last container this share wrote (this Mac only; vault id, group id and SHA-256 of the resolved path; the record is what covers a new share password, and a vault whose KDF needs a question at open). Or when it opens with the share key and has INT-08.12's shape (recycle bin off, vault name equal to its root group's name), so a container the other side rewrote is kept.
3. Anything else is left alone and the export says MI08-26: a file that does not open, a vault with its own shape, a link, a folder, a FIFO. Approve does not cover it; the sheet warns of it (MI08-28).

At the rename, in the folder the write uses, what the look saw must still be there, by kind, device, inode, size and status change time (or still nothing); else the same refusal. When the look saw nothing the rename is exclusive (`RENAME_EXCL`), so a file that appears in that last instant stays and the export says MI08-26; a volume with no exclusive rename gets the plain one. Known short gap: where a file was there, no call compares and replaces in one step, so another writer's change in the microseconds between that look and the rename is replaced. The save of the vault itself succeeds either way. No call waits on the path: a folder opens with `O_DIRECTORY | O_NONBLOCK`, so a FIFO in the path is refused at once (F-101). Known limit: a vault not open in Larsal whose password is the share password, with the recycle bin off and its name equal to its root group's name, is by every test this share's container.

INT-08.35 **Recycle bin** (D-INT08-8). A share group inside the recycle bin is inactive. A root share's export leaves out the recycle bin and recycled objects. Reference: shares inside the bin keep importing and exporting, and a root export carries the bin.

INT-08.36 **Hostile containers.** Every container is untrusted (AT-A08). The vault inside is read with the limits of FMT-08.12; the zip is parsed only within the vault file limit (FMT-01.31), and its vault entry never inflates past that limit (AT-A06). A KDF cost in the ask band or above a refuse rule of CRY-02.14 is refused without asking, because imports run without the user (AT-A05; LD-281 (1), T58, T67). The zip reader and the share settings parser are fuzz targets (AT-A10).

INT-08.37 **Import before export** (D-INT08-9, decided). Before writing a Synchronize share, Larsal imports its container if the file changed since the last import. Reference: the export overwrites the file, so another person's export made since the last import is lost from the file until that person saves again (it stays in their vault).

INT-08.38 **Work off the main thread.** Imports and exports run in the background; the vault stays usable. A save during a running export queues one more export.

INT-08.39 **Share password handling.** The share password is held in secret types (SecretString) after the item is decoded. It is never logged and never part of a message. An empty or weak (below Good, FEA-05) share password on a share Larsal creates gives warning MI08-23 in the editor; it is still allowed, for parity.

INT-08.40 **Command line tool.** Shares never run from the command line tool (INT-10), as in the reference. Its saves do not export.

## Edge cases and errors

- Paths outside Latin-1: the reference hands the zip library the path converted to Latin-1 (other characters become `?`), both when it writes a signed container and when it tries to read a file as a zip (source). Latin-1 bytes are not the UTF-8 that the Mac file system uses, so on a Mac a signed container whose path holds any character outside ASCII (`é`, `ж`, an emoji) is written under a wrong name or not at all, and is never read as a zip (the plain-file read then fails, MI08-02). Larsal passes paths as they are (UTF-8 file names on macOS).
- Path case: the reference picks signed or unsigned writing by an exact-case suffix, but warns about extensions without case. A path ending in the signed suffix in capitals gets an unsigned vault in the reference. Larsal: D-INT08-1.
- Container missing at import: error MI08-02 with the system reason (the reference shows this as an error, not a warning). Larsal: same; while the file stays missing, Larsal reports it once per unlock, not on every 30-second check.
- Group deleted while an import is pending: the import is dropped.
- Entry moved out of a share group: no deleted object is made, so it stays in every other copy of the share; in the reference it keeps being updated from the container wherever it now sits (the reference user guide says so). Larsal: it is no longer touched (INT-08.32); the container's copy then shows up again in the share group as a new entry only if it has a different id, which it does not, so it is skipped with MI08-19.
- Two share groups in one vault, one nested in the other: each runs on its own; the outer export includes the inner group's entries (Larsal without the inner share item).
- Share settings item edited outside Larsal to hold a huge value: INT-08.4 rejects a raw value over 256 KiB before decoding and a decoded path over 4,096 bytes; decoding failures are invalid too. FMT-14 and FMT-08.12 still limit the containing vault.
- Export of a share whose group has no entries: a container with an empty root is written.
- Allow export turned off: existing containers stay on disk unchanged.
- Locked vault: no imports or exports; watchers stop and restart with an import pass at unlock (INT-08.15 step 1).

Not on Mac: on Linux the reference watches network file systems by polling only. Windows paths use backslashes. Nothing else differs.

## Security notes

- **What the reference does not protect (SI-09).** Signatures are written but never checked; any holder of the share password who can write the file location can change what every importer gets. Larsal: INT-08.31 approval plus, with option b, verification and trust per signer (INT-08.29).
- **Merge reach.** In the reference a container can move or overwrite any entry of the importing vault whose id it carries, and erase entries anywhere in it (MOD-11.15). Ids leak to every share member (they are in every container). This must never happen in Larsal: INT-08.32 and D-11-9.
- **Settings arriving from outside.** A share item copied in by a merge or by another container becomes active at once in the reference: it can import from, or export the group to, a path someone else chose, overwriting any file the user can write (AT-I04); confirmed in E11-S1: a share item that arrived inside a container the reference made ran an import in the same run. Larsal: INT-08.31, INT-08.33, INT-08.34.
- **Share password storage.** The password sits base64-encoded (readable) in the group custom data inside the vault, not as a protected field (FMT-14.17), and the reference copies nested share passwords into containers. Larsal never exports it (INT-08.33) and holds it in a secret type (INT-08.39); it must never reach logs (SR-14, AT-C06).
- **Deletion history leak.** Every container carries the whole deleted-objects list of the source vault, so members learn when unrelated items were deleted (FMT-15.12, accepted). The Sharing page says so in one help line.
- **Hostile container.** A KDF cost bomb, decompression bomb or crafted document must not hang or crash Larsal (AT-A05, AT-A06, AT-A08, AT-A10). The reference runs imports on its main thread, so a slow container freezes it; Larsal does not (INT-08.38).
- **Old signed files.** Reference versions before 2.7.0 published the signer's private key in every signature file. Larsal never treats such a key as proof of anything (INT-08.29) and never writes a private key into a container.
- **Signing key storage.** The reference keeps the RSA private key unencrypted in its settings file (twice). With option b, Larsal keeps it only in the Keychain (INT-08.30).
- **Text from containers.** Group names, entry fields and paths are untrusted text shown as text only (AT-E01).
- **File writes.** Containers are written atomically with owner-only permissions (SD-01, SD-09, AT-I06); the reference writes signed containers non-atomically, so a reader can see half a file. Reference file modes (E11-S1): unsigned containers 0600 (atomic save), signed containers 0644 (written straight onto the path under the umask), so other accounts on the Mac can read a signed container. Larsal writes every container 0600 (T11).

## Owner summary

Size: medium to large. Shared groups need a group settings page, an app settings page, a file watcher per share, an export writer, a small zip reader and writer, and the merge from E4 with extra limits. About three stories without signatures; signatures and a trust list add one more story and a new RSA crate with a known timing advisory.

Risks, in plain words:
- In the reference, a share file can change or pull out any entry of your vault whose id it knows, not only the shared ones, and can delete entries anywhere. Larsal must limit it to the shared group (INT-08.32).
- Share settings can arrive inside someone else's file and make the app read from, or write to, a path that person chose, even over another file. Larsal asks first (INT-08.31), and even after a yes it replaces only this share's own file (INT-08.34).
- The share password sits readable inside the vault, and the reference copies nested share passwords into the files it writes.
- The reference writes signatures but never checks them, so anyone with the share password and write access to the folder can change what everyone receives. Old reference versions even put the signer's private key inside every signed file.
- Every share file reveals when unrelated items were deleted from the source vault.

Recommendation: build Import, Export and Synchronize with unsigned files and Larsal's safety rules (D-INT08-1 option a). Add signatures and per-person trust only if the owner wants protection against other share members.

Decided 2026-10-31 (W-15, LD-262 (6)): shared groups are built in E11 as recommended, with unsigned files (D-INT08-1 (a)); remote sync by commands (INT-09) is not built.
