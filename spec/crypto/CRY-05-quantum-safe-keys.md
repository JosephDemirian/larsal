## What it does

A large quantum computer, if one is ever built, breaks X25519, Ed25519 and P-256: the discrete-log problems they rest on fall to Shor's algorithm. It does not break AES-256, ChaCha20, SHA-256 or Argon2 in any known way; the best known attack (Grover's search) at most halves their strength, which leaves about 128 bits for a 256-bit key.

So the risk differs by use. A key that travels or is stored **encrypted under a public key** can be recorded today and opened the day such a computer exists ("harvest now, decrypt later"). A **signature** is different: it cannot be forged retroactively from a recording; a forger needs the quantum computer at the time it forges (Apple PQ3; OpenSSH). A signature matters later only when it is kept and trusted for a long time.

This card lists every public-key use in Larsal and its plan (the uses table), says for each one whether it can be recorded now and opened later, what proven apps and standards do, and what Larsal does. Then it fixes the crypto that E25 adds, all in larsal-crypto (AGENTS.md rule 3):

- one **hybrid KEM**, MLKEM768-X25519 (X-Wing): ML-KEM-768 (NIST FIPS 203) and X25519 together, so an attacker must break both;
- one **HPKE suite** on it, the suite that age's post-quantum recipient uses, for sync, sharing and files alike;
- one **hybrid signature**, the composite ML-DSA-65 + Ed25519 of RFC 10073, for the account's identity key and for Larsal's release and license keys;
- **X25519MLKEM768** in TLS 1.3 (RFC 10024) on the link to Larsal's server;
- the exact **words** Larsal may use about quantum safety.

What stays classical stays so for a stated reason (CRY-05.13). The vault file at rest is symmetric (AES-256 or ChaCha20, Argon2) and needs no change. Zero knowledge (LD-340) is unchanged: the server still holds only public keys, signatures and ciphertext.

Design and sources: LD-509, LD-510; CRY-04 (the classical suite this card replaces for sync); spec/research/sync-server.md P6 to P10; spec/research/file-encryption.md S07, S08. Every source is listed under "How this was learned", with what it supports.

## Rules

CRY-05.1 **The uses table is complete.** Every public-key operation in Larsal's code and plan is one of the rows U1 to U32: those Larsal's own Rust and Swift code makes, and those macOS, an outside standard or an outside release tool makes for Larsal (U29, U30, U32). A new use gets a row (its card, its answer to "record now, open later", its treatment) before it is built. Security relevant.

CRY-05.2 **The hybrid KEM** (draft-ietf-hpke-pq-05 section 8.2; draft-irtf-cfrg-concrete-hybrid-kems-04 section 4.2, "identical to the X-Wing construction"; X-Wing draft 11). MLKEM768-X25519, HPKE KEM id 0x647a: ML-KEM-768 (FIPS 203) and X25519 (RFC 7748), their two shared secrets combined with SHA3-256 together with the X25519 ciphertext and public key and the X-Wing label. Sizes: private key 32 bytes (a seed, from larsal-crypto's random source; the ML-KEM and X25519 keys are expanded from it), public key 1,216 bytes, enc 1,120 bytes, shared secret 32 bytes. Larsal never uses ML-KEM-768 alone or X25519 alone where this card asks for the hybrid: no post-quantum-only key (LD-510 (3)). The combination is the vendored code's; Larsal writes no combiner of its own (rule 3). Security relevant.

CRY-05.3 **The HPKE suite** (RFC 9180; draft-ietf-hpke-pq-05; C2SP age spec, `mlkem768x25519`). Base mode, single shot, with exactly one suite: KEM 0x647a MLKEM768-X25519, KDF 0x0001 HKDF-SHA256, AEAD 0x0003 ChaCha20-Poly1305 (Nk 32, Nn 12, Nt 16). CRY-04.5's other rules hold unchanged: base mode only, empty associated data, `info` a CRY-04.2 field list, no psk, auth or export modes, every failure one `WrapInvalid`. Seal refuses, before any work, a recipient public key that is not 1,216 bytes or whose ML-KEM part fails FIPS 203 section 7.2's encapsulation key check (type and modulus check). Open refuses an enc that is not 1,120 bytes. A changed enc or ct is not an error inside ML-KEM (FIPS 203's implicit rejection gives a different secret); the AEAD tag then fails, and that is `WrapInvalid`. Why this AEAD: it is age's suite, so one suite serves sync, sharing and files (CRY-05.12), and it is the suite whose published HPKE vectors exist (CRY-05.16); AES-256-GCM (Apple CryptoKit's X-Wing suite) is equally strong, but no published HPKE vector covers 0x647a with it. Security relevant.

CRY-05.4 **The hybrid wrap record** (replaces CRY-04.6's suite; E25-S3). A wrap record (CRY-04.6) carries the suite `[25722, 1, 3]`, enc of 1,120 bytes, ct, info, the signer id and the signer's composite signature (CRY-05.5) over the same field list as before (`sync-wrap-v1`, the suite as three u16, enc, ct, info, signer id). Opening keeps CRY-04.6's order: (1) the suite is this one suite, (2) info equals the caller's own, (3) the composite signature verifies with the pinned identity key, (4) hybrid HPKE open. A record with any other suite, the classical `[32, 1, 2]` included, is refused at step 1, before any signature check: there is no fallback and no negotiation, so a server cannot downgrade a wrap. A record is at most 16 KiB on the wire (CRY-05.14). Security relevant.

CRY-05.5 **The composite signature** (RFC 10073, id-MLDSA65-Ed25519-SHA512, OID 1.3.6.1.5.5.7.6.48). Exactly RFC 10073's algorithm, with Larsal's choices fixed:
- private key 64 bytes: the ML-DSA-65 seed ξ (32, FIPS 204 Algorithm 6) ‖ the Ed25519 seed (32, RFC 8032); public key 1,984 bytes: ML-DSA-65 public key (1,952) ‖ Ed25519 public key (32); signature 3,373 bytes: ML-DSA-65 signature (3,309) ‖ Ed25519 signature (64);
- sign: `M' = Prefix ‖ Label ‖ len(ctx) ‖ ctx ‖ SHA-512(M)`, with Prefix the ASCII `CompositeAlgorithmSignatures2025`, Label the ASCII `COMPSIG-MLDSA65-Ed25519-SHA512`, and Larsal's ctx always empty (one byte 0x00, no ctx bytes), because Larsal's M is a CRY-04.2 field list whose first field is already a label; then ML-DSA-65 signs M' with context Label, hedged (FIPS 204 Algorithm 2 with 32 fresh bytes from larsal-crypto's random source; the deterministic variant only in known-answer tests), and Ed25519 signs M' (pure, CRY-04.3);
- verify: the public key is exactly 1,984 bytes and the signature exactly 3,373; ML-DSA-65 verifies its half over M' with context Label (FIPS 204 Algorithm 3) and Ed25519 verifies its half over M' strictly (CRY-04.3, `verify_strict`); the signature is valid only when both halves verify (RFC 10073 section 3.3). Any failure is `SignatureInvalid`, with no detail of which half failed.
Security relevant.

CRY-05.6 **Where the composite signature is used.** The account's identity key (SYN-06.1) is a composite key, and every signature it makes is a composite signature: member-list entries (SHR-02.3), consents (SHR-03.8), the receiving-key binding (SYN-06.1), wrap records (CRY-04.6), upload signatures (SYN-01.7, SHR-03.10) and device approvals (SYN-06.11 step 5). Its Ed25519 half and its ML-DSA-65 half are never used alone, as keys or as signatures (RFC 10073 section 5.3: "Component keys of a composite MUST NOT be used in any other type of key or as a standalone key"). Why every use and not only the list: the list and the binding are kept and checked again for the group's life and the pinned identity cannot change (U5), and one key with one signature type leaves no stripped half that a verifier could take for a whole signature. A browser's device approval (E20-S7) is one of these, also when larsal-web makes it in the Recovery Kit path. Larsal's release and license keys are composite too (CRY-05.20). The device key (P-256), the recovery sign-in key (Ed25519), the web vault's passkey (U24), the TLS certificate and the browser's identification key are other keys and stay classical (CRY-05.13). Security relevant.

CRY-05.7 **No half alone, no mixing, no old records.** A Mac and the server never make or accept: a classical wrap record; an Ed25519-only identity key, binding, entry, consent, upload or approval signature; a composite signature with one half removed, swapped or taken from another signature; a receiving key that is X25519 alone. Each is refused as its card refuses a bad record (`WrapInvalid`, `SignatureInvalid`, or the entry check's message), never "accepted with a warning". No migration is needed: E17-S1 and E18-S2 wait for E25-S3 (LD-510 (4)), so no account, wrap or list exists before this card's records; a record left by E16-S7b's test helper is refused like any other classical record. Security relevant.

CRY-05.8 **Account keys** (replaces the key types of SYN-06.1, SYN-06.4, SYN-06.6, SYN-06.8 and SYN-06.11; E25-S3, E17-S1). At sign-up the Mac draws the account secret `S_acct` (32), the composite identity key (CRY-05.5, 64) and an X-Wing receiving key (CRY-05.2, a 32-byte seed). The identity key signs the receiving public key: the composite signature over the field list (`sync-kem-key-v1`, `account_id`, the receiving public key), which replaces `sync-x25519-v1`. The account blob's plaintext is the identity private key (64) followed by the receiving seed (32), 96 bytes; its version stays 1, because no blob was ever written before this card. `PUT /v1/account/keys` sends `{"identity_public_key","kem_public_key","kem_signature","recovery_public_key","blob"}`: 1,984, 1,216, 3,373 and 32 bytes, and the blob. On a new Mac (SYN-06.11 step 2) the one-request key is an X-Wing key pair, and E seals `S_acct` to it with CRY-05.4's record. The same holds for a new browser (E20-S7, U23): larsal-web makes the one-request key as an X-Wing key pair with larsal-crypto in WebAssembly, and the approving Mac seals `S_acct` to it with CRY-05.4's record; a Mac never seals to a one-request key that is not a valid 1,216-byte X-Wing key. The pin of an account (SHR-02.11, SYN-06.6) is the whole 1,984-byte identity public key and the 1,216-byte receiving key, compared in constant time (CRY-04.11). The recovery sign-in key stays Ed25519 (U7). Security relevant.

CRY-05.9 **Sharing records** (replaces the key types of SHR-01.9, SHR-01.10, SHR-02.2 to SHR-02.6, SHR-03.7, SHR-03.8; E25-S3, E18-S2). A member-list entry's field 10 `identity_key` holds the composite public key (1,984 bytes); field 11 is renamed `kem_key` and holds the X-Wing receiving key (1,216); field 12 is renamed `kem_signature` and holds the composite signature over (`sync-kem-key-v1`, `member_id`, `kem_key`) (3,373); field 17 `consent` and the entry's signature are composite signatures (3,373 each). The JSON names follow (`kem_key`, `kem_signature`). Vault keys are wrapped with CRY-05.4's record to the `kem_key` in the verified list. The code compare's `K_C` holds the same three values, so a swapped key still changes the code (SYN-05). Client and server run the same composite checks (SHR-02.6, SHR-02.7). Security relevant.

CRY-05.10 **Upload signatures** (SYN-01.7, SHR-03.10). `Upload-Signature` carries the 3,373-byte composite signature in base64url without padding: 4,498 characters, inside SYN-01.10's 8 KiB per header field. The signed field lists are unchanged.

CRY-05.11 **The link to Larsal's server** (RFC 10024; E25-S5). Larsal's server (rustls) offers TLS 1.3 key exchange groups in this order: X25519MLKEM768 (0x11EC), X25519, secp256r1; it still accepts TLS 1.2 and classical groups from other clients and writes the group of every classical handshake to its log (the group name only; nothing about the client beyond SYN-01.13's log rules). Larsal's own sync client, to a Larsal sync server, offers only TLS 1.3 (its ClientHello's `supported_versions` lists 0x0304 alone) and only X25519MLKEM768 (`supported_groups` and `key_share` list 0x11EC alone): a server that cannot pick it fails the handshake, shown as SYN-03's connection failure, so no sync connection is classical without the user knowing. Larsal's other opt-in HTTPS (U11) offers X25519MLKEM768 first and classical groups after it, and makes no claim. The TLS crypto provider is rustls's aws-lc-rs provider, the only provider built into rustls with X25519MLKEM768 (rustls's ring provider has X25519, secp256r1 and secp384r1 only, and ring 0.17 has no ML-KEM). Third-party rustls providers with the group exist; none is an approved crate, and none is taken (CRY-05.15). The certificate and its pin are unchanged (U10). Security relevant.

CRY-05.12 **File recipients** (C2SP age spec, "The mlkem768x25519 recipient type"; E25-S4; supersedes FIL-01.20's OPEN item). Larsal reads and writes age's hybrid recipient: recipient text with Bech32 prefix `age1pq`, identity text `AGE-SECRET-KEY-PQ-` (original Bech32, FIL-01.9); the stanza `-> mlkem768x25519 <base64 enc>`, enc exactly 1,120 bytes in canonical base64, body exactly 32 bytes (the 16-byte file key and the 16-byte tag), checked before any work; HPKE SealBase with CRY-05.3's suite, `info` = the ASCII `age-encryption.org/mlkem768x25519`, empty associated data. A file key Larsal creates (FIL-01.17) is a hybrid one; classical X25519 recipients still work for reading and writing and are labelled as not quantum-safe (MSG-FILE-QUANTUM). A recipient list that mixes hybrid and classical recipients is refused at write with W-QS-07, because the age spec says a file "SHOULD NOT" go to both (a classical stanza would let a future attacker open it anyway). Security relevant.

CRY-05.13 **What stays classical, and why.** These are not changed by E25, and Larsal makes no quantum claim for them:
- the vault file, key files, quick unlock and the Recovery Kit (U22): symmetric, 256-bit ciphers (CRY-01) with Argon2 or AES-KDF (CRY-02) and HMAC-SHA-256; a quantum computer at best halves their strength, which leaves about 128 bits; the master password stays the weakest part (LD-510 (1));

- the browser channel and identification key (U16, U17): local to the Mac, fresh per session, and WebCrypto in INT-11's browsers has no ML-KEM; revisit when every INT-11 browser ships it (open issue);
- passkeys (U18) follow WebAuthn: the website picks the algorithm; passkey import and export (U30) follow the OS's exchange;
- SSH keys (U19, U27, U28) follow OpenSSH: Larsal signs logins and git signatures (SSHSIG) with the key types servers and git accept, and checks host keys as OpenSSH does; the session's key exchange is the ssh program's. Git signatures are kept for years, so a future forger could sign in an SSH key's name; Larsal says so (W-QS-08) and moves to OpenSSH's post-quantum signature type when OpenSSH ships one (open issue);

## Edge cases and errors

- A wrap record with suite `[32, 1, 2]` (classical) or `[25722, 1, 2]`: refused at step 1, before any signature check (CRY-05.4).
- A wrap record whose enc is 1,119 or 1,121 bytes, or 32 bytes: `WrapInvalid`.
- A receiving key of 1,216 bytes whose ML-KEM part has a coefficient of 3,329 or more (fails the modulus check): refused before any wrap; the entry or account keys holding it fail their check.
- A receiving key of 32 bytes (an X25519 key): refused (CRY-05.7).
- A composite signature of 3,372 or 3,374 bytes; a 3,373-byte one whose ML-DSA half is valid and Ed25519 half is zero bytes; one whose halves come from two different valid signatures over the same message: `SignatureInvalid`.
- An Ed25519 signature of 64 bytes in place of a composite one (an old record or a stripped one): `SignatureInvalid`.
- A member-list entry over 32 KiB, or a reply with 31 entries: refused before parsing (SYN-01.10's way).
- A wraps reply over 4 MiB, or any other JSON reply over 1 MiB: a protocol error; the client reads no further (CRY-05.14).
- A sync server that answers the ClientHello with HelloRetryRequest for X25519 only: the handshake fails; Larsal shows the connection failure, never a classical sync.
- An age file with one `mlkem768x25519` stanza and one X25519 stanza: Larsal reads it (either identity opens it); Larsal never writes one.

## Security notes

- **Why a hybrid and not ML-KEM alone.** ML-KEM is new; X25519 has decades of study. With the hybrid, today's strength never drops below X25519's, and a recording needs both broken (Apple PQ3, Signal PQXDH, RFC 10024, LD-510 (3)).
- **Downgrade.** One suite, one signature type, no negotiation inside Larsal's records (CRY-05.4, CRY-05.7). In TLS, Larsal's sync client offers only the hybrid group; the server's certificate pin and TLS 1.3's signed transcript stop an active attacker from removing the offer today.
- **What the hybrid does not do.** It does not protect a weak master password, a weak account password without the account secret, a weak file passphrase, or a Mac that runs hostile code. It does not make the server trusted: P8 to P10's checks stay.
- **Unaudited code.** The PQ crates are unaudited (CRY-05.15); two Checkers review every change (team.md: crypto), every published vector passes, and fuzz targets cover each decode (E25-S2).
- **Zero knowledge.** The server stores longer public keys, signatures and ciphertext, and nothing else new (E13-S8's check, E25-S3).

## How this was learned

Public standards and public product documents only; the reference app has no server, accounts, sharing or public-key files, and no reference material was opened. Each source, read 2026-11-08 or 2026-11-09, and what it supports:

- NIST FIPS 203, ML-KEM (published 2024-08-13; section 7.2 input checks; implicit rejection): <https://csrc.nist.gov/pubs/fips/203/final>. CRY-05.2, CRY-05.3.
- NIST FIPS 204, ML-DSA (published 2024-08-13; Algorithms 2, 3, 6; hedged signing; context strings): <https://csrc.nist.gov/pubs/fips/204/final>. CRY-05.5.
- NIST IR 8547 final (October 2026), the transition of public-key algorithms to post-quantum: <https://csrc.nist.gov/pubs/ir/8547/final>. U22, CRY-05.13.
- RFC 9180, HPKE: <https://www.rfc-editor.org/rfc/rfc9180.html>. CRY-05.3.
- draft-ietf-hpke-pq-05 (2026-07-06): KEM ids, MLKEM768-X25519 = 0x647a, Npk 1,216, Nenc 1,120, Nsk 32; its vectors: <https://datatracker.ietf.org/doc/draft-ietf-hpke-pq/>, <https://github.com/hpkewg/hpke-pq>. CRY-05.2, CRY-05.3, CRY-05.16.
