# CRY-01 Ciphers, modes, IV and nonce sizes

Status: reviewed
Epics: E2-S4 (the field stream parts are also built in E2-S6)
Parity rows: SF-01, SF-08, SF-14

## What it does

A vault file uses two kinds of cipher.

1. The **payload cipher** encrypts the whole payload (the inner header plus the XML document, after optional gzip, see FMT-08). The outer header names it with a 16-byte cipher id (header field 2, see FMT-02) and carries its IV or nonce (header field 7). Three ciphers are in use: AES-256 in CBC mode, Twofish-256 in CBC mode, and ChaCha20.
2. The **field stream cipher** makes a keystream that is XORed onto every protected value inside the XML document (passwords and other protected fields, see FMT-09). It is named by a small number: 3 means ChaCha20 (written in version 4), 2 means Salsa20 (written in version 3, still readable in version 4).

This card fixes, for every cipher: its id, mode, key size, IV or nonce size, padding, counter start, what the reference writes, what it reads, what it rejects, and the public standards and known-answer vectors a Builder tests against. Where the 32-byte payload key comes from is in FMT-04. How the ciphertext is cut into blocks is in FMT-06 (version 4) and FMT-07 (version 3). Where the field stream key sits is in FMT-09. Which random values are fresh on each save is in CRY-03.

## Inputs and outputs

Payload cipher:
- In: the cipher id (16 bytes), the final key (32 bytes, from FMT-04), the IV or nonce (header field 7), and the plaintext (any length, streamed).
- Out: the ciphertext. CBC ciphertext is the plaintext length rounded up to the next multiple of 16, plus 16 when the plaintext length is already a multiple of 16 (PKCS#7 always adds 1 to 16 bytes). ChaCha20 ciphertext has exactly the plaintext length.

Field stream cipher:
- In: the stream id (u32, little endian) and the field stream key (64 bytes in version 4 files the reference writes, 32 bytes in version 3; see FMT-09).
- Out: an endless keystream. Byte i of the keystream is XORed onto byte i of the concatenated protected values, in document order (FMT-09).

### Payload cipher ids

The id is stored as 16 raw bytes in the order shown. This is the same order as the usual hyphenated text form (RFC 4122 byte order), so `31c1f2e6-bf71-4350-be58-05216afc5aff` is stored as `31 C1 F2 E6 BF 71 43 50 BE 58 05 21 6A FC 5A FF`.

| Cipher | Id bytes (as stored) | Mode | Key | IV or nonce | Padding | Reference offers for new vaults | Reference reads | Reference writes |
|---|---|---|---|---|---|---|---|---|
| AES-256 | `31 C1 F2 E6 BF 71 43 50 BE 58 05 21 6A FC 5A FF` | CBC, 128-bit block | 32 bytes | 16 bytes | PKCS#7 | yes, the default | yes | yes |
| Twofish-256 | `AD 68 F2 9F 57 6F 4B B9 A3 6A D4 7A F9 65 34 6C` | CBC, 128-bit block | 32 bytes | 16 bytes | PKCS#7 | yes | yes | yes |
| ChaCha20 | `D6 03 8A 2B 8B 6F 4C B5 A5 24 33 9A 31 DB B5 9A` | stream, RFC 8439 block function, 96-bit nonce, 32-bit block counter starting at 0 | 32 bytes | 12 bytes | none | yes | yes, with 12-byte nonces, and also 8 and 24-byte nonces (observed; Larsal: CRY-01.9) | yes, always a 12-byte nonce |
| AES-128 | `61 AB 05 A1 94 64 41 C3 8D 74 3A 56 3D F8 DD 35` | CBC | 16 bytes | 16 bytes | PKCS#7 | no | id is recognised, but opening fails (observed) | no |

The reference's screen lists the three usable ciphers in this order: AES-256, Twofish-256, ChaCha20. The command line tool always creates AES-256 vaults and has no option to pick a cipher.

The same table applies to version 3 and version 4 files. The reference reads and writes a version 3.1 file whose payload cipher is ChaCha20 (observed).

### Field stream ids

| Id (u32 LE) | Cipher | Key used by the cipher | Nonce | Block counter | Reference reads | Reference writes |
|---|---|---|---|---|---|---|
| 1 | an RC4-like legacy stream | none | none | none | rejected | never |
| 2 | Salsa20/20 | SHA-256(field stream key), 32 bytes | fixed 8 bytes `E8 30 09 4B 97 20 5D 2A` | 64-bit, starts at 0 | version 3 and version 4 | version 3 only |
| 3 | ChaCha20 | the first 32 bytes of SHA-512(field stream key) | the next 12 bytes of that hash (bytes 32 to 43) | 32-bit, starts at 0 | version 4 (see CRY-01.17 for version 3) | version 4 only |
| any other value | none | none | none | none | rejected | never |

## Rules

CRY-01.1 The payload cipher is chosen by comparing the 16 bytes of header field 2, byte for byte, with the ids in the table above. AES-256, Twofish-256 and ChaCha20 are supported for reading and writing.

CRY-01.2 A cipher field whose length is not 16 makes the open fail with `Corrupt`, because the field is malformed (FMT-02.7 owns the header field structure). A 16-byte field that matches no supported id makes the open fail with `Unsupported`. Both checks run while the header is read, before any key derivation work (CRY-02). The reference also rejects at this point: for an unknown non-zero id it says the cipher is not supported, for 16 zero bytes it says the id cannot be parsed, for a wrong length it names the bad length (paraphrased; the first two observed).

CRY-01.3 The AES-128 id is treated as unsupported (`Unsupported`, while the header is read, before key derivation). The reference recognises the id but then fails to start the cipher, because the final key is always 32 bytes, and shows a generic unknown-error message (observed). Larsal never writes this id. Parity note: the reference starts the cipher only after key derivation. In version 4 that is also after the header HMAC check, so with a wrong password the reference shows the wrong-key message instead. In version 3 the cipher is started before the start bytes are compared, so the failure shows whatever the password (source reading). Differential fuzzing (AT-A11) must list this as an expected difference: Larsal fails earlier, without a KDF run, and always with `Unsupported`.

CRY-01.4 AES-256-CBC follows NIST SP 800-38A (CBC mode) with AES from FIPS 197. The key is the 32-byte final key from FMT-04. The IV is the 16 bytes of header field 7. On write, PKCS#7 padding is always added: n bytes of value n, with n = 16 - (length mod 16), so n is 1 to 16 and a plaintext whose length is a multiple of 16 gets one full block of `10` bytes.

CRY-01.5 Twofish-256-CBC works exactly like CRY-01.4 with Twofish in place of AES: 128-bit block, 256-bit key (the 32-byte final key), 16-byte IV from header field 7, CBC chaining, PKCS#7 padding. Twofish is the cipher of the Twofish authors' specification, with their byte order: the 32 key bytes and each 16-byte block go in and come out in file order, exactly as in their known-answer tables (T9, T10). Interop with the reference is observed in both directions (T34).

CRY-01.6 ChaCha20 (payload) uses the ChaCha20 block function of RFC 8439 section 2.3 with the 32-byte final key, the 12-byte nonce from header field 7, and a 32-bit block counter that **starts at 0** (not at 1, which RFC 8439 uses only inside its AEAD construction). Block j of the keystream is the block function output for counter j. Ciphertext = plaintext XOR keystream. There is no padding, and no authentication tag (integrity comes from FMT-06).

CRY-01.7 Keystreams are continuous. Byte i of a payload or field stream always uses keystream block floor(i / 64) at offset i mod 64, no matter how the data is split into write or read calls. Streaming in chunks of any size gives the same bytes as one call.

CRY-01.8 IV size on write: 16 bytes for AES-256 and Twofish-256, 12 bytes for ChaCha20. The IV is fresh random data on every save (CRY-03). When the user changes the cipher, the next save writes an IV of the new cipher's size.

CRY-01.9 IV size on read: for AES-256 and Twofish-256 header field 7 must be exactly 16 bytes; for ChaCha20 exactly 12 bytes. Any other length makes the open fail with `Unsupported` while the header is read, before key derivation (FMT-02.11). A missing field 7, or one of length 0, makes the open fail with `Corrupt` before key derivation (FMT-02.23). The reference rejects a wrong CBC IV length with an invalid-IV-size message, a missing IV with a missing-header message, and a 16-byte ChaCha20 nonce with an invalid-IV-size message (all observed with the right password). The reference *accepts* 8-byte and 24-byte ChaCha20 nonces (see Edge cases); Larsal rejects them with `Unsupported` (decided: spec/decisions.md default rule, the card's proposal; no writer known to this card produces them, and the reference itself always writes 12 bytes). Parity note: the reference checks only for a missing or empty IV before key derivation. It checks the IV length when it starts the cipher, which is after key derivation and, in version 4, after the header HMAC check, so with a wrong password a version 4 file shows the wrong-key message instead of the invalid-IV-size message. In version 3 the cipher is started before the start bytes are compared, so the invalid-IV-size message shows whatever the password (source reading). Differential fuzzing (AT-A11) must list this as an expected difference, as in CRY-01.3.

CRY-01.10 CBC length and padding on read. (The version 3 decryptor end call without a padding check is built with E3: decided: spec/decisions.md LD-41.)
- **Version 4.** Checked only after every block HMAC has passed (FMT-06, FMT-08.11): the joined CBC ciphertext must be a non-zero multiple of 16 bytes, its last decrypted byte n must be 1 to 16, and the last n bytes must all equal n (FMT-08.5). The padding is removed before the result goes to gzip (FMT-08) or the inner header parser. Any failure is `Corrupt` (decided: spec/decisions.md LD-03 for the padding; the length rule is the card's proposal, kept by the default rule; only a key holder can make either). Reading n from the last byte is safe here, because no byte can be changed without the HMAC key. Bytes after the final block of the block stream are not ciphertext; they are ignored (FMT-06.12, decided: spec/decisions.md LD-01).
- **Version 3.** The CBC payload is decrypted in whole 16-byte blocks, **without** padding removal. The hashed block walk (FMT-07) stops at the end of the final hashed block, and everything after it is ignored and never read as content: the padding, any extra whole cipher blocks, and a partial cipher block of 1 to 15 bytes at the end of the file (decided: spec/decisions.md LD-01; FMT-01.20, FMT-07.11, FMT-17.15). So version 3 has no padding check and no multiple-of-16 check. Only the at-least-32-bytes rule remains, checked before key derivation (FMT-05.13 step 2); a file that ends before the final hashed block is complete fails the walk with `Corrupt` (FMT-07). Larsal never reads a padding length from a decrypted byte in version 3.
- **Reference (observed).** Version 4: it never checks the padding or the length. Version 3: it checks the padding only when the file's last cipher block also holds part of the final hashed block; a bad padding then fails the open with a message that the document has no root group. When the last cipher block is all padding, or when more bytes follow it, a bad padding is ignored and the file opens. Larsal opens the first case too (LD-01); differential fuzzing (AT-A11) lists it as an expected difference (only a key holder can make it, see Security notes).

CRY-01.11 One error (decided: spec/decisions.md LD-04 and LD-37). The `larsal-crypto` decrypt API returns one single error value, `Decrypt`, for every decrypt failure that depends on the data (a bad ciphertext length, bad padding, any other cipher failure), with no detail about which check failed, and no key, IV or plaintext bytes in the error or the log. So bad padding and a wrong key give the same error from the cipher API (E2-S4). A key or IV of the wrong length is not such a failure: it gives `KeyLength` or `IvLength`. These two depend only on public lengths, are checked before any cipher work, and are the same for encrypt and decrypt, so they tell an attacker nothing (decided: spec/decisions.md LD-37). In a file they cannot happen: the final key is always 32 bytes (FMT-04) and the IV length is checked while the header is read (CRY-01.9). In a file, `larsal-format` reports `Decrypt` as `Corrupt`, the same kind as the block integrity failures (FMT-06, FMT-07.12). When it can happen:
- Version 4: only after key derivation, after the header HMAC check (the wrong-key check, FMT-05) and after every block HMAC (FMT-06).
- Version 3: never, because no length or padding check is made (CRY-01.10). A file with fewer than 32 ciphertext bytes is `Corrupt` before key derivation, whatever the password (FMT-05.13 step 2). A wrong key is found at the start bytes and gives `WrongKey` (FMT-05.11, decided: spec/decisions.md LD-12).
Checks made while the header is read (cipher id and IV or nonce length: CRY-01.2, CRY-01.3, CRY-01.9) happen before key derivation and give `Unsupported`, or `Corrupt` for a malformed or missing field (FMT-02.7, FMT-02.23). No padding result can be seen before integrity passes (AT-B07).

CRY-01.12 Encryption and decryption are streaming: memory stays flat no matter how large the payload is, and the streamed result equals the one-shot result (E2-S4 check: a 1 GB streaming test).

CRY-01.13 ChaCha20 with one key and nonce produces at most 2^32 blocks (256 GiB). Larsal refuses to process more than that with one key and nonce. This bound is far above the payload limit in `larsal-format/limits.rs`, so it can never be reached by a valid file; the check is a guard.

CRY-01.14 Field stream id 3 (ChaCha20): compute H = SHA-512(field stream key). The cipher key is H bytes 0 to 31, the nonce is H bytes 32 to 43, the block counter starts at 0, and the keystream is the RFC 8439 block function output as in CRY-01.6. The field stream key may have any length; the reference writes 64 bytes (FMT-09 has the length rules).

CRY-01.15 Field stream id 2 (Salsa20): the cipher key is SHA-256(field stream key) (32 bytes), the nonce is the fixed 8 bytes `E8 30 09 4B 97 20 5D 2A`, and the keystream is Salsa20/20 with a 256-bit key and a 64-bit block counter starting at 0, as in Bernstein's Salsa20 specification. The reference writes a 32-byte field stream key in version 3.

CRY-01.16 Field stream ids accepted on read in version 4: 2 and 3. Id 1 and every other value make the open fail with `Unsupported`. The reference says the inner stream cipher is invalid (paraphrased, observed for ids 1 and 4).

CRY-01.17 Field stream id in version 3 files (outer header field 10): Larsal accepts only 2 and reads with Salsa20. An absent field 10 also means Salsa20, in Larsal and in the reference (FMT-02.20). A field 10 whose length is not 4 bytes is `Corrupt` (FMT-02.20). Any other id gives `Unsupported`. The reference accepts 2 and 3 but always reads with Salsa20, even when the id says 3. A version 3 file truly encrypted with ChaCha20 then opens and shows garbage in protected fields, with no error (observed). Larsal rejects id 3 in version 3 with `Unsupported` (decided: spec/decisions.md LD-10; no tool writes it).

CRY-01.18 On write, Larsal always uses field stream id 3 (ChaCha20) with a fresh 64-byte key (CRY-03), even when the file was read with Salsa20. The reference does the same: a version 4 file read with id 2 is saved with id 3 and a new 64-byte key (observed). The reference's version 3 writer uses id 2 with a 32-byte key; Larsal does not write version 3 (architecture: version 3 is read only).

CRY-01.19 Default cipher for a new vault is AES-256. Larsal offers the same three ciphers as the reference for new vaults and for a cipher change: AES-256 (the default), Twofish-256 and ChaCha20, listed in the reference's order (decided: spec/decisions.md LD-20). Reading and writing all three is required (SF-01). MOD-12 and APP-07 own the screens. The command line tool's new vaults use AES-256.

CRY-01.20 Changing the cipher of an open vault takes effect on the next save: the whole payload is encrypted again with the new cipher, a new IV of the right size (CRY-01.8) and fresh random values (CRY-03). Nothing else in the file format changes (SF-14).

CRY-01.21 Every primitive passes the public known-answer tests listed in Test cases before it is used: AES-256 (NIST SP 800-38A F.2.5 and F.1.5), Twofish-256 (the Twofish authors' known-answer tables), ChaCha20 (RFC 8439 sections 2.3.2 and A.1), Salsa20 (the eSTREAM verified Salsa20/20 256-bit vectors), plus the field stream derivation vectors below (AT-B01).

## Edge cases and errors

- **Unknown cipher id** (any 16 bytes not in the table, including 16 zero bytes): `Unsupported` while reading the header. Observed in the reference: 16 bytes of `01` give a not-supported message; 16 zero bytes give a cannot-parse message.
- **Cipher field not 16 bytes** (for example 15): `Corrupt` while reading the header (CRY-01.2, FMT-02.7). Reference: a message naming the bad length (source reading).
- **AES-128 id**: Larsal `Unsupported`, before key derivation. Reference: generic unknown-error message after key derivation (observed); in version 4 with a wrong password it shows the wrong-key message instead (source reading, CRY-01.3).
- **ChaCha20 nonce of 8 bytes**: the reference opens the file using the original ChaCha20 layout (state words 12 and 13 are a 64-bit block counter starting at 0, words 14 and 15 are the 8-byte nonce). Observed with a crafted demo vault. When saved again it writes a 12-byte nonce. Larsal: `Unsupported` (CRY-01.9, decided by the default rule).
- **ChaCha20 nonce of 24 bytes**: the reference opens the file as XChaCha20 (subkey = HChaCha20(final key, nonce bytes 0 to 15); then ChaCha20 with that subkey, counter 0, and nonce `00 00 00 00` followed by nonce bytes 16 to 23). Observed with a crafted demo vault. Larsal: `Unsupported` (CRY-01.9, decided by the default rule).
- **ChaCha20 nonce of 16 bytes**: reference fails with an invalid-IV-size message (observed). Larsal: `Unsupported`.
- **CBC IV of 12 bytes**: reference fails with an invalid-IV-size message (observed in version 3). Larsal: `Unsupported`, before key derivation.
- **Bad PKCS#7 padding, version 4, with valid block HMACs** (only a writer holding the key can make this): the reference opens the file anyway, with and without compression (observed). It never checks the padding in version 4. It also ignores trailing bytes after the gzip stream or after the end of the XML document (Larsal's rule for those: FMT-08.7). Larsal: `Corrupt` (CRY-01.10, decided: spec/decisions.md LD-03).
- **Bad PKCS#7 padding, version 3, last cipher block also holds the end of the final hashed block** (plaintext before the padding not a multiple of 16, for example 2,385 or 2,386 bytes, with the padding bytes written as `00`; only a key holder can make this): the reference fails the open with a message that the document has no root group (observed). Larsal: opens; the padding lies after the final hashed block and is ignored (CRY-01.10, LD-01). Expected difference for AT-A11.
- **Bad PKCS#7 padding, version 3, last cipher block all padding** (plaintext before the padding a multiple of 16, for example 2,384 bytes, also when that block was replaced without the key): the reference ignores the bad padding and opens the file (observed). Larsal: opens, same content (CRY-01.10, LD-01).
- **CBC ciphertext length not a multiple of 16, version 3** (for example 5 extra bytes appended by a sync tool that did not truncate the file): the reference ignores them (observed with 1, 5 and 16 extra bytes). Larsal: ignores them too; the partial block is never decrypted (CRY-01.10, LD-01). With a wrong password the result is `WrongKey` from the start bytes, not `Corrupt`.
- **CBC ciphertext length not a multiple of 16, version 4, inside valid block HMACs** (5 extra bytes; only a key holder can make this): the reference ignores them (observed). Larsal: `Corrupt` after the block HMACs (CRY-01.10). Bytes after the final block of the block stream are a different case: ignored by both (FMT-06.12, LD-01).
- **Ciphertext cut 5 bytes short, version 4, inside valid block HMACs**: the reference fails with an inner-header read error (observed). Larsal: `Corrupt`.
- **Version 3 file cut short**: when the cut reaches into the final hashed block or earlier, the walk fails: `Corrupt` (FMT-07). When fewer than 32 ciphertext bytes are left: `Corrupt` before key derivation (FMT-05.13 step 2).
- **Empty ciphertext** (version 4, valid empty block list): reference fails with an inner-header read error (observed). Larsal: `Corrupt`.
- **Field stream id 1, 4 or other** in version 4: `Unsupported` (reference: invalid inner stream cipher, observed).
- **Field stream id 3 in a version 3 file**: Larsal `Unsupported` (CRY-01.17, LD-10). Reference reads with Salsa20 and shows wrong protected values (observed).
- **Field stream key of unusual length** (empty, 1 byte, 1,000 bytes): the derivation in CRY-01.14 and CRY-01.15 works for any length. Whether Larsal accepts it is decided in FMT-09.

## Security notes

- The payload cipher gives confidentiality only. Integrity comes from the header HMAC and block HMACs (FMT-05, FMT-06) or from the hashed blocks (FMT-07). Larsal must never decrypt, decompress or parse a version 4 block before its HMAC passes, so CBC padding can never act as an oracle (AT-B07, AT-A03).
- Why `Corrupt` for bad padding and `WrongKey` for a wrong key is still no padding oracle (AT-B07; decided: spec/decisions.md LD-04, which is how E2-S4 and AT-B07 now read): the cipher API gives one error for any decrypt failure that depends on the data (CRY-01.11), and in files no padding result exists before the wrong-key check and the integrity checks have passed.
  - Version 4: the header HMAC (FMT-05) and every block HMAC (FMT-06) come first. Without the key no byte can be changed without failing an HMAC, so a person without the key never reaches the padding check.
  - Version 3: the start bytes (FMT-05.11, LD-12) and the whole hashed block walk (FMT-07) come first, and nothing after the final hashed block is ever checked or read (CRY-01.10, LD-01), so there is no padding result at all. A keyless change to the last cipher block either garbles part of the final hashed block (the walk fails: `Corrupt`) or, when that block holds only padding, changes nothing that is read, so the file opens with the same content, as in the reference (observed: an aligned version 3 demo vault with its last 16 ciphertext bytes replaced by random bytes opened). The outcome depends only on where the final hashed block ends, a fact about the plaintext length that the file size already nearly shows, never on decrypted bytes the attacker chose. Larsal must never read a padding length from a decrypted byte in version 3: then accept or reject would depend on such bytes, which is the oracle AT-B07 forbids.
  - Trailing bytes after the logical end (version 3) or after the final block (version 4) are ignored, never read as content, and never written by Larsal (LD-01). Cuts and swaps inside the checked data still fail (AT-A03).
- One generic error, `Decrypt`, for every decrypt failure that depends on the data (CRY-01.11); the key and IV length errors depend only on public lengths (LD-37). Never put the key, IV, keystream or plaintext into an error, log line or crash report (AGENTS.md rule 4, AT-C04, AT-C06).
- A nonce must never repeat under one key. Each save draws a fresh master seed and a fresh IV (CRY-03), so the final key and the nonce both change on every save. The field stream key is also fresh on every save, so its derived ChaCha20 key and nonce never repeat (AT-B03).
- The Salsa20 field stream uses a fixed nonce; its safety rests entirely on a fresh field stream key per save. Larsal reads Salsa20 but never writes it.
- The keystream for protected fields must be consumed in exactly the document order of FMT-09. A different order shows wrong values; it does not leak, but it breaks interop.
- Only `larsal-crypto` holds cipher code, built from the approved crates `aes`, `cbc`, `twofish`, `chacha20`, `salsa20` (architecture, AGENTS.md rule 3). No home-made cipher code.
- Keys, IVs in use and keystream buffers live in wiped memory types (SR-07).
- Parity rows: SF-01 (three payload ciphers, read and write), SF-08 (field stream cipher), SF-14 (cipher change applies on next save). Attacks and checks: AT-B01, AT-B07, AT-A02, AT-A03, AT-A11.

## How this was learned

- Read the reference's cipher wrapper (mode table, key sizes, IV sizes, the cipher id to mode mapping, the name to mode mapping), its stream wrapper around the cipher (block buffering, when the final padded block is processed), its field stream helper, the format constants (ids, the fixed Salsa20 nonce), both file readers (header field checks, IV handling, inner stream id checks) and both file writers (IV sizes, field stream id and key sizes).
- Read the reference's cipher tests and field stream test; they use the same public vectors listed here (NIST SP 800-38A, the Twofish authors' tables, eSTREAM Salsa20, the ChaCha20 drafts that became RFC 8439).
- Compared the installed release (2.7.11) source tag with the development source: the cipher code is the same apart from renames.
- Built a scratch reader and writer in `/tmp` (outside this folder) using only the standards above and the macOS `openssl` tool, and used them to (1) decrypt the reference's version 4.0 and protected-strings test vaults, which confirmed the ChaCha20 counter start, the 12-byte nonce and both field stream derivations; (2) craft demo vaults with password `demo-pw` and open them with the installed command line tool (2.7.11). That is how the 8 and 24-byte nonce acceptance, the 16-byte nonce and 12-byte CBC IV rejections, the AES-128 failure, the missing padding check in version 4, the ignored trailing bytes, the field stream id handling in both versions, the version 3 ChaCha20 payload, and the stream id rewrite on save were observed.
- Version 3 padding, observed with the installed command line tool on demo vaults (password `demo-pw`) built by a scratch version 3 writer: a vault whose plaintext before the padding was not a multiple of 16 (2,385 and 2,386 bytes in two builds) with its padding bytes set to `00` failed with a no-root-group error; the same vault with valid padding opened; an aligned vault (2,384 bytes) with its last 16 ciphertext bytes replaced by random bytes, without the key, opened. The source shows why: the cipher stream layer runs its padding-checking finish step only when its input reports end of data. In version 3 that input is the file itself, which reports end after the last cipher block, and the hashed block reader reads that block only when it holds part of the final hashed block. In version 4 the input is the block HMAC stream, which reports end only after the terminating block, so never on the last data block.
- Source reading of both file readers for the timing of the cipher start (CRY-01.3, CRY-01.9): the version 4 reader checks only for an empty IV before key derivation and starts the cipher after the header HMAC check; the version 3 reader starts the cipher after key derivation and before comparing the start bytes.
- Sprint 0 close-out: the lead rulings LD-01, LD-03, LD-04, LD-10, LD-12 and LD-20 and the default rule (CRY-01.9) were written in; the reference behavior observed before them is kept as facts. T38's raw last bytes were computed with the macOS `openssl` tool (decryption without padding removal).
- All vectors in Test cases were computed with the macOS `openssl` tool and Python's hashlib, and the ChaCha20 vectors were cross-checked between two independent implementations.
- Twofish (T9, T9b, T10, T34): computed with two independent open-source Twofish implementations installed on this Mac (libgcrypt and Nettle), called from a scratch script in `/tmp`; both gave the same bytes for every vector. The 49-step table and the 5 Monte Carlo rows match the Twofish authors' published known-answer tables (the reference's cipher tests quote the same public rows). The T34 demo vault was built by the scratch writer with those values and opened with the installed command line tool (2.7.11); the tool's own save of it (after an entry edit) was decrypted by the scratch reader with libgcrypt. Whether the approved `twofish` crate passes T9 to T10 is still for the Builder's unit tests and Verify to show.
- Sprint 1 close-out: CRY-01.11 now states LD-37: `KeyLength` and `IvLength` stay separate, public errors checked before any cipher work, and `Decrypt` covers every failure that depends on the data (test T38b). This matches the larsal-crypto error type.
