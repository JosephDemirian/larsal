# CRY-02 Key derivation: algorithms, defaults, limits, benchmark

Status: reviewed
Epics: E2-S5
Parity rows: SF-02, SF-03, SF-14

## What it does

The key derivation function (KDF) turns the 32-byte composite key (made from the password, key file and hardware-key response, see FMT-04) into the 32-byte **transformed key**. It is slow on purpose, so that guessing passwords is slow. FMT-04 then mixes the transformed key with the master seed into the payload key and the HMAC key.

Three KDFs exist: Argon2d, Argon2id (both RFC 9106) and AES-KDF (an old scheme: AES-256 applied many times). In version 4 files the KDF and its settings are stored in the KDF map (header field 11, encoding in FMT-03). Version 3 files always use AES-KDF, with its seed and rounds in header fields 5 and 6 (FMT-17).

This card fixes the ids, the exact algorithms, the settings and their defaults, the limits the reference enforces on the screen, in the command line tool and when reading a file, what happens to out-of-range values, and how the benchmark turns a target unlock time into settings.

## Inputs and outputs

- In: the composite key (32 bytes; FMT-04 says which parts go in, and when the hardware-key response is included), the KDF id, and its settings.
- Out: the transformed key (32 bytes); or an error before any work when a setting is out of range or the cost is above a refuse ceiling; or, before any work, the decision "ask the user first" with a cost report, which is not an error (CRY-02.14).

### KDF ids

Stored as 16 raw bytes in the `$UUID` entry of the KDF map (FMT-03), in RFC 4122 byte order (same order as the hyphenated text form).

| KDF | Id bytes (as stored) | Where it appears | Read | Written |
|---|---|---|---|---|
| AES-KDF, old id | `C9 D9 F3 9A 62 8A 44 60 BF 74 0D 08 C1 8A 4F EA` | implied by every version 3 file; in version 4 KDF maps | yes | yes: the reference always writes this id for AES-KDF, also in version 4 |
| AES-KDF, new id | `7C 02 BB 82 79 A7 4A C0 92 7D 11 4A 00 64 82 38` | version 4 KDF maps from other writers | yes, same algorithm as the old id | never |
| Argon2d | `EF 63 6D DF 8C 29 44 4B 91 F7 A9 A4 03 E3 0A 0C` | version 4 | yes | yes |
| Argon2id | `9E 29 8B 19 56 DB 47 73 B2 3D FC 3E C6 F0 A1 E6` | version 4 | yes | yes |

There is no id for Argon2i. Any other `$UUID` value is unsupported.

### Settings (KDF map keys)

FMT-03 owns the KDF map: the key names, value types, which keys are required, the accepted ranges, unknown keys and the write layout and order (FMT-03.11 to FMT-03.21). This table only says which algorithm input each key feeds.

| Key | Algorithm input | Used by |
|---|---|---|
| `$UUID` | which KDF (table above) | all |
| `R` | AES-KDF rounds R (CRY-02.1) | AES-KDF |
| `S` | AES-KDF seed (the AES-256 key), or Argon2 salt | all |
| `I` | Argon2 iterations t | Argon2 |
| `M` | Argon2 memory in **bytes**; m = floor(M / 1024) KiB | Argon2 |
| `P` | Argon2 lanes p | Argon2 |
| `V` | Argon2 version: `0x13` (1.3) or `0x10` (1.0), CRY-02.3 | Argon2 |
| `K`, `A` | Argon2 secret key and associated data: never passed to Argon2 (CRY-02.17) | none |

## Rules

### Algorithms

CRY-02.1 AES-KDF: split the 32-byte composite key into two 16-byte blocks. Encrypt each block R times with AES-256 in ECB mode (each block on its own, no chaining), using the 32-byte seed S as the AES key. Join the two resulting blocks (32 bytes) and hash them with SHA-256. The hash is the transformed key. In formula form: transformed = SHA-256(E_S^R(block0) || E_S^R(block1)), where E_S^R means R AES-256 encryptions with key S.

CRY-02.2 Argon2 (both types): Argon2 as defined in RFC 9106, type d for the Argon2d id and type id for the Argon2id id. Password = the 32-byte composite key. Salt = S. Iterations t = I. Memory m = floor(M / 1024) KiB. Lanes p = P. Version = V. Tag length = 32 bytes. No secret key and no associated data. The number of threads used to compute it does not change the result. Larsal computes on one thread: the approved `argon2` crate runs the lanes one after another, and its thread feature needs a crate that is not approved (decided: spec/decisions.md LD-38; adding threads is a later crate review, tracked for the E2-S7 gate). The reference computes the lanes on several threads (observed, CRY-02.14).

CRY-02.3 Argon2 version 0x13 and 0x10 are both computed as specified. RFC 9106 defines version 1.3 only; version 1.0 is defined by the Argon2 authors' earlier specification and reference implementation: the version number in the first hash is 0x10, and in every pass after the first a new memory block overwrites the old one, where version 1.3 XORs it into the old one. The approved `argon2` crate offers both versions. The installed reference (2.7.11) honours V: a demo vault with V = 0x10 derived with version 1.0 opens, the same file derived with version 1.3 fails with the wrong-key message (observed). The development source ignores V and always computes version 1.3 (differs in installed version; check with Verify). On open, Larsal follows the installed version and computes the version V names. On save, Larsal writes 0x13 (CRY-02.19, decided: spec/decisions.md LD-17).

CRY-02.4 The KDF always outputs exactly 32 bytes. Its output is a secret (wiped memory type).

### Reading settings from a file

CRY-02.5 Before any KDF work, Larsal validates every setting; no KDF work starts when a check fails.
- Version 4 KDF map: FMT-03 owns the structure, required keys, types and ranges (FMT-03.11 to FMT-03.19, with the error split in FMT-03.20). Every problem with the settings themselves is `Unsupported`, and so is m < 8 × p (CRY-02.10).
- Version 3 header fields 5 and 6: structure and presence errors are `Corrupt` (FMT-02.16, FMT-02.17, FMT-02.23); an out-of-range rounds value is `Unsupported` (CRY-02.13).
- The reference also refuses out-of-range version 4 settings before its KDF runs, with one message saying the KDF is unsupported or its parameters are invalid (paraphrased, observed). Where its checks are looser, the rules below say what its KDF then computes.

CRY-02.6 `$UUID`: FMT-03.11 owns the check. Both AES-KDF ids select the same algorithm (CRY-02.1); Argon2d and Argon2id select RFC 9106 types d and id (CRY-02.2).

CRY-02.7 Argon2 salt: the accepted lengths are in FMT-03.12 (8 to 32 bytes). The salt goes into Argon2 as read, at its stored length (RFC 9106 allows any salt of 8 bytes or more). The reference computes the same way (observed: a demo vault with a 16-byte Argon2 salt opened).

CRY-02.8 Argon2 version: the accepted values (0x10 and 0x13) and the full-width rule are in FMT-03.14 and FMT-03.18; CRY-02.3 says how each is computed. Reference note on computation: its setting check lets 0x11 and 0x12 through, and the installed version then computes a variant that no writer produces, so such a file fails with the wrong-key message (observed for 0x11).

CRY-02.9 Argon2 lanes: the range is in FMT-03.12 (1 to 16,777,215) and the full-width rule in FMT-03.18. This card adds the cost rule: above 128 lanes Larsal asks first (CRY-02.14). Reference note on computation: the installed version opened P = 129 (observed); the development source passes P to a general crypto library whose documented Argon2 limit is 1 to 128 lanes, so the source would refuse P > 128 with a KDF error (check with Verify).

CRY-02.10 Argon2 memory: m = floor(M / 1024) KiB and its range (8 KiB to 2^32 - 1 KiB) are in FMT-03.12 and FMT-03.13. This card adds m ≥ 8 × p, which RFC 9106 requires: a smaller m is `Unsupported` before any work. The reference has no such check before its KDF; its Argon2 code then refuses with a memory-too-small message (observed for m = 8, P = 2). Development source note: its crypto library also documents m ≤ 8,388,608 KiB (8 GiB) (check with Verify).

CRY-02.11 Argon2 iterations: the range (1 to 2,147,483,646) and the full-width rule are in FMT-03.12 and FMT-03.18. Reference note on computation: it computes with the cut-down value and writes that value back on save (observed: I = 2^32 + 1 ran 1 iteration, and the saved file said I = 1). Larsal never computes with or saves a number other than the stored one (CRY-02.19; Security notes).

CRY-02.12 AES-KDF in the version 4 map: the required keys, the range of R and the rule that S is exactly 32 bytes are in FMT-03.16. Any other seed length is `Unsupported` (decided: spec/decisions.md LD-14). The KDF fact behind it: AES-256 needs a 32-byte key. The reference accepts S of 8 to 32 bytes, and for any S shorter than 32 bytes its AES step does nothing, without any error (it only logs a warning that AES-256 cannot take a key of that length; the command line tool prints it to stderr, observed). The transformed key is then just SHA-256(composite key) (observed with 8 and 16-byte seeds: the file opens with zero KDF work; when saved, the reference writes a new seed of the same short length, so the vault stays without KDF protection, CRY-03.4).

CRY-02.13 AES-KDF in the version 3 header: field 5 (seed) must be exactly 32 bytes and field 6 (rounds) exactly 8 bytes, a u64 little endian; a wrong size or a missing field is `Corrupt` (FMT-02.16, FMT-02.17, FMT-02.23). The reference also rejects a wrong size (observed messages about an invalid transform seed size and an invalid transform rounds size), but fills in a default for a missing field (FMT-17.7). Larsal then requires 1 ≤ rounds ≤ 2,147,483,646 and rejects other values with `Unsupported`. Reference: drops to signed 32 bits and, if the result is outside 1 to 2^31 - 2, silently uses **1 round** without any message (observed for 0 and 2^31; 2^32 + 5 is read as 5 rounds). When saved, the reference writes the value it used (0 becomes 1, observed). Larsal's stricter rule stands (decided: spec/decisions.md default rule; a file genuinely written with such a count would not open in the reference either, because the reference derives with a different round count).

CRY-02.14 Cost ceiling before work (AT-A05). The thresholds live in `larsal-format/limits.rs`; the values below are decided (spec/decisions.md LD-22; revisit if a demo vault, or a vault a user reports, passes one).
- When: after CRY-02.5 to CRY-02.13 pass and after every check that needs no key. Version 4: step 4 of FMT-05.7, after the header SHA-256 check, so a damaged header gives `Corrupt` and never asks. Version 3: step 3 of FMT-05.13, after the ciphertext length check. No KDF work and no Argon2 memory before it.
- Estimate. Memory = m × 1,024 bytes for Argon2, none for AES-KDF. Time, from the speed record below, counted for one thread (decided: spec/decisions.md LD-38): Argon2 estimated ms = I × m × rec_ms / (rec_I × rec_m); AES-KDF estimated ms = R × rec_ms / rec_R. Rounded up to whole milliseconds. Lanes do not shorten the estimate, because Larsal computes Argon2 on one thread (CRY-02.2). Reference, for comparison: it runs the lanes on several threads (observed with the installed tool on this Mac, 14 logical processors: Argon2id demo vaults with m = 262,144 KiB and I = 4 opened in about 0.9 s with P = 1 and about 0.3 s with P = 4), so a vault with several lanes can unlock faster in the reference than in Larsal.
- Speed record. Every Larsal benchmark run (CRY-02.28) stores its measured run (the fastest of three at the final count, LD-40) per KDF family in Larsal's settings on this Mac, never in a vault: for Argon2 rec_I, rec_m (KiB), rec_p and rec_ms (rec_p is kept but not used by the one-thread estimate); for AES-KDF rec_R and rec_ms. If the family has no record yet, Larsal first runs a calibration and stores it as the record: the CRY-02.28 measuring loop (doubling until one run takes at least 50 ms) on dummy inputs, 32 zero bytes as password and 32 zero bytes as salt or seed; for Argon2 with the file's Argon2 type, m = 65,536 KiB and p = min(4, n), where n is the number of logical processors; for AES-KDF starting from 100,000 rounds. The calibration holds no secret and uses at most 64 MiB.
- Refuse with `TooLarge`, which cannot be approved: m larger than the Mac's physical memory, or I > 1,000,000,000. Only these two refuse rules give `TooLarge` here.
- Ask, when no refuse rule applies: m > 1,048,576 KiB (1 GiB), or P > 128, or the estimated time is over 10,000 ms.
- Run: none of the above applies.
- How the ask works. `larsal-format` cannot show a screen. In an ask case the cost check returns the decision "ask the user first" (FMT-04.21 step 2 and FMT-05.7 step 4a, which own the open order). It is not an error kind. It carries a cost report: the KDF id, m in bytes, I or R, P, the estimated ms, and which thresholds were hit. No KDF work has run. `larsal-core` hands the report to `larsal-desktop`, which shows memory and time and asks (APP-06 owns the words). On yes, `larsal-core` runs the open again with an approval holding the report's KDF id, m, I or R, and P; `larsal-format` runs the KDF only if the file's settings equal the approval, and otherwise decides again from the start. On no, or when the user closes the question, the open stops with nothing done and no error: nothing derived, nothing kept, the vault not opened, no error message. The command line tool cannot ask: it stops without any KDF work and prints the cost; how it reports that, and whether an option there may approve it, is for the command line tool's card (INT-10) to decide. A save never asks: the settings were approved at open or chosen by the user (CRY-02.24).
- Test hooks: the physical memory size, the number of logical processors and the speed record can be fixed by tests, so every Mac gives the same result (T17 and T25 to T25c use 16 GiB and 8 logical processors).
- Reference: it has no such step and starts the KDF right after reading the settings (source reading; a 4 TiB or 2^31-iteration file was not run because it could exhaust this Mac; check with Verify). The values in AT-A05 itself are already outside the ranges: 4 TiB is m = 2^32 KiB (rejected), 2^63 iterations drops to 0 (rejected), 2^24 lanes (rejected).

CRY-02.15 The KDF runs on a worker thread, never on the screen thread, both when opening and when saving (CRY-03: every save runs the KDF again because the salt changes).

CRY-02.16 Error kinds on open: a version 4 setting outside FMT-03's rules, a version 3 rounds value out of range, and m < 8 × p give `Unsupported`; a version 3 field 5 or 6 that is missing or of the wrong size gives `Corrupt` (CRY-02.13); a cost above a refuse ceiling gives `TooLarge` (CRY-02.14), and a cost in the ask band gives the "ask the user first" decision, which is not an error kind; an Argon2 or AES failure while computing (for example the library refuses the settings) gives `Unsupported` too, with no key bytes in the message; only the header HMAC (version 4, FMT-05.8) or the start bytes (version 3, FMT-05.11, decided: spec/decisions.md LD-12) give `WrongKey`. The reference shows three different messages for invalid parameters, a too-small memory and a wrong key (observed).

CRY-02.17 Argon2 `K` (secret) and `A` (associated data): FMT-03.15 owns the read rule (a non-empty value is `Unsupported`, an empty one counts as absent). Larsal never passes a secret or associated data to Argon2 (CRY-02.2). Reference: ignores both and derives without them (observed: demo vaults with `A` or `K` set, derived without them, open).

CRY-02.18 Unknown extra keys in the KDF map never change the derivation. FMT-03.19 owns how they are read and that they are not written back (the reference rebuilds the map from its settings, so it drops them, observed for `A` and `K`).

### Writing settings

CRY-02.19 On save Larsal writes the vault's KDF with these values; FMT-03.21 owns the types, order and layout. `$UUID`: the Argon2d or Argon2id id, or the **old** AES-KDF id for AES-KDF, never the new id. `S`: a fresh 32-byte random salt (CRY-03, LD-15). Argon2: `I`, `M` = m × 1024, `P`, and `V` = 0x13 always: a vault read with V = 0x10 is saved with 0x13, and that save's KDF run computes version 1.3 (decided: spec/decisions.md LD-17; the newer reference computes 1.3 anyway, and every save runs the KDF again). AES-KDF: `R`. No `K`, no `A`. Iterations, memory, parallelism and rounds are kept exactly as they are; a save never lowers them (AT-A09).

CRY-02.20 A vault opened from a version 3 file and saved as version 4 keeps AES-KDF with the same rounds and a new 32-byte seed, and is written with the old AES-KDF id (decided: spec/decisions.md LD-07; FMT-16.21 owns the conversion). Which parts of the composite key go into the KDF changes with the version (the hardware-key response is included in version 4); FMT-04 and FMT-16 own that.

CRY-02.21 Changing the KDF or its settings takes effect on the next save (SF-14). The new settings get a new salt at once and again on save (CRY-03).

### Defaults for new vaults

CRY-02.22 Reference defaults, new vault in the screen (same in the installed release and the source): KDF Argon2d (labelled as recommended), memory 64 MiB (m = 65,536 KiB, stored M = 67,108,864 = `00 00 00 04 00 00 00 00` as u64 LE), parallelism = the smaller of 4 and the number of logical processors (4 on this Mac), version 0x13, salt 32 random bytes, iterations set by the benchmark (CRY-02.27) for a 1,000 ms target; cipher AES-256 (CRY-01); file version 4. Reference defaults in the command line tool: AES-KDF with the old id, 1,000,000 rounds and a 32-byte seed, AES-256, file version 3.1 (observed: header field 6 = `40 42 0F 00 00 00 00 00`); with a target time option the rounds come from the AES-KDF benchmark (CRY-02.27). The result varies per run: about 130 to 150 million rounds for 1,000 ms on this Mac (observed: 150,000,000 in one run, after which the vault took about 1.2 s to open; 130,434,784 in another, see CRY-02.27 for how that number comes out).

CRY-02.23 Larsal defaults for new vaults: Argon2id, 64 MiB, parallelism min(4, logical processors), version 0x13, 32-byte salt, iterations from Larsal's benchmark for a 1,000 ms target, AES-256 (plan/security.md). This differs from the reference's Argon2d default; both read each other's choice (decided: spec/decisions.md LD-18; RFC 9106 recommends Argon2id).

### Limits on the screen and in the command line tool (reference)

CRY-02.24 Reference screen, advanced settings: iterations or rounds 1 to 1,000,000,000; memory 1 to 1,048,576 MiB; parallelism 1 to 128; KDF choices for version 4 are Argon2d, Argon2id and AES-KDF, for version 3 only AES-KDF. Choosing AES-KDF for version 4 stores the new AES-KDF meaning in memory but the file gets the old id (CRY-02.19). Before saving, the screen warns and asks to confirm when Argon2 iterations are above 10,000 (opening may take very long) or AES-KDF rounds are below 100,000 (weak against guessing); the user may keep the value. Larsal's own screen limits belong to MOD-12 and APP-07; Larsal keeps at least the same two warnings.

CRY-02.25 Reference screen, basic settings: a target unlock time slider from 100 ms to 5,000 ms in steps of 100 ms, default 1,000 ms. The chosen time is stored in the vault's custom data under a key stored encoded (name rule) `4B 50 58 43 5F 44 45 43 52 59 50 54 49 4F 4E 5F 54 49 4D 45 5F 50 52 45 46 45 52 45 4E 43 45`, value = the time in milliseconds as decimal text (for example `1000`). The item is removed when advanced settings are saved. When the screen opens again it shows max(100, stored value). Larsal keeps this item when present (FMT-14) and is free to store its own preference. Larsal writes it with the chosen time whenever it sets the count from that time by its own measurement (CRY-02.28: the wizard's simple mode and Option A's "Recommended" and "Custom", APP-07.10; the vault settings' unlock time, MOD-12.11), keeps it when only the cipher changes, and removes it when a count is set any other way, such as a typed count (decided: spec/decisions.md LD-224).

CRY-02.26 Reference command line tool: the vault create command takes an optional target time in milliseconds. It must parse as an integer greater than 0 (else an invalid-time error, observed for 0 and for text) and lie in 100 to 5,000 inclusive (else an error naming the range, observed for 99 and 5001; 100 and 5000 accepted). The tool has no option for cipher, KDF type, memory or parallelism.

### Benchmark

CRY-02.27 Reference benchmark (for parity notes; Larsal's own method is CRY-02.28). Target default 1,000 ms. Time is measured in whole milliseconds.
- All arithmetic is in single-precision floating point (IEEE 754 binary32, round to nearest), and the final value is cut toward zero to a signed 32-bit integer.
- AES-KDF: run the AES-KDF 3 times with 1,000,000 rounds each on a fixed 16-byte input and a fixed 32-byte seed, measure the total time T ms, and set rounds = (3,000,000 × target, as single precision) / T, cut toward zero. Worked example of the rounding: T = 23 ms, target 1,000: 3,000,000,000 / 23 = 130,434,782.6, which rounds to the nearest single-precision value 130,434,784 (spacing 8 at that size), so the tool sets 130,434,784, not the exact floor 130,434,782 (observed: the tool printed 130,434,784 and header field 6 = `e046c60700000000`). Note: the real KDF encrypts two blocks per round, the benchmark one; on this Mac the result still opened in about 1.2 s for a 1 s target (observed).
- Argon2: keep memory and parallelism as chosen, run Argon2 once with a baseline iteration count, measure T ms, and set iterations = baseline × (target / T), where target / T is computed first and rounded to single precision, then multiplied by the baseline in single precision, then cut toward zero. The baseline is 4 for the benchmark button in the advanced settings, and the vault's current iterations (10 for a brand-new vault) when the basic slider is saved.
- Where the result goes, and what happens to out-of-range results (source reading):
  - Basic slider and command line tool: the result goes straight to the setting check, which replaces a result below 1, or 2,147,483,647 or more, with **1** without a message. The command line tool still prints the unchecked number.
  - Benchmark button in the advanced settings: the result goes into the iterations (or rounds) field, which clamps it to that field's limits of 1 to 1,000,000,000 (CRY-02.24). So a result above 1,000,000,000 shows as 1,000,000,000, and a result below 1 shows as 1.
  - Overflow: a single-precision value too large for a signed 32-bit integer has no defined conversion; on this Mac (Apple silicon) the conversion saturates at 2,147,483,647. T = 0 ms gives an infinite ratio (no crash) and therefore the same saturated value. So on this Mac an overflow gives 1 through the slider or the command line tool and 1,000,000,000 through the advanced-settings button. An overflow happens when T is 0 ms or, for AES-KDF, on a Mac fast enough that 3,000,000 rounds take under about 7 ms with a 5,000 ms target (not reproducible on this Mac; check with Verify, including other processor types where the conversion may give a negative number instead).
- Further reference details (source reading):
  - The Argon2 benchmark returns **1** when its trial run fails (for example the Argon2 code refuses the settings). That value then goes through the paths above.
  - Each time the KDF choice changes in the advanced settings, the screen compares the new choice with the vault's stored KDF. Argon2d and Argon2id count as one family, the two AES-KDF ids as the other. Same family: the stored values are loaded into the fields. Different family: the screen runs the benchmark again; when the new choice is Argon2 (the stored KDF is AES-KDF), it first resets memory to 64 MiB and parallelism to a fixed **4**, not min(4, logical processors).
  - The advanced-settings benchmark (baseline 4, target 1,000 ms) also runs on its own when the settings of a brand-new vault are first opened, with the new vault's Argon2d defaults (64 MiB, parallelism min(4, logical processors)).

CRY-02.28 Larsal benchmark: given a KDF type, memory, parallelism and a target time (default 1,000 ms, allowed 100 to 5,000 ms), Larsal measures with a monotonic clock of at least microsecond resolution (in Larsal the thread's CPU time, so other work on the Mac cannot make the result weaker; decided: spec/decisions.md LD-72), starting from 1 iteration (Argon2) or 100,000 rounds (AES-KDF) and doubling until one run takes at least 50 ms. It runs that count twice more and keeps the fastest of the three times (decided: spec/decisions.md LD-40). Argon2 memory above the Mac's physical memory is refused with `TooLarge` before any run. It then sets iterations (or rounds) = ceiling(measured count × 1.1 × target / measured time), clamped to at least 1 and at most 2,147,483,646 (the maximum of FMT-03.12 and FMT-03.16). The caller that keeps the result clamps Argon2 iterations further, to at most the refuse ceiling of CRY-02.14 (1,000,000,000), so a tuned vault always opens again in Larsal (the benchmark itself does not know the ceilings, which live in `larsal-format/limits.rs`). AES-KDF rounds have no refuse ceiling; a very high count only asks (CRY-02.14). In practice this clamp is reached only with a fake clock (T42b) or a timer fault, and then the unlock is shorter than the target. The factor 1.1 aims at the middle of the window that meets both checks: AT-B06 wants an unlock that takes at least the target, and E2-S5 wants one within 20% of it, so a default run must land between 1.0 and 1.2 times the target on this Mac (T41; decided: spec/decisions.md LD-19). It never falls back to a smaller value on overflow. It never changes memory or parallelism. It stores its last measured run (count, memory, lanes, time) as the speed record of CRY-02.14. The wizard and the vault settings call it once with 1,000 ms and scale that count N for another time as ceiling(N × target / 1,000) (APP-07.8): never below this rule's count for that target, at most ceiling(target / 1,000) above it (decided: spec/decisions.md LD-224).

### Known answers

CRY-02.29 The KDF code passes the RFC 9106 test vectors for Argon2d and Argon2id (with secret and associated data, which only the vectors use), the no-secret vectors below, and the AES-KDF vectors below, before it is used (AT-B01).

## Edge cases and errors

- **Version 4 map problems** (unknown or malformed `$UUID`, a required key missing, a wrong type, a value out of range, a non-empty `K` or `A`, an AES-KDF seed other than 32 bytes, `M` not a multiple of 1024): FMT-03 owns every one of them (FMT-03.11 to FMT-03.19). The KDF-side effects in the reference are in CRY-02.7 to CRY-02.12 and CRY-02.17.
- **m < 8 × p**: `Unsupported` before work (CRY-02.10; reference fails inside the Argon2 code, observed).
- **Version 3 field 5 or 6 missing, or of the wrong size**: `Corrupt` (CRY-02.13, FMT-02.16, FMT-02.17, FMT-02.23); the reference fills in a default for a missing one (FMT-17.7).
- **Version 3 rounds 0 or above 2,147,483,646**: Larsal `Unsupported`; the reference cuts the value to 32 bits and silently uses 1 round when the result is out of its range (CRY-02.13).
- **Huge but in-range cost** (for example m = 2^32 - 1 KiB, or I = 2^31 - 2): Larsal asks or refuses per CRY-02.14 before allocating anything.
- **Huge cost and a damaged header together**: version 4 gives `Corrupt` from the header SHA-256 check and never asks; version 3 gives `Corrupt` from the ciphertext length check and never asks (CRY-02.14).
- **No speed record yet on this Mac**: Larsal runs the short calibration of CRY-02.14 first; it uses dummy inputs and at most 64 MiB.
- **User declines the cost question** (or closes it): the open stops with nothing done and no error: no KDF work, nothing kept, no error message (CRY-02.14, FMT-04.21 step 2).
- **Benchmark measures 0 ms or overflows**: Larsal's method (CRY-02.28) cannot produce either; the reference sets 1 through the basic slider or the command line tool, and 1,000,000,000 through the advanced-settings button (CRY-02.27).
- **KDF computation fails for any other reason** (out of memory): `Unsupported`, the open stops, no partial key is kept, memory is wiped.

## Security notes

- Argon2 working memory is the crate's own block type in a wiped `Zeroizing` buffer, not `SecretBytes` (decided: spec/decisions.md LD-39); it is private, wiped on drop, never cloned or printed.
- What could go wrong: a hostile file can ask for terabytes of memory or billions of iterations and freeze or crash the app before the HMAC can show the file is fake, because the KDF must run before the HMAC check. Larsal therefore checks ranges and cost first (CRY-02.5, CRY-02.14). This is attack AT-A05.
- A file can also ask for **too little** work: AES-KDF with a short seed (zero work in the reference), 1 round, 1 iteration, 8 KiB. Larsal never silently weakens a vault: it rejects broken settings (CRY-02.12, CRY-02.13), never lowers settings on save (CRY-02.19, AT-A09), and asks before the user sets weak values (plan/security.md extra hardening; CRY-02.24 warnings).
- Never truncate a 64-bit setting silently into a different number; the reference does (CRY-02.11 to CRY-02.13) and Larsal must not.
- The composite key, the transformed key and all Argon2 memory hold secrets. They live in wiped memory, never in logs or error text (AGENTS.md rule 4, SR-07, AT-C01).
- Only `larsal-crypto` computes the KDF, with the approved `argon2` and `aes` crates (AGENTS.md rule 3).
- The stored settings must equal the settings used: AT-B06 times an unlock and compares.
- Benchmark window (decided: spec/decisions.md LD-19): the tuned KDF takes 1.0 to 1.2 times the target, which meets both AT-B06 (at least the target) and E2-S5 (now worded the same way). CRY-02.28 aims at 1.1 times the target and rounds up (T41). A KDF that runs shorter than the user's target is weaker than promised, so the lower edge never goes below the target.
- Parity rows: SF-02 (Argon2d, Argon2id, AES-KDF with settings in the file), SF-03 (benchmark to a target time), SF-14 (change KDF and cost later). Attacks and checks: AT-A05, AT-A09, AT-B01, AT-B06.

## How this was learned

- Read the reference's KDF base (seed size limits, rounds check, default target times), its AES-KDF and Argon2 implementations (parameter checks, map reading and writing, transform, benchmark), the format constants (ids, map key names), the function that builds a KDF from a map (old-to-new AES-KDF id mapping), the vault object (defaults, salt refresh, KDF change), the encryption settings screen and its layout file (spin box limits, slider range, warnings, the stored time preference), the new-vault wizard, the command line create command, and both file readers (version 3 seed and rounds checks).
- Compared the installed release tag 2.7.11 with the development source: the only KDF difference is the Argon2 implementation (the installed release uses the Argon2 authors' reference library and passes the version; the development source uses a general crypto library that ignores the version). The installed app bundle links the Argon2 reference library and that crypto library 3.7.1.
- Used the installed command line tool (2.7.11) on demo vaults in `/tmp` (password `demo-pass-1` or `demo-pw`): created vaults with and without a target time, timed opening, tested the target-time limits.
- Built a scratch writer in `/tmp` (outside this folder) from the public standards and the macOS `openssl` tool (Argon2 via the Homebrew OpenSSL 3.6 KDF command, AES via the `openssl enc` command), crafted demo vaults with every edge setting listed above, and opened each with the installed tool. Every "observed" in this card comes from that run. Huge-memory and huge-iteration files were not run against the reference on purpose.
- RFC 9106 vectors T5 and T6 were reproduced with the OpenSSL 3.6 Argon2 KDF. AES-KDF vectors were computed with the `openssl enc` command (CBC with a zero IV and zero blocks after the input block gives the repeated ECB encryption; rounds 1 and 2 were cross-checked with plain ECB calls).
- Sprint 0 close-out: the lead rulings LD-07, LD-14, LD-15, LD-17, LD-18, LD-19 and LD-22 and the default rule (CRY-02.13) were written in; T25a no longer uses appended bytes as damage (LD-01). Observed reference behavior is kept as facts.
- Cross-check pass: re-read the version 3 header reader (a seed or rounds field of the wrong size is an error; a missing one leaves the model default in place) and aligned CRY-02.5 and CRY-02.13 with FMT-02. Map keys, types, ranges and the write layout now live only in FMT-03; this card points there and keeps the algorithms, the m ≥ 8 × p rule, the cost ceiling, defaults and the benchmark. The ask step of CRY-02.14 (when it runs, the estimate, the calibration, the approval) is Larsal design placed after the checks of FMT-05.7 and FMT-05.13; the reference has nothing to compare it with.
- Sprint 1 close-out: the ask band of CRY-02.14 is now a returned decision, not an error, as FMT-04.21 step 2 and FMT-05.7 step 4a say (it matches the larsal-crypto code's ask verdict); the time estimate counts one thread (LD-38), so T25b changed; the benchmark's caller clamps Argon2 iterations to the refuse ceiling (T42b); CRY-02.16 names the version 3 `WrongKey` case. Observed with the installed CLI (2.7.11) on two Argon2id demo vaults (m = 262,144 KiB, I = 4, password `demo-pw`) built by a scratch writer: P = 4 opened in about 0.3 s and P = 1 in about 0.9 s, three runs each, so the reference runs the lanes in parallel. Source reading: the installed version passes P to the Argon2 reference library as both the lane count and the thread count.
