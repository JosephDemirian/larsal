# guarded_check

One command for the full check of one commit, offline, with demo data, under private homes and targets.

    Python -B -I guarded_check.py <git-commit-or-repo-top-folder> [--only static,rust,native,docs,fuzz]
        [--repo PATH] [--baseline FILE] [--waivers FILE] [--hold FILE] [--busy FILE [--busy-from WORDS] [--busy-to WORDS]]
        [--part-of ROOT]

Python is the pinned interpreter named in `gc_lib.py`. With `--repo` the first word is always a commit. Without it, a repo's top folder means its HEAD, and anything else is a commit in the current folder's repo.

## Results

| Overall | Exit | Means |
|---|---|---|
| PASS | 0 | A full run: every step passed, every gate held, every grant held, and the running tool equals the commit's `scripts/guarded`. Only this stands for a merge. |
| PASS (only ...) | 4 | The steps asked for passed. A part never exits 0. |
| FAIL | 1 | `summary.txt` lists each reason. |
| (none) | 2 | The user database did not answer for 60 s (Live kernel rows 14), or the command line was wrong (a `--busy-from` or `--busy-to` that is not one line of words, or either without `--busy`): nothing ran, no root was made. |
| NEEDS_REVIEW | 3 | At least one grant was withheld, or the running tool's bytes differ from the commit's `scripts/guarded`. A commit with no such folder, or a link there, differs in every name. This outranks PASS and FAIL. `summary.txt` names the files that differ, and lists each row under "grant withheld: needs review", and failures of a withheld row are labelled "caused by a withheld grant". The label is by row, not proved test by test. Native runs under one profile, so with any needs row withheld every native failure carries it, and one can have another cause. |

A failed test can never be waived. Tests lost or newly ignored against `--baseline` fail unless the lead's waiver file lists them with a reason. A full run without a baseline, or with one holding no tests of the rust, native or docs step, fails: nothing would catch a lost test. A baseline with no table of tests, a value that is no state word, a full run's step missing, or made from the commit under test is refused at the start, exit 1, with no root made and no run time spent; so is a waiver file of another shape. `summary.txt` prints the commit a baseline was made from. A baseline holding fewer than half of a lane's tests in this run, counting only its passing ones, and more than 16 short, fails at the end, and no waiver clears that. A smaller gap passes, so a small lane that doubles stays green, and a wrong baseline can still hide a lost test inside those margins. A doc test's key holds no line number, so an edit above it does not lose it; doc tests on one item are numbered in line order, so a lost one still shows, as the last number.

## What it does

Each run makes a new root, `/private/tmp/larsal-gc-<short commit>-XXXX`, and runs in this order, with no retry. A run keeps its root, about 20 GB; nothing removes it. Sealed folders are read only, so remove a root with `chmod -R u+rwx` first.

1. **Source.** Refuses a repository with replace refs or a shallow file; every git call ignores replace refs and grafts. Reads the pins, then exports exactly the commit's tracked files, by blob, under a sandbox whose one write root is the export. Checks the route table, and the running tool against the commit's `scripts/guarded`.
2. **Static.** check.sh's own G1, deny and audit bodies, under the outer guard (`g/`).
3. **Rust.** Builds, records the six lanes without running a test, reconciles, screens imports, reruns the byte checks, makes the plans, runs each program alone through the helper, reconciles after each lane (`r/`). app09 runs in step 4.
4. **Native.** Setup, then G (Swift lint), A (build), B (Swift tests, APP09), one outer sandbox per attempt, with its gates (`runs/`, `lane-out/`, source `s/`). Each attempt has its own two live kernel readers and two sentinel denials (Live kernel rows, below), and reads the owner's simulator folder before and after (Live kernel rows 15).
5. **Docs.** The three doc lanes.
6. **Fuzz.** Every route the commit lists, 30 s each, four at a time.
7. **Summary.** `summary.json`, `summary.txt`, `test-names.json`, built only from the root's files, every count recounted from raw output.

`--hold FILE`: before each heavy step and before each native attempt, wait while that file exists, polled every 30 s, at most 30 minutes, not counted in the alarm. Only a stop signal or the 30 minutes end the wait, and then the step does not start; once the 30 minutes ran out, no later step waits on the file again. `--busy FILE`: one JSON line naming this run, held from before the native step's first attempt through its end compare; a dead run's mark is taken away, any other is waited for. `--busy-from WORDS` takes over a mark that holds exactly that one line, and `--busy-to WORDS` leaves that one line in place of this run's mark, both with no instant without a mark (Live kernel rows 12). `--part-of ROOT`: this run is part B of a two-part run (The 60-minute cap and the two-part form, below). `--baseline FILE`: an earlier run's `test-names.json`. Run the summary alone on a private copy of a run: `gc_summary.py <root>`. Parsers and compare: `gc_summary.py --self-test`.

## Grants follow reviewed content

Every row above base has one row in `tables/pins.json`: 37 Rust rows, 18 native needs rows. A row holds the paths its grant rests on, each path's git tree or blob hash at the reviewed commit, the review's name, why those paths, and its byte checks.

- At a run the tool asks git for each hash at the commit under test. On any difference the row runs at base with no grant: no profile above base, no class, no needs line. The sshd no-sandbox line is absent at base.
- At each run the build's bytes are read for every Rust row still holding a grant: R2b's byte checks, by name in `byte_checks`. A failed check withholds the row the same way.
- The grant also needs the program built from its pinned folder, `crates/<package>`: the source path in Cargo's JSON and the manifest folder in the capture are compared. A same-name package elsewhere runs at base and the run ends NEEDS_REVIEW. So does every row, needs rows too, with a pin on a crate the build took from another folder. This read goes by package name, so it does not see a dependency renamed with `package =`. Such a rename sits in a pinned manifest, the root `Cargo.toml` or `.cargo/config.toml`, and each row pinning that file goes to base the same way.
- A new program gets base and is listed. A row with no pin is withheld. No flag, waiver or environment variable overrides a pin.
- The pinned hashes come from one commit, and this round's proof compares each pinned path, file by file, with the source R2b and N1b read (`pins-vs-reviewed.json`, in its proof folder). No difference. The pins added later, own_agent's linked crates and the window rows' key event paths, hold the same hash at that commit and at the commit this tool landed on, and equal the source those reviews had; no review read them for this purpose. Own_agent's build paths (the root `Cargo.toml`, `.cargo/config.toml`, `Cargo.lock`, `rust-toolchain.toml`, `vendor`), its five folders that no other row pins (`larsal-hwkey`, `larsal-proto`, `larsal-server`, `larsal-share`, `uniffi-bindgen`) and the window rows' `crates/larsal-autotype` tree hold that commit's hash too, also unread for this purpose. `crates/larsal-browser`, on its three rows labelled F-334, moved later: it differs from what R2b read by `tests/int03.rs`, a program at base.

**What a pin does not cover.** A crate outside a row's paths is not pinned, so a change in a dependency keeps the grant; the byte checks, and on a board or window row the guard, are what is left there. A key has no kind: a bin and a test of one crate and name both get the row. Pins are content, not behaviour: an unchanged tree can still act differently on another Mac or toolchain.

**own_agent, the row that leaves the sandbox.** It pins `crates/larsal-sshagent` and every workspace crate it links: `larsal-core`, `larsal-crypto`, `larsal-format`, `larsal-model`, `larsal-platform` and `log`; what chooses them and their third-party code: the root `Cargo.toml`, `.cargo/config.toml`, `Cargo.lock`, `rust-toolchain.toml` and `vendor`, 134 packages by the proof run's build fingerprints, build scripts' own included; and the five workspace folders no other row pins, `larsal-hwkey`, `larsal-proto`, `larsal-server`, `larsal-share` and `uniffi-bindgen`, because the workspace lane builds them beside this program and a build script in one can rewrite its bytes. A change in one of them takes the row to base until the commit moves its pin, so a dependency renamed with `package =` loses the sshd line. A new folder in `crates/` is a new member, and `--locked` refuses it until `Cargo.lock` moves. What truly remains on this row: a build script in the workspace's other folders, `larsal-autotype`, `larsal-bridge`, `larsal-browser`, `larsal-cli`, `larsal-ffi` and `larsal-sync`, can rewrite these bytes too. Each has a tree pin on another row, so a change there ends the run NEEDS_REVIEW, yet own_agent keeps its line in that run. A commit that moves any of these pins in its own diff keeps the line and can read PASS, and that code can start sshd with any config, outside the sandbox. The guard does not load on this row, because its profile has no board or window line. Only the string byte checks stand there, and the review of the commit's diff, which holds the pin move. The cost: a story that touches one of the five must move this row's pin in its own commit, and C1 and C2 read that line; one that forgets spends a whole run to read NEEDS_REVIEW with own_agent at base.

## What is contained, and what is not

**Runs under a sandbox:** the export, every static, doc and fuzz phase (the guard), every Cargo build and capture, each Rust test program and its children under its own profile, every native attempt. All are `(allow default)` with deny lists, so a service nobody listed stays reachable.

**Not contained, plainly:**

- The driver, the helper (until its last exec), the summary, `clang` in setup and `git` for the pins run unsandboxed as the owner. The kernel refuses a sandbox inside a sandbox, so the driver cannot sit in one. So do `log show`, the two live kernel readers and the sentinel's `sandbox-exec`; its `touch` runs under its one-line profile.
- `sshd` and the login shell it starts leave the sandbox, for the one row `workspace:larsal-sshagent/own_agent`, while that row's pins, source path and byte checks hold. See R2b 2 below.
- Native has no `iokit` line (N1b 34). The window server line and the launch services line mean the profile does not itself stop xctest or Larsal from showing a window (N1b 7).
- The owner's home is readable by the export, except `.ssh` and `Library`, because it reads the repository there.

**Gates are per stage.** Reading them as run-wide would be wrong.

| Gate | Where it runs | Where it does not |
|---|---|---|
| Window watcher, about every 3 s; only the on-screen flag | native G and B | native A, Rust, static, docs, fuzz |
| Guard library, board requests | xctest; Rust rows holding the board or the window line | Larsal, static, docs, fuzz, every other Rust row, anything below |
| Kernel rows for sensitive grants, from the live readers merged with `log show` | native | Rust, static, docs, fuzz |
| Live kernel readers: reading before the attempt, not ended early, both sentinels denied and each one's row in both readers, each reader's exit 0 after SIGINT and the ndjson end record, no loss, at least one row of the run's own processes (pids the sampler read; rows kept by a name alone never count) | each native attempt, G, A and B | Rust, static, docs, fuzz |
| The owner's simulator folder: every name, kind, size, link text and file SHA-256 under `~/Library/Developer/CoreSimulator/Devices` the same after as before; a time or inode alone is information | each native attempt, G, A and B | Rust, static, docs, fuzz |
| A test `tables/programs.json` lists as `ignored` for a program exists, runs alone and passes | Rust, after that program | native, static, docs, fuzz |
| Test plan is the reviewed one (one bundle, real xctest host, no UI bundle) | after native A and before B | |
| Owner sentinels, a process left under the root | after each step and at the end | |
| Tool, profile and guard library custody | before each phase and at the end | |
| Source custody | `g/source` before each guard phase, `s` before each native attempt, both and the export at the end. `r/source`, which no lane can write, after each Rust lane. Before each guard phase, Rust build and native attempt, a Cargo or audit config file, or a `bin` in that step's Cargo home (`absent_configs`), stops the steps left | inside a phase or attempt: a step can change a later step's script in its own copy and put it back before the phase ends, and that reads clean; a plant in the Cargo home reaches the later steps of that phase or attempt, so in native B one from `xcode-test` reaches the `app09` line. Only `g/source` is compared: any other name in the guard's write root reads clean. | Total alarm, 3540 s of running time | everywhere | see below, and The 60-minute cap and the two-part form |

**What the guard does not reach in the Rust lanes, and why.** dyld strips `DYLD_*` for protected binaries, so the library loads through `/usr/bin/env` right after `sandbox-exec`, and from there it follows plain children.

- A `larsal` started through `/usr/bin/script` or `/bin/sh`: int10's `pty` and `spawn_ignoring_sigint` helpers. A forgotten private board there reaches the general board unseen under `cli-runtime.sb`. What holds: the pin on `crates/larsal-cli` and its review. Control: `c_forgotten_board`, case C.
- A row or child that clears its environment: none of the board rows does today. `env_clear` is only in `larsal-sshagent` tests, and in `larsal-ffi`'s `tests/ssh.rs`, which compiles the same helper by `#[path]`. Neither holds a board line.
- `/usr/bin/pbcopy` and `/usr/bin/pbpaste`, the system's clipboard tools. They are protected binaries, so the variable would not reach them: `/usr/bin/true` under the guard wrote no log. pbcopy itself was never run. A board profile has no process-exec line against them. What holds: the byte check `no-pbcopy`, which forbids both names in the 13 board rows' bytes at each run. A name built while the program runs passes it.
- A direct message to the service (N1b 31). The other routes N1b 4 and 31 name are narrower than they read: Carbon `PasteboardCreate` and a `dlsym` of `CFPasteboardCreate` end in a guarded call and are seen, and `-initWithName:` does not exist on this Mac.
- Hostile code: it can truncate its own log or clear its own environment. The guard is for the mistake, not for an attacker. An attacker is stopped, if at all, by the pin and its review.
- The Rust rows' guard, and the helper's lines that load it, are new in this tool and in no review's reading: R2b did not run with them. The helper's other lines are R2b's.

**The alarm is a flag, not a hard bound.** Log reads after it are cut to what is left with a floor of 5 s; each `ps` has its own 10 s to 30 s. Measured tails are under the 60 s it keeps back. A child in its own session is not named or signalled. SIGHUP or SIGKILL of the tool itself leaves children: SIGHUP stops the run in order, SIGKILL cannot be caught. Every stop signals only process groups the run started, through their handles.

**The tool cannot be rewritten by what it runs.** The generated profiles, the tool copy in `R/tool` and the guard library sit outside every write root, read only, with their hash compared before every use and at the end. A mismatch stops the steps left. The hashes are held only in the driver's memory. This holds for everything sandboxed; `sshd` on the own_agent row runs outside and can write wherever the owner can.

**The export.** Refuses `..`, an absolute name, an empty part, `.git`, a name below a file or link, names that fold together, submodules, odd modes, and a link pointing outside, by its text and, once every name exists, by resolving it inside the export, so a chain of links is refused too. Driver reads of paths a lane could write use `O_NOFOLLOW` and a regular-file check, so a lane cannot get a closed file copied into evidence and a FIFO cannot outlive the alarm.

**A lost gate fails.** `tables/routes.json` holds check.sh by whole hash and by each function's text, the step lists, the scripts its steps call, each fuzz route's bytes, each route's `[[bin]]` lines in `fuzz/Cargo.toml`, and the hash of that file outside those blocks: its dependencies, patches and build settings. A multi-line string or an indented table header in that file is red by itself, because either can show this reading a block Cargo does not use. So is `fuzz/build.rs` or a folder `fuzz/src`, which Cargo builds with no line in that file. Any change is red with "check.sh differs from the tool's route: needs a table update and review", and no step runs. A step or route lost, emptied or pointed at another body is a failure, not a smaller total. What the table does not see is the crates a route's body calls and `fuzz/Cargo.lock`: a change there is an ordinary code change. A new fuzz route needs no table change: it runs, and is listed.

Failing a pid with no image read is not the fix: a pid already gone reads none either, so honest rows would fail.
- C1R4-04: a pid the tree already holds gets no row in the process list's read, so an outsider that reuses that pid reads clean. It needs the pid counter to wrap inside one attempt. The start time is recorded and that read does not compare it.
- C1R4-06: a lane that passes double and grows by more than 16 fails the baseline floor; no waiver clears that and a baseline from that commit is refused, so such a story has no honest way through in one commit. The same-commit refusal compares whole strings: a baseline with its commit field removed, shortened or capitalised is not refused. Both need a wrong or hand-made file to read green.
- C2R4-06: a step can change a later step inside one phase and put it back, a new name in `s` reaches the later attempts and is read at the end (both in the Source custody row above), and a baseline holding 1 of doc-workspace's 9 tests passes the floor (Results above).

**Limit stated at each run:** `summary.txt` names the crates with no yanked proof and the newest advisory date, because the route is offline.

## Live kernel rows, the busy mark and the user database

From the tool round on the kernel's quarantine, 2026-11-12. Each rule, and what it leaves open.

1. **Why.** logd quarantines a process that fills its log files too fast: it drops that process's stored rows and keeps doing so until the process ends, with no public override (Apple's developer forum, thread 814022). For the kernel that lasts until a restart. `/var/db/diagnostics/logd.*.log` holds `Quarantined: /kernel` nine times since 2025-07, the last at 2026-11-12 11:40:36. From then `log show` returned no kernel `Sandbox: ` row while `log stream` still showed them live, so every native attempt failed "no kernel rows read".
2. **Two live readers per attempt.** Before the lane starts the tool starts `log stream --style ndjson` and `log stream --style default`, both with the show predicate `OR (type == lossEvent)`, in the same small environment as `log show`, with `LOGRC=/dev/null`, each in its own process group, writing `runs/<attempt>/kernel-stream.ndjson` and `kernel-stream-default.txt`. A reader is reading when it is alive and has printed its `Filtering the log data using` line, within 30 s. `--timeout` is the attempt's cap plus 600 s, so a driver that dies cannot leave them running longer. `log` reads `$LOGRC`, else `.logrc` in the home the user database names, never HOME (Checker 1, F3: the strings of `/usr/bin/log`, and a `.logrc` in the private HOME was not obeyed). So every `log` call of the tool, both readers, `log show` and the Rust step's `denials()`, carries `LOGRC=/dev/null`: a `.logrc` of the owner's never narrows or reshapes what they read.
3. **The sentinel.** Right after both read, one denied write of the tool's own: `sandbox-exec -p '(version 1)(allow default)(deny file-write* (literal P))' /usr/bin/touch P`, P being the fresh `runs/<attempt>/sentinel`, inside the run root. Denied means exit 1, "Operation not permitted" and P absent. Its row must reach both readers; the lane starts once it has, or after 15 s. After the late-row wait a second one, the end sentinel `runs/<attempt>/sentinel-end`, the same way: its row too must reach both readers, within 15 s, before they are stopped (F1). So the start proves the readers read before the lane and the end proves they still deliver after it; a stall from mid-lane through the stop cannot read clean. The sentinels' rows are never rows of the run's processes and never reach the deny rows, though `touch` is a tool name: each is told apart by pid, name, operation and path.
4. **Stop.** After the 8 s late-row wait and the end sentinel each reader gets SIGINT through its own handle, which makes the ndjson reader write its `{"count":N,"finished":1}` record, and its group is closed as every group is. A reader that had already exited ended early. A reader that did not end on SIGINT with exit 0 (the group close kills it after 20 s, exit -9), or an ndjson file with no end record, fails the attempt (F1). Whatever ends an attempt early, an exception included, a `finally` stops both readers and scrubs their files to the sentinels' rows (F6).
5. **Rows.** The ndjson reader's kernel rows timed in [start - 2 s, end + 4 s), without the sentinel's, and `log show`'s rows over its window as before, are merged by `machTimestamp`, `threadID` and `eventMessage`: one event read by both carries the same three, while `log show`'s `timestamp` text differs from the stream's by milliseconds (measured), so that text is no key. Everything that reads rows reads the merged rows: sensitive grants, the identity gate, T cleanup and the named set, `kernel-rows.ndjson`, `deny-rows.json`, `deny-rows.txt`, `sensitive-rows.json`. A kept row is the run's own when its pid is one the sampler read in the attempt's tree. A row kept only for its name (a tool name, a test program's name, a hash-named program) whose pid no sample read is listed apart as kept by name only: other agents' programs carry those names too (Checker 1, F2: 48 such rows with no own row passed), so it never counts toward "no kernel rows read", and every text that prints rows says so. The receipt's `log` row holds `stream_rows`, `show_rows`, `read_by_both`, `merged`, `kept`, `own`, `by_name_only`, `by_name_only_names` and `other_rows_removed`, and `kernel_rows` adds each sentinel's row by reader, each reader's exit and the end record; `summary.txt` prints them per attempt. Once read, other programs' rows leave the attempt's folder: each reader's file keeps its header, notices, end record and loss rows, the sentinels' rows and the kept rows, and as before only other programs' names and counts stay (`kernel-other-process-names.json`). A row the ndjson reader missed is recorded by time, name and pid only.
6. **Loss, as measured on this Mac.** With a reader stopped 60 s by SIGSTOP every style lost the rows of those seconds, and only the default and compact styles said so, with `=== Messages dropped during live streaming (use `log show` to see what they were)`; ndjson, json and syslog printed nothing. logd held about 650 rows of this predicate for a stopped reader, then dropped the rest. So the default reader is there for its notice, and its rows are compared with the ndjson reader's from the sentinel's row to the window's end: a row it read that the ndjson reader lacks is a silent drop. logd's `lost N unreliable messages` comes as a `lossEvent` row, which ndjson prints as a row; none came in 60 s system-wide at load 58 to 62, so whether a kernel loss passes the predicate is not measured.
7. **Gate reasons, one each:** the live kernel stream was not reading before the attempt; it ended before it was stopped; the sentinel write was not denied; the sentinel row is missing from the live stream, naming the reader; the end sentinel write was not denied; the end sentinel row is missing from the live stream, naming the reader; the live kernel stream did not end on SIGINT, naming the reader and its exit; the ndjson reader wrote no finished record; the live stream reports lost messages; it reports dropped messages; the ndjson reader dropped rows without a word; and no kernel rows read: no row of the run's own processes (pids the sampler read) from either reader, rows kept by name only do not count, or `log show` failed. None is a safety stop: the later attempts run.
8. **Keeping up.** At load 65 to 72 a burst of 300 denials in about 5 s reached both readers, 300 of 300.
9. **Privilege and leftovers.** `log stream` asked for no root here. `/usr/bin/log` refuses some commands to an account outside the admin group (`Must be admin to run '%s' command`, in its strings); the owner's account is in that group, and a reader refused would read "not reading". Not tried from another account. After SIGINT it exits 0 and leaves no process, and nothing in its HOME, TMPDIR or cache; that it did is now read at each attempt (rule 4).
10. **Not covered.** A row the kernel never wrote (its rate limit, merged duplicate reports) is in no reader. A loss before logd is seen only as a `lossEvent` row. A stall of both readers from mid-lane through the stop fails on the end sentinel and on the exits (rule 4); one that ends sooner and drops rows prints the default reader's notice (rule 6). A stall that ends before the end sentinel and drops nothing reads clean, rightly. Whether a stall can drop rows in both readers with no notice in either is not measured. The default reader is text: a path with a newline can make it show a row the ndjson reader lacks, a false failure, never a pass. While an attempt runs, and after a tool killed by SIGKILL before its `finally`, the two files hold every kernel `Sandbox: ` row of the Mac inside the 0700 run root.
11. **Other readers.** The Rust step's `denials()` still reads `log show` alone, to explain a failed program; it gates nothing and under a kernel quarantine explains nothing. A reader per program would not be small. Nothing in the tool reads rows of tccd, trustd, runningboardd, cloudd, fseventsd or audiomxd: every reader takes `processIdentifier == 0` only.
12. **The busy mark names its run, held once through the native step.** `--busy FILE` is one JSON line, `pid`, its kernel `start` time, `commit`, `root` and the Mac's `boot` time. The native step takes it once, after setup and before its first attempt, and keeps it through every attempt and the end compare of SwiftLint and the guard library; between attempts it is not dropped, and the hold file is still read before each attempt (ruling 3). Every change the tool makes at the mark happens under an exclusive `flock` on one fixed file beside it, `FILE.lock`, made the first time and never removed, so two runs of this tool never act on one reading (F5). Under that lock:
    - **Free path:** the mark is made with the exclusive create.
    - **A dead run's line:** its pid is gone, or the pid is now another process by its kernel start time. The boot time counts only beside one of those, added to the reason (F4): a live pid with the mark's own start time is a live run, whatever its boot field holds. The tool writes its own line to `FILE.<root name>.new` beside the mark and swaps the two names in one step (`renamex_np`, `RENAME_SWAP`), so a mark exists at every instant. The file that came out must be the one it read, by inode and bytes: then it moves into the root as `busy-mark-N-stale.txt` and is recorded in `run.json` (`busy_marks`) and `summary.txt`. If not, the swap is undone, nothing else is touched, and that is recorded; there is no put-back that could remove another run's mark.
    - **`--busy-from WORDS`:** a mark that holds exactly that one line, the words and one newline, is taken the same way, by swap, and moves into the root as `busy-mark-N-words.txt`. Any other content, other words or that line with anything more, is a hold.
    - **Anything else**, words, an empty mark, a live run's line, unreadable bytes, is someone's hold: waited on, polled every 30 s, at most 30 minutes, never touched.
    - **On every way out** of the native step, an exception included, and only while the mark is still this run's by inode and bytes: with `--busy-to WORDS` the mark is swapped for that one line, so the next holder's mark is there before this one goes; without it, it is removed. If it is no longer this run's, it is left alone and that is recorded.
    - **Without `--busy-from` and `--busy-to`** nothing else changes. Both must be one line of words, never starting with `{`, so no run can read them as a mark; either without `--busy` exits 2.
    - **Who removes which mark, and when.** A run removes or swaps out only its own line, on its way out of the native step. It takes a dead run's line, or the `--busy-from` line it was handed, when it starts the native step, and keeps either in its root. The lead's own words marks, and any `--busy-to` line a run left, are removed only by the lead (or taken by the next run started with that `--busy-from`). The lock file stays. A `FILE.<root name>.new` exists only inside the lock; a run killed there leaves it, and it is no mark.
13. **Limits of 12.** The lock orders runs of this tool only: an older tool copy or a hand-made mark acts without it, and the swap check then sees a changed file and undoes its swap rather than act on it. A run killed by SIGKILL leaves its line, which the next run takes as stale. An empty mark, like the one a killed run left at 12:09 on 2026-11-12, still waits its 30 minutes: only a mark with the line can be judged. The hold file is read before each attempt while this run holds its mark: a lead that sets the hold and waits for the mark to go waits until this run's hold wait ends, at most 30 minutes, and then this run's step stops with "hold still there".
14. **The user database.** `gc_lib` reads the owner's home from the user database at import. While the owner's session restarts it may not answer (`KeyError: 'getpwuid(): uid not found: 501'`, twice on 2026-11-12). The tool asks again each second for at most 60 s, then prints `the user database did not answer for uid N: try again` and exits 2, before any root is made. There is no fallback to HOME or a variable. `owner_home`'s `lookup` and `wait` exist for the controls only.
15. **The owner's simulator folder** (ruling 5). Before the readers start and after the attempt, each native attempt reads `~/Library/Developer/CoreSimulator/Devices` of the owner, read only: the folder's uid and kind, and for every name under it its kind, size, inode and times, a regular file's SHA-256 and a link's text; a folder it cannot list is a row with its error. Both lists are kept, `runs/<attempt>/owner-simulator-before.json` and `-after.json`. A name added or gone, or a changed kind, size, link text, SHA-256 or error, fails the attempt with "owner simulator folder changed:" and the paths, a safety reason. An inode or a time that alone changed is listed as information (`times_or_inodes_only`). Today the folder holds about 2,000 names and 385 MB, read twice per attempt. It is the owner's: the gate reads who changed it no more than the crash folder does, so any process of the owner's that writes there during an attempt fails it too.
16. **Ignored tests run alone** (ruling 4). A row of `tables/programs.json` may hold `"ignored": [names]`. After that program's own run, each name runs alone in the same lane, through the same helper and profile, with `--ignored --exact <name> --test-threads 1`, under the lane's time left, as `<target>-ignored-<i>` beside it. The summary counts these on their own line, `rust ignored tests run alone`, never in the lane totals or the baseline names, and fails a run whose named test does not exist (`running 0 tests`), did not run (no receipt, a refusal, a stop, no result line) or failed. Today one row: `workspace:larsal-crypto/larsal_crypto` runs `pq::tests::cry05_17_pq_stack_depth` (E25-S2), which needs nothing above the base profile: its own thread's 3 MiB stack and its own memory. The tool runs it in the debug build of the workspace lane only; the release build has no lane for this crate, so its release run stays by hand (CANDIDATE-NOTES of tool round 2 holds both times).

## The 60-minute cap and the two-part form

The owner's cap is 60 minutes of running time per run; the alarm fires at 3540 s, which keeps 60 s for the tails it cuts (The alarm is a flag, above). Hold and busy waits are idle time and not counted. A full run on a busy Mac can pass that cap, so a run may be made in two parts, each its own run with its own root, alarm and summary:

- **Part A:** `--only static,rust`. It reads `PASS (only static,rust)`, exit 4, when its steps pass.
- **Part B:** `--only native,docs,fuzz --part-of <part A's root>`. Before any root is made or any step runs, part B reads part A's `run.json`, `summary.json` and `summary.txt` and refuses, exit 1, unless part A ran the same commit, with the same tool copy (the tool's own file hashes, every file of `scripts/guarded` and `tables`), steps static and rust only, and reads PASS. Part B's `summary.txt` prints part A's root, its first line (the Overall line) and its time and hold wait.

The baseline compare in each part: each part compares only the tests of its own steps, part A the Rust programs' tests (`rust:` keys), part B the Swift tests, APP09 and the doc tests (`swift:`, `app09:`, `doc-` keys). A test lost or newly ignored in either part fails that part, unless the waivers list it. The checks that need the whole run do not run in a part: a part without `--baseline` is not refused, the baseline need not hold every step, and the floor of "fewer than half of a lane's tests" is not read. So pass the same `--baseline` and `--waivers` to both parts. A two-part run stands for a full run only with both parts read together: part B's PASS says part A passed this commit with this tool, nothing more.

## The tables are data

`tables/programs.json`, `needs.json`, `native-expected.txt`, `pins.json`, `routes.json`. The seal covers code and tables. Once this tool lives in the project, a table change is part of a story's commit, and that story's C1 and C2 review it like any code. So a run takes the tool of the commit under test: if the running bytes differ from that commit's `scripts/guarded`, the run ends NEEDS_REVIEW with that reason, which keeps tool and tables from drifting from the reviewed commit. That is the only way to move a pin, approve a route change or add a grant: adding a Swift test changes `native-expected.txt`, a change in a pinned crate changes `pins.json`, and neither is a flag.
